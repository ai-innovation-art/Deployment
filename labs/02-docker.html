    Tagging

    # Tag an existing image with a new name. This does NOT copy — it's just a new pointer to the same IMAGE ID.
docker tag nginx:alpine myregistry.io/myteam/nginx:1.27-alpine

    Tags are pointers, not copies

    Running docker tag does not copy any data. It creates a new name (reference) pointing to the same image ID and its layers. Disk usage doesn't increase.

    Cache behavior experiment

    Understanding when Docker uses the cache prevents mysterious stale builds. Create this Dockerfile:

    FROM python:3.12-slim
WORKDIR /app
# Layer 1: copy only requirements → only invalidated when requirements change
COPY requirements.txt .
# Layer 2: install deps → only re-runs when requirements.txt changes
RUN pip install --no-cache-dir -r requirements.txt
# Layer 3: copy app code → invalidated on every code change, but does NOT re-run pip
COPY app/ ./app/
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0"]
    1. Build once: docker build -f Dockerfile.cache-demo -t cache-demo:1 . — all layers build fresh.
    2. Build again without changes: docker build -f Dockerfile.cache-demo -t cache-demo:2 . — all layers say CACHED.
    3. Touch a source file: echo "# comment" >> app/main.py, then rebuild. Only the COPY app/ layer re-runs; pip install is still CACHED.
    4. Change requirements.txt (add any package), rebuild. Both pip install AND COPY app/ re-run — cache is invalidated from the changed layer downward.

    Removing images

    # Remove by tag
docker rmi nginx:alpine

# Remove by image ID (removes all tags pointing to it)
docker image rm abc123def456

# Force remove even if a container (stopped) uses it
docker rmi -f nginx:alpine

    Edge case: removing an image a running container uses

    If you try docker rmi nginx:alpine while a container is using it, Docker returns an error:

    Error response from daemon: conflict: unable to remove repository reference "nginx:alpine" (must force) - container abc123 is using its referenced image def456

    If you run docker rmi -f nginx:alpine, Docker untags the image (removes the nginx:alpine label) but the underlying image bytes are not deleted — the running container holds a reference that keeps the data alive. The image disappears from docker images but continues to function for the container. The bytes are garbage-collected only when the last container using them is removed.

    2. Containers

    Lifecycle state machine

    create vs run

    docker create
    Creates a container (allocates filesystem layer, assigns ID) but does not start it. PID 1 is not launched. Useful when you need the container ID before starting (e.g., to docker cp files into it first).
    docker run
    docker create + docker start in one step. This is what you use 99% of the time.
    docker start
    Starts an existing (created or exited) container. PID 1 launches and the container enters running state.

    🚨 Trial & Error Drills: Common docker run Errors & How to Diagnose Them

    Before moving to advanced projects, practice generating these classic container errors in your terminal. Seeing the exact error and resolving it builds instant troubleshooting muscle memory.

    Drill 1: Container Name Collision

    docker run -d --name web_app nginx:alpine
    docker run -d --name web_app nginx:alpine

    What you observe (The Error):

    docker: Error response from daemon: Conflict. The container name "/web_app" is already in use by container "abc123...". You have to remove (or rename) that container to be able to reuse that name.

    How to diagnose & resolve: Check who owns the name with docker ps -a --filter name=web_app. Either remove the old container with docker rm -f web_app or assign a distinct name.

    Drill 2: Host Port Conflict (Address Already in Use)

    docker run -d -p 8080:80 --name web1 nginx:alpine
    docker run -d -p 8080:80 --name web2 nginx:alpine

    What you observe (The Error):

    docker: Error response from daemon: driver failed programming external connectivity on endpoint web2: Bind for 0.0.0.0:8080 failed: port is already allocated.

    How to diagnose & resolve: Find which container holds the port with docker ps --filter publish=8080. Either stop it with docker rm -f web1 or choose another host port like -p 8081:80.

    Drill 3: Read-Only Filesystem Violation

    docker run --rm --read-only alpine touch /tmp/test.txt

    What you observe (The Error):

    touch: /tmp/test.txt: Read-only file system

    How to diagnose & resolve: The root filesystem is immutable. To provide writable scratch space for temporary files, mount a memory-backed tmpfs: docker run --rm --read-only --tmpfs /tmp alpine touch /tmp/test.txt (succeeds cleanly).

    Drill 4: Privileged Port Binding as Non-Root

    docker run --rm --user 1000 python:3.12-slim python -m http.server 80

    What you observe (The Error):

    PermissionError: [Errno 13] Permission denied

    How to diagnose & resolve: Linux ports below 1024 require root or CAP_NET_BIND_SERVICE. Either run on an unprivileged port (e.g. 8000) and publish it to 80 via -p 80:8000, or add the capability explicitly: --cap-add NET_BIND_SERVICE.

    Clean up: docker rm -f web_app web1 web2 2>/dev/null

    SIGTERM vs SIGKILL — the 10-second experiment

    This experiment shows why shell form as PID 1 causes the 10-second stop delay.

    1. Run a container with shell-form CMD (Docker wraps it in /bin/sh -c, making sh PID 1, not your app): 
      docker run -d --name slow-stop alpine \
  sh -c 'echo "started"; sleep 3600'
    2. Time the stop: time docker stop slow-stop 
      slow-stop
real    0m10.302s   # 10+ seconds — sh doesn't forward SIGTERM to sleep
    3. Clean up: docker rm slow-stop
    4. Now run with exec-form CMD (your binary IS PID 1 and receives SIGTERM directly): 
      docker run -d --name fast-stop alpine \
  sleep 3600
# alpine's sleep is PID 1 here; it receives SIGTERM and exits cleanly
    5. Time the stop: time docker stop fast-stop 
      fast-stop
real    0m0.618s   # ~0.6s — SIGTERM received and handled immediately
    6. Clean up: docker rm fast-stop

    Key insight: always use exec form in Dockerfile CMD/ENTRYPOINT, or use --init at runtime to insert tini as PID 1.

    🚨 Trial & Error Drills: Common docker exec Errors & Fixes

    Drill 1: Executing in a Stopped Container

    docker create --name c_dormant alpine
docker exec -it c_dormant sh

    What you observe (The Error):

    Error response from daemon: Container abc123... is not running

    How to resolve: You cannot exec into a container unless PID 1 is actively running. Start it first: docker start c_dormant && docker exec -it c_dormant sh.

    Drill 2: Executing a Missing Shell/Binary (bash in Alpine)

    docker run -d --name c_alp alpine sleep 100
docker exec -it c_alp bash

    What you observe (The Error):

    OCI runtime exec failed: exec failed: unable to start container process: exec: "bash": executable file not found in $PATH: unknown

    How to resolve: Minimal distributions like Alpine or distroless images do not ship with /bin/bash. Use POSIX sh: docker exec -it c_alp sh.

    Clean up: docker rm -f c_dormant c_alp 2>/dev/null

    exec experiments — verify container isolation
    1. Verify PID 1: docker exec reliability-api ps aux — PID 1 should be your app's process (or tini if --init was used), not a shell.
    2. Verify non-root: docker exec reliability-api id — should show a non-root UID if the Dockerfile sets USER.
    3. Verify code is immutable: docker exec reliability-api touch /app/injected.txt — should fail with "Read-only file system" if --read-only was set, or succeed but the file disappears when the container is removed (the writable layer is ephemeral).
    4. Verify filesystem isolation: docker exec reliability-api ls / — you see the container's root filesystem, not the host's.

    attach — connect to PID 1's stdio

    # Attach your terminal to PID 1's stdin/stdout/stderr of a running container
docker attach reliability-api

# Detach WITHOUT stopping the container: press Ctrl+P then Ctrl+Q
# WARNING: pressing Ctrl+C sends SIGINT to PID 1 and will STOP the container
    attach vs exec

    docker attach connects to PID 1's streams — exiting the attached session may stop the container. docker exec starts a new process inside the container; exiting it never affects PID 1. For debugging, prefer docker exec -it container /bin/bash.

    1. Run reliability-api with a tight CPU limit: docker run -d --name api-throttled --cpus 0.1 -p 8001:8000 reliability-api:0.1.0

    Bind mounts

    # Mount a host directory into the container — changes are bidirectional
docker run -d \
  --name reliability-api \
  --mount type=bind,source=$(pwd)/app,destination=/app/app \
  reliability-api:0.1.0

# -v shorthand for bind mounts: host path must be absolute (or use $(pwd))
docker run -d -v $(pwd)/app:/app/app reliability-api:0.1.0

# Read-only bind mount — container cannot write to the host directory
docker run -d \
  --mount type=bind,source=$(pwd)/config,destination=/app/config,readonly \
  reliability-api:0.1.0

# -v shorthand for read-only
docker run -d -v $(pwd)/config:/app/config:ro reliability-api:0.1.0
    Bind mount edge case: empty host directory hides image content

    If you bind-mount an empty host directory over a directory that has content in the image, the image content becomes invisible — the empty mount overlays it. Example: -v ./empty:/app/site-packages will cause ModuleNotFoundError because all the installed Python packages are hidden. Always make sure the host source directory has the content you need.

    UID/GID mismatch with bind mounts

    If the container runs as UID 1001 but the host directory is owned by root (UID 0), the container process may get "Permission denied" when writing. Fix: chown 1001 ./data on the host, or use a named volume instead (Docker manages ownership).

    tmpfs mounts

    # Mount a tmpfs (RAM-backed, non-persistent) filesystem
docker run -d \

    4. Networks

    Network types

    bridge (default)
    Containers get a private IP on an internal bridge network (docker0). Containers on the same bridge can reach each other by IP. Port publishing (-p) is needed to reach containers from the host or outside. DNS by container name only works on user-defined bridges, not the default bridge.
    host
    Container shares the host's network namespace. No port mapping — the container's port IS the host's port. Maximum performance, zero isolation. Linux only.
    none
    Container has no network interfaces (except loopback). Completely isolated. Use for security-sensitive batch jobs that should never touch the network.

    User-defined bridges

docker network create lab-net

    Name Collision Ambiguity: docker inspect vs docker <object> inspect

    If you create a network named lab-net and a volume also named lab-net, typing the legacy docker inspect lab-net is ambiguous! Docker's internal search priority is: Container → Image → Network → Volume. Because Network comes before Volume, docker inspect will always inspect the network, making the volume completely inaccessible via the generic command. Always use modern typed commands: docker network inspect <name> and docker volume inspect <name>.

    🚨 Trial & Error Drill: Name Collision Ambiguity (Network vs Volume)
    1. Create a network: docker network create lab-net
    2. Create a volume with the identical name: docker volume create lab-net
    3. Run generic inspect: docker inspect lab-net → Docker resolves to the Network JSON (ignoring the volume due to search precedence).
    4. Explicitly inspect each typed object to resolve ambiguity: 
      # Specifically inspect the Network (shows Subnet and Gateway):
docker network inspect lab-net

# Specifically inspect the Volume (shows host Mountpoint):
docker volume inspect lab-net
    5. Clean up: docker network rm lab-net && docker volume rm lab-net
    DNS by container name — user-defined bridge vs default bridge
    1. Create a custom network: docker network create dns-demo
    2. Start two containers on it: docker run -d --name server --network dns-demo nginx:alpine and docker run -d --name client --network dns-demo alpine sleep 3600
    3. From client, resolve server by name: docker exec client ping -c 2 server → works! Docker DNS resolves the name.
    4. Now try the same on the default bridge: docker run -d --name srv2 nginx:alpine and docker run --rm alpine ping -c 2 srv2 → fails with "bad address" — the default bridge does NOT have automatic DNS.
    5. Clean up: docker rm -f server client srv2 && docker network rm dns-demo
    Container-to-container — no -p needed on same network
    1. docker network create internal-net
    2. docker run -d --name api --network internal-net reliability-api:0.1.0 — note: no -p!
    3. docker run --rm --network internal-net alpine wget -qO- http://api:8000/health → returns {"status":"ok"}
    4. The port 8000 is NOT exposed to the host — only containers on internal-net can reach it. This is the correct pattern for internal microservices.

    Docker HEALTHCHECK vs Kubernetes probes — important distinction

    Docker HEALTHCHECK only changes the container's reported status — Docker does not automatically restart an unhealthy container (unless you use --restart on-failure and the container actually exits, which a health check failure doesn't cause).

    Kubernetes probes are active: a liveness probe failure causes kubelet to restart the container; a readiness probe failure removes the Pod from Service endpoints (stops traffic). If you run Docker HEALTHCHECK and Kubernetes together, the HEALTHCHECK status is visible in docker inspect inside the node but Kubernetes acts on its own probes independently.

    # --- Stage 1: build / dependency installation ---
FROM python:3.12-slim AS builder
# FROM sets the base image. Use slim/alpine variants to reduce size.
# AS gives this stage a name for multi-stage builds.

ARG APP_VERSION=0.1.0
# ARG declares a build-time variable. Not available in the running container unless also set as ENV.
# Pass at build time: docker build --build-arg APP_VERSION=0.2.0 .

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1
# ENV sets environment variables that PERSIST into the running container.
# PYTHONDONTWRITEBYTECODE: don't create .pyc files (keeps image clean).
# PYTHONUNBUFFERED: stdout/stderr not buffered (logs appear immediately in docker logs).

WORKDIR /app
# WORKDIR sets the working directory for all subsequent RUN, COPY, CMD, ENTRYPOINT instructions.
# Created automatically if it doesn't exist. Prefer over: RUN mkdir /app && cd /app.

COPY requirements.txt .
# COPY copies files from the build context (your local machine) into the image.
# Copy ONLY requirements.txt first so that pip install is cached unless requirements change.

RUN pip install --no-cache-dir -r requirements.txt
# RUN executes a command during the build and commits the result as a new layer.
# --no-cache-dir: don't save pip's download cache inside the image (keeps size down).
# Each RUN creates a new layer — chain commands with && to keep layers small.

# --- Stage 2: runtime image ---
FROM python:3.12-slim
# Start a FRESH base — the builder stage artifacts (pip cache etc.) are NOT carried over.
# This is the key benefit of multi-stage builds.

WORKDIR /app

# Copy installed packages from the builder stage
COPY --from=builder /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages
COPY --from=builder /usr/local/bin /usr/local/bin

# Copy only the application source
COPY app/ ./app/

ADD https://github.com/krallin/tini/releases/download/v0.19.0/tini /tini
# ADD can fetch remote URLs and auto-extract tarballs. For regular file copies, prefer COPY.
# Here: download the tini init process binary for signal handling.
RUN chmod +x /tini

USER 1000:1000
# USER sets the UID:GID for all subsequent RUN, CMD, and ENTRYPOINT instructions.
# NEVER run as root in production — violates least-privilege principle.
# Note: set USER AFTER installing packages (pip needs root).

EXPOSE 8000
# EXPOSE is documentation only — it does NOT publish the port to the host.
# It tells docker run -P which port to map randomly, and documents the app's port.
# You still need -p 8000:8000 to actually reach the container from outside.

LABEL org.opencontainers.image.version="${APP_VERSION}" \
      org.opencontainers.image.source="https://github.com/you/reliability-lab"
# LABEL adds metadata key-value pairs. OCI standard labels are the convention.
# Visible with: docker inspect --format '{{json .Config.Labels}}' reliability-api:0.1.0

HEALTHCHECK --interval=10s --timeout=5s --start-period=15s --retries=3 \
  CMD ["wget", "-qO-", "http://localhost:8000/health"]
# HEALTHCHECK defines how Docker tests if the container is healthy.

STOPSIGNAL SIGTERM
# STOPSIGNAL sets which signal Docker sends when docker stop is called.
# Default is SIGTERM. Override if your app uses a different signal for graceful shutdown.

ENTRYPOINT ["/tini", "--"]
# ENTRYPOINT sets the main command. Exec form (array) — signal-safe.
# With tini as ENTRYPOINT, CMD is passed as arguments to tini, which then execs CMD.
# tini handles signal forwarding and zombie reaping correctly.

CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
# CMD provides default arguments to ENTRYPOINT (or the full command if no ENTRYPOINT).
# Exec form (array): the binary IS PID 1 (inside tini here) — signal-safe.
# Shell form would be: CMD python -m uvicorn ... — this runs /bin/sh -c "..." as PID 1, NOT your app.
# Shell form: SIGTERM goes to sh, which may not forward it → 10s stop delay.

# Instructions not shown above but available:
# VOLUME ["/data"]  — declares mount points; Docker creates an anonymous volume if not mounted
# ONBUILD COPY . /app  — runs when THIS image is used as a base by another Dockerfile (rare)

    Experiment 1 · Startup Warm-up Delay: Health vs. Readiness

    Goal: Observe how readiness differs from liveness, why 503 warm-up windows matter, and how load balancers can send traffic to an unready pod if misconfigured.

    Step 1 (Baseline — Instant ready): Run the container with default READY_DELAY_SECONDS=0:

    docker run -d --name exp1 -p 8000:8000 reliability-api:0.1.0

    Step 3 (Observe the divergence): Poll both endpoints in a loop for the first 18 seconds:

    11:05:01  ready=503  health=200

    If an orchestrator routes traffic based only on /health (or process running state), clients receive HTTP 503 errors while the app is still warming up. Inspect the 503 body:

    curl -s http://localhost:8000/ready
{"ready":false,"warming_up_seconds_remaining":6.42}

    Experiment 2 · PID 1 Signals: Exec Form vs. Shell Form (The 10-Second Delay)

    Goal: Understand why shell form in CMD causes ungraceful SIGKILL shutdowns, 10-second delays, and exit code 137.

    Step 1 (Baseline — Exec form): Run the default image (uses CMD ["uvicorn", ...]):

    docker run -d --name exp2_fast reliability-api:0.1.0

    Verify PID 1 inside the container:

    docker exec exp2_fast cat /proc/1/cmdline | tr '\0' ' '
/opt/venv/bin/python /opt/venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000

    Stop the container and time it:

    time docker stop exp2_fast

    What you observe: Stops cleanly in under 1 second:

    real    0m0.6s
exit=0 (or 143)

    Step 2 (Tweak parameter — Override with Shell Form): Start the container with sh -c "uvicorn ...; echo done" so /bin/sh becomes PID 1:

    docker run -d --name exp2_slow reliability-api:0.1.0 \
  sh -c 'uvicorn app.main:app --host 0.0.0.0 --port 8000; echo done'

    Verify who is PID 1 now:

    docker exec exp2_slow cat /proc/1/cmdline | tr '\0' ' '
sh -c uvicorn app.main:app --host 0.0.0.0 --port 8000; echo done

    Notice that /bin/sh is PID 1, and uvicorn is only a child process.

    Step 3 (Trigger Failure — The 10-Second Hang): Stop the container and time it:

    time docker stop exp2_slow

    What you observe (Failure): The command freezes for 10 full seconds before exiting!

    real    0m10.3s

    Step 4 (Diagnosis Playbook): Inspect the container's exit code:

    docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' exp2_slow
exit=137 oom=false

    Root cause: Under Linux pid_namespaces(7), PID 1 ignores any signal for which it has not registered a handler. /bin/sh does not forward SIGTERM to Uvicorn. Docker waits its default 10-second timeout, gives up, and sends SIGKILL (exit 128 + 9 = 137). In Kubernetes, this causes 30s delays per pod on rolling updates!

    Step 5 (Fix without editing Dockerfile — The --init flag):

    docker run -d --init --name exp2_fixed reliability-api:0.1.0 \
  sh -c 'uvicorn app.main:app --host 0.0.0.0 --port 8000; echo done'
time docker stop exp2_fixed
real    0m0.4s

    --init inserts tini as PID 1, which forwards SIGTERM down to Uvicorn.

    Clean up: docker rm -f exp2_fast exp2_slow exp2_fixed 2>/dev/null

    Experiment 3 · Memory Limits, Heap Leak & OOMKill (Exit 137)

    Goal: Trigger an Out-Of-Memory (OOM) kill, distinguish it from a normal kill, and inspect the evidence.

    Step 1 (Baseline — Normal Memory Limit): Run container with 256 MiB limit:

    docker run -d --name exp3 -p 8000:8000 --memory 256m reliability-api:0.1.0

exp3    0.00%    48.5MiB / 256MiB      18.94%

    Everything runs normally within the 256 MiB boundary.

    Step 2 (Tweak parameter — Constrain to 64 MiB and disable swap):

    Step 3 (Trigger Failure — Force Heap Allocation beyond Limit): Call /leak?mb=80 to request 80 MB (exceeding the 64 MB ceiling):

    curl "http://localhost:8000/leak?mb=80"

    What you observe (Failure): The connection immediately drops without a response:

    curl: (52) Empty reply from server

    Check running containers: docker ps → exp3_oom is no longer running!

    Step 4 (Diagnosis Playbook): How do you confirm it was killed by OOM and not a Python traceback?

    Experiment 4 · CPU Throttling vs. Crashing (Soft Throttle vs Hard Ceiling)

    Goal: Prove that exceeding CPU quota never kills a process (unlike memory). It only throttles execution bandwidth.

    Step 1 (Baseline — Unconstrained CPU): Run container and measure latency of 200 ms of CPU-intensive computation:

    docker run -d --name exp4 -p 8000:8000 reliability-api:0.1.0

    10. Container Security & Privilege Boundaries (Root vs Non-Root)

    In Linux, containers share the host kernel. A process running as root (UID 0) inside a container shares the root user identity with the host, meaning container breakout vulnerabilities or code injection can compromise the entire underlying operating system.

    The Danger of UID 0 in Production

    If an attacker achieves Remote Code Execution (RCE) in an application running as root, they can overwrite system configurations (/etc/hosts), install malicious toolkits with apt, or tamper with mounted host volumes.

    Security Drill: Root vs Non-Root Exploit Test

    Goal: Prove that an unprivileged user (UID 10001) is blocked from modifying critical operating system files, while a naive root container permits tampering.

    Step 1: Exploit the naive root container:

    docker run --rm reliability-api:naive sh -c "echo '1.2.3.4 evil-hacker.com' >> /etc/hosts && cat /etc/hosts"

    Result: Succeeded! The malicious entry 1.2.3.4 evil-hacker.com is successfully appended to /etc/hosts.

    Step 2: Attempt the exact same attack on the production non-root container:

    docker run --rm kumawatsunil/reliability-api sh -c "echo '1.2.3.4 evil-hacker.com' >> /etc/hosts"

    Result: sh: 1: cannot create /etc/hosts: Permission denied — The Linux kernel rejects the write operation because user app (UID 10001) has read-only access to system files.

    Step 3: Why choose UID 10001?

    UID RangeDesignationSignificance in Containers
    0rootSuperuser. Full kernel administration. Strictly forbidden in production.
    1 – 999System DaemonsReserved by Linux OS packages (sshd, systemd, www-data).
    1000Primary Host UserDefault human account on Ubuntu / Codespaces. Collides with host volume mounts.
    10001+Application SandboxGold standard: No host collision, CIS Benchmark & Kubernetes MustRunAsNonRoot compliant.

    11. Local Kubernetes Testing with Kind (Offline Image Loading)

    Kind (Kubernetes in Docker) runs local Kubernetes clusters by containerizing control plane and worker nodes inside Docker. Because Kind nodes run an isolated internal containerd runtime, images built in your host Docker daemon are not automatically visible to Kubernetes.

    The Problem: ImagePullBackOff

    When Kubernetes deploys a pod, it defaults to reaching out to public registries (Docker Hub, GHCR). To run local development builds without pushing them over the internet, you must inject the image into the cluster node with kind load docker-image and set imagePullPolicy: Never.

    Local Kubernetes Cluster & Offline Image Workflow

    Step 1: Install Kind (Linux AMD64):

    curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.25.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind
kind --version

    Step 2: Create a local Kubernetes cluster:

    kind create cluster --name reliability-lab
kubectl get nodes

    Step 3: Bridge the host image into the Kind node:

    # Ensure local image has matching tag
docker tag kumawatsunil/reliability-api:latest reliability-api:0.1.0

# Inject image into Kind containerd runtime
kind load docker-image reliability-api:0.1.0 --name reliability-lab

    Step 4: Verify image inside the node using crictl:

    docker exec -it reliability-lab-control-plane crictl images | grep reliability-api

    Step 5: Run your Pod with offline pull policy:

    kubectl run my-first-pod --image=reliability-api:0.1.0 --image-pull-policy=Never
kubectl get pods

    Clean up: kubectl delete pod my-first-pod (or kind delete cluster --name reliability-lab)

    13. Quick Reference Cheat Sheet

    ## IMAGES
docker pull nginx:alpine                          # pull an image
docker image ls                                   # list images
docker build -t myapp:1.0 .                       # build from Dockerfile
docker build --no-cache --progress=plain -t x .   # build without cache, verbose
docker tag myapp:1.0 registry.io/team/myapp:1.0   # tag (pointer, no copy)
docker push registry.io/team/myapp:1.0            # push to registry
docker rmi myapp:1.0                              # remove image
docker image prune -a                             # remove all unused images
docker save myapp:1.0 -o myapp.tar                # export to file
docker load -i myapp.tar                          # import from file

## CONTAINERS — run
docker run -d --name api -p 8000:8000 myapp:1.0   # detached, named, port published
docker run -it --rm ubuntu bash                   # interactive, auto-remove on exit
docker run --rm -v $(pwd):/work -w /work node npm test  # one-off with bind mount

## CONTAINERS — manage
docker ps                                         # running containers
docker ps -a                                      # all containers
docker stop api                                   # graceful stop (SIGTERM → SIGKILL)
docker rm api                                     # remove stopped container
docker rm -f api                                  # force stop + remove
docker container prune                            # remove all stopped containers

## CONTAINERS — inspect
docker logs -f api                                # follow logs
docker logs --tail 50 api                         # last 50 lines
docker exec -it api /bin/bash                     # interactive shell inside
docker exec api cat /etc/hosts                    # one-off command
docker inspect api                                # full JSON
docker inspect --format '{{.State.ExitCode}}' api # Go template
docker stats --no-stream                          # resource snapshot
docker top api                                    # processes inside
docker cp api:/app/logs/app.log .                 # copy file out

## VOLUMES
docker volume create mydata                       # create named volume
docker volume ls                                  # list
docker volume inspect mydata                      # details
docker volume rm mydata                           # remove (must not be in use)
docker volume prune                               # remove all unused

## NETWORKS
docker network create mynet                       # create bridge network
docker network ls                                 # list
docker network inspect mynet                      # details
docker network connect mynet api                  # attach running container
docker network disconnect mynet api               # detach
docker network rm mynet                           # remove
docker network prune                              # remove unused

## COMPOSE
docker compose up -d --build                      # start / rebuild
docker compose down                               # stop + remove containers
docker compose down -v                            # also remove volumes
docker compose logs -f api                        # follow service logs
docker compose exec api bash                      # shell in service
docker compose ps                                 # status

## SYSTEM
docker system df                                  # disk usage
docker system prune                               # remove unused resources
docker system prune --volumes                     # include volumes (destructive)
docker builder prune                              # clear build cache
