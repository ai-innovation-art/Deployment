    7.2 Dynamic provisioning: a disk appears on demand

    apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: notes, namespace: state }
spec:
  accessModes: ["ReadWriteOnce"]
  resources: { requests: { storage: 100Mi } }
    apiVersion: v1
kind: Pod
metadata: { name: writer, namespace: state }
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "date >> /data/log.txt; sleep 3600"]
      volumeMounts: [ { name: d, mountPath: /data } ]
  volumes:
    - name: d
      persistentVolumeClaim: { claimName: notes }
    kubectl apply -f pvc.yaml
kubectl get pvc,pv -n state
kubectl describe pvc notes -n state | tail -3
kubectl apply -f writer.yaml
kubectl wait -n state --for=condition=Ready pod/writer
kubectl get pvc -n state ; kubectl get pv
    Predict: PVC status before and after the pod? When does the PV appear?

    Before: Pending, event waiting for first consumer to be created before binding, no PV. After the pod is scheduled: the provisioner creates a PV on that pod's node and the PVC becomes Bound. WaitForFirstConsumer exists so the disk is made where the pod lands (with Immediate, a zonal cloud disk could end up in a zone the pod can't reach).

    7.3 Where the data physically is

    PV=$(kubectl get pvc notes -n state -o jsonpath='{.spec.volumeName}')
kubectl get pv $PV -o yaml | grep -A8 -E "hostPath|local:|nodeAffinity"
NODE=$(kubectl get pod writer -n state -o jsonpath='{.spec.nodeName}')
docker exec $NODE ls /var/local-path-provisioner/
docker exec $NODE sh -c 'cat /var/local-path-provisioner/*notes*/log.txt'
    Predict: what is the "disk" in kind?

    A plain folder on the node, /var/local-path-provisioner/pvc-…_state_notes/, and the PV has a nodeAffinity for that node. That's why postgres-0 is pinned to worker2. In the cloud it's a network disk that can detach and re-attach to another node (in the same zone).

    7.4 Reclaim policy: what deleting a PVC does

    kubectl delete pod writer -n state
kubectl get pvc,pv -n state ; kubectl get pv            # still there?
kubectl delete pvc notes -n state
kubectl get pv ; docker exec $NODE ls /var/local-path-provisioner/
    Predict: after deleting the pod? After deleting the PVC?

    Pod deleted → PVC and PV stay, data safe. PVC deleted → with reclaimPolicy: Delete the PV and the folder are removed. The data is gone.

    apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: keep }
provisioner: rancher.io/local-path
reclaimPolicy: Retain
volumeBindingMode: WaitForFirstConsumer
    kubectl apply -f retain-sc.yaml
sed -i 's/  accessModes:/  storageClassName: keep\n  accessModes:/' pvc.yaml
kubectl apply -f pvc.yaml -f writer.yaml
kubectl wait -n state --for=condition=Ready pod/writer
kubectl delete pod writer -n state ; kubectl delete pvc notes -n state
kubectl get pv
    Predict: PV status after deleting the PVC with Retain?

    The PV stays, status Released, data still on disk. It isn't reused automatically (it still remembers its old claim in spec.claimRef). An admin recovers the data, or removes the claimRef to make it Available, or deletes the PV by hand. Production databases: Retain.

    7.5 Why a database is not a Deployment

    apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: shared, namespace: state }
spec:
  accessModes: ["ReadWriteOnce"]
  resources: { requests: { storage: 100Mi } }
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: fakedb, namespace: state }
spec:
  replicas: 2
  selector: { matchLabels: { app: fakedb } }
  template:
    metadata: { labels: { app: fakedb } }
    spec:
      containers:
        - name: db
          image: busybox:1.36
          command: ["sh", "-c", "while true; do echo $(hostname) >> /data/owner.txt; sleep 2; done"]
          volumeMounts: [ { name: d, mountPath: /data } ]
      volumes:
        - name: d
          persistentVolumeClaim: { claimName: shared }
    kubectl apply -f shared.yaml
kubectl get pods -n state -l app=fakedb -o wide
kubectl exec -n state deploy/fakedb -- sh -c 'tail -6 /data/owner.txt'
    Predict: where do both pods run, and what's in owner.txt?

    Both on the same node (the PV's nodeAffinity), both writing one file: lines from two hostnames interleaved. RWO means one node, not one pod. Two Postgres processes on one data folder = corrupted database. On cloud disks the 2nd pod on another node would hang in ContainerCreating (Multi-Attach error).

    apiVersion: apps/v1
kind: StatefulSet
metadata: { name: realdb, namespace: state }
spec:
  serviceName: realdb
  replicas: 2
  selector: { matchLabels: { app: realdb } }
  template:
    metadata: { labels: { app: realdb } }
    spec:
      containers:
        - name: db
          image: busybox:1.36
          command: ["sh", "-c", "echo $(hostname) >> /data/owner.txt; sleep 3600"]
          volumeMounts: [ { name: data, mountPath: /data } ]
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: ["ReadWriteOnce"]
        resources: { requests: { storage: 100Mi } }
    kubectl apply -f sts.yaml
kubectl get pods,pvc -n state -l app=realdb
for i in 0 1; do kubectl exec -n state realdb-$i -- cat /data/owner.txt; done
kubectl scale sts realdb -n state --replicas=1 ; kubectl get pvc -n state
kubectl scale sts realdb -n state --replicas=2
kubectl wait -n state --for=condition=Ready pod/realdb-1
kubectl exec -n state realdb-1 -- cat /data/owner.txt
    Predict: after scaling to 1 and back to 2, what does realdb-1's file contain?

    Two lines realdb-1: scale-down deletes the pod but keeps data-realdb-1; scale-up re-attaches the same PVC. Each replica has its own data forever (unless persistentVolumeClaimRetentionPolicy says Delete).

    7.6 Back up QuickBite's Postgres

    kubectl exec -n quickbite postgres-0 -- pg_dump -U quickbite quickbite > ~/state/quickbite.sql
grep -c "INSERT\|COPY" ~/state/quickbite.sql ; head -20 ~/state/quickbite.sql
# restore (into an empty DB): kubectl exec -i -n quickbite postgres-0 -- psql -U quickbite quickbite < ~/state/quickbite.sql
    • A PV is not a backup: deleting the PVC, a bad migration or a corrupted disk loses everything. Back up the data (pg_dump, CronJob to object storage) or the disk (VolumeSnapshot with a CSI driver).
    • Production Postgres on Kubernetes usually runs through an operator (CloudNativePG): replicas, failover, scheduled backups.

    7.7 Clean up

    kubectl delete namespace state
kubectl get pv                                   # Retain PVs survive the namespace
kubectl delete pv $(kubectl get pv -o jsonpath='{.items[?(@.spec.storageClassName=="keep")].metadata.name}')
kubectl delete storageclass keep

    7.8 Review questions

    1. A PVC sits in Pending with "waiting for first consumer". Problem?

    No. WaitForFirstConsumer: the disk is created when a pod using the PVC is scheduled.

    2. Delete vs Retain reclaim policy?

    Delete: removing the PVC removes the disk and data. Retain: the PV stays Released with the data; an admin decides.

    3. Does ReadWriteOnce mean only one pod can mount it?

    No, one node. Pods on that node can share it. ReadWriteOncePod is the one-pod mode.

    4. Why does a StatefulSet scale-down keep PVCs?

    To protect data: scaling back up re-attaches the same disk to the same pod name.

    5. Is a PersistentVolume a backup?

    No. It's the live data. Backups are separate copies (pg_dump, snapshots) stored elsewhere.
