    Chapter 03 · Scheduling: predict where every pod lands

    The scheduler decides which node runs each pod. By the end you'll predict placement before applying, steer pods with labels, affinity, taints and spread rules, empty a node for maintenance, and read any Pending message.

    Checkpoint at start: make resume Experiments run in a scratch namespace sched ≈ 2 h

    3.0 Setup

    QuickBite stays untouched. We experiment with a small nginx Deployment in its own namespace, and you'll edit its YAML in every section.

    cd /workspaces/Deployment/labs/quickbite && make resume
kubectl create namespace sched
mkdir -p ~/sched && cd ~/sched
cat > demo.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo
  namespace: sched
spec:
  replicas: 3
  selector:
    matchLabels: { app: demo }
  template:
    metadata:
      labels: { app: demo }
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          resources:
            requests: { cpu: 50m, memory: 16Mi }
EOF
kubectl apply -f demo.yaml
    kubectl get pods -n sched -o wide -w

    3.1 How the scheduler decides

    1. FILTER   remove nodes that CAN'T run it
            not enough free requests · taint not tolerated · nodeSelector/affinity mismatch
            · volume on another node · port conflict
2. SCORE    rank the nodes that are left (0–100 per plugin)
            least allocated · spread pods of the same app · image already present · preferred affinity
3. BIND     write spec.nodeName = winner  →  that node's kubelet starts the pod
none left after FILTER → pod stays Pending, reason in Events
    • The scheduler only looks at requests, never actual usage. A node at 5% real CPU can still be "full".
    • Placement happens once. A running pod is never moved by the scheduler; it's replaced (delete, drain, eviction).
    Seen in the watch

    Pending, NODE <none> = waiting for the scheduler → Pending, NODE worker = bound (step 3 done) → ContainerCreating = kubelet's turn → Running.

    kubectl get nodes -o custom-columns=NODE:.metadata.name,CPU:.status.allocatable.cpu,MEM:.status.allocatable.memory
kubectl describe node quickbite-worker | grep -A8 "Allocated resources"

    Free for new pods = allocatable − requested (e.g. 2000m − 390m = 1610m). Limits may exceed 100% (overcommit); requests can't.

    kind caveat

    Every kind node reports the whole Codespace (2 CPU) as its own. The cluster looks like 6 CPU but really shares 2. Scheduling maths still works; real performance doesn't.

    Predict: with 3 replicas, how will the demo pods spread over worker and worker2?

    2 + 1 (or 1 + 2), none on the control plane. The control plane is filtered out by its taint, and the default spread scoring prefers putting pods of the same Deployment on different nodes.

    3.2 Requests vs capacity: make a pod Pending

    Edit demo.yaml: change the request to cpu: 1500m, then apply.

    kubectl apply -f demo.yaml
kubectl get pods -n sched -o wide
kubectl describe pod -n sched $(kubectl get pod -n sched --field-selector=status.phase=Pending -o name | head -1) | tail -5
    Predict: how many pods run, how many are Pending, and what does the message say?

    Each worker has 2 CPU minus what QuickBite already requests, so one 1500m pod fits per worker. With maxSurge the rollout tries a 3rd/4th: those stay Pending.

    Warning  FailedScheduling  0/3 nodes are available: 1 node(s) had untolerated taint
{node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu. preemption: ...

    Read it as a list of reasons, one per node: 1 node rejected for its taint, 2 for CPU.

    Seen

    2 new pods Running (one per worker), 1 Pending, 1 old 50m pod kept: the rollout stalls, capacity never drops. "preemption: no victims" = no lower-priority pod could be evicted to make room (PriorityClass).

    Set the request back to 50m and apply.

    3.3 nodeSelector: "only nodes with this label"

    kubectl label node quickbite-worker2 disk=ssd
kubectl get nodes -L disk                       # -L shows a label as a column

    Add to demo.yaml under template.spec, then apply:

          nodeSelector:
        disk: ssd
    Predict: where do the 3 pods go? Then change it to disk: nvme. What happens?

    disk: ssd → all 3 on worker2. disk: nvme → no node matches → new pods Pending (didn't match Pod's node affinity/selector), old pods keep running because of maxUnavailable.

    Remove the nodeSelector block and apply.

    3.4 Node affinity: richer rules

          affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:     # hard rule (filter)
            nodeSelectorTerms:
              - matchExpressions:
                  - { key: kubernetes.io/os, operator: In, values: [linux] }
          preferredDuringSchedulingIgnoredDuringExecution:    # soft rule (score)
            - weight: 80
              preference:
                matchExpressions:
                  - { key: disk, operator: In, values: [ssd] }
    PartMeaning
    required...Must match, else Pending (like nodeSelector)
    preferred... + weight 1–100Try to match; adds score, never blocks
    IgnoredDuringExecutionRemove the label later → running pods stay
    operatorsIn · NotIn · Exists · DoesNotExist · Gt · Lt
    several nodeSelectorTermsOR. Several expressions inside one term: AND
    Predict: where do the pods go now? Then kubectl label node quickbite-worker2 disk-. Do they move?

    Mostly worker2 (preferred weight 80), but not guaranteed: spread scoring may still put one on worker. Removing the label doesn't move anything (IgnoredDuringExecution). Only new pods see the change.

    3.5 Pod affinity and anti-affinity: placement relative to other pods

    Node affinity looks at node labels. Pod (anti-)affinity looks at which pods are already on a node.

          affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels: { app: demo }
              topologyKey: kubernetes.io/hostname    # "same node" = same hostname label
    Predict: 3 replicas, 2 schedulable nodes. Result?

    2 Running (one per worker), 1 Pending: didn't match pod anti-affinity rules. Switch to preferredDuringScheduling... (with weight + podAffinityTerm) and all 3 run, spread as well as possible.

    • topologyKey = what counts as "the same place": kubernetes.io/hostname (node), topology.kubernetes.io/zone (zone).
    • podAffinity = "put me near pods with label X" (e.g. notifier next to redis, less network).
    • Use anti-affinity so replicas don't share a node: one node dying shouldn't take all copies.

    3.6 Taints and tolerations in practice

    kubectl taint node quickbite-worker2 team=payments:NoSchedule
kubectl rollout restart deploy/demo -n sched
kubectl get pods -n sched -o wide
    Predict: where do the restarted pods go? What about QuickBite pods already on worker2?

    All new demo pods go to worker (worker2 filtered out). QuickBite pods already on worker2 stay: NoSchedule only affects new placement.

    Add a toleration to demo.yaml and apply:

          tolerations:
        - { key: team, operator: Equal, value: payments, effect: NoSchedule }
    Predict: do the pods now go to worker2?

    They may. A toleration only removes the block; it doesn't attract. To dedicate a node to a team: taint it and give the team's pods a toleration plus node affinity.

    kubectl taint node quickbite-worker2 team=payments:NoSchedule-     # remove
kubectl taint node quickbite-worker2 maintenance=true:NoExecute
kubectl get pods -A -o wide | grep worker2                          # what's left?
kubectl taint node quickbite-worker2 maintenance=true:NoExecute-
    Predict: which pods survive the NoExecute taint?

    Only pods that tolerate everything: DaemonSet pods (kube-proxy, kindnet). Deployment pods are evicted and recreated on worker. postgres-0 is evicted too and stays Pending: its disk lives on worker2 (volume node affinity conflict). It comes back once the taint is removed. tolerationSeconds lets a pod stay N seconds before eviction.

    3.7 Topology spread constraints

          topologySpreadConstraints:
        - maxSkew: 1                               # max difference between nodes
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule         # or ScheduleAnyway (soft)
          labelSelector:
            matchLabels: { app: demo }
    Predict: 4 replicas over 2 workers?

    2 + 2. With 5 replicas: 3 + 2 (skew 1 allowed). Spread constraints are the modern, flexible replacement for "anti-affinity to spread": they allow several per node, but evenly.

    3.8 Cordon, drain, uncordon: node maintenance

    kubectl cordon quickbite-worker                     # no NEW pods; running pods stay
kubectl get nodes                                   # Ready,SchedulingDisabled
kubectl drain quickbite-worker --ignore-daemonsets --delete-emptydir-data
kubectl get pods -A -o wide | grep -v kube-system
kubectl uncordon quickbite-worker
    Predict: after drain, where is everything? Do pods move back after uncordon?

    Every Deployment pod is evicted and recreated on worker2 (cordon adds a unschedulable taint). DaemonSet pods stay (--ignore-daemonsets). After uncordon, nothing moves back; only new pods use worker again. Rebalance with kubectl rollout restart.

    Draining worker2 instead would leave postgres-0 Pending (disk on worker2): local disks tie stateful pods to a node. A PodDisruptionBudget (Chapter 08) makes drain wait instead of breaking an app.

    3.9 Reading Pending

    kubectl get pods -A --field-selector=status.phase=Pending
kubectl describe pod <pod> -n <ns> | grep -A3 Events
kubectl get events -n <ns> --field-selector reason=FailedScheduling

    3.11 Review questions

    1. A node shows 10% real CPU usage, yet a pod is Pending with "Insufficient cpu". How?

    The scheduler counts requests, not usage. The node's requests are already near its allocatable.

    2. nodeSelector vs required node affinity vs preferred node affinity?

    nodeSelector: exact label match, hard. Required affinity: hard with operators and OR. Preferred: soft, only adds score.

    3. You removed a node label used by required affinity. Are pods evicted?

    No. IgnoredDuringExecution: only scheduling checks it.

    4. Taint vs toleration vs affinity, in one line each?

    Taint: node repels pods. Toleration: pod may ignore a taint. Affinity: pod is attracted to nodes or pods.

    5. Why does draining the node with postgres-0 break it on kind?

    Its local-path PV is tied to that node; the replacement pod can't schedule anywhere else.
