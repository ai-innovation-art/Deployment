    Chapter 00 · Setup: Codespace, images, cluster, checkpoints

    By the end of this chapter, QuickBite runs on plain Docker, its images are on Docker Hub, and you have an empty 3-node Kubernetes cluster. You'll also have opened one of its "nodes" and found the kubelet running inside. You do this chapter once.

    Checkpoint at start: none Checkpoint at end: cluster ≈ 1 h, once

    0.1 What we are building

    QuickBite is a small food-ordering system with five services of our own and two off-the-shelf ones. A user opens the web page, sees the menu, and places an order. The order is saved, a confirmation "SMS" is sent, and every evening a sales report is printed.

    ServiceWhy it exists in the productThe Kubernetes lesson it carries
    webThe only thing users reach. Serves the page and forwards /api/*NodePort, then Ingress (Ch 5), the edge of the cluster
    menu-apiRead-heavy, stateless. Shows which pod on which node answeredReplicas, load balancing, rolling update and rollback (Ch 2), scheduling (Ch 3)
    orders-apiWrites orders; useless without the databaseInit container (schema migration), readiness tied to a dependency (Ch 4), Secrets (Ch 6)
    notifierBackground worker: no port, nobody calls itA Deployment without a Service; logs as the only window
    daily-reportRuns once a day and exitsJob and CronJob (Ch 8)
    redisMenu cache + order-event queue. Losing it is acceptableDeployment for disposable state
    postgresThe source of truth. Losing it is not acceptableStatefulSet, PVC, headless Service (Ch 7)

    0.2 Create the Codespace

    1. Push this repo (with labs/quickbite and .devcontainer/k8s-deep) to GitHub.
    2. On GitHub: Code → Codespaces → ⋯ → New with options.
    3. Dev container configuration: K8s Deep Dive. Machine type: 2-core / 8 GB.
    4. Wait for the post-create step: it runs install-tools.sh (kind, kubectl, helm, plus the k alias).
    Free hours

    Personal accounts get 120 core-hours per month: 60 hours on a 2-core machine, 30 on a 4-core. A Codespace stops itself after 30 idle minutes, and stopped time is not billed for compute. When you finish a session, stop it yourself: Codespaces → ⋯ → Stop codespace. Your cluster and data survive a stop; make resume brings them back.

    0.3 Step 1: Run QuickBite on plain Docker first

    Why: you already understand Docker 100%. Seeing the app work there first means that when something fails in Kubernetes, you know it's Kubernetes, not the app. It also gives us a "before" picture to compare every Kubernetes object against.

    make compose-up                 # = docker compose up -d --build
docker compose ps
    Predict: in what order do the containers become ready, and which one exits?

    postgres first (its healthcheck must pass), then db-migrate runs, creates the table and exits with code 0. Only then does orders-api start (condition: service_completed_successfully). redis and menu-api start in parallel. web waits for both APIs. docker compose ps -a shows db-migrate Exited (0). In Kubernetes this becomes an init container.

    Open the PORTS tab in VS Code → port 8080 → globe icon. Click "Order" a few times, then:

    curl -s localhost:8080/api/version; echo
docker compose logs notifier --tail 5
docker compose run --rm daily-report
    {"version":"1.0","pod":"3f2a9c1e7b4d","node":"not-in-k8s","uptime_s":42}
notifier-1  | [notifier 8e1d2c0a9b1f@not-in-k8s] SMS sent: order #1 (1 x Masala Dosa) confirmed
=========== QuickBite sales report ===========
item                                 units  orders
Masala Dosa                              1       1
TOTAL orders: 1
    Think: what is missing here that a real business needs?
    • One menu-api container. If it crashes, the menu is down until you notice. (Kubernetes: replicas + self-healing.)
    • Everything is on one machine. If the machine dies, everything dies. (Kubernetes: many nodes + a scheduler.)
    • Releasing a new version means stop → start, which is downtime. (Kubernetes: rolling update and rollback.)
    • The daily report only runs when you type the command. (Kubernetes: CronJob.)
    • The DB password sits in compose.yaml. (Kubernetes: Secret + RBAC.)

    Each bullet is a chapter. This is the reason Kubernetes exists.

    make compose-down

    0.4 Step 2: Build and push the images (once)

    A kind cluster can't see images that only exist in your Codespace's Docker. It pulls from a registry, the same as a production cluster. So we publish to Docker Hub once, and every future cluster (new Codespace, new account, real VMs later) pulls the same images.

    1. Create an access token: hub.docker.com → Account settings → Personal access tokens → Generate (Read & Write).
    2. Log in and push:

    The repos must be public

    New Docker Hub repos are public by default on a free account. If you made them private, the cluster can't pull them and the pods show ErrImagePull (we'll create exactly this error on purpose in Chapter 1).

    0.5 Step 3: Create the 3-node cluster

    nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080   # NodePort of the web Service
        hostPort: 8080         # Codespace port → opens in your browser
  - role: worker
  - role: worker
    make cluster
kubectl get nodes -o wide
    Predict: how many nodes, what roles, what status?
    NAME                      STATUS   ROLES           VERSION   INTERNAL-IP   CONTAINER-RUNTIME
quickbite-control-plane   Ready    control-plane   v1.31.0   172.18.0.4    containerd://1.7.x
quickbite-worker          Ready    <none>          v1.31.0   172.18.0.2    containerd://1.7.x
quickbite-worker2         Ready    <none>          v1.31.0   172.18.0.3    containerd://1.7.x

    Note the runtime: containerd, not Docker. Kubernetes talks to containerd through CRI. Docker is only the "fake hardware" kind uses to create the node machines.

    0.6 Look inside a "node": it's a real machine for Kubernetes

    This is the answer to "is kind real?". Each node is a Docker container, but inside it is exactly what a VM node runs.

    docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
    NAMES                     IMAGE                  PORTS
quickbite-control-plane   kindest/node:v1.31.0   0.0.0.0:8080->30080/tcp, 127.0.0.1:4xxxx->6443/tcp
quickbite-worker          kindest/node:v1.31.0
quickbite-worker2         kindest/node:v1.31.0

    Port 6443 is the API server. kubectl talks to it via the address saved in ~/.kube/config.

    docker exec -it quickbite-control-plane bash

# 1. The node agent and the runtime: ordinary Linux processes
ps -eo pid,comm | grep -E 'kubelet|containerd$'

# 2. The control plane runs as "static pods": the kubelet starts whatever YAML is in this folder
ls /etc/kubernetes/manifests

# 3. Containers on this node, seen through CRI (no docker in here!)
crictl ps --name 'kube-|etcd' -o table

exit
        1xx kubelet
    1xx containerd
etcd.yaml  kube-apiserver.yaml  kube-controller-manager.yaml  kube-scheduler.yaml
CONTAINER   IMAGE   CREATED   STATE     NAME                      ...
a1b2...             10m       Running   kube-scheduler
c3d4...             10m       Running   kube-controller-manager
e5f6...             10m       Running   kube-apiserver
0a1b...             10m       Running   etcd
...                           Running   kube-proxy
    Predict: run the same three commands inside quickbite-worker. What's different?

    kubelet and containerd are there. /etc/kubernetes/manifests is empty, and crictl ps shows only kube-proxy and kindnet-cni. A worker has no brain; it only runs what the control plane assigns to it. That is the whole architecture in one comparison:

    • Control plane = decides (API server, etcd, scheduler, controllers)
    • Worker = executes (kubelet, runtime, kube-proxy, CNI)
    kubectl get pods -n kube-system -o wide

    Every control-plane component is also visible as a pod. Look at the NODE column: kube-proxy and kindnet have one pod per node (that's a DaemonSet, Ch 8), while the API server, etcd and the scheduler run only on quickbite-control-plane.

    0.7 Your session routine from now on

    Start of session

    cd labs/quickbite
git pull
make resume      # or: make cluster
make status

    End of session

    Just stop the Codespace (⋯ → Stop). No cleanup needed; next time make resume picks up.

    New account? Same commands. The images come from Docker Hub.
