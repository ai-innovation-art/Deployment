    How to write any Kubernetes YAML

    A method, not memorization. It works for any object in any project: find the type → generate a template → find where fields go with explain → validate → compare with what's running. Keep this page open whenever you write or change a manifest.

    Reference page Used in every chapter

    The skeleton every object shares

    apiVersion: apps/v1          # 1. which API group/version   ┐ WHAT it is
kind: Deployment             # 2. which type of object       ┘
metadata:                     # 3. WHO it is
  name: menu-api              #    name is INSIDE metadata
  namespace: quickbite
  labels:
    app.kubernetes.io/name: menu-api
  annotations: {}
spec:                         # 4. WHAT YOU WANT (desired state), written by you
  replicas: 3
status:                       # 5. WHAT IS (actual state), written by Kubernetes, never by you
  readyReplicas: 3
    The core idea

    You write spec. Controllers keep working until status matches it. READY 2/3 in kubectl get output means status hasn't caught up with spec yet.

    Exceptions: ConfigMap and Secret have data / stringData instead of spec, because they hold data, not a desired state.

    Step 1 · Find apiVersion and kind

    kubectl api-resources                          # every object type the cluster knows
kubectl api-resources | grep -i deployment     # one type
kubectl api-resources --namespaced=false       # cluster-wide types (Node, PV, Namespace...)
    NAME          SHORTNAMES   APIVERSION   NAMESPACED   KIND
deployments   deploy       apps/v1      true         Deployment

    Copy APIVERSION → apiVersion: and KIND → kind:. apiVersion is group/version; the core group has no name, so it's just v1.

    apiVersionObjects
    v1Pod, Service, ConfigMap, Secret, Namespace, PersistentVolumeClaim, ServiceAccount
    apps/v1Deployment, StatefulSet, DaemonSet, ReplicaSet
    batch/v1Job, CronJob
    networking.k8s.io/v1Ingress, NetworkPolicy
    rbac.authorization.k8s.io/v1Role, RoleBinding, ClusterRole, ClusterRoleBinding
    autoscaling/v2HorizontalPodAutoscaler
    policy/v1PodDisruptionBudget
    Version suffixMeaning
    v1alpha1Experimental: can change or disappear
    v1beta1Mostly stable: changes come with a migration path
    v1Stable: never breaks

    Step 2 · Generate a template (never start from a blank file)

    --dry-run=client -o yaml means "don't create anything, just print the YAML". You get a correct structure to edit.

    # Deployment
kubectl create deployment menu-api --image=kumawatsunil/quickbite-menu-api:1.0 --replicas=3 \
  --port=8000 --dry-run=client -o yaml > deployment.yaml

# Service (ClusterIP) for an existing Deployment name
kubectl create service clusterip menu-api --tcp=8000:8000 --dry-run=client -o yaml > service.yaml

# Service from a Deployment that already exists in the cluster
kubectl expose deployment menu-api --port=8000 --dry-run=client -o yaml

# Pod
kubectl run test --image=nginx --port=80 --dry-run=client -o yaml

# ConfigMap / Secret
kubectl create configmap app-config --from-literal=REDIS_HOST=redis --dry-run=client -o yaml
kubectl create secret generic db-creds --from-literal=password=s3cret --dry-run=client -o yaml

# Namespace
kubectl create namespace quickbite --dry-run=client -o yaml

# Job / CronJob
kubectl create job report --image=busybox --dry-run=client -o yaml -- echo hi
kubectl create cronjob report --image=busybox --schedule="0 21 * * *" --dry-run=client -o yaml -- echo hi

# Ingress
kubectl create ingress web --rule="quickbite.local/*=web:80" --dry-run=client -o yaml

# RBAC
kubectl create role pod-reader --verb=get,list --resource=pods --dry-run=client -o yaml
kubectl create rolebinding read-pods --role=pod-reader --user=alice --dry-run=client -o yaml
    No generator?

    StatefulSet, DaemonSet, PVC and NetworkPolicy have no kubectl create generator. Copy the nearest template (a Deployment for StatefulSet/DaemonSet), or the example from kubernetes.io/docs, then use Step 3.

    Step 3 · Find WHERE a field goes, with kubectl explain

    The path you type is the place in the YAML: one dot = one indentation level.

    kubectl explain deployment.spec                                    # → template
kubectl explain deployment.spec.template.spec                      # → containers
kubectl explain deployment.spec.template.spec.containers           # → readinessProbe
kubectl explain deployment.spec.template.spec.containers.readinessProbe

kubectl explain deployment.spec --recursive | less                 # the whole tree at once
    spec:                          # deployment.spec
  template:                    #   .template
    spec:                      #     .spec
      containers:              #       .containers
        - name: menu-api
          readinessProbe:      #         .readinessProbe   ← here
            httpGet:
              path: /ready
              port: 8000

    Each explain output shows the field's type and description, and whether it's required. The type tells you how to write it:

    Type in explainWrite it asExample
    <string>a valueimage: nginx:1.27
    <integer> / <boolean>number / true or false (no quotes)replicas: 3
    <Object> (e.g. <PodSpec>)a nested block, indented 2 spacesresources: ↵ limits: ...
    <[]Object>a list: every item starts with - containers: ↵ - name: web
    <map[string]string>free key: value pairslabels: ↵ tier: backend
    <IntOrString>number or nameport: 8000 or port: http

    Step 4 · Validate before applying

    kubectl apply -f deployment.yaml --dry-run=client   # YAML syntax + structure, local only
kubectl apply -f deployment.yaml --dry-run=server   # full validation by the API server, nothing saved

    Use --dry-run=server: it catches wrong field names, wrong types, wrong apiVersion, a missing namespace, and policy rejections.

    Step 5 · Compare with what's running

    kubectl get deploy menu-api -n quickbite -o yaml   # the live object, incl. defaults you never wrote + status
kubectl diff -f deployment.yaml                     # exactly what apply would change
kubectl apply -f deployment.yaml                    # apply for real
    Learn defaults from the live object

    -o yaml shows every field Kubernetes filled in for you (strategy, revisionHistoryLimit, terminationGracePeriodSeconds, ...). This is the fastest way to discover options you didn't know existed.

    The whole method on one screen

    kubectl api-resources | grep -i <thing>                      # 1 apiVersion + kind
kubectl create <thing> ... --dry-run=client -o yaml > x.yaml  # 2 template
kubectl explain <kind>.spec.<path>                           # 3 where does it go?
kubectl apply -f x.yaml --dry-run=server                      # 4 validate
kubectl diff -f x.yaml && kubectl apply -f x.yaml             # 5 compare, then apply

    YAML syntax rules that cause most errors

    RuleWrongRight
    Spaces only, never tabs; 2 per level(tab) name: x name: x
    Space after the colonreplicas:3replicas: 3
    List items start with - containers: ↵ name: webcontainers: ↵ - name: web
    Quote values that look like numbers or booleans but must be stringsCACHE_TTL_SECONDS: 30 (in a ConfigMap)CACHE_TTL_SECONDS: "30"
    Several objects in one file: separate with ---two objects with no separator--- on its own line between them
    Flow style is the same thing on one line{ cpu: 50m, memory: 64Mi } = block style

    Common errors and what they mean

    ErrorCause
    no matches for kind "X" in version "Y"Wrong apiVersion for that kind (Step 1)
    unknown field "spec.template.spec.containers[0].readynessProbe"Typo, or field at the wrong level (Step 3)
    error converting YAML to JSON: yaml: line 12: mapping values are not allowedIndentation or a missing space after :
    cannot unmarshal number into ... of type stringUnquoted number where a string is required
    selector does not match template labelsspec.selector.matchLabels ≠ spec.template.metadata.labels
    namespaces "quickbite" not foundNamespace not created yet
    field is immutableSome fields can't change after creation (e.g. a Deployment's selector): delete and recreate
