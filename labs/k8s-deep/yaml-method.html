    YAML: commands cheat sheet

    The 5 steps

    # 1. Find the kind, apiVersion, and whether it's namespaced
kubectl api-resources | grep -i deployment

# 2. Generate a template (then delete creationTimestamp, {} and status)
kubectl create deployment menu-api --image=nginx --replicas=3 --dry-run=client -o yaml > my.yaml

# 3. Find where a field goes, and its type
kubectl explain deployment.spec.template.spec.containers
kubectl explain deployment --recursive | less

# 4. Validate against the real API server (nothing is created)
kubectl apply -f my.yaml --dry-run=server

# 5. Compare with what's running, then apply
kubectl diff -f my.yaml
kubectl apply -f my.yaml

    Generators: Namespace, ConfigMap, Secret

    kubectl create namespace quickbite --dry-run=client -o yaml > ns.yaml

kubectl create configmap quickbite-config -n quickbite \
  --from-literal=DB_HOST=postgres --from-literal=CACHE_TTL_SECONDS=30 \
  --dry-run=client -o yaml > cm.yaml

kubectl create secret generic postgres-credentials -n quickbite \
  --from-literal=username=quickbite --from-literal=password=quickbite-dev-password \
  --dry-run=client -o yaml > secret.yaml

    Remember

    ConfigMap values are plain text. A Secret's stringData is plain text, and its data must be base64 (echo -n 'pw' | base64). base64 is encoding, not encryption.

    Service and StatefulSet

    Service typeGives you
    ClusterIP (default)One fixed virtual IP, inside the cluster only. Load-balances across pods
    clusterIP: None (headless)No virtual IP. DNS returns the pod IPs directly
    NodePortClusterIP + a port (30000–32767) open on every node
    LoadBalancerNodePort + a cloud load balancer
     
    StatefulSet  spec.selector.matchLabels ──must match──► spec.template.metadata.labels (pod labels)
Service      spec.selector             ──must match──► the same pod labels

Service DNS: postgres.quickbite.svc.cluster.local              (5 parts)
Pod DNS:     postgres-0.postgres.quickbite.svc.cluster.local   (6 parts, StatefulSet + headless only)
    • serviceName (StatefulSet) must name a headless Service. It gives each pod its DNS name.
    • Pods are named <name>-0, -1, -2, created in order. Each pod gets its own PVC, and keeps it when replaced.
    • Replicas are separate databases. Copying data between them is the database's job (an operator), not Kubernetes'.
    • clusterIP and selector can't be changed later: delete and recreate.
    • metadata.labels = tags on this object. spec.selector = a search for pods.
    4-line summary

    1. Labels tag pods. Selectors find pods by those tags.
    2. If the StatefulSet/Deployment selector doesn't match the template labels, apply is rejected (loud error).
    3. If the Service selector doesn't match, the pod runs but has 0 endpoints (silent error). Check kubectl get endpointslices.
    4. Headless means DNS returns the pod IP directly. With a StatefulSet, each pod gets pod.service.ns.svc.cluster.local.

    Downward API

    Passes facts about the pod into the container (env var or file). The app can't ask Kubernetes; Kubernetes tells it.

    Taints and tolerations

    Taint = "keep out" sign on a node. Toleration = a pod's pass that ignores that sign. Pass ≠ invitation: a toleration allows the node, it doesn't force it.

    EffectNew podsPods already running
    NoScheduleNot placed (unless they tolerate it)Stay
    PreferNoScheduleAvoided if possibleStay
    NoExecuteNot placedEvicted (unless tolerated, optionally for N seconds)
     
    kubectl describe node quickbite-control-plane | grep Taints
# node-role.kubernetes.io/control-plane:NoSchedule
kubectl taint node <node> key=value:NoSchedule     # add
kubectl taint node <node> key=value:NoSchedule-    # remove (trailing -)

    Container: env, probes, resources

    env:
  - { name: X, value: "fixed" }
  - { name: X, valueFrom: { configMapKeyRef: { name: <cm>,     key: <key> } } }
  - { name: X, valueFrom: { secretKeyRef:    { name: <secret>, key: <key> } } }
  - { name: X, valueFrom: { fieldRef: { fieldPath: spec.nodeName } } }
    • The app decides the variable names. You only supply values. A wrong cm/secret name or key gives CreateContainerConfigError.
    • exec has no shell. Use sh -c "..." when the command needs $VAR.
    • containerPort is documentation, like EXPOSE. Name it so Services can use targetPort: <name>.
    ProbeFails →
    readinessRemoved from endpoints (no traffic). No restart
    livenessContainer restarted. Keep it gentler than readiness (initialDelaySeconds)
    startupHolds the other two until the app has started

    Defaults: initialDelay 0 · period 10 · timeout 1 · failureThreshold 3. No liveness is fine. A crashed process is restarted anyway.

    requestslimits
    Used byScheduler (placement)Kernel (runtime cap)
    Over the limit—CPU throttled · memory OOMKilled

    100m = 0.1 core · Mi/Gi binary. QoS: Guaranteed (requests = limits) · Burstable · BestEffort (nothing set, evicted first).

    Storage

    PVC           the request: "1Gi, RWO"     (namespaced)
PV            the actual disk             (cluster-wide)
StorageClass  how disks are made          (kind default: standard / local-path)

volumeClaimTemplates name "data" + pod postgres-0  →  PVC data-postgres-0
    • Access modes: RWO (one node) · ROX · RWX (needs NFS) · RWOP (one pod).
    • Deleting a pod or StatefulSet keeps the PVC. Delete it yourself.
    • local-path disks live on one node, so the pod is pinned to that node.
    • Delete the pod → same name, same node, same disk, same data.

    • targetPort is NOT a host port. It's the port inside the pod. It defaults to port and can be a name.

    Deployment rollout settings

    max pods during update  = replicas + maxSurge       = 4
min Ready pods          = replicas - maxUnavailable = 3
new pod never Ready     → rollout stops, old pods keep serving
    • RollingUpdate = no downtime. Recreate = kill all, then start (use when old and new can't run together).
    • revisionHistoryLimit = old ReplicaSets kept for rollout undo. 0 = no rollback.
    • kubernetes.io/change-cause annotation = the CHANGE-CAUSE column in rollout history.
    • kubectl rollout status changes nothing. It waits until all new pods are Ready (used in scripts/CI).

    Probes: /health vs /ready

    • Liveness (/health): "is the process alive?" Never check dependencies, or a Redis outage restarts every pod (restart storm).
    • Readiness (/ready): "should I get traffic?" Fast (period 5, failureThreshold 2). Liveness slow (~30 s).
    • httpGet: 200–399 = pass. port: http and targetPort: http refer to the named containerPort.

    Init containers and command

    • initContainers: run one by one, each must exit 0, then the main containers start. Retried on failure. Status: Init:0/1 → PodInitializing → Running.
    • They run on every pod start (each replica, each restart), so their job must be safe to repeat (CREATE TABLE IF NOT EXISTS).
    • Replaces compose depends_on: service_completed_successfully. Kubernetes has no depends_on.
    • command = Docker ENTRYPOINT · args = Docker CMD. Use them to run a different program from the same image.
    • The list decides when (initContainers vs containers); command decides what.
    • Each container has its own image and env (nothing is shared or inherited). The same image is pulled once per node and reused. Keep both tags in sync (Kustomize images: / Helm values).
    • Logs: kubectl logs <pod> -c db-migrate.

    When you need a Service

    Deployment ─► ReplicaSet ─► Pod ─► Container    (creates and keeps pods running)
Service ──selector──► Pods                      (finds pods: DNS name + virtual IP + kube-proxy rules on every node)
    • Need a Service only if something connects in to the pod. Workers that only connect out (notifier → redis) need none.
    • A Service gives a stable name, load balancing, and tracks only Ready pods.
    • NodePort = ClusterIP + a port (30000–32767) opened on every node, even nodes without the pod. Omit nodePort to get a random one.
    • Ports below 1024 need root, so non-root containers use 8080 and the Service maps 80 → 8080.
    • Production: LoadBalancer or Ingress instead of NodePort.

    Job and CronJob

    CronJob   spec.schedule ...                    WHEN
  Job     spec.jobTemplate.spec ...            retries, cleanup
    Pod   spec.jobTemplate.spec.template.spec  containers (restartPolicy: Never | OnFailure)
    • Cron: min hour day month weekday · 0 21 * * * = 21:00 daily · */15 * * * * = every 15 min. Set timeZone, else UTC.
    • concurrencyPolicy: Allow (default) · Forbid (skip new) · Replace (kill old).
    • backoffLimit retries (default 6) · ttlSecondsAfterFinished auto-delete · history limits 3 / 1.
    • Never = a new pod per retry (old logs kept) · OnFailure = same pod restarts.
    • Run now: kubectl create job report-now --from=cronjob/daily-report. Done pod = Completed, not restarted.

    Kustomize

    • kubectl apply -k <dir> applies every file listed in kustomization.yaml. Unchanged objects print unchanged (apply is safe to repeat).
    • kubectl kustomize <dir> shows the combined YAML without applying.

    What creates a new ReplicaSet

    Rule

    Change anything inside spec.template (image, env, probes, resources, pod labels, annotations) → a new ReplicaSet + rolling update. The existing RS is never edited.
    Change anything outside the template (replicas, strategy, minReadySeconds, Deployment labels/annotations) → applied in place, no new RS, no new pods.
    Go back to an old template → its old RS is reused (same hash), and its revision gets a new number.

    Self-healing

    CONTAINER fails  → kubelet restarts it INSIDE the same pod     (same name, RESTARTS +1)
POD disappears   → ReplicaSet creates a NEW pod                (new name, new IP)
BAD RELEASE      → rollout stops; you roll back                (old pods keep serving)
    • Bad image → ErrImagePull ⇄ ImagePullBackOff, retried forever (back-off up to 5 min). Never auto-rolled back.
    • After progressDeadlineSeconds (default 600) the rollout is marked failed (ProgressDeadlineExceeded); rollout status exits with an error. Still no automatic undo.
    • maxUnavailable: 0 → old pods keep serving during a broken rollout.
    • rollout undo scales the old ReplicaSet back up (same hash). Its revision gets a new number: 1 → 3. The old number disappears.
    • Rollback after a stuck rollout is near-instant: the old pods never stopped, only the broken pod is removed.
    • Two kinds of bad release: image missing → ImagePullBackOff · app broken → Running 0/1 (readiness fails, liveness passes, RESTARTS 0). Both: users unaffected with maxUnavailable: 0.
    • Not-Ready pods are listed in the EndpointSlice with ready=false. kube-proxy sends traffic only to ready=true.
    • Without a readiness probe, a broken pod counts as Ready and the rollout replaces all good pods.
    • Update change-cause with every change. undo also restores the old annotation, so stale causes make the history lie.
    The undo trap

    undo = "go to the previous revision". After one undo, the previous revision is the broken one, so a second undo rolls forward into it.
    In an incident: rollout history → pick the number → rollout undo --to-revision=N. Never chain undos.

    kubectl rollout history deploy/menu-api --revision=N            # template of one revision
diff <(kubectl rollout history deploy/menu-api --revision=4)      <(kubectl rollout history deploy/menu-api --revision=5)      # what differs
kubectl get deploy menu-api -o jsonpath='{.status.conditions[?(@.type=="Progressing")].reason}'
# ReplicaSetUpdated → still trying · ProgressDeadlineExceeded → failed (600 s)
    kubectl set image deploy/menu-api menu-api=<image:tag> -n quickbite
kubectl annotate deploy/menu-api kubernetes.io/change-cause="..." --overwrite
kubectl rollout status  deploy/menu-api --timeout=60s
kubectl rollout history deploy/menu-api
kubectl rollout undo    deploy/menu-api                 # previous revision
kubectl rollout undo    deploy/menu-api --to-revision=N
kubectl get rs -l app.kubernetes.io/name=menu-api       # old vs new ReplicaSet
