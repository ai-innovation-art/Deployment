    6.1 Env var vs mounted file

    apiVersion: v1
kind: ConfigMap
metadata: { name: app-config, namespace: config }
data:
  GREETING: hello-v1
  app.properties: |              # a whole file as one value
    color=blue
    timeout=30
---
apiVersion: v1
kind: Pod
metadata: { name: reader, namespace: config }
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "while true; do echo \"env=$GREETING file=$(cat /config/GREETING)\"; sleep 5; done"]
      env:
        - name: GREETING
          valueFrom: { configMapKeyRef: { name: app-config, key: GREETING } }
      volumeMounts:
        - { name: cfg, mountPath: /config }
  volumes:
    - name: cfg
      configMap: { name: app-config }      # every key becomes a file
    kubectl apply -f app.yaml
kubectl exec -n config reader -- ls -la /config
kubectl exec -n config reader -- cat /config/app.properties
kubectl logs -n config reader --tail=2
    kubectl logs -n config reader -f
    Predict: what does ls -la /config show?

    Two names (GREETING, app.properties) that are symlinks into a hidden ..data folder. That indirection is how the kubelet swaps all files at once on an update.

    6.2 Change the ConfigMap

    Objective: the same ConfigMap reaches a container two ways. Env var = a copy taken once at start (frozen). Mounted file = a live view the kubelet keeps updated. Choose by whether the value must change without a restart.

    kubectl patch configmap app-config -n config -p '{"data":{"GREETING":"hello-v2"}}'
# watch Terminal 2 for ~90 s
    Predict: what happens to env= and file=?
    env=hello-v1 file=hello-v1
...  (up to ~60–90 s)
env=hello-v1 file=hello-v2     ← file updated, env never

    Env vars are copied once when the container starts. Mounted files are refreshed by the kubelet (sync period + cache, up to ~1–2 min). The app must re-read the file to notice (nginx reload, file watcher).

    Seen

    File changed after the kubelet's sync, env never. In ls -la: a new timestamped folder (09_42 → 09_47), ..data re-pointed to it, old folder deleted; GREETING/app.properties links untouched (they point at ..data).

    env / envFromMounted volumeMounted with subPath
    ConfigMap change seen?Never (until restart)Yes, ~1 minNever
    Good forSimple settingsConfig files (nginx.conf, app.yaml)One file into an existing folder

    6.3 QuickBite: change the cache TTL

    kubectl patch configmap quickbite-config -n quickbite -p '{"data":{"CACHE_TTL_SECONDS":"5"}}'
kubectl exec -n quickbite deploy/menu-api -- printenv CACHE_TTL_SECONDS
kubectl run t --rm -it --restart=Never -n quickbite --image=curlimages/curl -- curl -s menu-api:8000/menu >/dev/null
kubectl exec -n quickbite deploy/redis -- redis-cli TTL menu:1.0
    Predict: printenv and TTL after the patch? What fixes it?

    Still 30 and a TTL near 30: the pods read the env at start. Fix:

    kubectl rollout restart deploy/menu-api -n quickbite
kubectl rollout status deploy/menu-api -n quickbite
kubectl exec -n quickbite deploy/menu-api -- printenv CACHE_TTL_SECONDS    → 5
    Seen

    After the patch: printenv 30. After rollout restart: printenv 5, TTL 3 (5 s minus the curl pod's start time). DEL → 0 = key didn't exist. Redis TTL −2 = no key.

    kubectl apply -f /workspaces/Deployment/labs/quickbite/k8s/base/00-namespace-config.yaml
kubectl rollout restart deploy/menu-api -n quickbite

    6.4 envFrom and missing keys

    envFrom:
  - configMapRef: { name: app-config }        # every key → env var (invalid names skipped)
  - secretRef:    { name: db-creds }
    prefix: DB_                               # DB_username, DB_password

env:
  - name: X
    valueFrom: { configMapKeyRef: { name: app-config, key: NOPE, optional: true } }   # missing → just unset
    • Missing ConfigMap/Secret or key, not optional → pod stuck CreateContainerConfigError.
    • optional: true + missing → the variable is simply not set (no random or empty value); the app's own default applies, e.g. os.getenv("X", "30").
    • envFrom is short but hides which values an app uses; explicit env is clearer.

    6.5 Secrets as files

    kubectl create secret generic db-creds -n config --from-literal=username=app --from-literal=password=s3cr3t
kubectl run sec -n config --image=busybox:1.36 --overrides='{"spec":{"containers":[{"name":"sec","image":"busybox:1.36","command":["sleep","3600"],"volumeMounts":[{"name":"s","mountPath":"/secrets","readOnly":true}]}],"volumes":[{"name":"s","secret":{"secretName":"db-creds","defaultMode":256}}]}}'
kubectl exec -n config sec -- ls -lL /secrets
kubectl exec -n config sec -- cat /secrets/password; echo
kubectl exec -n config sec -- sh -c 'mount | grep secrets'
kubectl exec -n config sec -- ls /var/run/secrets/kubernetes.io/serviceaccount
    Predict: file permissions, the mount type, and the last folder?

    -r-------- (defaultMode 256 = octal 0400). Mount type tmpfs: Secret files live in RAM, never on the node's disk. The last folder exists in every pod: the ServiceAccount token, CA cert and namespace, auto-mounted (Chapter 09).

    Seen

    -r-------- (0400), mount type tmpfs read-only (RAM), and every pod also has the ServiceAccount folder (ca.crt, namespace, token) on tmpfs.

    • Files beat env vars for secrets: env vars show up in kubectl describe-style dumps, crash reports and child processes.
    • Real protection: RBAC on Secrets, encryption at rest in etcd, and an external store (Vault, cloud secret manager) synced by External Secrets Operator or Sealed Secrets, so no plain secret sits in git.

    6.6 Immutable ConfigMaps

    kubectl create configmap frozen -n config --from-literal=MODE=prod --dry-run=client -o yaml \
  | sed 's/^data:/immutable: true\ndata:/' | kubectl apply -f -
kubectl patch configmap frozen -n config -p '{"data":{"MODE":"dev"}}'
    Predict: does the patch work?

    No: field is immutable when `immutable` is set. To change it: create frozen-v2, point the Deployment at it (template change → rollout), delete the old one. Benefits: no accidental edits, and the kubelet stops watching it (less API server load in big clusters).

    Seen

    Forbidden: field is immutable when `immutable` is set. The long JSON line in the grep is the last-applied-configuration annotation that kubectl apply stores for its 3-way merge. Immutable can't be switched back off; delete and recreate.

    6.7 Automatic rollout on config change: the hash trick

    A ConfigMap change doesn't touch the pod template, so no rollout. Kustomize's configMapGenerator adds a hash of the content to the name; new content → new name → the Deployment's reference changes → rollout.

    namespace: config
configMapGenerator:
  - name: web-config
    literals: [ "COLOR=blue" ]
resources: [ deploy.yaml ]
    apiVersion: apps/v1
kind: Deployment
metadata: { name: hashdemo }
spec:
  replicas: 2
  selector: { matchLabels: { app: hashdemo } }
  template:
    metadata: { labels: { app: hashdemo } }
    spec:
      containers:
        - name: app
          image: busybox:1.36
          command: ["sh", "-c", "echo COLOR=$COLOR; sleep 3600"]
          envFrom: [ { configMapRef: { name: web-config } } ]   # kustomize rewrites this name
    mkdir -p ~/config/gen && cd ~/config/gen      # create the two files above
kubectl kustomize .  | grep -E "name: web-config"
kubectl apply -k .
kubectl get cm -n config
sed -i 's/COLOR=blue/COLOR=green/' kustomization.yaml
kubectl apply -k .
kubectl get cm,rs -n config
kubectl logs -n config deploy/hashdemo
    Predict: what are the ConfigMap names, and does the Deployment roll out?

    web-config-<hash1>, then web-config-<hash2> beside it. The Deployment's reference changed → template change → new ReplicaSet → pods print COLOR=green. Rollback works too (the old ConfigMap still exists). Helm does the same with a checksum/config annotation.

    Seen

    Two ConfigMaps (blue + green hash), two ReplicaSets, rollout started by itself. No if/else: content → hash → new name → template changed → normal rollout. logs deploy/X picks any pod, maybe an old one.

    Rollback and config

    rollout undo restores the template, i.e. the ConfigMap name it references, never the ConfigMap's content. Versioned names (hash, -v2, immutable) + keeping the old one = undo really restores old config. A ConfigMap edited in place can't be rolled back; deleting the old one breaks undo (CreateContainerConfigError).

    6.10 Review questions

    1. You updated a ConfigMap. Env-based pods still use the old value. Why, and the fix?

    Env vars are read only at container start. kubectl rollout restart, or use the hash trick so changes roll out automatically.

    2. A mounted config file changed, but the app still behaves the old way. Why?

    The file updated (~1 min), but the app read it only at start. It must watch or re-read it (or be restarted). Also check for subPath, which never updates.

    3. Why mount Secrets as files instead of env vars?

    Files live in tmpfs with strict permissions and don't leak into env dumps or child processes; they also update without a restart.

    4. What does immutable: true give you?

    Protection from accidental edits and less load (the kubelet stops watching). Changes require a new object name.

    5. How does configMapGenerator trigger a rollout?

    It names the ConfigMap with a content hash; new content → new name → the pod template's reference changes → new ReplicaSet.
