    Chapter 02 · Ship 1.1, ship a broken 1.2, roll back

    QuickBite wants to add a new dish without any downtime, and when a release is bad, get back to safety in seconds. You'll watch two ReplicaSets trade pods while live traffic flows, see a release that runs but never becomes Ready, and learn every rollout command.

    Checkpoint at start: make resume Images already on Docker Hub: 1.0 · 1.1 · 1.2-broken ≈ 1.5 h

    2.0 Setup: three terminals

    cd /workspaces/Deployment/labs/quickbite
make resume
alias kq='kubectl -n quickbite'
    kubectl -n quickbite get rs -l app.kubernetes.io/name=menu-api -w
    kubectl run loop --rm -it --restart=Never --image=curlimages/curl -n quickbite -- \
  sh -c 'while true; do curl -s -m 1 menu-api:8000/version; echo; sleep 0.5; done'

    Terminal 3 shows version and pod for every request. During a rollout you'll see 1.0 and 1.1 answer side by side. If a line is empty, a request failed: that's downtime.

    2.1 Deployment → ReplicaSet → Pod

    Deployment menu-api            "3 pods of THIS template, updated like THIS"
  ├── ReplicaSet menu-api-645d8c8f4b   template 1.0   replicas 3
  └── ReplicaSet menu-api-7cc6c8f77c   template 9.9   replicas 0   ← kept for rollback
        └── Pods menu-api-645d8c8f4b-xxxxx   label pod-template-hash=645d8c8f4b
    • The hash is a fingerprint of spec.template. Same template → same hash → same ReplicaSet is reused.
    • The Deployment never touches pods. It only changes the replica counts of its ReplicaSets.
    • Only a change inside spec.template starts a rollout.
    ChangeIn template?Rollout?
    image, env, probes, resources, pod labelsYesYes
    kubectl rollout restart (adds a restartedAt annotation to the template)YesYes
    replicas / kubectl scaleNoNo: the current RS grows or shrinks
    strategy, minReadySeconds, revisionHistoryLimitNoNo
    Deployment's own labels / annotations (change-cause)NoNo
     
    kq get pods -l app.kubernetes.io/name=menu-api --show-labels   # find pod-template-hash

kq scale deploy/menu-api --replicas=4 ; kq get rs -l app.kubernetes.io/name=menu-api
kq scale deploy/menu-api --replicas=3

kq patch deploy/menu-api -p '{"spec":{"minReadySeconds":10}}' ; kq get rs -l app.kubernetes.io/name=menu-api

kq set env deploy/menu-api LOG_LEVEL=debug ; kq get rs -l app.kubernetes.io/name=menu-api
kq set env deploy/menu-api LOG_LEVEL-                          # trailing - removes it
    Predict: which of the three creates a new ReplicaSet?

    Only set env. Scale changes the existing RS's count. minReadySeconds is outside the template. The env var is inside the template → new hash → new RS → rolling update. Removing it brings the template back to the 1.0 hash, so the old RS is reused (no third RS).

    We keep minReadySeconds: 10 on purpose: a new pod must stay Ready 10 s before it counts as available, which slows rollouts down so you can watch them.

    2.2 Rolling update maths

    max pods at once   = replicas + maxSurge
min available pods = replicas − maxUnavailable
percentages: maxSurge rounds UP, maxUnavailable rounds DOWN
both 0 → rejected (the rollout could never move)
    replicas 3 with…Max podsMin availableBehaviour
    maxSurge 1, maxUnavailable 0 (ours)43Add 1 new, wait for Ready, remove 1 old. Safest, needs spare room
    maxSurge 0, maxUnavailable 132Remove 1 old first, then add. No extra room needed, capacity dips
    maxSurge 3, maxUnavailable 063Start all new at once (blue/green-like), then drop the old
    default 25% / 25%4 (0.75→1)3 (0.75→0)Same as ours at 3 replicas
    Recreate30Kill all, then start all. Downtime
    Predict: replicas 10, maxSurge 25%, maxUnavailable 25%. Max pods and min available?

    maxSurge = 2.5 → rounds up to 3 → max 13 pods. maxUnavailable = 2.5 → rounds down to 2 → at least 8 available.

    2.3 Ship 1.1 (the good release)

    kq set image deploy/menu-api menu-api=kumawatsunil/quickbite-menu-api:1.1
kq annotate deploy/menu-api kubernetes.io/change-cause="1.1: add Spicy Paneer Wrap" --overwrite
kq rollout status deploy/menu-api
    NAME                  DESIRED   CURRENT   READY
menu-api-645d8c8f4b   3         3         3      ← 1.0
menu-api-58b7d9c6f    1         1         0      ← 1.1 created (surge +1)
menu-api-58b7d9c6f    1         1         1      ← Ready, waits minReadySeconds 10 s
menu-api-645d8c8f4b   2         2         2      ← one 1.0 removed
menu-api-58b7d9c6f    2         2         1
...
menu-api-58b7d9c6f    3         3         3
menu-api-645d8c8f4b   0         0         0      ← kept, empty
    Predict: in Terminal 3, do you ever see an empty line? Do 1.0 and 1.1 answer at the same time?

    No empty lines (maxUnavailable 0, readiness gates traffic). Yes, for about 30–40 s you'll see a mix of "version":"1.0" and "version":"1.1". During a rolling update, old and new versions serve users together, so new code must be compatible with old code (APIs, DB schema).

    Open the UI (port 8080): the menu now shows Spicy Paneer Wrap (NEW in 1.1).

    kq rollout history deploy/menu-api
kq rollout history deploy/menu-api --revision=<N>     # the template of one revision
kq describe deploy/menu-api | grep -A12 Events         # "Scaled up replica set ... to 1" etc.

    2.4 Ship 1.2-broken (runs, never Ready)

    Different from 9.9 in Chapter 01: this image exists and starts. Its /ready returns 503 (BROKEN=true). This is the realistic failure: bad config, a missing dependency.

    kq set image deploy/menu-api menu-api=kumawatsunil/quickbite-menu-api:1.2-broken
kq annotate deploy/menu-api kubernetes.io/change-cause="1.2: broken build" --overwrite
kq rollout status deploy/menu-api --timeout=60s
    Predict: STATUS and READY of the new pod? Does it get traffic? Does rollout status finish?
    menu-api-58b7d9c6f-aaaaa   1/1   Running   0   ← 1.1 ×3, untouched
menu-api-6c4f7b8d9-zzzzz   0/1   Running   0   ← 1.2: Running but NOT Ready

    Running 0/1, no restarts (liveness /health passes). It's not in the endpoints, so Terminal 3 shows only 1.1. rollout status times out: error: timed out waiting for the condition.

    kq get endpointslices -l kubernetes.io/service-name=menu-api   # 3 IPs only
kq describe pod -l pod-template-hash=<new-hash> | grep -A3 Readiness
# Warning  Unhealthy  Readiness probe failed: HTTP probe failed with statuscode: 503
kq logs -l pod-template-hash=<new-hash>
kq get deploy menu-api -o jsonpath='{.status.conditions[?(@.type=="Progressing")]}'; echo
    • After progressDeadlineSeconds (default 600 s) Progressing becomes False / ProgressDeadlineExceeded. Kubernetes still does not roll back.
    • Readiness + maxUnavailable: 0 = a broken release can't hurt users. Without a readiness probe, the 503 pod would be "Ready" and the rollout would replace all good pods.

    2.5 Roll back

    kq rollout history deploy/menu-api
kq rollout undo deploy/menu-api                     # to the previous revision (1.1)
kq rollout status deploy/menu-api
kq rollout history deploy/menu-api
    Predict: are new 1.1 pods created? What happens to the revision numbers?

    No new 1.1 pods: the three 1.1 pods never stopped. Undo sets the 1.1 RS back as current and scales the 1.2 RS to 0 (one pod deleted). The 1.1 revision is renumbered to the newest number; its old number disappears.

    The undo trap

    A second undo goes to the previous revision, which is now 1.2-broken. In an incident, read rollout history and use --to-revision=N.

    kq rollout history deploy/menu-api
kq rollout undo deploy/menu-api --to-revision=<the 1.0 revision>
kq rollout undo deploy/menu-api --to-revision=<the 1.1 revision>   # back to 1.1

    2.6 Pause and resume: batch several changes

    Each template change starts a rollout. To change image and resources as one release:

    kq rollout pause deploy/menu-api
kq set image deploy/menu-api menu-api=kumawatsunil/quickbite-menu-api:1.0
kq set resources deploy/menu-api -c menu-api --requests=cpu=60m,memory=64Mi
kq get rs -l app.kubernetes.io/name=menu-api        # nothing happened yet
kq rollout resume deploy/menu-api
kq rollout status deploy/menu-api
    Predict: how many new ReplicaSets after resume?

    One. Both changes land in a single template, one hash, one rollout, one revision. While paused, rollout undo is refused too.

    2.7 Recreate: see downtime

    kq patch deploy/menu-api -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'
kq set image deploy/menu-api menu-api=kumawatsunil/quickbite-menu-api:1.1
    Predict: what does Terminal 3 show?

    Several empty lines (failed requests): all 1.0 pods are terminated first, the Service has 0 endpoints until 1.1 pods are Ready. Use Recreate only when old and new must never run together.

    2.8 rollout restart

    Same image, fresh pods: after a ConfigMap/Secret change (env vars are read only at start), or to clear a stuck process.

    kq rollout restart deploy/menu-api
kq get deploy menu-api -o jsonpath='{.spec.template.metadata.annotations}'; echo
# {"kubectl.kubernetes.io/restartedAt":"2026-..."}  ← template changed → new RS → rolling

    2.9 Imperative vs declarative: back to the files

    set image, patch, scale change the live cluster only. The YAML in git still says 1.0, RollingUpdate, no minReadySeconds.

    kubectl diff -f k8s/base/30-menu-api.yaml        # what apply would change
kubectl apply -f k8s/base/30-menu-api.yaml
kq patch deploy/menu-api -p '{"spec":{"minReadySeconds":0}}'
    Predict: what does the apply do?

    It brings back the file's state: image 1.0, RollingUpdate 1/0, resources from the file. That's a template change → a rollout back to 1.0. minReadySeconds isn't in the file, and apply only manages fields it wrote before, so we reset it by hand.

    Real teams change the YAML in git and apply it (or let Argo CD do it). Live edits are for experiments and emergencies, and are overwritten by the next apply ("drift").

    2.11 Review questions

    1. You changed only replicas from 3 to 5. How many ReplicaSets now?

    The same number. Replicas is outside the template; the current RS just scales to 5.

    2. A new release crashes on start (CrashLoopBackOff). With maxSurge 1 / maxUnavailable 0, how many users are affected?

    None. Only one surge pod is created, it never becomes Ready, no old pod is removed.

    3. Why might two rollout undo commands in a row be dangerous?

    The second undo goes back to the revision you just escaped from (e.g. the broken one). Use --to-revision.

    4. You changed a ConfigMap value. Why didn't the pods pick it up, and what's the fix?

    Env vars are read once at container start, and a ConfigMap is outside the pod template, so no rollout happened. Run kubectl rollout restart.

    5. revisionHistoryLimit: 0. What breaks?

    Old ReplicaSets are deleted right away, so rollout undo has nothing to go back to.
