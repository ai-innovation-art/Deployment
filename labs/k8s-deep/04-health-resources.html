    What metrics-server is

    One pod (Deployment) in kube-system, not a node or cluster. It scrapes every kubelet every ~15 s, keeps the numbers in memory, and the APIService registers it with the API server as metrics.k8s.io. No APIService → "Metrics API not available". Run git pull in the Codespace first.

    kubectl get pods -n health -w
    Predict: compare kubectl top pods -n quickbite with the requests in the YAML. Are the requests close?

    menu-api requests 64Mi and uses ~40–50Mi; CPU usage is a few m against 50m requested. Requests should sit near typical usage: too high wastes nodes (scheduler counts them), too low overloads nodes.

    4.1 Startup probe: protect slow starters

    An app that needs 30 s to start, with a liveness probe that gives up after 15 s, is killed before it ever starts: a restart loop.

    apiVersion: v1
kind: Pod
metadata: { name: slow, namespace: health }
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "sleep 30; httpd -f -p 8080"]   # listens only after 30 s
      livenessProbe:
        tcpSocket: { port: 8080 }
        periodSeconds: 5
        failureThreshold: 3            # 3 × 5 s = killed after ~15 s
    kubectl apply -f slow.yaml
kubectl describe pod slow -n health | grep -A3 -E "Liveness|Last State" ; kubectl get events -n health --field-selector involvedObject.name=slow
    Predict: does the app ever start?

    Never. Liveness fails at ~15 s → container killed → restarted → same again → CrashLoopBackOff. Events: Liveness probe failed ... connection refused then Container app failed liveness probe, will be restarted.

    Seen

    Started → 15 s later Liveness probe failed: connection refused → Killing → restart ~20–30 s later: PID 1 is sh, which ignores SIGTERM, so the kubelet waits the grace period (30 s) then SIGKILLs.

    Fix: add a startup probe. Liveness and readiness don't run until it passes once.

          startupProbe:
        tcpSocket: { port: 8080 }
        periodSeconds: 5
        failureThreshold: 12           # up to 60 s to start
    kubectl delete pod slow -n health
kubectl apply -f slow.yaml
    Predict: RESTARTS and READY now?

    ~30 s at 0/1 Running with 0 restarts, then 1/1. After startup succeeds, liveness takes over with its fast settings. Better than a big initialDelaySeconds: fast detection after start, plenty of time during start.

    Seen

    A Pod's spec can't be changed in place (only image, tolerations additions, activeDeadlineSeconds): apply is Forbidden → delete and recreate. Deployments avoid this by making a new pod. With the startup probe: a few Startup probe failed warnings, no Killing, RESTARTS 0. Events of a deleted pod with the same name stay visible (~1 h).

    4.2 CPU limit: throttled, never killed

    apiVersion: v1
kind: Pod
metadata: { name: cpu-hog, namespace: health }
spec:
  containers:
    - name: app
      image: python:3.12-alpine
      command: ["python", "-c", "while True: pass"]       # wants 100% of a core
      resources:
        requests: { cpu: 100m, memory: 32Mi }
        limits:   { cpu: 200m, memory: 64Mi }
    kubectl apply -f cpu.yaml
sleep 60; kubectl top pod cpu-hog -n health
    Predict: CPU usage shown, and is the pod restarted?

    ~200m, never more, and RESTARTS 0. CPU is compressible: over the limit the kernel just pauses the process (CFS throttling). The app gets slower, nothing dies.

    Seen

    top: 200–201m, RESTARTS 0. Proof of throttling: kubectl exec cpu-hog -n health -- cat /sys/fs/cgroup/cpu.stat → nr_throttled keeps rising. First top right after create = NotFound (no scrape yet).

    4.3 Memory limit: OOMKilled

    apiVersion: v1
kind: Pod
metadata: { name: mem-hog, namespace: health }
spec:
  containers:
    - name: app
      image: python:3.12-alpine
      command: ["python", "-c", "import time; x = b'x' * (200*1024*1024); time.sleep(3600)"]
      resources:
        requests: { memory: 64Mi }
        limits:   { memory: 100Mi }     # wants 200Mi
    kubectl apply -f mem.yaml
kubectl get pod mem-hog -n health
kubectl describe pod mem-hog -n health | grep -A5 "Last State"
    Predict: STATUS, exit code, and what happens next?
    mem-hog   0/1   OOMKilled          1   ...
mem-hog   0/1   CrashLoopBackOff   2   ...
    Last State:  Terminated
      Reason:    OOMKilled
      Exit Code: 137          ← 128 + 9 (SIGKILL)

    Memory is incompressible: it can't be paused, so the kernel's OOM killer kills the process the moment it crosses the limit. Restarted, killed again → CrashLoopBackOff. Fix: raise the limit or fix the leak.

    Seen

    Started and Finished in the same second: killed instantly. Status alternates OOMKilled ⇄ CrashLoopBackOff while RESTARTS climbs. Exit code 137 = 128 + 9 (SIGKILL); 143 = 128 + 15 (SIGTERM, graceful).

    CPU over limitMemory over limit
    Resource typeCompressibleIncompressible
    ResultThrottled (slower)OOMKilled, exit 137
    RestartNoYes → CrashLoopBackOff

    4.4 QoS classes: who dies first

    ClassRuleKilled under node memory pressure
    GuaranteedEvery container: requests = limits, for CPU and memoryLast
    BurstableSome requests/limits set, not GuaranteedMiddle (by usage over request)
    BestEffortNo requests or limits at allFirst
     
    apiVersion: v1
kind: Pod
metadata: { name: qos-guaranteed, namespace: health }
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: { cpu: 50m, memory: 32Mi }
        limits:   { cpu: 50m, memory: 32Mi }
---
apiVersion: v1
kind: Pod
metadata: { name: qos-burstable, namespace: health }
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: { memory: 32Mi }
---
apiVersion: v1
kind: Pod
metadata: { name: qos-besteffort, namespace: health }
spec:
  containers:
    - { name: app, image: busybox:1.36, command: ["sleep", "3600"] }
    kubectl apply -f qos.yaml
kubectl get pods -n health -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
for p in qos-guaranteed qos-burstable qos-besteffort; do
  echo -n "$p: "; kubectl exec -n health $p -- cat /proc/1/oom_score_adj
done
    Predict: the oom_score_adj values?

    Guaranteed -997, BestEffort 1000, Burstable in between (based on its request vs node memory). The kernel kills the process with the highest score first. The kubelet sets these numbers from the QoS class: that's how "who dies first" is actually enforced.

    Seen

    -997 / 996 / 1000. Burstable = 1000 − 1000 × memory request / node memory (32Mi of ~7.9Gi → 996): a bigger memory request = safer. slow (probes only, no resources) = BestEffort.

    • Node-pressure eviction: when a node runs low (e.g. memory.available < 100Mi), the kubelet evicts pods (status Evicted), BestEffort first, then Burstable using the most over their request. Guaranteed last.
    • Critical apps (databases): Guaranteed. Most apps: Burstable with honest requests. BestEffort: only throwaway work.

    4.5 LimitRange: defaults and maximums per namespace

    apiVersion: v1
kind: LimitRange
metadata: { name: defaults, namespace: health }
spec:
  limits:
    - type: Container
      defaultRequest: { cpu: 50m, memory: 32Mi }   # added when a container sets no request
      default:        { cpu: 200m, memory: 128Mi } # added when it sets no limit
      max:            { cpu: 500m, memory: 256Mi } # reject anything bigger
    kubectl apply -f limits.yaml
kubectl run plain -n health --image=busybox:1.36 -- sleep 3600
kubectl get pod plain -n health -o jsonpath='{.spec.containers[0].resources}'; echo
kubectl run big -n health --image=busybox:1.36 --overrides='{"spec":{"containers":[{"name":"big","image":"busybox:1.36","command":["sleep","3600"],"resources":{"limits":{"memory":"1Gi"}}}]}}'
    Predict: what resources does plain get? Is big created?

    plain gets requests 50m/32Mi and limits 200m/128Mi, filled in by the LimitRange at creation (admission). big is rejected by the API server: maximum memory usage per Container is 256Mi, but limit is 1Gi. Existing pods are never changed.

    4.6 ResourceQuota: a budget for the whole namespace

    apiVersion: v1
kind: ResourceQuota
metadata: { name: budget, namespace: health }
spec:
  hard:
    pods: "8"
    requests.cpu: "400m"
    requests.memory: 512Mi
    limits.memory: 1Gi
    kubectl apply -f quota.yaml
kubectl describe quota budget -n health
kubectl create deployment many -n health --image=busybox:1.36 --replicas=10 -- sleep 3600
kubectl get deploy many -n health
kubectl describe rs -n health -l app=many | grep -A2 -i "forbidden\|exceeded" | head -6
    Predict: how many of the 10 pods are created, and where is the error shown?

    Only as many as the remaining budget allows (pods count or requests.cpu, whichever runs out first, counting the pods already there). The rest are never created, so there's no Pending pod to describe: the error is on the ReplicaSet: exceeded quota: budget, requested: requests.cpu=50m, used: ..., limited: 400m.

    When a quota covers requests/limits, every pod must set them, or it's rejected. The LimitRange defaults solve that.

    LimitRangeResourceQuota
    ScopeEach container / podWhole namespace total
    DoesDefaults + min/maxHard budget (cpu, memory, pod count, objects)
    ViolationPod rejected at createPod rejected; Deployment shows fewer ready

    4.9 Review questions

    1. Why not just use a large initialDelaySeconds instead of a startup probe?

    It delays failure detection forever after start too, and still breaks if startup ever takes longer. A startup probe allows a long start and fast liveness afterwards.

    2. A pod is slow but never restarts; another restarts with exit 137. Which limit is each hitting?

    Slow: CPU limit (throttling). Exit 137 + OOMKilled: memory limit.

    3. What makes a pod Guaranteed?

    Every container sets CPU and memory requests equal to limits.

    4. A Deployment shows 3/10 ready, no Pending pods. Where do you look?

    The ReplicaSet events: likely a ResourceQuota is exceeded, so pods were never created.

    5. LimitRange added today: do yesterday's pods get the defaults?

    No. LimitRange is applied only when a pod is created.
