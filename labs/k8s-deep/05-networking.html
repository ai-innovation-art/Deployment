    Chapter 05 · Networking: Services, DNS, Ingress

    Chapter 01 traced one click through iptables and DNS (request trace notes). This chapter adds what that trace didn't cover: calling across namespaces, Services that point outside the cluster, sticky sessions, and replacing NodePort with an Ingress that routes by path and host.

    Checkpoint at start: make resume Scratch namespace net ≈ 2 h

    5.0 Setup

    cd /workspaces/Deployment && git pull
cd labs/quickbite && kubectl get nodes          # not all Ready → make resume
kubectl create namespace net
kubectl run client -n net --image=curlimages/curl -- sleep infinity
kubectl wait -n net --for=condition=Ready pod/client

    The client pod is a long-lived shell inside the cluster, in a different namespace from QuickBite.

    5.1 Calling across namespaces

    kubectl exec -n net client -- curl -s -m 3 menu-api:8000/version; echo
kubectl exec -n net client -- curl -s -m 3 menu-api.quickbite:8000/version; echo
kubectl exec -n net client -- curl -s -m 3 menu-api.quickbite.svc.cluster.local:8000/version; echo
kubectl exec -n net client -- cat /etc/resolv.conf
    Predict: which of the three calls work?

    1st fails (Could not resolve host): the search list starts with net.svc.cluster.local, so menu-api becomes menu-api.net.svc..., which doesn't exist. 2nd and 3rd work. Rule: same namespace → name; other namespace → name.namespace.

    Namespaces separate names, not traffic: the call is allowed. Blocking it needs a NetworkPolicy (Chapter 09).

    Seen

    curl exit code 6 = couldn't resolve host. name.namespace works thanks to the 2nd search entry: menu-api.quickbite + .svc.cluster.local. "Unknown stream id" = harmless kubectl exec warning.

    5.2 ExternalName: a DNS alias

    A Service with no pods that just answers "this name = that other name". Used to give an outside dependency (managed DB, SaaS API) a stable in-cluster name, or to alias across namespaces.

    kubectl create service externalname menu -n net --external-name menu-api.quickbite.svc.cluster.local
kubectl get svc menu -n net
kubectl exec -n net client -- curl -s -m 3 menu:8000/version; echo
kubectl exec -n net client -- nslookup menu.net.svc.cluster.local
    Predict: does menu:8000 work from the net namespace? What does nslookup return?

    Yes. CoreDNS answers with a CNAME to menu-api.quickbite.svc.cluster.local, then that name's ClusterIP. No ClusterIP of its own, no iptables rules, no port mapping: only DNS.

    5.3 A Service without a selector

    A normal Service fills its EndpointSlice from the selector. Leave the selector out and you write the endpoints: useful for pointing a stable name at a fixed IP outside the cluster.

    apiVersion: v1
kind: Service
metadata: { name: legacy-db, namespace: net }
spec:
  ports: [{ port: 5432 }]                 # no selector
---
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: legacy-db-1
  namespace: net
  labels: { kubernetes.io/service-name: legacy-db }   # links it to the Service
addressType: IPv4
ports: [{ port: 5432 }]
endpoints:
  - addresses: ["10.244.1.21"]             # put the postgres-0 pod IP here
    kubectl get pod postgres-0 -n quickbite -o jsonpath='{.status.podIP}'; echo
# edit the IP in external.yaml, then:
kubectl apply -f external.yaml
kubectl get svc,endpointslices -n net
kubectl exec -n net client -- sh -c 'nc -zv -w 2 legacy-db 5432'
    Predict: does it connect? What happens when postgres-0 restarts with a new IP?

    It connects (open). After a restart it breaks: nobody updates a hand-written EndpointSlice. That's fine for an outside server with a fixed IP, never for pods.

    5.4 Session affinity: sticky clients

    loop='for i in 1 2 3 4 5 6; do curl -s menu-api.quickbite:8000/version | cut -c1-60; echo; done'
kubectl exec -n net client -- sh -c "$loop"
kubectl patch svc menu-api -n quickbite -p '{"spec":{"sessionAffinity":"ClientIP"}}'
kubectl exec -n net client -- sh -c "$loop"
kubectl patch svc menu-api -n quickbite -p '{"spec":{"sessionAffinity":"None"}}'
    Predict: the pod names before and after the patch?

    Before: mixed pods. After: the same pod every time. kube-proxy adds an iptables recent rule that remembers each client IP for 3 hours (timeoutSeconds: 10800). Use only when an app keeps per-user state in memory; better apps keep state in Redis/DB.

    5.5 Ingress: one entry point for HTTP

    NodePort:  one port per Service (30000–32767), no hostnames, no paths, no TLS
Ingress:   one entry → routes by host and path → many Services, TLS in one place
           Ingress (rules, a YAML object)  +  Ingress controller (a pod that applies them: nginx)

    An Ingress object does nothing alone: a controller must be installed. We use ingress-nginx and give it NodePort 30080, the only port kind maps to your Codespace (8080). web becomes a plain ClusterIP.

    kubectl label node quickbite-control-plane ingress-ready=true
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.2/deploy/static/provider/kind/deploy.yaml
kubectl -n ingress-nginx rollout status deploy/ingress-nginx-controller --timeout=180s
kubectl get pods,svc -n ingress-nginx -o wide
    kubectl patch svc web -n quickbite --type=json \
  -p '[{"op":"replace","path":"/spec/type","value":"ClusterIP"},{"op":"remove","path":"/spec/ports/0/nodePort"}]'
kubectl patch svc ingress-nginx-controller -n ingress-nginx --type=json \
  -p '[{"op":"replace","path":"/spec/ports/0/nodePort","value":30080}]'
kubectl get svc web -n quickbite ; kubectl get svc ingress-nginx-controller -n ingress-nginx
    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: quickbite, namespace: quickbite }
spec:
  ingressClassName: nginx                   # which controller handles it
  rules:
    - http:                                 # any host
        paths:
          - { path: /version, pathType: Prefix, backend: { service: { name: menu-api, port: { number: 8000 } } } }
          - { path: /,        pathType: Prefix, backend: { service: { name: web,      port: { number: 80 } } } }
    - host: menu.localhost                  # only this Host header
      http:
        paths:
          - { path: /, pathType: Prefix, backend: { service: { name: menu-api, port: { number: 8000 } } } }
    kubectl apply -f ingress.yaml
kubectl get ingress -n quickbite
curl -s localhost:8080/ | head -5                   # web
curl -s localhost:8080/version; echo                # menu-api directly
curl -s -H 'Host: menu.localhost' localhost:8080/menu | cut -c1-80; echo
    Predict: which Service answers each curl? Does the browser UI still work?

    / → web. /version → menu-api (longest matching prefix wins). Host menu.localhost → menu-api for every path. The UI still works: web serves the page and proxies /api/* itself.

    FieldMeaning
    ingressClassNameWhich controller (nginx, traefik, cloud LB…)
    hostMatch the HTTP Host header; omitted = any
    pathTypePrefix (path and below) · Exact · ImplementationSpecific
    backend.serviceService name + port (ClusterIP is enough)
    tlsHosts + a kubernetes.io/tls Secret: HTTPS ends at the controller
     
    kubectl -n ingress-nginx exec deploy/ingress-nginx-controller -- cat /etc/nginx/nginx.conf | grep -A3 "location /version"
kubectl -n ingress-nginx logs deploy/ingress-nginx-controller --tail=5
    • The controller watches Ingress objects and rewrites its nginx config; traffic goes controller → pod IPs directly (it reads EndpointSlices).
    • In the cloud the controller's Service is LoadBalancer: one public IP for every app. The newer Gateway API is Ingress's successor, with the same idea.

    5.6 Clean up and restore NodePort

    We changed web live (drift). make resume re-applies k8s/base, which wants NodePort 30080 back, so remove the controller first.

    kubectl delete namespace net
kubectl delete -f ingress.yaml
kubectl delete -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.2/deploy/static/provider/kind/deploy.yaml
kubectl label node quickbite-control-plane ingress-ready-
kubectl apply -f /workspaces/Deployment/labs/quickbite/k8s/base/60-web.yaml
kubectl get svc web -n quickbite                 # NodePort 80:30080 again

    5.7 Review questions

    1. A pod in namespace shop calls redis:6379 but Redis is in cache. Fix?

    Call redis.cache:6379 (or the full redis.cache.svc.cluster.local).

    2. ExternalName vs a Service without a selector?

    ExternalName: DNS alias to a hostname, no IP, no ports. No-selector Service: a real ClusterIP and iptables rules, endpoints you maintain by hand (fixed IPs).

    3. Why is an Ingress object alone not enough?

    It's only rules. An Ingress controller (a pod) must read them and route traffic.

    4. Paths / and /version both match /version/x. Which wins?

    The longest matching prefix: /version.

    5. When is sessionAffinity: ClientIP appropriate?

    When an app keeps per-user state in its own memory. Better design: keep state in a shared store so any pod can serve any user.
