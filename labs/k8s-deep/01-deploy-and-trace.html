    Chapter 01 · Deploy QuickBite and trace everything

    You'll deploy QuickBite by hand, one service at a time in the order a real team would. After each step you'll stop and prove what happened inside the cluster. Then you'll follow one click in the browser across nodes, iptables, DNS and three services. This is the chapter where the dots connect.

    1.2 The deploy order, and why it's this order

    Dependencies flow downwards: config first, then data stores, then the services that use them, then the edge.

      00 namespace + config + secret      # everything else references these
  10 postgres   20 redis              # data stores, no dependencies
  30 menu-api   40 orders-api         # need redis / postgres
  50 notifier                         # needs redis
  60 web                              # needs the APIs' Services to exist (nginx resolves them at start)
  70 daily-report (CronJob)           # needs postgres with data
    Kubernetes doesn't really need the order

    If you apply everything at once (kubectl apply -k k8s/base, which is what make resume does), it still works. Pods that start too early fail or wait, and controllers keep retrying until everything converges. That is reconciliation. We go in order today only so you can watch each piece.

    kubectl get pods -n quickbite -o wide -w

    The one-sentence model of Kubernetes

    etcd holds what you want. Controllers keep changing the world until it matches. Everything else is detail. Only the API server reads and writes etcd; every other component talks to the API server.

    1.5 Step 3: Redis and menu-api: Deployment → ReplicaSet → Pods

    k apply -f k8s/base/20-redis.yaml -f k8s/base/30-menu-api.yaml
k -n quickbite rollout status deploy/menu-api
    Predict: menu-api has replicas: 3 and 2 workers. How will the 3 pods be placed?

    Almost always 2 on one worker and 1 on the other, and 0 on the control plane. Why:

    • The control plane carries the taint node-role.kubernetes.io/control-plane:NoSchedule, and our pods have no toleration, so it's filtered out.
    • The scheduler's default scoring includes a soft spreading rule (pods of the same workload on different nodes score higher), so it avoids putting all 3 on one worker.

    "Almost always", because spreading is a preference, not a rule. Chapter 3 turns it into a hard rule, and you'll predict cases where pods stay Pending.

    k -n quickbite get pods -l app.kubernetes.io/name=menu-api -o wide
k describe node quickbite-control-plane | grep -A1 Taints

    1.6 Step 4: orders-api and its init container

    k apply -f k8s/base/40-orders-api.yaml
    Predict: which STATUS values will you see in Terminal 2, in order?
    orders-api-5d8c...-abcde   0/1   Pending           0   0s
orders-api-5d8c...-abcde   0/1   Init:0/1          0   1s    ← db-migrate running
orders-api-5d8c...-abcde   0/1   PodInitializing   0   4s    ← db-migrate exited 0
orders-api-5d8c...-abcde   0/1   Running           0   5s    ← API started, readiness not yet passed
orders-api-5d8c...-abcde   1/1   Running           0   10s   ← /ready returned 200 (DB reachable)

    Init:0/1 means "0 of 1 init containers finished". The API container doesn't start at all until every init container exits with 0. Same as service_completed_successfully in Compose, but per pod, on every restart, on every node.

    k -n quickbite logs deploy/orders-api -c db-migrate
    [db-migrate] schema ready (attempt 1)

    Break it on purpose: init container can't reach the database

    k -n quickbite scale statefulset postgres --replicas=0
k -n quickbite rollout restart deploy/orders-api
sleep 20; k -n quickbite get pods -l app.kubernetes.io/name=orders-api
    Predict: what happens to the OLD orders-api pods, and to the new ones?

    New pods sit in Init:0/1. db-migrate prints postgres not ready (n/30) and retries. Meanwhile the old pods keep running: the rolling update doesn't remove an old pod until a new one is Ready. They now fail readiness (no DB), so they show 0/1 and are removed from the Service. Orders fail, but nothing crashes or restarts in a loop.

    k -n quickbite logs -l app.kubernetes.io/name=orders-api -c db-migrate --tail=2 --prefix
    k -n quickbite scale statefulset postgres --replicas=1
k -n quickbite rollout status deploy/orders-api

    No action needed on orders-api: the init container was still retrying, saw the DB come back, and the pods continued on their own. That is reconciliation. Note too that postgres came back with the same PVC, so the table still exists.

    You clicked "Reload". Here's every hop that request took. Step through it, then prove each hop with the commands below.

    Prove every hop

    docker port quickbite-control-plane
    docker exec quickbite-control-plane iptables-save -t nat | grep -E 'quickbite/(web|menu-api)' | head -20
    -A KUBE-NODEPORTS -p tcp -m comment --comment "quickbite/web:http" -m tcp --dport 30080 -j KUBE-EXT-...
-A KUBE-SERVICES -d 10.96.142.17/32 -p tcp -m comment --comment "quickbite/menu-api:http cluster IP" --dport 8000 -j KUBE-SVC-...
-A KUBE-SVC-... -m comment --comment "quickbite/menu-api:http -> 10.244.1.4:8000" -m statistic --mode random --probability 0.33333 -j KUBE-SEP-...
-A KUBE-SVC-... -m comment --comment "quickbite/menu-api:http -> 10.244.1.5:8000" -m statistic --mode random --probability 0.50000 -j KUBE-SEP-...
-A KUBE-SVC-... -m comment --comment "quickbite/menu-api:http -> 10.244.2.3:8000" -j KUBE-SEP-...
-A KUBE-SEP-... -p tcp -j DNAT --to-destination 10.244.1.4:8000
    Why 0.333, then 0.5, then nothing? Is that fair?

    Rules are checked top to bottom. Rule 1 matches 1/3 of packets. Of the remaining 2/3, rule 2 takes half, which is another 1/3. The last rule takes everything left, the final 1/3. So it's equal 1/3 each. This is the "load balancer" behind a ClusterIP: random, per connection, in the kernel.

    k -n quickbite get endpointslices -l kubernetes.io/service-name=menu-api
k -n quickbite get pods -l app.kubernetes.io/name=menu-api -o wide

    The IPs in the EndpointSlice = the IPs of the Ready menu-api pods = the IPs in the iptables rules. Three views of the same fact.

    1.10 Self-healing: three kinds of failure, three different reactions

    "Kubernetes heals itself" is too vague to be useful. Who heals, and how? Predict each case before running it.

    A. A pod is deleted

    POD=$(k -n quickbite get pod -l app.kubernetes.io/name=menu-api -o jsonpath='{.items[0].metadata.name}')
k -n quickbite delete pod $POD
k -n quickbite get pods -l app.kubernetes.io/name=menu-api -o wide
    Predict: same name back? Same node? Who did it?

    A new pod with a new random suffix, possibly on a different node. The ReplicaSet controller saw 2 < 3 and created a new Pod object; the scheduler placed it fresh. The deleted pod is gone forever; pods are never "moved". The other two pods kept serving, so the menu never went down.

    B. The process inside a container crashes

    POD=$(k -n quickbite get pod -l app.kubernetes.io/name=menu-api -o jsonpath='{.items[0].metadata.name}')
k -n quickbite exec $POD -- python -c "import os,signal; os.kill(1, signal.SIGTERM)"
k -n quickbite get pod $POD
    Predict: new pod or same pod? What column changes?

    Same pod name, same node, same IP, and RESTARTS goes from 0 to 1. The kubelet on that node restarted the container (pod restartPolicy: Always). No controller, no scheduler involved. k -n quickbite logs $POD --previous shows the logs of the dead container.

    Pod restart (kubelet, same pod) vs pod replacement (controller, new pod) is one of the most important distinctions in Kubernetes troubleshooting.

    C. A bad image is released

    k -n quickbite set image deploy/notifier notifier=kumawatsunil/quickbite-notifier:9.9
k -n quickbite get pods -l app.kubernetes.io/name=notifier
    Predict: is notifier down now?

    No. You'll see the old pod still Running and a new pod in ErrImagePull → ImagePullBackOff. The Deployment won't kill the old pod until the new one is Ready, so a broken release doesn't take the service down. Diagnose with:

    k -n quickbite describe pod -l app.kubernetes.io/name=notifier | grep -A3 -E 'Failed|Back-off'
Warning  Failed   ...  Failed to pull image "kumawatsunil/quickbite-notifier:9.9": ... not found
Warning  Failed   ...  Error: ErrImagePull
Normal   BackOff  ...  Back-off pulling image "kumawatsunil/quickbite-notifier:9.9"
    k -n quickbite rollout undo deploy/notifier
k -n quickbite rollout status deploy/notifier

    1.12 Check yourself

    1. You run kubectl apply and get "created", but no pod appears. Name three components that could be the reason, and the command that shows which one.

    Controller-manager (didn't create the pod: check k get rs and k describe deploy), scheduler (pod Pending: k describe pod → "FailedScheduling"), kubelet/runtime (pod scheduled but stuck in ContainerCreating / ImagePullBackOff: k describe pod events). k get events --sort-by=.lastTimestamp shows all three.

    2. Does traffic from the browser go through the control-plane node? Is that a problem in production?

    Here yes, because only the control-plane container has the port mapping. NodePort works on any node, so in production a cloud load balancer spreads traffic across all worker nodes (Service type LoadBalancer or Ingress, Ch 5), and the control plane is not in the data path.

    3. A menu-api pod fails its readiness probe. Does it restart? Does it receive traffic?

    It does not restart (that's liveness). It's removed from the EndpointSlice, so iptables rules stop sending it traffic. When readiness passes again, it's added back. Chapter 2 uses exactly this with 1.2-broken.

    4. What survived when you scaled postgres to 0 and back? Why?

    The data. The PVC data-postgres-0 isn't deleted when a StatefulSet scales down, and the new postgres-0 re-attaches the same claim by name.

    5. Pod restart vs pod replacement: who does each, and what changes?

    Restart: the kubelet, same pod and IP, RESTARTS+1. Replacement: the ReplicaSet controller + scheduler, new name, new IP, maybe a new node.
