    Kubernetes Deep Dive: building QuickBite

    One real product, built up chapter by chapter. Every Kubernetes object appears only when QuickBite runs into a problem that needs it. You don't learn "here is a Secret"; you learn "our database password is sitting in plain text in a Deployment, so how do we fix that?"

    Prereq: Docker (Lab 02) Cluster: kind, 3 nodes, in a GitHub Codespace Images: hub.docker.com/u/kumawatsunil

    The checkpoint system

    Codespaces stop after 30 minutes idle, and free hours run out, so you will often start in a "cold" machine. You never repeat earlier chapters by hand. Each chapter starts by naming a checkpoint, and one command restores it.

    Your situationRun (inside labs/quickbite)What it does
    Brand-new Codespace (or new GitHub account)make resumeInstalls kind/kubectl/helm, creates the 3-node cluster, pulls images from Docker Hub, deploys QuickBite
    Codespace was stopped and restartedmake resumeRestarts the stopped node containers, re-applies manifests, waits until everything is Ready

    Images are built once

    Chapter 0 builds and pushes the images to Docker Hub one time. After that, no session ever rebuilds them; the cluster pulls kumawatsunil/quickbite-* directly.

    Deploy QuickBite and trace everything

    Deploy service by service in dependency order. Follow kubectl apply through the API server, etcd, controllers, scheduler and kubelet, then follow one browser click through NodePort, kube-proxy, DNS and three services.

    02

    Workloads and releases: ship 1.1, ship a broken 1.2, roll back

    Pod → ReplicaSet → Deployment from the inside. Rolling update maths (maxSurge / maxUnavailable), watching two ReplicaSets trade pods, a rollout that never finishes, rollout history / undo / pause / resume, and change-cause.

    readyrolloutrollback
    03

    Scheduling: predict where every pod lands

    Filter → score, requests vs capacity, nodeSelector, node affinity (required / preferred), pod affinity and anti-affinity, taints and tolerations (NoSchedule / NoExecute), topology spread, cordon / drain / uncordon, Pending pods and how to read why.

    04

    Health and resources: probes, QoS, OOMKill, eviction

    Liveness vs readiness vs startup on QuickBite services, what happens when Postgres dies, CPU throttling vs memory kill, Guaranteed / Burstable / BestEffort, LimitRange and ResourceQuota.

    05

    Networking: Services, DNS, kube-proxy, Ingress

    ClusterIP, NodePort, headless, EndpointSlices, CoreDNS search domains, iptables rules on the node, cross-namespace calls, Ingress with path routing replacing NodePort.

    06

    Config and secrets

    ConfigMap as env vs mounted file, why changing a ConfigMap does not restart pods, Secrets and base64, immutable config, rolling restarts.

    07

    State: Postgres, volumes and StatefulSets

    PV, PVC, StorageClass, reclaim policy, why a database is not a Deployment, stable names and DNS, data surviving pod deletion and rescheduling.

    08

    Other workload types

    Job and CronJob (the daily report), init containers, sidecars, DaemonSet (a node agent on every node), PodDisruptionBudget.

    09

    Security: ServiceAccounts, RBAC, NetworkPolicy

    Who can do what (a read-only "support engineer" user), and which pod may talk to which (only orders-api may reach Postgres), plus pod securityContext.

    10

    Helm: package all of QuickBite as one chart

    Turn k8s/base into a chart, values per environment (dev / prod), install, upgrade, rollback, and how Helm releases relate to Deployment revisions.

    Pending: do later, on real machines

    kind runs a real kubelet, containerd, kube-proxy, CNI, etcd, API server and scheduler, so everything above behaves as it does in production. These topics are the exceptions: kind hides them or can't show them. We do them after Chapter 10, on separate VMs (Multipass, Killercoda or cloud VMs).

    TopicWhy kind can't show it properly
    P1 kubeadm init / kubeadm join, bootstrap tokens, certificateskind runs kubeadm for you, behind the scenes
    P2 kubelet as a systemd service (systemctl, journalctl -u kubelet)kind nodes are containers
    P3 Installing a CNI yourself (Calico or Cilium) and seeing nodes stay NotReady until you dokind installs kindnet automatically
    P4 Pod traffic across a real network, firewalls, ports 6443 / 10250 / 2379All kind nodes share one Docker bridge
    P5 A machine really dying: power off, NotReady after ~40 s, pod eviction after ~5 minCan be imitated with docker stop, but timings and side effects differ
    P6 etcd backup and restore, kubeadm upgrade of a live clusterDay-2 operations on real infrastructure
    P7 Managed clusters (GKE / EKS) compared with self-built onesCloud load balancers, cloud disks and node pools
