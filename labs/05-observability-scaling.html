    1. Deploy Metrics-Server & Validate `kubectl top`

    The standard Kubernetes metrics-server collects resource metrics (CPU and memory usage) from Kubelets on each worker node. In a local kind cluster, Kubelet uses self-signed TLS certificates, which standard metrics-server rejects by default. We patch it with --kubelet-insecure-tls.

    # Apply the patched metrics-server manifest
kubectl apply -f labs/k8s-observability/01-metrics-server.yaml

# Wait for metrics-server pod to become Ready
kubectl rollout status deployment/metrics-server -n kube-system

# Wait ~30 seconds for the first metrics collection cycle, then test:
kubectl top nodes
kubectl top pods
    Understanding `kubectl top` Output

    CPU is reported in millicores (m), where 1000m = 1 vCPU core. Memory is reported in Mebibytes (Mi). If kubectl top returns "error: Metrics API not available", metrics-server needs another 15–30 seconds to scrape its first sample.

    3. PromQL Queries: The RED Method

    Prometheus Query Language (PromQL) allows you to aggregate time-series data. The RED Method focuses on three core microservice signals:

    RED SignalWhat it measuresPromQL Example
    RateRequests per secondrate(http_requests_total[1m])
    ErrorsFailed requests per secondrate(http_requests_total{status=~"5.."}[1m])
    DurationLatency histogram distributionhistogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

kubectl port-forward svc/prometheus 9090:9090

sum(rate(http_requests_total[1m]))

    5. The Horizontal Pod Autoscaler (HPA) Formula

    The Kubernetes HPA controller evaluates metrics every 15 seconds (configurable via --horizontal-pod-autoscaler-sync-period). It calculates the desired replica count using this exact mathematical formula:

    $$\text{desiredReplicas} = \left\lceil \text{currentReplicas} \times \left( \frac{\text{currentMetricValue}}{\text{desiredMetricValue}} \right) \right\rceil$$

    Example: If 2 replicas are running at an average of 100m CPU, and your target is 50m CPU:

    $$\text{desiredReplicas} = \lceil 2 \times (100 / 50) \rceil = \lceil 2 \times 2 \rceil = 4 \text{ pods}$$

    # Apply the HPA manifest targeting reliability-api
kubectl apply -f labs/k8s-observability/02-hpa.yaml

# Inspect active HPA status
kubectl get hpa
kubectl describe hpa reliability-api-hpa

    6. Load Generation: Simulating Traffic Surges

    To watch HPA trigger scale-out, we deploy a load-generator pod that repeatedly invokes /work?ms=40. Each request forces the CPU to calculate cryptographic hashes, generating real, measurable CPU utilization.

    # Start the load generator
kubectl apply -f labs/k8s-observability/03-load-generator.yaml

# Watch HPA metrics update in real-time
kubectl get hpa reliability-api-hpa -w

    7. Observing HPA Scale-Out Live ($2 \to 8$ Pods)

    As the CPU load crosses the 50% target threshold, watch the ReplicaSet spawn new pods automatically:

    # Watch deployment replicas expand
kubectl get deployment reliability-api -w

# View CPU consumption per pod
kubectl top pods -l app.kubernetes.io/name=reliability-api

    8. Anti-Flapping: Stabilization Windows & Scale-Down

    The Flapping Problem: If traffic drops for 3 seconds, scaling down immediately would cause replicas to thrash (scaling up and down rapidly). Kubernetes solves this using a Stabilization Window (default 300s, configured to 60s in our manifest).

    # Delete load generator
kubectl delete -f labs/k8s-observability/03-load-generator.yaml

# Watch HPA: Notice CPU drops to 0%, but replicas stay at 8 for 60 seconds
kubectl get hpa reliability-api-hpa -w

# After 60 seconds of calm traffic, HPA smoothly scales back down to 2!

    9. Chaos Engineering & Failure Injection

    Testing resilience requires breaking things under load:

    1. Run load generator.
    2. While under heavy traffic, manually kill 2 pods simultaneously: kubectl delete pod -l app.kubernetes.io/name=reliability-api --now.
    3. Observe: The ReplicaSet spawns replacements instantly, and the Service maintains zero-downtime routing through remaining healthy endpoints!

    10. Quick Reference Cheat Sheet: The Verb x Resource Matrix

    Kubernetes CLI follows a universal grammar: kubectl <VERB> <RESOURCE> <NAME> [FLAGS]. Use this matrix for all monitoring and autoscaling operations.

    ## 1. METRICS & RESOURCE MONITORING
kubectl top nodes                                   # [TOP] View real-time CPU (m) & RAM (Mi) usage across all nodes
kubectl top pods                                    # [TOP] View CPU and memory usage of all pods in current namespace
kubectl top pods -A --sort-by=cpu                   # [TOP] Find highest CPU-consuming pods cluster-wide
kubectl top pods -A --sort-by=memory                # [TOP] Find highest memory-consuming pods cluster-wide

## 2. HORIZONTAL POD AUTOSCALER (hpa)
kubectl apply -f 02-hpa.yaml                        # [APPLY] Create or update HPA definition
kubectl get hpa                                     # [GET] View current targets, MIN/MAX replicas, and current replicas
kubectl get hpa -w                                  # [GET -W] Stream HPA metric changes and scale events in real-time
kubectl describe hpa <hpa-name>                     # [DESCRIBE] View scaling event history and stabilization conditions
kubectl autoscale deployment <name> --min=2 --max=10 --cpu-percent=70 # [AUTOSCALE] Imperatively create HPA
kubectl delete hpa <hpa-name>                       # [DELETE] Remove autoscaler (deployment remains at current replica count)

## 3. PROMETHEUS & METRICS SCRAPING
kubectl port-forward svc/prometheus 9090:9090       # [PORT-FORWARD] Tunnel Prometheus Web UI to localhost:9090
curl -s http://localhost:8000/metrics               # [CURL] Inspect raw application Prometheus metrics
curl -s http://localhost:9090/api/v1/targets        # [CURL] Check active Prometheus scrape targets and health status

## 4. CHAOS & RESILIENCE TESTING
kubectl scale deployment <name> --replicas=0        # [SCALE] Drain all pods to simulate complete service outage
kubectl delete pod -l app=<name> --now              # [DELETE] Force-kill pods under load to test resurrection speed
