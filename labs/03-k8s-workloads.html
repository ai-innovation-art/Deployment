    0. Prerequisites & Local Cluster Setup

    All Kubernetes labs run on a kind (Kubernetes IN Docker) cluster. kind creates real Kubernetes nodes as Docker containers on your machine — no cloud account required. You need Docker running and two CLI tools: kind and kubectl.

    Why kind?

    kind uses the same real kubelet, kube-apiserver, CoreDNS and kube-proxy as production clusters. Your YAML, probes and Services behave identically. A cluster takes ~60 seconds to create and costs nothing. You can afford to break it — and that's the point.

chmod +x kind && sudo mv kind /usr/local/bin/kind

# Windows — via Winget or Chocolatey

# Verify both tools are installed

    imagePullPolicy trap

    kind nodes have their own separate container image store (containerd inside each node container). docker build places the image in the Docker daemon — not inside kind. You must explicitly load the image, then use imagePullPolicy: IfNotPresent so the kubelet uses the loaded image instead of trying to pull from Docker Hub.

    1. Control Plane Architecture

    A Kubernetes cluster is divided into two tiers: the control plane (the brain) and the worker nodes (the muscle). Every action you take with kubectl goes to the control plane, which then figures out what to tell the nodes.

    ComponentRuns onResponsibilityWhat breaks when it's down
    kube-apiserverControl planeThe single front door for all operations. All reads and writes go through it (kubectl, controllers, kubelet). Validates and persists objects to etcd.Nothing can be created, deleted or updated. Running pods continue running.
    etcdControl planeDistributed key-value store — the only persistent store for cluster state. Every object (Pod, Deployment, ConfigMap…) lives here.Total cluster amnesia. If you lose etcd without a backup, you lose the cluster.
    kube-schedulerControl planeWatches for newly-created Pods with no node assigned. Picks a node (filter → score) and writes the decision to the Pod's spec.nodeName via the API server.New pods get stuck in Pending forever. Running pods are unaffected.
    kube-controller-managerControl planeRuns all the built-in controllers (ReplicaSet, Deployment, Node, Endpoints…). Each controller watches desired state vs actual state and reconciles.Self-healing stops. Deleted pods are not replaced. ReplicaSets drift from desired count.
    kubeletEvery nodeThe node agent. Watches for Pods assigned to its node. Starts and stops containers via the CRI (containerd). Runs health probes. Reports status back to API server.Pods on that node stop being managed. New pods can't start on it.
    kube-proxyEvery nodeMaintains iptables/IPVS rules on each node so Service virtual IPs are reachable and traffic is load-balanced to ready pods.Service routing breaks on that node. ClusterIP services become unreachable.
    CoreDNSControl plane (pod)Cluster DNS server. Resolves service.namespace.svc.cluster.local names to ClusterIP addresses.DNS-based service discovery fails. Pod-to-pod IP still works.

    The reconciliation loop

    Every controller in Kubernetes runs the same fundamental loop: observe → diff → act. The ReplicaSet controller, for example, reads the desired replica count from the spec, counts how many pods matching its selector currently exist, and creates or deletes pods until the counts match. This loop runs continuously — so even if you make a change by hand, the controller will revert it.

    2. First Pod

    A Pod is the smallest deployable unit in Kubernetes. It wraps one or more containers that share a network namespace (same IP address, same localhost) and optionally share volumes. Kubernetes schedules, starts, and monitors Pods — but a bare Pod has no self-healing; if it dies, it stays dead.

    apiVersion: v1
kind: Pod
metadata:
  name: reliability-api-pod
  namespace: default
  labels:
    app.kubernetes.io/name: reliability-api
    env: lab
spec:
  containers:
    - name: reliability-api
      image: kumawatsunil/reliability-api:0.1.0
      imagePullPolicy: IfNotPresent  # use the image we loaded into kind
      ports:
        - containerPort: 8000
      env:
        - name: LOG_LEVEL
          value: "info"
        - name: READY_DELAY_SECONDS
          value: "5"
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          memory: "256Mi"
    # Apply the pod manifest
kubectl apply -f labs/k8s-reliability/01-pod.yaml

# Watch the pod until it's Running
kubectl get pods -w

NAME                  READY   STATUS    RESTARTS   AGE
reliability-api-pod   0/1     Pending   0          2s
reliability-api-pod   0/1     ContainerCreating   0   4s
reliability-api-pod   1/1     Running   0          12s

# Describe — most useful debugging command you will ever use
kubectl describe pod reliability-api-pod

# Read the application logs
kubectl logs reliability-api-pod
kubectl logs reliability-api-pod -f   # follow

# Execute a shell command inside the running container
kubectl exec -it reliability-api-pod -- sh

# Inside the container — hit the health and ready endpoints
# wget is available; curl is usually not in minimal images
wget -qO- http://localhost:8000/health

# Port-forward to access the pod from your laptop

    3. Why Raw Pods Are Dangerous

    A bare Pod has no owner. When it dies — whether because the process crashed, the node rebooted, or you deleted it by accident — Kubernetes does nothing. There is no controller watching it. This section proves it, then shows how a ReplicaSet fixes it.

    Never run bare Pods in production

    Bare Pods are fine for one-off debugging. For anything that needs to stay running, use a Deployment (which manages a ReplicaSet, which manages Pods). The ownership chain is Deployment → ReplicaSet → Pod.

    # Delete the pod manually — simulates a crash
kubectl delete pod reliability-api-pod

# Check — the pod is gone and NOT replaced
kubectl get pods
No resources found in default namespace.

# There is no ReplicaSet watching it — nothing to bring it back
kubectl get replicasets
No resources found in default namespace.
    # Create a standalone ReplicaSet (for understanding only — normally Deployments manage these)
kubectl create deployment rs-demo --image=kumawatsunil/reliability-api:0.1.0 --replicas=2 --dry-run=client -o yaml \
  | sed 's/kind: Deployment/kind: ReplicaSet/' \
  | kubectl apply -f -

# Or just apply the full deployment — it creates a ReplicaSet automatically
kubectl apply -f labs/k8s-reliability/02-deployment.yaml

# Watch the pods appear
kubectl get pods -w

# Find the ReplicaSet the Deployment created
kubectl get replicasets
NAME                        DESIRED   CURRENT   READY   AGE
reliability-api-7d4b95cbc   3         3         3       45s

# Delete one pod — watch the ReplicaSet immediately create a replacement
POD=$(kubectl get pods -l app.kubernetes.io/name=reliability-api -o name | head -1)
kubectl delete $POD
kubectl get pods -w   # A new pod appears within seconds

    4. Deployments

    A Deployment adds a versioning layer on top of a ReplicaSet. When you update the pod template (e.g., new image version), the Deployment creates a new ReplicaSet and gradually shifts traffic to it while scaling down the old one. It also remembers the history, so you can roll back to any previous revision.

    # Apply the deployment (if not already applied)
kubectl apply -f labs/k8s-reliability/02-deployment.yaml

# List deployments — shows READY count vs desired
kubectl get deployments
NAME              READY   UP-TO-DATE   AVAILABLE   AGE
reliability-api   3/3     3            3           2m

# Get the full status with rollout history
kubectl rollout status deployment/reliability-api
deployment "reliability-api" successfully rolled out

# Scale up to 5 replicas
kubectl scale deployment reliability-api --replicas=5
kubectl get pods -w   # 2 new pods start immediately

# Scale back down
kubectl scale deployment reliability-api --replicas=3

# Prove self-healing at the Deployment level
# Delete ALL pods — the Deployment will recreate all 3
kubectl delete pods -l app.kubernetes.io/name=reliability-api
kubectl get pods -w   # Watch 3 new pods appear
    spec:
  replicas: 3
  selector:            # immutable — must match pod template labels
    matchLabels:
      app.kubernetes.io/name: reliability-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1         # allow 4 pods total (3+1) during rollout
      maxUnavailable: 0   # never drop below 3 ready pods

    5. Health Probes

    Kubernetes has three probe types, each answering a different question and taking a different action on failure:

    ProbeQuestionOn failure (after failureThreshold)reliability-api endpoint
    startupProbeHas the app finished starting?Kill and restart container. While pending, liveness and readiness are blocked./health
    livenessProbeIs the process stuck in a broken state?Kill and restart the container (same Pod, RESTARTS counter +1)./health
    readinessProbeShould this Pod receive traffic now?Mark Pod Ready=False → remove its IP from Service endpoints. No restart./ready
     
    startupProbe:           # gates the other two probes until success
  httpGet:
    path: /health
    port: 8000
  failureThreshold: 30  # 30 × 3s = 90 seconds to start
  periodSeconds: 3
livenessProbe:
  httpGet:
    path: /health
    port: 8000
  periodSeconds: 10
  failureThreshold: 3   # restart after 3 × 10s = 30s of failure
  timeoutSeconds: 2
readinessProbe:
  httpGet:
    path: /ready
    port: 8000
  periodSeconds: 5
  failureThreshold: 3   # unready after 3 × 5s = 15s of failure
  successThreshold: 1   # back in rotation after 1 success

    Live demo: readiness probe failure

    # Terminal 1 — watch pod ready status
kubectl get pods -w

# Terminal 2 — patch the deployment to set a long READY_DELAY
kubectl set env deployment/reliability-api READY_DELAY_SECONDS=60

# Terminal 2 — watch endpoints (pod IPs in Service backend)
kubectl get endpoints reliability-api -w

# During the rollout, new pods will show READY=0/1 and their IPs
# will NOT appear in the endpoints list until /ready returns 200

# Reset to normal
kubectl set env deployment/reliability-api READY_DELAY_SECONDS=5
    Liveness ≠ Readiness

    Use readiness when the pod is temporarily unable to serve (warming up, flushing queue). Use liveness when the pod is permanently broken and only a restart helps. Never use liveness for things that could cause cascading restarts under load (e.g., a shared dependency being slow). Prefer readiness in those cases.

    6. Resource Requests & Limits

    Resource management in Kubernetes has two knobs per container:

    • Requests — the amount the scheduler reserves on a node when placing the pod. The node must have this much available or the pod stays Pending.
    • Limits — the hard ceiling the Linux kernel enforces via cgroups. Exceeding the memory limit causes an OOMKill (exit code 137). Exceeding the CPU limit causes throttling (the process slows, not killed).
    ResourceUnitRequest effectLimit effect
    CPUm (millicores), 1 = 1 coreScheduler checks allocatable CPUCFS throttle — process pauses when quota exhausted
    MemoryMi, Gi, bytesScheduler checks allocatable memorycgroup OOM kill → container exits with code 137
     
    resources:
  requests:
    cpu: "100m"      # 0.1 vCPU — reserved for scheduling
    memory: "128Mi"  # 128 MiB — reserved for scheduling
  limits:
    memory: "256Mi"  # OOMKilled if exceeded
    # No CPU limit set — avoids throttling spikes under load

    QoS Classes

    Based on requests and limits, Kubernetes assigns a Quality of Service class to each pod, which determines eviction priority under node pressure:

    • Guaranteed — requests == limits for all containers. Never evicted (unless they exceed their own limits).
    • Burstable — at least one container has a request or limit. Our deployment is Burstable.
    • BestEffort — no requests or limits at all. Evicted first.
    # Temporarily set a very low memory limit to trigger OOMKill
kubectl set resources deployment/reliability-api --limits=memory=10Mi

# The containers will be OOMKilled as soon as they start
kubectl get pods -w
NAME                               READY   STATUS      RESTARTS   AGE
reliability-api-849d6f4f4-2xvtk    0/1     OOMKilled   1          8s

# Read the failure reason
kubectl describe pod <pod-name>
# Look for: Last State: Terminated  Reason: OOMKilled  Exit Code: 137

# Fix: restore sane limits
kubectl set resources deployment/reliability-api --limits=memory=256Mi --requests=cpu=100m,memory=128Mi
    Lab 6 · Resources

    7. Rolling Updates & Rollbacks

    A rolling update replaces pods one batch at a time — new pods come up, prove they are healthy (pass readiness probe), then old pods are terminated. The maxSurge and maxUnavailable parameters control the speed and safety of the transition.

    # Update the image to a new tag (simulate v0.2.0 — use same image for lab)
kubectl set image deployment/reliability-api \
  reliability-api=kumawatsunil/reliability-api:0.1.0

# Or edit the deployment YAML and apply
kubectl apply -f labs/k8s-reliability/02-deployment.yaml

# Watch the rollout in real time (best command for this)
kubectl rollout status deployment/reliability-api
Waiting for deployment "reliability-api" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "reliability-api" rollout to finish: 2 out of 3 new replicas have been updated...
deployment "reliability-api" successfully rolled out

# Inspect rollout history — shows each revision
kubectl rollout history deployment/reliability-api
REVISION  CHANGE-CAUSE
1         <none>
2         <none>

# Add a change-cause annotation before applying
kubectl annotate deployment reliability-api \
  kubernetes.io/change-cause="update to v0.2.0" --overwrite

# Roll back to the previous revision
kubectl rollout undo deployment/reliability-api

# Roll back to a specific revision
kubectl rollout undo deployment/reliability-api --to-revision=1
    Rollout only happens on pod template changes

    Changing spec.replicas or spec.strategy does NOT trigger a rollout. Only changes inside spec.template (image, env vars, resource limits, probe config) cause the Deployment to create a new ReplicaSet.

    Lab 7 · Rolling Updates & Rollbacks

    8. Namespaces

    Namespaces are virtual clusters inside a physical Kubernetes cluster. They provide scope for names (two Pods can have the same name in different namespaces), and are used to separate teams, environments, or applications. RBAC policies and resource quotas are usually applied at namespace level.

    9. Labels, Selectors & Annotations

    Labels are key-value pairs attached to any Kubernetes object. They are the primary mechanism for grouping, selecting, and targeting objects. Selectors find objects by label. Annotations store arbitrary non-identifying metadata (build IDs, URLs, descriptions) — they cannot be used in selectors.

    FeatureLabelsAnnotations
    Queryable by selector✅ Yes❌ No
    Used by Deployment/Service to find pods✅ Yes❌ No
    Character restrictions63 chars, alphanumeric, -_.Arbitrary strings
    Typical useapp=api, env=prod, version=v2CI build URL, git SHA, owner team, runbook URL
     
    # List pods filtered by label selector
kubectl get pods -l app.kubernetes.io/name=reliability-api

# Add a label to a running pod (does not trigger rollout)
kubectl label pod <pod-name> track=canary

# Remove a label
kubectl label pod <pod-name> track-

# Show labels as columns
kubectl get pods --show-labels

# Selector with multiple conditions (AND logic)
kubectl get pods -l 'app.kubernetes.io/name=reliability-api,env=lab'

# Set-based selector (In, NotIn, Exists, DoesNotExist)
kubectl get pods -l 'env in (lab,staging)'

# Annotations — for human-readable metadata and tooling
kubectl annotate deployment reliability-api \
  "team=platform" \
  "docs=https://wiki.example.com/reliability-api" \
  "kubernetes.io/change-cause=bump to v0.2.0"

    Canary pattern with labels

    # Apply canary pod with same app label so it receives 1/4 of Service traffic
kubectl run reliability-canary \
  --image=kumawatsunil/reliability-api:0.1.0 \
  --labels="app.kubernetes.io/name=reliability-api,track=canary" \

# The ClusterIP service selector matches both stable pods AND the canary
kubectl get endpoints reliability-api
# 4 IPs: 3 stable + 1 canary

# Remove canary from Service rotation without deleting it
kubectl label pod reliability-canary app.kubernetes.io/name-   # removes the label

## PODS & DIAGNOSTICS
kubectl run my-pod --image=nginx:alpine             # imperative: run a bare test pod
kubectl apply -f pod.yaml                           # declarative: create/update pod from YAML
kubectl get pods -o wide                            # list pods with node placement & pod IPs
kubectl get pods --show-labels                      # list pods with all assigned labels
kubectl describe pod <pod-name>                     # inspect pod events, exit codes, probe statuses
kubectl logs <pod-name>                             # view stdout/stderr container logs
kubectl logs <pod-name> -f                          # stream/follow logs in real-time
kubectl logs <pod-name> --previous                  # read logs of container *before* it crashed
kubectl exec -it <pod-name> -- sh                   # open interactive shell inside container
kubectl exec <pod-name> -- env                      # run single command inside container
kubectl port-forward pod/<pod-name> 8080:8000       # tunnel host port 8080 to container port 8000
kubectl delete pod <pod-name>                       # graceful deletion (triggers SIGTERM)
kubectl delete pod <pod-name> --now                 # immediate deletion (grace-period=0)

## ROLLING UPDATES, ROLLBACKS & RESILIENCY
kubectl set image deployment/my-app c=img:v2        # trigger rolling update by updating image
kubectl rollout status deployment/my-app            # watch rolling update progress in real-time
kubectl rollout history deployment/my-app           # view list of past revisions
kubectl rollout history deployment/my-app --rev=2   # inspect exact pod template of a specific revision
kubectl rollout undo deployment/my-app              # rollback to immediately preceding revision
kubectl rollout undo deployment/my-app --to-rev=1   # rollback to an explicit historical revision
kubectl rollout restart deployment/my-app           # trigger zero-downtime restart of all pods
kubectl annotate deployment/my-app \
  kubernetes.io/change-cause="deploy v2.0" --overwrite # document release description in rollout history

kubectl delete namespace staging                    # deletes namespace AND all resources inside it

## LABELS, SELECTORS & ANNOTATIONS
kubectl get pods -l app=reliability-api             # filter resources by exact key=value label
kubectl get pods -l 'env in (staging, prod)'        # set-based filter: match either staging or prod
kubectl get pods -l tier=backend,env=lab            # multi-label AND filter
kubectl get pods -l '!track'                        # filter pods that do NOT have the 'track' key
kubectl label pod my-pod env=canary                 # add or update a label dynamically on a running pod
kubectl label pod my-pod env-                       # remove a label from a running pod (notice trailing -)
kubectl annotate pod my-pod note="OOM test"         # attach non-identifying metadata annotation
