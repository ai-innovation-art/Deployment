    1. Services

    A Kubernetes Service provides a stable network identity (IP + DNS name) for a set of Pods. Pod IPs are ephemeral — they change every time a pod is created. A Service selects pods by label and maintains an EndpointSlice of their current IPs. kube-proxy programs iptables/IPVS rules on every node so traffic to the Service's ClusterIP is forwarded to a ready Pod.

    Service TypeReachable fromTypical use
    ClusterIP (default)Inside cluster onlyInternal microservice communication
    NodePortAny node IP + static port (30000–32767)Direct external access, simple dev testing
    LoadBalancerCloud load balancer IPProduction external traffic (cloud providers)
    ExternalNameDNS CNAME aliasRouting to external services via DNS

    ClusterIP Service

    apiVersion: v1
kind: Service
metadata:
  name: reliability-api
  namespace: default
spec:
  type: ClusterIP          # default; virtual IP only inside cluster
  selector:
    app.kubernetes.io/name: reliability-api  # must match pod labels
  ports:
    - name: http
      protocol: TCP
      port: 80         # port clients use
      targetPort: 8000 # port the container listens on
    # Apply the ClusterIP service
kubectl apply -f labs/k8s-reliability/03-service-clusterip.yaml

# Check the service — note the CLUSTER-IP assigned
kubectl get service reliability-api
NAME              TYPE        CLUSTER-IP    EXTERNAL-IP   PORT(S)   AGE
reliability-api   ClusterIP   10.96.45.23   <none>        80/TCP    10s

# Check that pod IPs appear as endpoints (only READY pods)
kubectl get endpoints reliability-api
NAME              ENDPOINTS                                         AGE
reliability-api   10.244.1.5:8000,10.244.1.6:8000,10.244.2.3:8000   25s

# Test the service from a debug pod inside the cluster
kubectl run debug --image=busybox:1.36 --restart=Never -it --rm -- \
  wget -qO- http://reliability-api.default.svc.cluster.local/health
    Selector mismatch — the #1 Service bug

    If kubectl get endpoints shows <none>, your Service selector does not match any pod labels. Compare kubectl get svc -o yaml selector with kubectl get pods --show-labels. They must match exactly, including namespace.

    2. DNS & Service Discovery

    Every Kubernetes cluster runs CoreDNS as an in-cluster DNS server. It resolves service names to ClusterIP addresses. The full DNS name of a Service follows a strict pattern:

    # Full qualified DNS name
<service-name>.<namespace>.svc.cluster.local

# Example for our service in namespace 'default':
reliability-api.default.svc.cluster.local

# Short names that also work — resolved by the pod's search domain
# From a pod IN THE SAME namespace:
reliability-api                                  # works
reliability-api.default                          # works
reliability-api.default.svc                      # works
reliability-api.default.svc.cluster.local        # works (FQDN)

# From a pod IN A DIFFERENT namespace (e.g., monitoring):
# Short name 'reliability-api' WON'T resolve — must use full namespace
reliability-api.default.svc.cluster.local        # works
reliability-api.default                          # works
    # Launch a debug pod with DNS tools
kubectl run dnsutils --image=registry.k8s.io/e2e-test-images/jessie-dnsutils:1.3 \
  --restart=Never -it --rm -- bash

# Inside the pod:
# Lookup the service — should return the ClusterIP
nslookup reliability-api
Server:   10.96.0.10
Address:  10.96.0.10#53

Name:     reliability-api.default.svc.cluster.local
Address:  10.96.45.23

# View the pod's DNS search list
cat /etc/resolv.conf
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local

# Cross-namespace lookup (from 'default', reach 'kube-system' CoreDNS)
nslookup kube-dns.kube-system.svc.cluster.local

# Reach the API using the full DNS name
wget -qO- http://reliability-api.default.svc.cluster.local/health
exit

    3. Ingress

    An Ingress routes external HTTP/HTTPS traffic into Services based on hostnames and URL paths. It requires an Ingress Controller — a dedicated pod that watches Ingress objects and configures a reverse proxy (nginx, Traefik, HAProxy…). kind ships without one by default.

    # Apply the kind-specific nginx ingress controller manifest
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml

# Wait for the controller pod to be ready (~60 seconds)
kubectl wait --namespace ingress-nginx \
  --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller \
  --timeout=120s

# Verify it's running
kubectl get pods -n ingress-nginx
NAME                                        READY   STATUS    RESTARTS
ingress-nginx-controller-5bc4c7d4d8-xmmpq   1/1     Running   0
    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: reliability-api-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    nginx.ingress.kubernetes.io/use-regex: "true"
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /api(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: reliability-api
                port:
                  number: 80
    # Apply the Ingress rule
kubectl apply -f labs/k8s-reliability/07-ingress.yaml

# Verify the Ingress got an address (requires kind extraPortMappings on port 80)
kubectl get ingress
NAME                       CLASS   HOSTS   ADDRESS     PORTS   AGE
reliability-api-ingress    nginx   *       localhost   80      15s

# Test path-based routing from your host
# The /api prefix is stripped by the rewrite-target annotation
curl http://localhost/api/health
{"status":"ok","uptime_seconds":300}

curl http://localhost/api/ready
{"status":"ready"}

    4. ConfigMaps

    A ConfigMap decouples configuration from the container image. It stores key-value pairs that can be injected into pods as environment variables, command-line arguments, or mounted files. ConfigMaps are not encrypted — don't store passwords or tokens there.

    apiVersion: v1
kind: ConfigMap
metadata:
  name: reliability-api-config
  namespace: default
data:
  LOG_LEVEL: "info"
  READY_DELAY_SECONDS: "5"
    # Method 1: inject ALL keys as env vars (envFrom)
envFrom:
  - configMapRef:
      name: reliability-api-config

# Method 2: inject ONE key as a named env var (env + valueFrom)
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: reliability-api-config
        key: LOG_LEVEL

# Method 3: mount the entire ConfigMap as files in a directory
volumes:
  - name: config-vol
    configMap:
      name: reliability-api-config
volumeMounts:
  - name: config-vol
    mountPath: /etc/config
    readOnly: true
# Result: /etc/config/LOG_LEVEL and /etc/config/READY_DELAY_SECONDS files
    # Create the ConfigMap
kubectl apply -f labs/k8s-reliability/05-configmap.yaml

# Alternatively, create from literal values imperatively
kubectl create configmap reliability-api-config \
  --from-literal=LOG_LEVEL=info \
  --from-literal=READY_DELAY_SECONDS=5 \
  --dry-run=client -o yaml | kubectl apply -f -

# Inspect the ConfigMap
kubectl get configmap reliability-api-config -o yaml

# Verify env vars are set in a running pod
kubectl exec -it deployment/reliability-api -- env | grep -E 'LOG_LEVEL|READY_DELAY'
LOG_LEVEL=info
READY_DELAY_SECONDS=5

# Update a ConfigMap value (env vars need pod restart; volume files update automatically)
kubectl patch configmap reliability-api-config \
  --patch '{"data":{"LOG_LEVEL":"debug"}}'
kubectl rollout restart deployment/reliability-api
    Volume mount vs env var

    When a ConfigMap is mounted as a volume, Kubernetes updates the files within ~60 seconds without restarting the pod — but your application must watch and reload the file (inotify or polling). Env vars only update on pod restart. Prefer volume mounts for config that changes frequently.

    Lab 4 · ConfigMaps

    5. Secrets

    A Secret stores sensitive data like passwords, API keys, and TLS certificates. The values are base64-encoded (not encrypted) in etcd by default. Base64 is trivially reversible — it is encoding, not encryption. Real protection comes from RBAC (limiting who can get secrets) and encryption-at-rest (enabled by cluster operators).

    Secrets are not encrypted by default

    Anyone with kubectl get secret permission and base64 -d can read your secret. Always: restrict access with RBAC, enable encryption at rest in production, and use a dedicated secrets manager (Vault, AWS Secrets Manager, External Secrets Operator) for real credentials.

    apiVersion: v1
kind: Secret
metadata:
  name: reliability-api-secret
  namespace: default
type: Opaque
data:
  # echo -n "postgresql://admin:changeme@postgres:5432/reliability" | base64
  DATABASE_URL: cG9zdGdyZXNxbDovL2FkbWluOmNoYW5nZW1lQHBvc3RncmVzOjU0MzIvcmVsaWFiaWxpdHk=
  API_KEY: czNjcjN0LWFwaS1rZXktcmVwbGFjZS1tZQ==
    # Apply the secret
kubectl apply -f labs/k8s-reliability/06-secret.yaml

# Inspect (values are base64 encoded in the output)
kubectl get secret reliability-api-secret -o yaml

# Decode a specific key
kubectl get secret reliability-api-secret \
  -o jsonpath='{.data.DATABASE_URL}' | base64 -d
postgresql://admin:changeme@postgres:5432/reliability

# Imperative create — Kubernetes handles the base64 encoding for you
kubectl create secret generic reliability-api-secret \
  --from-literal=DATABASE_URL="postgresql://admin:changeme@postgres:5432/reliability" \
  --from-literal=API_KEY="s3cr3t-api-key-replace-me" \
  --dry-run=client -o yaml

# Inject into pod as env var — same pattern as ConfigMap
# In deployment spec.containers:
env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef:
        name: reliability-api-secret
        key: DATABASE_URL

    6. Persistent Volumes & PVCs

    Container storage is ephemeral by default — when a pod is deleted, all data written inside the container filesystem is lost. For durable storage, Kubernetes uses a three-layer abstraction:

    ObjectWho creates itWhat it represents
    PersistentVolume (PV)Cluster admin (or dynamically by StorageClass)A piece of storage in the cluster (NFS mount, cloud disk, hostPath). Exists independently of pods.
    PersistentVolumeClaim (PVC)Developer (you)A request for storage: "I need 1 Gi with ReadWriteOnce access." The cluster binds it to a matching PV.
    StorageClassCluster adminA provisioner recipe. When a PVC names a StorageClass, the cluster creates a PV on-demand (dynamic provisioning).
     
    apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: api-data
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce   # one node at a time (RWO)
  storageClassName: standard  # kind's default hostPath provisioner
  resources:
    requests:
      storage: 1Gi
    # Apply the PVC — kind's 'standard' StorageClass provisions it automatically
kubectl apply -f labs/k8s-reliability/08-pvc.yaml

# Check that the PVC is bound to a PV
kubectl get pvc
NAME       STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
api-data   Bound    pvc-3d8b1a2c-4f5e-11ef-bc9a-0242ac110002   1Gi       RWO            standard       10s

kubectl get pv
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM              STORAGECLASS
pvc-3d8b1a2c-4f5e-11ef-bc9a-0242ac110002   1Gi        RWO            Delete           Bound    default/api-data   standard

# Add this to your deployment pod spec to mount the PVC:
volumes:
  - name: api-data
    persistentVolumeClaim:
      claimName: api-data
# In the container spec:
volumeMounts:
  - name: api-data
    mountPath: /data

# Prove data survives pod deletion
POD=$(kubectl get pods -l app.kubernetes.io/name=reliability-api -o name | head -1)
kubectl exec $POD -- sh -c 'echo "hello-persistence" > /data/test.txt'
kubectl delete $POD
# Wait for replacement pod to start
NEW_POD=$(kubectl get pods -l app.kubernetes.io/name=reliability-api -o name | head -1)
kubectl exec $NEW_POD -- cat /data/test.txt
hello-persistence   # Data survived!
    RWO in kind

    kind's standard StorageClass uses hostPath on the node. With ReadWriteOnce, only pods on the same node as the PV can mount it. If the pod is rescheduled to a different node, it stays Pending. This is a known kind limitation — production clusters use ReadWriteMany NFS/EFS or cloud-native storage.

    7. RBAC

    Role-Based Access Control (RBAC) controls who can do what to which Kubernetes resources. It uses four objects:

    ObjectScopePurpose
    ServiceAccountNamespaceIdentity for a pod (like a user account for a workload)
    RoleNamespaceSet of permissions on namespace-scoped resources
    ClusterRoleClusterSet of permissions on cluster-scoped or cross-namespace resources
    RoleBinding / ClusterRoleBindingNamespace / ClusterAttaches a Role to a subject (user, group, ServiceAccount)
     
    ---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: reliability-api-sa
  namespace: default
automountServiceAccountToken: false  # least privilege: opt-in mounting
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: reliability-api-role
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]   # read-only
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: reliability-api-rolebinding
  namespace: default
subjects:
  - kind: ServiceAccount
    name: reliability-api-sa
    namespace: default
roleRef:
  kind: Role
  name: reliability-api-role
  apiGroup: rbac.authorization.k8s.io
    # Apply all three RBAC objects
kubectl apply -f labs/k8s-reliability/09-rbac.yaml

# Verify what the ServiceAccount can do
kubectl auth can-i list pods \
  --as=system:serviceaccount:default:reliability-api-sa
yes

kubectl auth can-i delete pods \
  --as=system:serviceaccount:default:reliability-api-sa
no

kubectl auth can-i get secrets \
  --as=system:serviceaccount:default:reliability-api-sa
no

# Assign the ServiceAccount to the Deployment
kubectl patch deployment reliability-api \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"reliability-api-sa"}}}}'

    8. Helm Basics

    Helm is the package manager for Kubernetes. It bundles manifests into a chart — a versioned, parameterizable package. A chart installed into a cluster is called a release. Helm tracks release history so you can upgrade, inspect and rollback.

    Helm conceptAnalogyDescription
    Chartapt package / npm moduleA directory (or .tgz) of templates, values, and metadata
    ReleaseInstalled package instanceOne deployment of a chart with specific values and a name
    Repositoryapt source / npm registryA collection of chart packages, hosted at a URL
    values.yamlconfig fileDefault parameter values for the chart templates
    Revisionpackage version historyEach upgrade/rollback increments the release revision number

    Install Helm

    # macOS / Linux via Homebrew
brew install helm

# Linux — script install
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# Windows via Winget
winget install Helm.Helm

# Verify
helm version
version.BuildInfo{Version:"v3.16.4",...}

    Install an existing chart

    # Add the ingress-nginx repository
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
Hang tight while we grab the latest from your chart repositories...
...Successfully got an update from the "ingress-nginx" chart repository

# Search for available charts
helm search repo ingress-nginx
helm search hub nginx | head -10   # search Artifact Hub

# Install a chart into a namespace
helm install my-ingress ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --create-namespace \
  --set controller.service.type=NodePort

# List installed releases
helm list -A
NAME         NAMESPACE      REVISION   STATUS     CHART
my-ingress   ingress-nginx  1          deployed   ingress-nginx-4.11.3

# Upgrade a release (e.g., change a value)
helm upgrade my-ingress ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --set controller.replicaCount=2

# Rollback to a previous revision
helm rollback my-ingress 1 --namespace ingress-nginx

# View release history
helm history my-ingress -n ingress-nginx

# Uninstall the release (removes all k8s objects the chart created)
helm uninstall my-ingress -n ingress-nginx

    10. Quick Reference Cheat Sheet: The Verb x Resource Matrix

    Kubernetes CLI follows a universal grammar: kubectl <VERB> <RESOURCE> <NAME> [FLAGS]. Use this structured matrix as your master lookup table.

    ## 1. PODS (po) — Atomic Compute Unit
kubectl run my-pod --image=nginx:alpine             # [RUN] Imperatively start a single test pod
kubectl apply -f pod.yaml                           # [APPLY] Declaratively create/update pod from YAML
kubectl get pods -o wide                            # [GET] List pods with node placement & pod IPs
kubectl get pods --show-labels                      # [GET] List pods with all assigned labels
kubectl describe pod <pod-name>                     # [DESCRIBE] Deep inspection: events, probe states, exit codes
kubectl logs <pod-name> -f                          # [LOGS] Stream container stdout/stderr in real-time
kubectl logs <pod-name> --previous                  # [LOGS] Read logs of container *before* it crashed
kubectl exec -it <pod-name> -- sh                   # [EXEC] Open interactive shell inside container
kubectl port-forward pod/<pod-name> 8080:8000       # [PORT-FORWARD] Tunnel host port 8080 to container port 8000
kubectl label pod <pod-name> env=canary             # [LABEL] Dynamically add/update label
kubectl label pod <pod-name> env-                   # [LABEL] Remove label (notice trailing -)
kubectl delete pod <pod-name> --now                 # [DELETE] Force-delete pod without grace period

## 2. DEPLOYMENTS (deploy) & REPLICASETS (rs) — Self-Healing Workloads
kubectl apply -f 02-deployment.yaml                 # [APPLY] Create or declaratively update deployment
kubectl get deploy,rs,pods                          # [GET] View full workload hierarchy in one command
kubectl scale deployment/<app> --replicas=5         # [SCALE] Adjust replica count imperatively
kubectl set image deployment/<app> c=img:v2         # [SET IMAGE] Trigger rolling update with new container image
kubectl rollout status deployment/<app>             # [ROLLOUT STATUS] Watch rolling update progress in real-time
kubectl rollout history deployment/<app>            # [ROLLOUT HISTORY] View list of past release revisions
kubectl rollout history deployment/<app> --rev=2    # [ROLLOUT HISTORY] Inspect pod template of specific revision
kubectl rollout undo deployment/<app>               # [ROLLOUT UNDO] Rollback to immediately preceding revision
kubectl rollout undo deployment/<app> --to-rev=1    # [ROLLOUT UNDO] Rollback to explicit historical revision
kubectl rollout restart deployment/<app>            # [ROLLOUT RESTART] Zero-downtime rolling restart of all pods
kubectl annotate deployment/<app> \
  kubernetes.io/change-cause="deploy v2" --overwrite #[ANNOTATE] Record release description in rollout history
kubectl delete deployment/<app>                     # [DELETE] Remove deployment, replicasets and pods

## 3. SERVICES (svc) & ENDPOINTS (ep) — Traffic Balancing
kubectl apply -f 03-service-clusterip.yaml          # [APPLY] Create internal virtual IP load-balancer
kubectl expose deployment/<app> --port=80           # [EXPOSE] Auto-generate a service from deployment
kubectl get svc -o wide                             # [GET] List ClusterIPs, NodePorts, and External IPs
kubectl get endpoints <svc-name>                    # [GET] Inspect backend pod IPs matching service selector
kubectl describe svc <svc-name>                     # [DESCRIBE] Inspect selector, targetPort and active endpoints
kubectl port-forward svc/<svc-name> 8080:80         # [PORT-FORWARD] Tunnel traffic directly to service virtual IP
kubectl set selector svc <svc-name> "app=v2"        # [SET SELECTOR] Repoint service to different pod label
kubectl delete svc <svc-name>                       # [DELETE] Tear down service and remove routing rules

## 4. INGRESS (ing) — HTTP Domain & Path Routing
kubectl apply -f 07-ingress.yaml                    # [APPLY] Create Ingress path-routing rules
kubectl get ingress                                 # [GET] List ingress resources, hosts and backend paths
kubectl describe ingress <ing-name>                 # [DESCRIBE] Inspect path regex, rewrite rules and backends
kubectl delete ingress <ing-name>                   # [DELETE] Remove ingress rules

## 5. CONFIGMAPS (cm) & SECRETS — External Configuration & Credentials
kubectl create cm <name> --from-literal=K=V         # [CREATE CM] Create ConfigMap imperatively from key=value
kubectl create cm <name> --from-file=config.json    # [CREATE CM] Load entire config file into ConfigMap
kubectl create secret generic <name> --from-literal=pass=123 # [CREATE SECRET] Auto-encodes to base64
kubectl get cm,secrets                              # [GET] List configuration and secret stores
kubectl describe cm <cm-name>                       # [DESCRIBE CM] Read plain-text config values
kubectl describe secret <sec-name>                  # [DESCRIBE SECRET] Inspect keys (values are masked)
kubectl get secret <sec-name> \
  -o jsonpath='{.data.password}' | base64 -d        # [GET JSONPATH] Decode base64 secret to terminal
kubectl delete cm,secret <name>                     # [DELETE] Remove config or secret store

## 6. STORAGE (sc, pvc, pv) — Persistent Volume Lifecycle
kubectl get storageclass                            # [GET SC] List CSI storage provisioners & binding modes
kubectl apply -f 08-pvc.yaml                        # [APPLY PVC] Request dynamic volume from StorageClass
kubectl get pvc                                     # [GET PVC] Check status: Pending vs Bound
kubectl describe pvc <pvc-name>                     # [DESCRIBE PVC] View attached PV name and capacity
kubectl get pv                                      # [GET PV] List dynamically created physical/cloud volumes
kubectl delete pvc <pvc-name>                       # [DELETE PVC] Release storage claim

## 7. RBAC & SECURITY (sa, role, rolebinding)
kubectl apply -f 09-rbac.yaml                       # [APPLY] Create ServiceAccount, Role and RoleBinding
kubectl get sa,role,rolebinding                     # [GET] Inspect active security principals
kubectl auth can-i list pods                        # [AUTH CAN-I] Test admin user permissions
kubectl auth can-i delete pods \
  --as=system:serviceaccount:default:reliability-sa # [AUTH CAN-I --AS] Impersonate and test robot account

## 8. HELM V3/V4 — Package & Release Management
helm create <chart-name>                            # [CREATE] Scaffold standard chart structure
helm lint ./<chart-name>                            # [LINT] Validate syntax, templates and values.yaml
helm template <release> ./<chart>                   # [TEMPLATE] Dry-run render YAML locally to terminal
helm install <release> ./<chart>                    # [INSTALL] Deploy entire app stack in one atomic command
helm list -A                                        # [LIST] List deployed releases across all namespaces
helm status <release>                               # [STATUS] Check release health and resources
helm upgrade <release> ./<chart> --set replicas=3   # [UPGRADE] Update release with overridden parameters
helm history <release>                              # [HISTORY] View revision numbers, timestamps, descriptions
helm rollback <release> 1                           # [ROLLBACK] Instantly revert stack to revision 1
helm uninstall <release>                            # [UNINSTALL] Delete all associated Kubernetes resources
