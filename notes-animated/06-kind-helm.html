    Module 06 · Local Clusters with kind & Packaging with Helm

    You now understand the raw objects behind reliability-api: Deployment, Service, ConfigMap, ServiceAccount, HPA. This module gives you two tools that make that work repeatable. kind runs a real, multi-node Kubernetes cluster as Docker containers on your laptop or in CI, so you can create, break and delete reliability-lab in a minute.     Part A — kind: Kubernetes IN Docker

    A1. What kind is

    kind creates local Kubernetes clusters using Docker containers as "nodes". Each node container runs a full node image (kindest/node:<k8s-version>) containing systemd, containerd, the kubelet and — on control-plane nodes — the API server, etcd, scheduler and controller manager, all bootstrapped with kubeadm. It was built to test Kubernetes itself and is widely used for local development and CI.

    The problem it solves

    • Cost and speed: a cluster in about a minute, for free, deleted just as quickly. You can afford to break it on purpose.
    • Reality: it's upstream Kubernetes with real kubelets, real kube-proxy, real CoreDNS and a real CNI — not a simulator. Your YAML, Helm charts, probes, Services and NetworkPolicies behave as they would elsewhere.
    • Reproducibility: the cluster is described in a YAML config file you commit next to the code; CI (Module 09) can create the identical cluster.

    You can see this from the host. Observed on a machine with a single-node kind cluster named mlops (yours will show your cluster name and a different port):

    docker ps --filter label=io.x-k8s.kind.cluster --format '{{.Names}} {{.Image}} {{.Ports}}'
mlops-control-plane kindest/node:v1.37.0 127.0.0.1:54749->6443/tcp

    And inside, the familiar system Pods (same machine): coredns ×2, etcd-…, kindnet-…, kube-apiserver-…, kube-controller-manager-…, kube-proxy-…, kube-scheduler-….

    Pin versions

    Write the kind version (and the node image, see below) into your README and CI. "Works on my machine" for clusters usually means two different Kubernetes versions. kind's known-issues page also warns about client/server version skew: keep kubectl within the supported skew of the cluster version.

    A4. Cluster configuration file

    A config file (kind: Cluster, apiVersion: kind.x-k8s.io/v1alpha4) describes the nodes and networking. The v1alpha4 means the format may still change between kind versions — another reason to pin kind.

    kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: reliability-lab                    # same as --name
nodes:
  - role: control-plane
    extraPortMappings:                   # Docker publishes hostPort → node containerPort
      - containerPort: 30080             # must EQUAL the Service nodePort
        hostPort: 8080                   # http://127.0.0.1:8080 on your laptop
        listenAddress: "127.0.0.1"       # default would be 0.0.0.0 (all interfaces)
        protocol: TCP
  - role: worker
    labels:
      tier: app                          # per-node labels for scheduling experiments
  - role: worker
    labels:
      tier: app
    kubeadmConfigPatches:                # patch kubeadm config for this node
      - |
        kind: JoinConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "reliability-lab/chaos-target=true"
# networking: (defaults shown in comments — only set if you must)
#   podSubnet: 10.244.0.0/16   serviceSubnet: 10.96.0.0/16
#   disableDefaultCNI: true    # to install Calico/Cilium yourself
#   kubeProxyMode: ...         # e.g. to try nftables
    FieldWhat it doesWhen you need it in this course
    nodes[].rolecontrol-plane or worker; one entry per node container2 workers for scheduling, PDB and "kill a node" experiments (Module 08)
    extraPortMappingsDocker port publish from host to a node container: containerPort, hostPort, listenAddress (default 0.0.0.0), protocol (TCP/UDP/SCTP)Reach a NodePort Service or an ingress/gateway proxy from the laptop without port-forward

    kubeadmConfigPatchesPatches kubeadm's InitConfiguration (control plane), JoinConfiguration (workers), ClusterConfiguration, KubeletConfiguration, KubeProxyConfigurationExtra kubelet args such as node-labels; some third-party ingress setups ask for a specific node label this way

    nodes[].imageNode image per node (pin with a digest)Pin the Kubernetes version
    Port mappings are fixed at creation

    extraPortMappings become Docker port publishes on the node containers, which are set when the container is created. To change them you delete and recreate the cluster. Decide your mappings up front and keep them in the committed config.

    The port chain with extraPortMappings

    The kind docs are explicit for NodePort: "the kind node containerPort and the service nodePort needs to be equal".

    apiVersion: v1
kind: Service
metadata:
  name: reliability-api-nodeport
  namespace: reliability-lab
spec:
  type: NodePort
  selector:
    app.kubernetes.io/name: reliability-api
  ports:
    - name: http
      port: 80
      targetPort: 8000
      nodePort: 30080            # == extraPortMappings[].containerPort

    A5. Getting your image into the cluster

    The node containers run their own containerd with their own image store. docker build puts reliability-api:0.1.0 in the host's Docker image store, which the kubelet inside the node cannot see. Two options (study guide §10): push to a registry the cluster can reach, or side-load the image:

    docker build -t reliability-api:0.1.0 .
kind load docker-image reliability-api:0.1.0 --name reliability-lab
# verify it is present inside a node:
docker exec -it reliability-lab-worker crictl images | grep reliability-api

    Example output of the load (yours will show your image ID and nodes):

    Image: "reliability-api:0.1.0" with ID "sha256:3f1c…" not yet present on node "reliability-lab-worker", loading...
Image: "reliability-api:0.1.0" with ID "sha256:3f1c…" not yet present on node "reliability-lab-worker2", loading...
Image: "reliability-api:0.1.0" with ID "sha256:3f1c…" not yet present on node "reliability-lab-control-plane", loading...

    A6. The :latest / imagePullPolicy trap

    Rules from the Kubernetes "Images" page, applied when the Pod object is created and the field is omitted:

    Image referenceDefault imagePullPolicyOn kind with a side-loaded image
    reliability-api (no tag) or reliability-api:latestAlwayskubelet tries docker.io/library/reliability-api:latest → ErrImagePull / ImagePullBackOff, even though the image is on the node
    reliability-api:0.1.0IfNotPresentUses the loaded image ✓
    reliability-api@sha256:…IfNotPresentUses the loaded image if the digest matches ✓

    The kind quick start repeats this warning and suggests specifying imagePullPolicy: IfNotPresent or Never for loaded images. Better: never use :latest — the Kubernetes docs advise against it in production because it's hard to know which version is running and hard to roll back. Use 0.1.0 locally and the git SHA in CI.

    A second, subtler trap: you rebuild reliability-api:0.1.0 with a code change and load it again, but running Pods keep the old process, and new Pods with IfNotPresent may start from whichever image the node has under that tag. Bump the tag (0.1.1, or a SHA) for every build you want to deploy; that also gives the Deployment a real change to roll out.

    Self-check: why does a three-node kind cluster not give you three times the capacity of a one-node cluster?
    All node containers run on the same host (inside the same Docker VM on macOS) and share its CPU and memory. More nodes give you more scheduling targets and failure domains to experiment with, not more hardware.
    Self-check: your Deployment uses image: reliability-api:latest and you ran kind load docker-image reliability-api:latest. The Pod is in ImagePullBackOff. Explain.
    With the :latest tag and no explicit policy, imagePullPolicy defaults to Always, so the kubelet tries to pull from Docker Hub (where the image doesn't exist) instead of using the loaded copy. Use a versioned tag (0.1.0) or set IfNotPresent/Never.

    Part B — Helm: packaging reliability-api

    B1. Why Helm (and why not first)

    By the end of Module 05 reliability-api is seven or eight YAML files whose names, labels and ports must agree with each other exactly. For a second environment (CI's kind cluster, then GKE) you'd copy them and edit the image, replica count and resources by hand — and drift begins. Helm is a package manager for Kubernetes that solves this with three ideas (Helm "Using Helm" page):

    ConceptMeaningIn this project
    ChartA package: templates for all the Kubernetes resources an app needs, plus default values and metadatacharts/reliability-api
    RepositoryA place where packaged charts are stored and shared (HTTP chart repo or an OCI registry)Third-party charts such as kube-prometheus-stack (Module 07); optionally GHCR for your own chart
    ReleaseA running instance of a chart in a cluster, with a name. Installing the same chart twice gives two releases.Release reliability-api in namespace reliability-lab
    ValuesConfiguration that fills the templates: defaults in values.yaml, overridden per installreplicaCount, image.tag, autoscaling.enabled…
    RevisionA numbered version of a release; every install, upgrade and rollback creates a new one, starting at 1What helm history lists and helm rollback targets

    Benefits listed in the study guide (§11): no near-duplicate YAML per environment, central configuration of replicas/resources, versioned installs/upgrades/rollbacks, and an easy install for another engineer. The guide's warning stands: don't start with Helm. If you can't read the rendered YAML, you can't debug the chart.

    Helm version

    These notes follow the current Helm docs (v4.3). Helm 4 renamed two common flags — --atomic → --rollback-on-failure and --force → --force-replace; the old names still work with a deprecation warning. Helm 4 also defaults to server-side apply for new releases. Charts written for Helm 3 (apiVersion: v2) keep working.

    B2. How Helm works

    1. Merge values: chart defaults ← parent chart (for subcharts) ← each -f file left to right ← each --set left to right.
    2. Render: every file in templates/ (except those starting with _) is executed as a Go template with the built-in objects (.Values, .Release, .Chart, .Capabilities, .Files, .Template). The output must be valid YAML Kubernetes objects.
    3. Apply: the manifests are sent to the API server (install creates; upgrade computes changes against the previous revision).
    4. Record: a new revision with status deployed (or failed) is stored; the previous one becomes superseded.
    5. Wait (optional): in Helm 4, if you don't pass --wait the default strategy is hookOnly — Helm returns once the objects are accepted, not when Pods are ready. Use --wait (default strategy watcher) with --timeout in CI.

    B3. Chart structure for charts/reliability-api

    The official chart layout (Charts page) with what this project uses:

    charts/reliability-api/
├── Chart.yaml              # required: apiVersion v2, name, version (SemVer 2); appVersion
├── values.yaml             # default values (documented!)
├── values.schema.json      # optional: JSON Schema to validate values (not used in v1)

├── charts/                 # dependency charts (none here)

    ├── _helpers.tpl        # named templates; "_" => not rendered as a manifest

    ├── serviceaccount.yaml

    helm create <name> scaffolds a similar chart. With Helm v4.3.0 the scaffold contains .helmignore, Chart.yaml, values.yaml and templates NOTES.txt, _helpers.tpl, deployment.yaml, hpa.yaml, httproute.yaml, ingress.yaml, service.yaml, serviceaccount.yaml, tests/test-connection.yaml (observed locally). Generating one and reading it is a great exercise; the chart below is a trimmed, commented version of the same patterns.

    version vs appVersion

    Two different numbers (Charts page): version is the version of the chart (SemVer 2, bump it on every chart change; it's what repositories and OCI tags key on). appVersion documents the version of the application the chart deploys by default. In our chart an empty image.tag falls back to .Chart.AppVersion, so the two are linked deliberately.

    B4. Templating basics

    Helm templates are Go templates plus a large function library. Everything between {{ }} is evaluated; everything else is copied verbatim. Built-in objects always start with a capital letter.

    Why include + nindent, not template

    YAML is indentation-sensitive, and a named template doesn't know where it will be inserted. The template action inserts text as-is; include returns a string, so you can pipe it to nindent to put it on a new line at exactly the right depth. The Helm docs call include "preferable" for this reason, and the tips page recommends the pattern {{- include "…" $value | nindent 2 }}: the {{- chomps the preceding newline and nindent re-adds one plus the indentation.

      labels:
    {{- include "reliability-api.labels" . | nindent 4 }}

# renders to
  labels:
    helm.sh/chart: reliability-api-0.1.0
    app.kubernetes.io/name: reliability-api
    app.kubernetes.io/instance: reliability-api
    app.kubernetes.io/version: "0.1.0"
    app.kubernetes.io/managed-by: Helm

    range example

    If you later want arbitrary extra env vars from values:

    # values.yaml
extraEnv:
  - name: FEATURE_X
    value: "on"

# templates/deployment.yaml (inside the container)
          {{- with .Values.extraEnv }}
          env:
            {{- range . }}
            - name: {{ .name }}
              value: {{ .value | quote }}
            {{- end }}
          {{- end }}
    Quote strings, don't quote integers

    From the chart tips page: quote string values ({{ .Values.config.logLevel | quote }}) but not integers like replicas or ports — quoting them can cause parsing errors in Kubernetes. Environment variable values are the exception: they must be strings, which is why every ConfigMap value in our chart is quoted, including READY_DELAY_SECONDS.

    B5. Values and precedence

    From the Helm values-files guide, values come from (lowest → highest precedence):

    1. the chart's values.yaml;
    2. for a subchart, the parent chart's values.yaml;
    3. files passed with -f/--values — several allowed; "the priority will be given to the last (right-most) file specified";
    4. individual --set parameters — also right-most wins.

    Maps are merged key by key (so -f only needs the keys it changes); setting a key to null deletes a default. Lists are replaced, not merged.

    Verified with helm template on the chart below (Helm v4.3.0; rendering is local, so you can reproduce this exactly):

    helm template reliability-api ./charts/reliability-api -n reliability-lab \
  -f values-lab.yaml --set config.logLevel=warning --set autoscaling.maxReplicas=4 \
  --show-only templates/configmap.yaml --show-only templates/hpa.yaml | grep -E 'LOG_LEVEL|Replicas'
  LOG_LEVEL: "warning"
  minReplicas: 2
  maxReplicas: 4

    where values-lab.yaml sets replicaCount: 3, config.logLevel: debug and autoscaling.enabled: true. --set beat the file for LOG_LEVEL; minReplicas came from the chart default.

    Widget — values precedence calculator
    Edit the layers as dotted.key=value lines (one per line). The calculator merges them the way Helm does for scalar keys and shows where each final value came from.

    --set syntax you'll actually need

    --set replicaCount=3                         # scalar
--set image.tag=3f9c2e1                      # nested key
--set a=1,b=2                                # several at once (commas)
--set-string config.readyDelaySeconds=5      # force string type

    Prefer files over long --set chains: files are reviewable in Git. In CI, the one thing you typically pass with --set is the image tag (the git SHA).

    Upgrades and remembered values

    helm upgrade has three explicit behaviours you should choose deliberately: --reuse-values (reuse the last release's values and merge in command-line overrides), --reset-values (reset to the chart's built-in values) and --reset-then-reuse-values (reset to chart defaults, apply the last release's values, then merge overrides). The robust habit: always pass the full set of -f files on every upgrade so the release is fully described by files in Git.

    B7. The release lifecycle

    # 0. static checks — no cluster needed
helm lint ./charts/reliability-api
helm template reliability-api ./charts/reliability-api -n reliability-lab > /tmp/rendered.yaml

# 1. install (revision 1)
helm install reliability-api ./charts/reliability-api -n reliability-lab --create-namespace --wait --timeout 5m

# 2. idempotent deploy: install if missing, otherwise upgrade (what CI should run)
helm upgrade --install reliability-api ./charts/reliability-api -n reliability-lab \
  -f values-lab.yaml --set image.tag=0.1.1 --wait --timeout 5m

# 3. inspect
helm list -n reliability-lab
helm status reliability-api -n reliability-lab
helm history reliability-api -n reliability-lab
helm get values reliability-api -n reliability-lab          # user-supplied values
helm get manifest reliability-api -n reliability-lab        # what was actually applied

# 4. roll back (omit the revision or use 0 to go to the previous one)
helm rollback reliability-api 1 -n reliability-lab --wait

# 5. remove (add --keep-history to keep the release record)
helm uninstall reliability-api -n reliability-lab
    Command / flagBehaviour (from the Helm command reference)
    helm upgrade --install (-i)"if a release by this name doesn't already exist, run an install"
    --waitWait until resources are ready, up to --timeout. Strategies watcher (default when you pass --wait alone), hookOnly (default when omitted), legacy
    --timeoutTime to wait for any individual Kubernetes operation (default 5m0s)
    --rollback-on-failureUpgrade: roll back to the previous successful release on failure; install: uninstall on failure. Implies --wait=watcher. Helm 3 name: --atomic
    --create-namespaceCreate the release namespace if missing
    --history-maxMaximum revisions kept per release (default 10) — older ones can't be rolled back to
    --dry-run=client|serverSimulate: client avoids cluster connections; server simulates on the server (needs connectivity, so lookup works)
    helm rollback <RELEASE> [REVISION]Roll back to a previous revision; omitted or 0 → previous release
    helm uninstall --keep-historyDelete the resources but keep the release history

    Revisions are append-only

    A rollback doesn't delete history; it creates a new revision whose content is copied from the target. Statuses you'll see: deployed (current), superseded (replaced), failed, uninstalled (with --keep-history), and transient pending-install/pending-upgrade/pending-rollback.

    B9. Hooks and tests (brief)

    Hooks let a chart run resources (typically Jobs) at points in the release lifecycle, by annotation helm.sh/hook with values pre-install, post-install, pre-delete, post-delete, pre-upgrade, post-upgrade, pre-rollback, post-rollback, test. Order with helm.sh/hook-weight (string numbers); clean up with helm.sh/hook-delete-policy (before-hook-creation — the default — hook-succeeded, hook-failed). Important: resources created by hooks are not tracked as part of the release, so helm uninstall doesn't remove them unless a delete policy does.

    Typical uses: a pre-upgrade database migration Job; a post-install warm-up. reliability-api needs no hooks.

    Chart tests are hooks with helm.sh/hook: test, conventionally under templates/tests/. helm test reliability-api -n reliability-lab runs them; a test passes when its container exits 0. Our test Pod wgets reliability-api:80/ready through the Service — a real end-to-end check of Service, selector, targetPort and readiness. If you enforce the Module 05 NetworkPolicy, this test Pod (in the same namespace) is allowed by the podSelector: {} rule.

    B10. Chart repositories and OCI registries

    Two ways to distribute charts:

    • Classic chart repositories — an HTTP server with an index.yaml: helm repo add NAME URL, helm repo update, helm search repo, then helm install REL NAME/CHART. This is how you'll install kube-prometheus-stack in Module 07 (check that chart's own docs for its current source).
    • OCI registries — the same registries that store container images (GHCR, Artifact Registry). No helm repo add; you use oci:// references directly:
    helm package ./charts/reliability-api                     # → reliability-api-0.1.0.tgz
helm registry login ghcr.io -u <you>                       # host only, no scheme/path
helm push reliability-api-0.1.0.tgz oci://ghcr.io/<you>/charts
# → stored as oci://ghcr.io/<you>/charts/reliability-api:0.1.0 (name → repo, version → tag)
helm install reliability-api oci://ghcr.io/<you>/charts/reliability-api --version 0.1.0 -n reliability-lab

    The push reference omits the chart name and tag — Helm infers them from Chart.yaml's name and version, which is why version must be valid SemVer and bumped on every change. You can also install by immutable digest (…/reliability-api@sha256:…).

    B12. Trade-offs

    • Helm vs raw YAML / Kustomize: Helm adds templating, packaging and release history; the cost is a template language that can hide the actual YAML. Kustomize (built into kubectl apply -k) patches plain YAML without templates but has no release concept. Many teams use Helm for third-party apps and either for their own.
    • Configurability vs readability: every value you expose is API you must support. Expose what changes between environments (image, replicas, resources, autoscaling, config); hard-code the rest.
    • Helm-managed vs GitOps-managed: later you might let a GitOps controller render charts; the chart stays the same.

    Self-check

    1. What exactly is a "node" in a kind cluster, and where do your Pods' containers run?
    A node is a Docker container running the kindest/node image with containerd and the kubelet (plus control-plane components on the control-plane node). Pods' containers are run by that node container's own containerd — containers inside a container.
    2. You want curl 127.0.0.1:8080 on your laptop to reach reliability-api without port-forward. What two things must agree?
    The kind config's extraPortMappings (hostPort: 8080, containerPort: N) and the NodePort Service's nodePort: N. containerPort must equal nodePort. And the mapping must exist at cluster creation.
    3. Why does kind load docker-image exist at all?
    Nodes have their own containerd image store, separate from the host's Docker store. Without loading (or pushing to a reachable registry), the kubelet can't find a locally built image.
    4. Give three ways kind results can mislead you about production.
    Shared host CPU/RAM (load numbers measure your laptop; load generator competes); no real LoadBalancer/cluster autoscaler/zones; local-path storage without real durability. Also: image distribution differs (side-loading vs registry pulls).
    5. Distinguish chart, release and revision using reliability-api.
    Chart: charts/reliability-api (version 0.1.0). Release: the installed instance named reliability-api in reliability-lab. Revision: each numbered state of that release (1 install, 2 upgrade, …).
    6. values.yaml says replicaCount: 2, -f a.yaml -f b.yaml set it to 3 and 4, and --set replicaCount=5. Final value? And if you remove --set?
    5 (--set wins). Without it, 4 — the right-most -f file wins.
    7. Why does the chart's Deployment template use include … | nindent 4 rather than template?
    include returns a string that can be piped to nindent, which puts the multi-line label block on a new line at the correct indentation. template inserts raw text and can't be piped, so indentation breaks YAML.
    8. You run helm rollback reliability-api 2 when the current revision is 4. What does helm history show afterwards?
    A new revision 5, status deployed, description like "Rollback to 2", with revision 2's content. Revisions 1–4 remain (4 becomes superseded or stays failed).
    9. Why is replicas wrapped in {{- if not .Values.autoscaling.enabled }}?
    When the HPA manages the Deployment, a replicas field in the template would reset the count on every upgrade, fighting the HPA.
    10. What problem does the checksum/config annotation solve?
    reliability-api reads config from env vars, which don't update when the ConfigMap changes. The checksum of the rendered ConfigMap is placed in the Pod template, so any config change alters the template and triggers a rolling update.
    11. helm lint passes but the install fails. Name two classes of problem lint can't catch and the tool that would.
    API-server validation (unknown fields, immutable field changes, missing CRDs) → --dry-run=server; runtime issues (image pulls, failing probes) → install with --wait and helm test.
    12. In Helm 4, you run helm upgrade without --wait and it returns success, but the new Pods are crash-looping. Why did Helm report success?
    Without --wait the default wait strategy is hookOnly: Helm only waits for hooks, not for resources to become ready, so success means "objects accepted by the API server". Use --wait --timeout (and optionally --rollback-on-failure).
