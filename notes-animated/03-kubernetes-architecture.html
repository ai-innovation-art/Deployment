    1. Why orchestration?

    Definition. A container orchestrator is a system that runs containers across a pool of machines on your behalf: it decides where each container runs, restarts or replaces it when it fails, keeps the requested number of copies running, rolls out new versions gradually, and gives clients a stable way to reach whichever copies are currently healthy. Kubernetes is the dominant open-source orchestrator. The official overview describes it as a platform for managing containerized workloads that facilitates both declarative configuration and automation.

    The problem: what docker run leaves to you

    Imagine you are on call for reliability-api and the only tool you have is Docker on one VM:

    SituationWith plain Docker on one hostWhat Kubernetes provides
    Process crashes--restart=always restarts it on the same host onlykubelet restarts the container; if the Pod is lost, a controller creates a replacement Pod (possibly on another node)
    The VM diesService is down until a human builds a new VMPods on the failed node are replaced on healthy nodes by their controller
    You need 2 (or 6) copiesRun several containers, pick host ports by hand, wire a load balancer yourselfreplicas: 2 in a Deployment; a Service load-balances across ready Pods
    Deploying v0.2.0Stop old, start new, hope; or write a scriptRolling update with surge/unavailability limits, rollout status, one-command rollback

    Placing work on machinesYou choose a host by handScheduler places Pods by resource requests and constraints
    Config and secrets-e flags and files on the hostConfigMaps and Secrets as API objects (Module 05)
    Who changed what?Shell history on someone's laptopEverything is an API object; manifests live in Git and are applied declaratively

    What Kubernetes is not

    • It is not a build system: it runs images that already exist in a registry (or, in kind, that you load into the node).
    • It does not make a buggy app reliable. If reliability-api deadlocks, Kubernetes can only restart it if you configured a liveness probe (Module 04).
    • It does not add capacity by itself. If Pods request more CPU than your nodes have, they stay Pending. Adding nodes is a cluster-autoscaler or human job (Module 08).
    • It is not magic networking: Services, DNS and policies are explicit objects (Module 05).
    Trade-off

    Kubernetes adds a lot of moving parts. For a single small service on one VM, Docker plus a process supervisor can be enough. The orchestration pays off once you need several replicas, zero-downtime rollouts, self-healing across machines, or many services sharing infrastructure. In this course we use it because the reliability behaviours (probes, rollouts, autoscaling, recovery) are exactly what we want to study.

    2. Cluster architecture: control plane and nodes

    Definition. A Kubernetes cluster is a set of machines (nodes) plus a control plane. The control plane holds the cluster's state and makes global decisions (for example scheduling) and reacts to events; nodes run your Pods. In production the control plane is usually replicated across several machines; in kind it is a single Docker container named reliability-lab-control-plane.

    The single most important structural fact: components do not call each other directly; they all read and write objects through the API server. The scheduler does not "tell" a kubelet to start a Pod. It writes the chosen node name into the Pod object; the kubelet on that node is watching for Pods bound to it, notices, and acts. This makes the system loosely coupled: any component can restart and simply re-read the current state.

    Control-plane components

    ComponentWhat it doesIf it is down…
    kube-apiserverExposes the Kubernetes HTTP API. Every request (from kubectl, controllers, kubelets) is authenticated, authorized, passed through admission control, validated, then persisted. The front door and the only component that talks to etcd.No one can read or change cluster state: kubectl fails, no new scheduling, no scaling. Already running containers keep running — kubelets keep their Pods alive.
    etcdConsistent, highly-available key-value store that is the backing store for all API server data. If it is not in etcd, it does not exist in the cluster.API server cannot serve or persist state → same symptoms as API down. Losing etcd data without a backup means losing the cluster's definition of everything.
    kube-schedulerWatches for Pods with no node assigned and picks a node for each one (filtering then scoring, Module 04), then binds the Pod to it.New Pods stay Pending forever. Existing Pods are unaffected.
    kube-controller-managerOne binary running many controllers (control loops): Deployment, ReplicaSet, Job, node, EndpointSlice, namespace, and more. Each watches some object types and moves actual state toward desired state.Nothing reconciles: delete a Pod and no replacement is created; a new Deployment never gets a ReplicaSet; rollouts stall.
    cloud-controller-manager optionalEmbeds cloud-specific logic: e.g. creating cloud load balancers for type: LoadBalancer Services, labelling nodes with zones, noticing deleted VMs. Exists on managed clouds such as GKE; absent in kind.Cloud integrations stop (new load balancers are not provisioned); core workloads keep running.

    Node components

    ComponentWhat it doesIf it is down…
    kubeletThe agent on every node. Registers the node, watches the API for Pods bound to its node, asks the container runtime to create/stop containers, runs probes, reports Pod and node status, and sends heartbeats (Node status updates and Lease objects in the kube-node-lease namespace).Containers on that node may keep running, but nothing is updated: no restarts, no probe results, no status. The node controller eventually marks the node not ready / unreachable and its Pods get replaced elsewhere.
    kube-proxy optionalMaintains network rules on each node (for example iptables or nftables rules, depending on its mode) that implement Service virtual IPs. Some network plugins replace it entirely.Service IPs on that node stop being updated; Pod-to-Pod IP traffic still works. Details in Module 05.
    Container runtimeThe software that actually runs containers: containerd, CRI-O, or another implementation of the Container Runtime Interface (CRI). kind nodes use containerd.kubelet cannot start or stop containers; node becomes NotReady.

    The Container Runtime Interface (CRI)

    The kubelet does not link against containerd directly. It speaks the CRI, a gRPC protocol in which the kubelet is the client and the runtime is the server. From Kubernetes v1.26 onward the kubelet requires the runtime to support the v1 CRI API, or the node will not register. This is why "Docker" is not needed on Kubernetes nodes any more: Docker builds the image (an OCI image), and any CRI runtime can run it. Your laptop still uses Docker — kind runs each Kubernetes node as a Docker container, and containerd runs inside it.

    Addons

    Addons are ordinary Kubernetes workloads that provide cluster features: cluster DNS (CoreDNS) so Pods can resolve reliability-api.reliability-lab.svc.cluster.local, a network plugin (kind ships kindnet), optional dashboards, resource-metrics collection (metrics-server, Module 08) and cluster-level logging. They usually live in kube-system.

    Where the control plane runs in kind: static Pods

    In kubeadm-style clusters (kind uses kubeadm internally) the control-plane components run as static Pods: manifest files on the control-plane node's disk that the kubelet runs directly, then mirrors into the API so you can see them. That is why kubectl get pods -n kube-system lists kube-apiserver-reliability-lab-control-plane even though the API server is what you are talking to.

    Applied to reliability-api

    With a single-node kind cluster, everything in Figure 2 lives in one container. That is fine for learning, but notice what it means for reliability: "2 replicas" of reliability-api on one node do not survive a node failure. Replicas protect you against process crashes and give you rolling updates; spreading across nodes (Module 04: anti-affinity, topology spread) is what protects you against machine failure.

    Self-check: The scheduler crashes. Does the running reliability-api Pod stop serving traffic?
    No. The scheduler only assigns new Pods to nodes. Already-bound Pods are run by their node's kubelet. What breaks is anything needing a new Pod: scaling up, rollouts, replacing a deleted Pod (the ReplicaSet controller will create the Pod object, but it will stay Pending).
    Self-check: Why is it a deliberate design choice that only the API server talks to etcd?
    It gives one place for authentication, authorization, admission, validation, versioning and change notifications (watches). Every other component is just an API client, so they can be restarted, replaced or scaled independently, and they all see a consistent view of state.

    3. The life of kubectl apply

    This is the single most useful mental model in Kubernetes. When you run kubectl apply -f deploy/kubernetes/deployment.yaml, kubectl does not start any container. It writes a record of intent into the API. Then half a dozen independent loops each notice something new and do one small job. Step through it:

    Read the OBJECT column top to bottom: deployment → replicaset → pod. The REASON column names the actor: ScalingReplicaSet is the Deployment controller, SuccessfulCreate the ReplicaSet controller, Scheduled the scheduler, Pulled/Created/Started the kubelet.

    Failure cases along the path
    • Step 2 fails (validation/RBAC): kubectl prints an error; nothing exists. Example: a typo like replica: 2 is rejected by strict field validation (unknown field "spec.replica").
    • Step 5 fails (no node fits): Pod stays Pending; Event FailedScheduling explains why (Module 04).
    • Step 6 fails (image): ErrImagePull / ImagePullBackOff. In kind the classic cause is forgetting kind load docker-image, or using tag :latest, which defaults imagePullPolicy to Always and makes the kubelet try a registry.
    • Step 7 never completes: container runs but readiness fails → READY 0/1; or the process exits → CrashLoopBackOff.

    4. The Kubernetes API and objects

    Definition. A Kubernetes object is a persistent entity stored in the API that represents part of the cluster's state. The docs call an object a "record of intent": once you create it, the system constantly works to make it exist and match what you described.

    Problem it solves. Instead of a sequence of commands ("start container, then add to load balancer…"), the whole cluster is described as data. Data can be stored in Git, diffed, reviewed, validated and replayed. Every tool (kubectl, Helm, CI, controllers you write) uses the same API.

    Anatomy of an object

    FieldMeaningreliability-api example
    apiVersiongroup/version. Core objects (Pod, Service, ConfigMap, Namespace) have no group, so just v1. Workload controllers live in group apps; Jobs in batch; PodDisruptionBudgets in policy.apps/v1 for the Deployment; v1 for the Service
    kindThe object type (schema). The URL path uses the lower-case plural resource name: kind Deployment ↔ resource deployments.Deployment
    metadata.nameUnique per kind per namespace.reliability-api
    metadata.namespaceWhich namespace (for namespaced kinds).reliability-lab
    metadata.uidUnique ID generated by the server for this incarnation. Delete and recreate → new uid.server-generated
    metadata.labels / annotationsIdentifying key/values for selection / non-identifying metadata (section 7).app.kubernetes.io/name: reliability-api
    metadata.ownerReferencesWho owns this object; used by garbage collection (delete a Deployment → its ReplicaSets and Pods go too).Pod → ReplicaSet → Deployment
    metadata.resourceVersionOpaque version used for optimistic concurrency and watches. Changes on every write.server-generated
    metadata.generation & status.observedGenerationgeneration increments when the spec changes; a controller sets observedGeneration when it has processed that spec. If they differ, the controller has not caught up yet.check during rollouts

    Spec vs status in practice

    The split is not cosmetic. spec is yours; status belongs to controllers. If you copy a manifest out of kubectl get -o yaml and commit it, strip status, metadata.uid, resourceVersion, creationTimestamp, managedFields and the last-applied-configuration annotation — those are server-owned.

    kubectl get deploy reliability-api -o jsonpath='{.spec.replicas} desired, {.status.readyReplicas} ready{"\n"}'
kubectl get deploy reliability-api -o jsonpath='{range .status.conditions[*]}{.type}={.status} ({.reason}){"\n"}{end}'

    5. Declarative vs imperative management

    Imperative: you tell the system what to do ("create this", "scale to 3", "set image"). Declarative: you tell it what you want (a set of files) and let it work out the operations. The official docs list three techniques and warn that an object should be managed using only one technique — mixing them gives undefined behaviour.

    TechniqueExampleOperates onGood forWeakness
    Imperative commandskubectl create deployment reliability-api --image=reliability-api:0.1.0Live objectsLearning, one-off tasksNo review, no audit trail, no record except what is live
    Imperative object configurationkubectl create -f d.yaml, kubectl replace -f d.yamlIndividual filesSimple production usereplace drops fields changed by others; you must know whether to create or replace
    Declarative object configurationkubectl apply -f deploy/kubernetes/Directories of filesProduction, GitOps, CIHarder to reason about merges; needs diff discipline

    How kubectl apply merges: the three-way merge

    Client-side kubectl apply stores the file you applied in the annotation kubectl.kubernetes.io/last-applied-configuration. On the next apply it compares three things: your new file, the live object, and the last-applied configuration. This lets it tell apart "you removed this field from the file" (so delete it) from "someone else, e.g. the HPA, set this field" (so keep it). Maps such as labels are merged; primitive fields are replaced; lists are generally replaced.

    A real trap with reliability-api

    In Module 08 the HPA will own spec.replicas. If your manifest still says replicas: 2, every kubectl apply resets the Deployment to 2 and fights the autoscaler. The common fix is to remove replicas from the manifest once an HPA manages the Deployment. This is a direct consequence of the declarative model: whatever is in your file is what you are declaring you want.

    Preview before you change: diff and server-side dry-run

    kubectl diff -f deploy/kubernetes/                    # what would change? exit 0 = none, 1 = differences, >1 = error
kubectl apply -f deploy/kubernetes/ --dry-run=server  # full server validation + admission, nothing persisted
kubectl apply -f deploy/kubernetes/ --dry-run=client  # only prints what would be sent; no server checks

    --dry-run=server submits the request so it goes through authentication, authorization, admission and validation, but the server does not persist it. It is the honest test of "would this be accepted?". kubectl diff itself uses server-side dry-run to compute the would-be object, so it also shows defaults and mutations the server would add. In CI (Module 09) kubectl diff's exit code is a convenient drift detector.

    Trade-off

    Imperative commands are fastest when exploring (kubectl scale, kubectl set image), and kubectl create deployment … --dry-run=client -o yaml is a great way to generate a starter manifest. But for anything you want to reproduce, the manifest in Git is the source of truth. A hand-run kubectl scale is silently undone at the next apply.

    6. Controllers and the reconciliation loop

    Definition. A controller is a control loop that watches the state of the cluster and makes or requests changes to move the current state closer to the desired state. The official docs use a thermostat analogy: you set the desired temperature; the thermostat repeatedly measures the room and turns heating on or off.

    Problem it solves. Distributed systems fail partially and constantly. A one-shot script that "creates 2 Pods" is wrong the moment a Pod dies. A loop that keeps asking "is reality equal to the spec? if not, take one step closer" handles crashes, deletions, node loss and your own edits with the same code path.

    Important properties

    • Converge, don't script. Each pass takes the next step toward desired state. If something changes mid-way (you edit the spec, a node dies), the next pass simply uses the new facts.
    • Small, focused controllers. The Deployment controller manages ReplicaSets; the ReplicaSet controller manages Pods; the scheduler binds Pods; the kubelet runs containers. None knows the whole story.
    • Never "done". The docs note the cluster may never reach a stable state, and that is fine: as long as controllers run and can make useful changes, the system keeps converging.
    • Status is how controllers talk back. status.conditions and Events are where you read what a controller thinks is going on.
    Reconciliation simulator — the ReplicaSet controller
    Desired state is spec.replicas. Break reality with the buttons and watch the loop converge. Pause the controller to see what happens when kube-controller-manager is down.
    Applied to reliability-api

    The "stray Pod" button models a real gotcha from the ReplicaSet docs: a ReplicaSet acquires any Pod that matches its selector and has no owner. If you kubectl run a debug Pod and give it the label app.kubernetes.io/name=reliability-api plus the hash label, the ReplicaSet counts it and may delete a real replica (or the debug Pod) to get back to 2. Moral: never hand-create Pods with labels that match a controller's selector.

    Self-check: You run kubectl scale deploy/reliability-api --replicas=5, then later kubectl apply -f deployment.yaml (which says 2). What happens and why?
    The Deployment goes back to 2. The manifest declares replicas: 2, and the last-applied annotation also says 2, so apply sets the live value to the file's value. Imperative changes to fields that your manifest owns are overwritten at the next declarative apply.
    Self-check: Who creates the Pod objects for a Deployment — the Deployment controller or the ReplicaSet controller?
    The ReplicaSet controller. The Deployment controller creates and scales ReplicaSets; the ReplicaSet controller creates and deletes Pods to match its own replicas. You can see this in Events: ScalingReplicaSet on the Deployment vs SuccessfulCreate on the ReplicaSet.

    7. Namespaces

    Definition. A namespace is a scope for names inside one cluster. Names must be unique within a namespace (per kind), but not across namespaces. Namespaces are also the unit you attach access control (RBAC), quotas and default policies to.

    Problem it solves. One cluster, many teams/apps/environments: without namespaces every object name would be global and every permission cluster-wide. In this course reliability-api lives in namespace reliability-lab, and the monitoring stack in monitoring, so you can delete or lock down one without touching the other.

    Built-in namespacePurpose
    defaultWhere objects go if you do not specify a namespace. Avoid using it for real work.
    kube-systemObjects created by the Kubernetes system (control-plane static Pods, CoreDNS, kube-proxy, network plugin).
    kube-publicReadable by all clients (including unauthenticated); reserved for cluster-wide public info.
    kube-node-leaseHolds one Lease object per node: the kubelet heartbeats used to detect node failure.

    Do not create namespaces whose names start with kube-; that prefix is reserved. Since v1.22 every namespace automatically carries the immutable label kubernetes.io/metadata.name: <name>, which is handy for NetworkPolicy selectors (Module 05).

    Namespaced vs cluster-scoped

    Most things you deploy (Pods, Deployments, Services, ConfigMaps, Secrets) are namespaced. Some are cluster-scoped: Nodes, PersistentVolumes, StorageClasses, Namespaces themselves, ClusterRoles. Ask the API:

    kubectl api-resources --namespaced=true    # namespaced kinds
kubectl api-resources --namespaced=false   # cluster-scoped kinds

    Working with namespaces

    kubectl create namespace reliability-lab                    # imperative; or apply a Namespace manifest
kubectl get pods -n reliability-lab                         # one namespace
kubectl get pods -A                                         # all namespaces
kubectl config set-context --current --namespace=reliability-lab   # make it your default
kubectl config view --minify | grep namespace:              # verify
    apiVersion: v1
kind: Namespace
metadata:
  name: reliability-lab
  labels:
    app.kubernetes.io/part-of: kubernetes-reliability-lab

    Namespaces also show up in DNS: a Service is reachable as <service>.<namespace>.svc.cluster.local, so reliability-api.reliability-lab.svc.cluster.local. From inside the same namespace, the short name reliability-api is enough (Module 05).

    Failure cases
    • "No resources found in default namespace." — the most common beginner confusion. Your Pods exist; you are looking in the wrong namespace. Use -n reliability-lab or set the context namespace.
    • Namespaces are not a security boundary by themselves. Pods in different namespaces can still talk to each other over the network unless NetworkPolicies say otherwise, and a cluster-admin can do anything everywhere.
    • Deleting a namespace deletes everything in it. That is a feature for cleaning up labs, and a hazard in production.

    8. Labels, selectors and annotations

    Labels are key/value pairs on objects that carry identifying information meaningful to you. Selectors are queries over labels. Annotations are key/value pairs for non-identifying metadata that tools and people read but that you never select on.

    Problem they solve. Kubernetes has no hard-coded "this Pod belongs to that Service" pointer. Membership is computed: a Deployment manages the Pods its selector matches; a Service routes to the ready Pods its selector matches; a PodDisruptionBudget protects the Pods its selector matches. Loose coupling through labels is what lets Pods come and go with random names.

    Label syntax rules

    • Key = optional prefix + / + name. Name: ≤ 63 characters, starts and ends with an alphanumeric, may contain -, _, .. Prefix: a DNS subdomain ≤ 253 characters. The prefixes kubernetes.io/ and k8s.io/ are reserved for Kubernetes core components.
    • Value: ≤ 63 characters, may be empty; if non-empty, starts and ends with an alphanumeric. This is why you cannot put a full Git SHA plus a message into a label — use an annotation.

    Recommended labels

    Kubernetes documents a shared set under the app.kubernetes.io/ prefix so that tools (Helm, dashboards) can understand your objects. We use them for reliability-api:

    LabelMeaningOur value
    app.kubernetes.io/nameName of the applicationreliability-api (also our selector)
    app.kubernetes.io/instanceUnique instance nameHelm sets this to the release name (Module 06)
    app.kubernetes.io/versionCurrent app version"0.1.0" (quoted — YAML would read some versions as numbers)
    app.kubernetes.io/componentComponent within the architectureapi
    app.kubernetes.io/part-ofHigher-level applicationkubernetes-reliability-lab
    app.kubernetes.io/managed-byTool managing itkubectl now, Helm later

    Selector types

    TypeCLI syntax (-l)YAML formSupported by
    Equality-basedapp.kubernetes.io/name=reliability-api, tier!=frontendmatchLabels: {key: value}Everything, including Services (Services support only this, as a plain map under spec.selector)
    Set-based'env in (dev,qa)', 'tier notin (cache)', partition (exists), '!partition' (does not exist)matchExpressions: [{key, operator: In|NotIn|Exists|DoesNotExist, values}]Deployments, ReplicaSets, Jobs, DaemonSets, and other newer resources

    Comma means AND: -l 'app.kubernetes.io/name=reliability-api,app.kubernetes.io/version=0.1.0' selects only Pods with both labels. There is no OR across different keys; use set-based in for OR over values of one key.

    Label selector playground
    Type a selector in kubectl -l syntax. Matching Pods light up. Supports =, ==, !=, in (…), notin (…), key (exists) and !key. Comma = AND.

    Annotations

    Annotations hold arbitrary non-identifying data: build info (Git SHA, CI run URL), tool configuration, ownership contacts, change reasons. Keys follow the same prefix/name rules as labels, but values can be large structured strings. Examples you will meet in this course:

    • kubernetes.io/change-cause — copied into kubectl rollout history as CHANGE-CAUSE (Module 04).
    • kubectl.kubernetes.io/last-applied-configuration — written by client-side kubectl apply (section 5).
    • deployment.kubernetes.io/revision — set by the Deployment controller on ReplicaSets.
    • Tool-specific keys from Helm, Prometheus operators, ingress controllers etc. — always check the tool's docs.
    Rule of thumb

    If you will ever select on it → label (short, stable). If you only want to record it → annotation. Labels on Pods that change every build (like a Git SHA) are fine on the Pod template, but never put them in a Deployment's selector — selectors in apps/v1 are immutable.

    Failure case: the selector/label mismatch

    A Service whose selector says app: reliability-api while Pods carry app.kubernetes.io/name: reliability-api matches nothing. The Service exists, has a ClusterIP, and returns connection errors because it has no endpoints. Diagnose with kubectl get endpointslices -l kubernetes.io/service-name=reliability-api and kubectl get pods --show-labels. (For Deployments the API server rejects a selector that does not match the template labels — see Lab 3.)

    9. Pods

    Definition. A Pod is the smallest deployable unit in Kubernetes: a group of one or more containers that share network and storage and are always scheduled together on the same node. The docs describe a Pod as an application-specific "logical host".

    Problem it solves. Some processes are so tightly coupled they must live together: a web server plus a helper that refreshes its files, or an app plus a proxy. If they were separate scheduling units they might land on different machines. The Pod is the unit of co-location, shared fate and shared networking.

    How a Pod works

    1. Sandbox first. The kubelet asks the runtime to create a Pod sandbox: the network namespace (with an IP from the network plugin) and other shared namespaces. The Pod condition PodReadyToStartContainers becomes True when the sandbox and networking are ready. Many runtimes implement the sandbox with a hidden "pause" container; the Pod-lifecycle docs mention the kubelet cleaning it up "if that container runtime uses one".
    2. Init containers run one at a time, in order, each to successful completion, before any app container starts. If one fails, the kubelet retries it (unless the Pod's restartPolicy is Never). kubectl get pods shows progress as Init:0/2, Init:1/2. Init containers do not support liveness/readiness/startup probes.
    3. App containers start. Each has its own image, command, env, resources and probes.
    4. Sidecars are init containers with restartPolicy: Always (stable since v1.29). They start before the app containers, keep running alongside them, and are stopped after the main containers during termination.

    Pods are ephemeral — don't create them directly

    A Pod is bound to one node for its whole life. If the node dies, the Pod is gone; it is never "moved". Replacement means a new Pod with a new name and new IP, created by a controller. This is why the docs say Pods are usually not created directly; you create a Deployment (stateless), StatefulSet (stable identity), Job (run-to-completion) or DaemonSet (one per node). Note also that restarting a container is not the same as replacing the Pod: a liveness failure restarts the container in place (same Pod name, same IP, restart count +1).

    This Pod demonstrates three facts at once: the init container runs first; the sidecar reaches the app on localhost; and both share a volume.

    Failure cases & diagnosis
    • Init:CrashLoopBackOff — an init container keeps failing; app containers never start. kubectl logs <pod> -c prepare.
    • Port clash — two containers in one Pod both binding 8000 fail exactly like two processes on one host (shared port space). The second gets "address already in use".
    • Wrong container in logs/exec — with several containers, kubectl logs picks a default; always pass -c reliability-api.
    • Over-packing a Pod — putting the API and a database in one Pod forces them to scale together and die together. Use separate workloads unless they are truly coupled.

    10. ReplicaSet

    Definition. A ReplicaSet maintains a stable set of replica Pods: it has a selector (which Pods it counts), a replicas number, and a Pod template (what to create when it needs more).

    Problem it solves. "Keep N identical copies alive." It is the controller that recreates a Pod you delete.

    How it works. Each loop iteration it counts Pods that match its selector and are not terminating. Too few → create from template. Too many → delete some. Pods it creates get metadata.ownerReferences pointing back to it; it also acquires matching Pods that have no owner (the stray-Pod trap). The official docs recommend using Deployments instead of creating ReplicaSets directly, because a ReplicaSet never updates existing Pods when you change its template — it only uses the template for new Pods.

    Self-check: You edit a ReplicaSet's template to use image 0.2.0. What happens to its two running Pods?
    Nothing. A ReplicaSet only uses its template to create new Pods. The existing 0.1.0 Pods keep running until something deletes them. This is exactly the gap the Deployment fills: it creates a new ReplicaSet for the new template and shifts replicas across gradually.

    11. Deployment

    Definition. A Deployment declares a desired set of interchangeable Pods and manages them through ReplicaSets, providing declarative updates (rolling updates), rollout status, history and rollback.

    Problem it solves. ReplicaSets keep N copies alive but cannot change them. A Deployment adds versioning: every change to the Pod template creates a new ReplicaSet (a new revision), and the Deployment controller scales the new one up and the old one down according to its strategy. Scaling alone (changing replicas) does not create a new revision.

    How it works (summary; rollout mechanics are in Module 04).

    1. Hash the Pod template → pod-template-hash. Find the ReplicaSet with that hash or create it.
    2. If there are older ReplicaSets with Pods, move replicas from old to new within maxSurge/maxUnavailable, waiting for new Pods to become available.
    3. Keep up to revisionHistoryLimit (default 10) old ReplicaSets at 0 replicas so kubectl rollout undo can scale one back up.
    4. Report progress in status.conditions (Available, Progressing), and mark the rollout failed if no progress is made within progressDeadlineSeconds (default 600).

    1apiVersion: apps/v1Deployments live in API group apps, version v1 (stable).
    2kind: DeploymentSelects the Deployment schema and the Deployment controller.
    3metadata.nameUnique within the namespace. ReplicaSets and Pods derive their names from it (reliability-api-<hash>-<suffix>).
    4metadata.namespacePins the object to reliability-lab regardless of your kubectl context. Omit it if you prefer to choose the namespace at apply time (-n); do not mix both styles.
    5metadata.labelsLabels on the Deployment object itself (for kubectl get deploy -l … and tooling). They do not affect which Pods it manages.
    6kubernetes.io/change-causeAnnotation copied into the new revision and shown as CHANGE-CAUSE in kubectl rollout history. Update it with each change. (The old --record flag is deprecated.)
    7spec.replicas: 2Desired number of Pods. Defaults to 1 if omitted. Two gives you one spare during crashes and rollouts. Remove this field once an HPA manages scaling (Module 08).
    8revisionHistoryLimit: 10How many old ReplicaSets to keep for rollback. 10 is the default; written explicitly here for teaching. Setting 0 makes rollback impossible.
    9spec.selectorWhich Pods this Deployment owns. Must match the template labels (12) or the API rejects the object. Immutable in apps/v1: to change it you must delete and recreate the Deployment. Keep it minimal and stable — just the app name.
    10strategyRollingUpdate (default) or Recreate. With only 2 replicas, the defaults (25%/25%) give maxSurge = ceil(0.5) = 1 and maxUnavailable = floor(0.5) = 0. We write those values explicitly so the intent is visible: add one new Pod, never go below 2 available. Module 04 explains the arithmetic.
    11spec.templateA full Pod spec plus metadata. Any change here (image, env, probes, labels) creates a new revision and triggers a rollout.
    12template.metadata.labelsLabels every Pod gets. Must include the selector labels. Extra labels (version, component) are allowed and useful for queries and dashboards, but keep them out of the selector.
    13terminationGracePeriodSeconds: 30Time between SIGTERM and SIGKILL when a Pod is deleted. 30 is the default; shown explicitly because Module 04's graceful shutdown depends on it.
    14containers[].name: reliability-apiContainer name used by kubectl logs -c reliability-api, exec -c reliability-api, and in events. Must be unique within the Pod.
    15imageThe image built in Module 02. In CI it becomes ghcr.io/<you>/reliability-api:<git-sha>. Never use :latest for anything you want to roll back.
    16imagePullPolicy: IfNotPresentUse the image already on the node if present. Essential with kind, where you kind load the image instead of pushing it. If the tag is :latest or omitted, the default becomes Always, which fails in kind for local-only images.
    17ports[].name: http, containerPort: 8000Informational for the container port (it does not open or publish anything — the app already listens on 0.0.0.0:8000), but naming it lets probes and Services refer to http instead of a number.
    18envThe three app settings. READY_DELAY_SECONDS: "5" simulates warm-up so readiness is observable. Values must be strings — quote them. Module 05 moves these into ConfigMap reliability-api-config.
    19resourcesRequests are what the scheduler reserves (100m CPU = 0.1 core, 128Mi memory). Memory limit 256Mi caps a leak (OOMKill). No CPU limit, deliberately — Module 04 discusses the throttling trade-off.
    20readinessProbeKubelet calls GET /ready every 5 s; Pod receives Service traffic only while it passes. With 5 s warm-up, a new Pod becomes Ready after ~5–10 s.
    21livenessProbeGET /health every 10 s; 3 consecutive failures (each allowed 2 s) → container restart. Deliberately not /ready: a warming-up or overloaded Pod should be taken out of rotation, not killed. Full analysis in Module 04.

    What the API server adds (defaults)

    Run kubectl get deploy reliability-api -o yaml after applying and compare with your file. You will see fields you did not write: progressDeadlineSeconds: 600, minReadySeconds absent (0), restartPolicy: Always, dnsPolicy: ClusterFirst, schedulerName: default-scheduler, terminationMessagePath, probe defaults (successThreshold: 1, timeoutSeconds: 1 on readiness) and more. That is the API server's defaulting. It is why kubectl diff against a live object is more trustworthy than eyeballing YAML.

    Trade-offs

    • Deployment vs bare Pod: always Deployment for long-running stateless services; bare Pods only for throwaway debugging.
    • Deployment vs StatefulSet: reliability-api is stateless (no local data, any replica can serve any request), so Deployment. Databases needing stable identity/storage use StatefulSets (Module 04 overview).
    • Explicit vs default fields: writing defaults explicitly (like revisionHistoryLimit) documents intent but adds noise. We do it here for teaching; in your repo, be explicit about anything reliability-critical (strategy, probes, resources, grace period).

    kubectl is just an HTTP client for the API server. It reads ~/.kube/config (or $KUBECONFIG) for the cluster URL, credentials, and current context/namespace. kind created the context kind-reliability-lab for you.

kubectl exec reliability-api-multi -c poller -- ip addr show eth0
    4. Clean up: kubectl delete pod reliability-api-multi.

    Glossary

    Cluster
    A control plane plus one or more nodes that run Pods.
    Control plane
    kube-apiserver, etcd, kube-scheduler, kube-controller-manager (and optionally cloud-controller-manager): stores state and makes global decisions.
    Node
    A machine (VM, physical, or in kind a Docker container) running kubelet, a container runtime and usually kube-proxy.
    kubelet
    Node agent that makes the containers described by Pods bound to its node actually run, runs probes and reports status.
    CRI
    Container Runtime Interface: the gRPC API between kubelet (client) and runtime (server, e.g. containerd).
    Object
    A persistent record of intent in the API, with metadata, spec (desired) and status (observed).
    Resource vs kind
    Kind is the type name (Deployment); resource is the API path name (deployments).
    Controller
    A control loop that moves actual state toward desired state for some kinds of objects.
    Reconciliation
    The repeated observe → diff → act cycle a controller performs.
    Declarative
    You describe the desired end state (files + apply); the system works out operations.
    Namespace
    A naming and policy scope inside a cluster.
    Label / selector
    Identifying key/value metadata / a query over labels used to define membership.
    Annotation
    Non-identifying key/value metadata for tools and humans; not selectable.
    Pod
    Smallest deployable unit: one or more containers sharing network namespace and volumes, scheduled together.
    Pod sandbox / pause
    The runtime's holder of a Pod's shared namespaces; many runtimes use a tiny "pause" container.
    Init container
    Runs to completion, in order, before app containers start.
    Sidecar container
    An init container with restartPolicy: Always; runs alongside the app for the Pod's life.
    Static Pod
    A Pod defined by a file on a node and run directly by that node's kubelet (how kind/kubeadm run the control plane).
    ReplicaSet
    Keeps N Pods matching a selector running.
    Deployment
    Manages ReplicaSets to give declarative, versioned, rolling updates and rollback.
    ownerReferences
    Metadata linking a child to its owner; drives garbage collection and adoption.
    pod-template-hash
    Label the Deployment controller adds to each ReplicaSet and its Pods to keep revisions apart.
    generation / observedGeneration
    Spec version counter / the generation a controller has acted on.
    Server-side dry run
    A request fully validated and admitted by the API server but not persisted.

    Self-check

    1. Name the five control-plane components and the three node components, with one sentence each.
    kube-apiserver (HTTP API front door, the only etcd client), etcd (consistent key-value store of all cluster data), kube-scheduler (binds unscheduled Pods to nodes), kube-controller-manager (runs built-in control loops), cloud-controller-manager (optional cloud integrations). Node: kubelet (runs Pods' containers via CRI, probes, status), kube-proxy (optional; programs Service networking rules), container runtime (containerd/CRI-O: actually runs containers).
    2. etcd becomes unavailable for two minutes. What do users of reliability-api notice?
    Probably nothing for requests already being served: Pods keep running and existing networking rules stay in place. But the API cannot persist changes, so nothing new happens: no scaling, no rollouts, no replacement Pods, probe-driven readiness changes cannot be recorded, and kubectl fails. If a Pod crashes during that window, the kubelet can still restart its container locally, but a lost Pod cannot be replaced.
    3. Put these in order for kubectl apply of a new Deployment: scheduler binds, ReplicaSet created, etcd write, Pod objects created, kubelet starts container, admission.
    Admission → etcd write → ReplicaSet created (Deployment controller) → Pod objects created (ReplicaSet controller) → scheduler binds → kubelet starts container (via CRI).
    4. What is the difference between spec and status, and why should status never be in your Git manifests?
    spec is desired state written by you; status is observed state written by controllers. Status in Git is meaningless (it describes a past moment) and it is ignored/overwritten by the system; including it only adds noise and confusion.
    5. Why does a Deployment-managed ReplicaSet not adopt a Pod that only has app.kubernetes.io/name: reliability-api?
    Its selector also requires pod-template-hash=<hash>, which the Deployment controller adds. A Pod without that label does not match, so it is not counted or adopted.
    6. A Service has selector app: reliability-api; Pods have app.kubernetes.io/name: reliability-api. What happens and how do you prove it?
    The Service selects zero Pods, so it has no endpoints and requests fail. Prove with kubectl get endpointslices -l kubernetes.io/service-name=reliability-api (no addresses) and kubectl get pods --show-labels. Unlike Deployments, the API cannot reject this because a Service selecting nothing is valid.
    7. When would you use an annotation instead of a label? Give two reliability-api examples.
    When the data is not used for selection, or is too long/irregular for label value rules. Examples: kubernetes.io/change-cause describing a rollout; the CI run URL or full Git commit message that produced the image.
    8. Two containers in one Pod. Can container B reach container A at localhost:8000? Can they both listen on port 8000?
    Yes to the first: they share the Pod's network namespace. No to the second: they share one port space, so the second bind fails with "address already in use".
    9. Why are Pods "not moved" when a node fails?
    A Pod is bound to a node for its whole life. When a node is lost, its Pods are lost; the owning controller (ReplicaSet) sees fewer matching Pods and creates new Pods, with new names and IPs, which the scheduler places on healthy nodes.
    10. What does --dry-run=server catch that --dry-run=client does not?
    Everything the API server checks: authentication and RBAC, admission (mutating and validating, including policies and webhooks), schema and strict field validation, immutability rules, selector/label consistency. Client dry-run just prints the object kubectl would send.
    11. You changed only replicas from 2 to 3. Is that a new revision? What about changing LOG_LEVEL?
    Scaling is not a new revision: the same ReplicaSet just scales. Changing an env var changes the Pod template, so the Deployment creates a new ReplicaSet (new pod-template-hash) and performs a rolling update.
    12. In kind, why does image: reliability-api:latest without a pull policy fail while :0.1.0 works?
    For the :latest tag (or no tag) the default imagePullPolicy is Always, so the kubelet tries to pull from a registry where the image does not exist. With a specific tag the default is IfNotPresent, and the image you kind load-ed is used.
