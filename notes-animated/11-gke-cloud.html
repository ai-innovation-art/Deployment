    Google Cloud resource hierarchy, billing and APIs

    Definition. Every Google Cloud resource (a GKE cluster, a disk, a bucket, an Artifact Registry repository) belongs to exactly one project. Projects can be grouped under folders, and folders sit under an organization node (which exists if you use Google Workspace or Cloud Identity; a personal account usually has projects with no organization). The official docs describe four tiers: organization, folders, projects, and service resources.

    Problem it solves. Without a hierarchy you could not answer three basic operational questions: who may touch this? (IAM is attached to nodes of the tree and inherited downward), who pays for this? (a project is linked to one billing account), and how do I delete everything from this experiment? (shutting down a project removes the resources inside it).

    How it works, step by step

    1. Create a project. You pick a globally unique project ID (e.g. reliability-lab-1234), which can never be changed. Google assigns a numeric project number. The display name is just a label you can edit. Most gcloud commands take the ID; some identity strings (Workload Identity principals) use the number.
    2. Link a billing account. Until a project is linked to an active billing account, billable APIs such as GKE cannot be used. The billing account is a separate resource with its own IAM (Billing Account Administrator/User).
    3. Enable APIs. Each Google Cloud service is an API that must be enabled per project before use: for this module, container.googleapis.com (GKE), artifactregistry.googleapis.com, and later iam.googleapis.com, iamcredentials.googleapis.com, sts.googleapis.com for federation. Enabling an API is free; using it may not be.
    4. Create resources inside the project. They inherit IAM from the project, folder and organization.
    5. Delete. Deleting individual resources stops their charges. Shutting down the whole project is the strongest cleanup (it schedules everything inside for deletion), which is why we use a dedicated project per lab.
    Applied to reliability-api

    Create one project just for this course, e.g. reliability-lab-<random4>. Put the GKE cluster, the Artifact Registry repository reliability, and (in the Terraform lab) the state bucket inside it. Label everything app=reliability-api, env=lab, owner=<you>. When the course ends, deleting this single project is your final safety net.

    Trade-offs. One project per environment/experiment gives clean isolation and trivial cleanup, at the cost of re-enabling APIs and re-granting IAM each time (which Terraform makes cheap). One shared project is convenient but makes "what is this disk and who created it?" hard to answer.

    Self-check: why do Workload Identity principal strings use the project number while gcloud mostly uses the project ID?
    The ID is a human-chosen name; the number is the stable, system-assigned identifier. IAM principal identifiers for federation pools are defined in terms of projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/…, so you must look up the number (gcloud projects describe PROJECT_ID --format='value(projectNumber)').

    IAM: principals, roles, service accounts, least privilege

    Definition. Identity and Access Management answers "who can do what on which resource". The who is a principal: a human (Google Account, Google group, federated workforce identity) or a workload (a service account, or a workload identity pool identity). The what is a role, a named bundle of permissions such as roles/artifactregistry.writer. The binding of principals to a role on a resource is stored in that resource's allow policy.

    Problem it solves. A Kubernetes cluster you can reach is also a cluster an attacker can reach with your credentials. IAM lets you give the CI pipeline only "push images", give the running Pod only "read this bucket", and keep "delete the cluster" for yourself.

    Role types

    TypeExamplesUse
    Basicroles/owner, roles/editor, roles/viewerHighly permissive, across services. OK for you in a throwaway lab project; avoid for service accounts and production.
    Predefinedroles/container.developer, roles/artifactregistry.reader, roles/artifactregistry.writer, roles/storage.objectViewerMaintained by Google per service. Your default choice.
    Customyour own list of permissionsWhen no predefined role is narrow enough. Higher maintenance.

    Service accounts

    A service account is an identity for software, with an email like gke-nodes@PROJECT_ID.iam.gserviceaccount.com. Two facts matter for GKE:

    • Node service account. GKE nodes run as a service account (by default the Compute Engine default service account, unless you pass --service-account at creation, which the docs recommend and which cannot be changed later). Nodes use it to pull images from Artifact Registry and write logs/metrics. If image pulls fail with 403, this account usually lacks roles/artifactregistry.reader on the repository.
    • Workload identity. Your Pods should not borrow the node's identity. They get their own via Workload Identity Federation for GKE (covered below).
    Never download service account keys for this course

    A JSON key file is a long-lived password. It ends up in a repo, a Docker layer, or a CI secret and stays valid until someone revokes it. Everything in this module (Pods → Google APIs, GitHub Actions → Google Cloud) is done with federation instead: short-lived tokens, no key files.

    Failure cases

    • PERMISSION_DENIED / HTTP 403: the message names the missing permission (e.g. artifactregistry.repositories.uploadArtifacts). Find which role contains it, grant it at the narrowest scope. Inspect current bindings with gcloud projects get-iam-policy PROJECT_ID or gcloud artifacts repositories get-iam-policy reliability --location=REGION.
    • "It works for me but not in CI": you are Owner, CI is not. Always test with the CI identity's roles.
    • IAM changes are eventually consistent; a grant can take a short while to take effect. Retry before re-granting.
    Self-check: a colleague suggests giving the CI service account roles/editor "to stop permission errors". What do you answer?
    Editor is a basic role that grants write access to almost every service in the project, so a compromised workflow could delete clusters or read data. CI only needs to push images: grant roles/artifactregistry.writer on the single repository, and use Workload Identity Federation so no key exists to steal.

    Regions, zones and cluster location

    Definition. A region is a geographic location (e.g. us-central1, europe-west1, asia-south1). Each region contains several zones (us-central1-a, -b, -c, …), which are isolated failure domains. Resources are zonal (a VM, a zonal persistent disk), regional (an Artifact Registry repo, a regional cluster's control plane), or global.

    Problem it solves. A single zone can fail. Spreading control plane replicas and nodes across zones lets the service survive a zone outage — at the cost of more resources and cross-zone traffic.

    How to choose for reliability-api

    • Region: pick one close to you, with the services you need, and check its prices (Autopilot prices are per region). Use the same region for the cluster and the Artifact Registry repository, so image pulls stay in-region.
    • Autopilot: always regional, so you do not choose zonal vs regional. Spread the 2 replicas of reliability-api across zones with topologySpreadConstraints (Module 04) if you want to test zone-level resilience.
    • Standard: a zonal cluster is cheapest for learning; regional is what the docs recommend for production. Remember cross-zone node-to-node traffic is billed.

    SLA context (from the GKE pricing page, read 29 Oct 2026): 99.95% for the control plane of Autopilot clusters and regional Standard clusters; 99.5% for the control plane of zonal Standard clusters; 99.9% for Autopilot Pods in multiple zones. An SLA is a commercial promise about the platform — your app's SLO (Module 07) still depends on your probes, replicas and rollout settings.

    VPC basics for GKE

    Definition. A VPC network is a global, private software-defined network in your project. It contains regional subnets, each with a primary IPv4 range and optional secondary ranges. Firewall rules (or policies) allow/deny traffic to VM interfaces by direction, protocol/port, source/destination range, tags or service accounts.

    Problem it solves. Pods need routable IPs that do not collide with anything else in your network, and you need a place to control what can reach the nodes.

    VPC-native clusters. "VPC-native is the default network mode for all new clusters". They use alias IP ranges:

    • Subnet primary range → nodes. Each node VM gets its IP from here.
    • Secondary range → Pods. Each node receives a slice (alias range) of the Pod range; Pod IPs are therefore real VPC addresses, routable from the VPC and peered networks, and reserved before Pods are created.
    • Services → ClusterIPs. Either a GKE-managed range (34.118.224.0/20 per the docs) or a secondary range you supply.

    Applied to reliability-api

    For the labs you can let Autopilot use the default VPC and auto-created ranges. In the Terraform section we create a dedicated reliability-vpc and subnet with named secondary ranges pods and services, so the address plan is explicit and reviewable in a plan.

    Failure cases

    • Pods stuck Pending with IP exhaustion events: the Pod secondary range is too small for the node count × per-node alias range. Fix by adding ranges or planning bigger ones; you cannot shrink a primary range after creation.
    • Overlapping CIDRs with a peered network or VPN: traffic silently goes to the wrong place. Plan ranges before creating the cluster.
    • LoadBalancer Service has an IP but connections hang: check firewall rules and that the Pods are Ready (Module 05 EndpointSlices).
    Self-check: why is "Pod IPs are real VPC addresses" useful, and what is the price?
    Other VPC resources (and Google load balancers using container-native NEGs) can reach Pods directly without node-level NAT hops, and IPs are reserved before Pods start, avoiding conflicts. The price is IP planning: Pod ranges consume VPC address space and must be sized up front.

    GKE architecture

    Definition. GKE is Google's managed Kubernetes. Per the GKE overview: "In GKE, Google Cloud manages the control plane and system components for you", and in Autopilot "Google Cloud also manages your worker nodes". Nodes are Compute Engine VMs; your workloads are ordinary Pods.

    Problem it solves. Running etcd, the API server, upgrades and security patches yourself is a full-time job. GKE turns the control plane into a service with an SLA so you can concentrate on workloads.

    Node pools

    A node pool is a group of nodes with identical configuration (machine type, disk, image, labels, taints, autoscaling bounds). In Standard mode you create pools explicitly: e.g. a small general-purpose pool for reliability-api and a separate GPU pool, tainted so only inference Pods land there (Module 12). Pools let you upgrade, resize or replace one class of nodes without touching another. In Autopilot you express needs in the Pod spec instead (resource requests, compute classes, accelerators), and GKE creates appropriate nodes.

    Failure cases specific to managed clusters

    • Automatic upgrades drain nodes. If reliability-api lacks a PodDisruptionBudget, readiness probe or graceful shutdown (Module 04), users see errors during routine maintenance. Configure maintenance windows and PDBs.
    • Deprecated APIs removed in a new minor version break old manifests. Run helm template output through your tests against the target version before the channel upgrades you.
    • Autopilot rejects or mutates Pods that violate its rules (privileged containers, host access, resource ratios). Read the admission error in kubectl describe / the apply output.

    Billing gotcha worth memorising

    Autopilot bills Pods "that have been scheduled to a node and have resources allocated to them. This includes Pods in the Running phase, as well as Pods in error or retry loops (such as ImagePullBackOff or CrashLoopBackOff)." Pending (unscheduled) and successfully terminated Pods are not billed, nor are unmodified system DaemonSets. A crash-looping reliability-api is therefore still costing money.

    Requests are now money: an estimator

    On Autopilot, the numbers you set in resources.requests (Module 04) become the bill. reliability-api requests cpu: 100m and memory: 128Mi. Depending on the cluster's bursting support, Autopilot's general-purpose minimums are 50m CPU / 52 MiB (with bursting) or 250m / 512 MiB (without), and CPU is rounded to 0.25 vCPU steps when bursting is not supported — so always check what Autopilot actually set on the Pod (kubectl get pod … -o yaml, look at resources and annotations).

    Autopilot cost estimator (general-purpose Pods)
    Default unit prices are what the GKE pricing page showed for us-central1 on 29 Oct 2026 (vCPU $0.0445/h, memory $0.0049225/GiB-h, ephemeral $0.0001389/GiB-h). Replace them with the current prices for your region. This ignores load balancers, logs, disks and egress.

    Which mode for this course?

    Use Autopilot for the labs: no node pools to forget, per-Pod billing means two tiny reliability-api Pods cost very little, and the cluster fee for one cluster is covered by the free-tier credit (verify on the current pricing page). Use Standard only if you specifically want to practise node-pool and cluster-autoscaler operations — and then use a small zonal cluster and delete it the same day.

    Self-check: reliability-api enters CrashLoopBackOff on Autopilot overnight. Are you billed for it? On Standard?
    On Autopilot yes — Pods in error/retry loops that are scheduled and have resources allocated are billed per request. On Standard you pay for the node VMs regardless of what Pods do; the crash loop does not change the node bill, but the nodes would be billed even if every Pod were healthy or deleted.

    Release channels and versions

    Definition. A release channel is a subscription that decides which GKE versions your cluster gets and how fast automatic upgrades arrive.

    ChannelIntent (from the docs)Use it for

    Regular (default)Features soon after GA, qualified for longer; "what we recommend for most users"this course

    Why it matters for reliability. Auto-upgrades are routine disruptions: nodes are drained and Pods rescheduled. Your Module 04 work (readiness probes, PDB minAvailable: 1, graceful SIGTERM handling, 2+ replicas) is exactly what keeps reliability-api available through them. Use maintenance windows/exclusions to control when they happen.

    Artifact Registry: storing reliability-api images

    Definition. Artifact Registry is Google Cloud's package and container registry. A repository has a format (docker), a location (region or multi-region) and its own IAM policy.

    Problem it solves. GKE nodes must pull your image from somewhere reachable, authenticated, and ideally close by. Pulling from a same-region repository is fast and keeps traffic inside Google Cloud; IAM on the repo controls who can push and pull.

    Image path anatomy

    LOCATION-docker.pkg.dev/PROJECT-ID/REPOSITORY/IMAGE:TAG
us-central1-docker.pkg.dev/reliability-lab-1234/reliability/reliability-api:3f9c2ab
└── host per location ─────┘ └── project ────────┘ └ repo ───┘ └ image ───────┘ └ git sha

    How a push works

    1. gcloud services enable artifactregistry.googleapis.com
    2. gcloud artifacts repositories create reliability --repository-format=docker --location=us-central1
    3. gcloud auth configure-docker us-central1-docker.pkg.dev — adds a credential helper entry to ~/.docker/config.json so docker push obtains short-lived tokens from your gcloud login.
    4. docker tag the local image with the full path, then docker push.
    5. Pullers need roles/artifactregistry.reader; pushers need roles/artifactregistry.writer (on the repo is narrowest).
    Architecture mismatch

    If you build on an Apple Silicon Mac, a plain docker build produces an arm64 image. GKE nodes are usually amd64, so the Pod fails with exec format error. Build with docker buildx build --platform linux/amd64 … (or multi-arch) — or let CI on an amd64 runner build it.

    Workload Identity Federation for GKE (Pods → Google APIs)

    Definition. A mechanism that lets a Kubernetes ServiceAccount (KSA) act as an IAM principal, so code in a Pod can call Google APIs (Cloud Storage, Pub/Sub, …) with short-lived tokens and no key file. The cluster's workload identity pool is PROJECT_ID.svc.id.goog. In Autopilot, "Workload Identity Federation for GKE is always enabled".

    Problem it solves. Before it existed, Pods either used the node's service account (every Pod on the node got the same, usually broad, permissions) or mounted a JSON key from a Secret (long-lived, leak-prone). Workload Identity gives each workload its own identity, scoped by namespace and KSA name.

    Principal identifier for one KSA (verbatim format from the docs):

    principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/NAMESPACE/sa/SERVICEACCOUNT
    Step through: how a Pod gets a Google token

    ProsNo extra service account; fewer moving partsWorks with APIs that do not accept federated principals; reuse existing GSA permissions
    ConsSome APIs/features have limitations (see docs)Extra object and an extra exchange step

# then set spec.template.spec.serviceAccountName: reliability-api in the Deployment (Helm value)

    Failure cases

    • 403 from the API: principal string typo (project ID vs number, namespace or KSA name), Pod not actually using the KSA (kubectl get pod -o jsonpath='{.spec.serviceAccountName}'), or IAM propagation delay.
    • App uses a key file instead: an env var such as GOOGLE_APPLICATION_CREDENTIALS left from local development overrides metadata-based credentials. Remove it in the cluster.
    • Standard cluster without Workload Identity enabled on cluster or node pool: Pods get the node identity. Enable with --workload-pool=PROJECT_ID.svc.id.goog.

    Workload Identity Federation for GitHub Actions (no long-lived keys)

    Definition. GitHub Actions can mint an OIDC ID token for each workflow run, signed by GitHub and describing the repo, ref, actor, etc. A Google Cloud workload identity pool provider trusts that issuer (https://token.actions.githubusercontent.com), maps token claims to attributes, and enforces an attribute condition. The workflow exchanges the GitHub token for a short-lived Google token.

    Problem it solves. Module 09 pushed to GHCR using GITHUB_TOKEN. To push to Artifact Registry you need a Google credential. The old way was a service account JSON key in a GitHub secret — exactly the long-lived key we refuse to create. Federation means nothing secret is stored in GitHub at all.

    Setup (one time, from the official auth action README)

    export GITHUB_ORG=<your-github-user-or-org>
export REPO="$GITHUB_ORG/kubernetes-reliability-lab"
gcloud services enable iam.googleapis.com iamcredentials.googleapis.com sts.googleapis.com

gcloud iam workload-identity-pools create "github" \
  --project="${PROJECT_ID}" --location="global" \
  --display-name="GitHub Actions Pool"

gcloud iam workload-identity-pools providers create-oidc "reliability-repo" \
  --project="${PROJECT_ID}" --location="global" \
  --workload-identity-pool="github" \
  --display-name="reliability-lab repo" \
  --attribute-mapping="google.subject=assertion.sub,attribute.actor=assertion.actor,attribute.repository=assertion.repository,attribute.repository_owner=assertion.repository_owner" \
  --attribute-condition="assertion.repository_owner == '${GITHUB_ORG}'" \
  --issuer-uri="https://token.actions.githubusercontent.com"

export POOL_ID=$(gcloud iam workload-identity-pools describe github \
  --project="$PROJECT_ID" --location=global --format='value(name)')
gcloud artifacts repositories add-iam-policy-binding reliability \
  --location="$REGION" --role=roles/artifactregistry.writer \
  --member="principalSet://iam.googleapis.com/${POOL_ID}/attribute.repository/${REPO}"
    Harden the condition

    Google's deployment-pipeline guide warns that name-based claims (repository, repository_owner) are exposed to cybersquatting/typosquatting and recommends mapping the numeric *_id claims; you can also restrict to a branch, e.g. assertion.repository_owner=='ORG' && assertion.ref=='refs/heads/main'.

    permissions:
  contents: 'read'
  id-token: 'write'          # allow the job to request the OIDC token
jobs:
  push:
    runs-on: ubuntu-latest
    steps:
      - uses: 'actions/checkout@v7'
      - uses: 'google-github-actions/auth@v3'
        with:
          project_id: 'reliability-lab-12345'
          workload_identity_provider: 'projects/123456789/locations/global/workloadIdentityPools/github/providers/reliability-repo'
      - uses: 'google-github-actions/setup-gcloud@v3'
      - run: gcloud auth configure-docker us-central1-docker.pkg.dev --quiet
      - run: |
          IMAGE=us-central1-docker.pkg.dev/reliability-lab-12345/reliability/reliability-api:${GITHUB_SHA::7}
          docker build -t "$IMAGE" .
          docker push "$IMAGE"

    Action versions above match the READMEs as of 29 Oct 2026; pin to the current major (or a commit SHA) when you copy them. If a Google API you call does not accept direct federated principals, pass service_account: to the auth action to impersonate a service account instead, and grant the principal set roles/iam.workloadIdentityUser on it.

    Failure cases

    • Unable to get ACTIONS_ID_TOKEN_REQUEST_URL / no token: missing id-token: write permission (or a fork PR where it is not granted).
    • The given credential is rejected by the attribute condition: the condition does not match the token (wrong owner name, branch restriction).
    • Permission … denied on push: the principalSet string or role binding is wrong (pool full name uses the project number).
    • Long jobs fail late: derived credentials share the short OIDC token lifetime noted in the auth README; authenticate close to where you need it.

    In kind you reached the app with kubectl port-forward. On GKE you have three options, with very different cost and capability:

    Prerequisites and health checks

    Regional external managed load balancers need a proxy-only subnet in the region; the GKE Gateway docs explain how to create it. Google load balancers health-check your Pods; GKE can derive the check from the readiness probe or you can set a HealthCheckPolicy. If the LB marks backends unhealthy, compare its health-check path/port with /ready on 8000.

    Failure cases

    • EXTERNAL-IP stays <pending>: quota, missing permissions, or invalid annotations — kubectl describe svc events.
    • Gateway has no address: kubectl describe gateway reliability-gw conditions (Accepted, Programmed), missing proxy-only subnet, wrong class name.
    • 502 from the LB: backends unhealthy (readiness failing, health check on wrong port) — see Module 05/13 playbooks.
    Self-check: you need to demo reliability-api to a teammate for 10 minutes. Which option and why?
    Port-forward (or a short-lived LoadBalancer Service that you delete immediately). Port-forward costs nothing and exposes nothing publicly; a Gateway is overkill for a demo and keeps billing until deleted.

    Cloud Logging, Cloud Monitoring and Managed Service for Prometheus

    GKE ships container stdout/stderr to Cloud Logging and system metrics to Cloud Monitoring by default. reliability-api already logs to stdout (Module 02/07), so its log lines appear without code changes; query them in Logs Explorer with a filter like resource.type="k8s_container" resource.labels.namespace_name="reliability-lab".

      app.kubernetes.io/name: reliability-api

    Cost controls: budgets, labels, checklists, cleanup

    Problem. Cloud bills are driven by things that are easy to forget: a load balancer left from a demo, a disk orphaned by a deleted cluster, debug logs at load-test volume, a regional Standard cluster with nine nodes. Cost control is an engineering habit, not a finance task.

    Budgets and alerts

    • A budget tracks actual (and forecasted) spend against an amount for a scope: billing account, projects, services, labels, folders.
    • Default thresholds notify at 50%, 90%, 100% of actual spend; add forecasted thresholds to be warned earlier.
    • Alerts go to Billing Account Administrators/Users (and Project Owners for single-project budgets), or to Cloud Monitoring notification channels.
    • Critical: "Setting an alerts-only budget doesn't automatically cap … usage or spending." Alerts are smoke detectors, not sprinklers. Your cleanup procedure is the sprinkler.

    Labels

    Labels are key/value pairs on Google Cloud resources (clusters, disks, repos, buckets) that appear in billing exports and can scope budgets. Use the same three everywhere: app=reliability-api, env=lab, owner=<you>. They are not the same thing as Kubernetes labels on Pods, though GKE can propagate cluster labels to underlying resources and cost allocation can break costs down by namespace/K8s labels when enabled.

    Cleanup procedure (always in this order)

    1. Kubernetes objects that own cloud resources: LoadBalancer Services, Gateways/Ingresses, PVCs (decide: keep data or delete). Verify with kubectl get svc,gateway,ingress,pvc -A.

    Terraform for a GKE Autopilot cluster

    Module 10 taught providers, state, plan/apply/destroy. Here we apply them to GKE. Boundary reminder: Terraform owns the VPC, subnet, cluster, repository and IAM; Helm owns what runs inside the cluster. Do not manage the reliability-api Deployment with Terraform in this course.

    Arguments below were checked against the google_container_cluster documentation for the hashicorp/google provider (latest version listed on the registry API on 29 Oct 2026: 8.9.0). Key points from that page:

    • enable_autopilot — "Enable Autopilot for this cluster. Defaults to false."
    • location — a region gives a regional cluster (Autopilot must be regional).
    • deletion_protection — "Deleting this cluster via terraform destroy or terraform apply will only succeed if this field is false in the Terraform state." Since provider 5.0.0 you must set it to false and apply before you can destroy.
    • ip_allocation_policy with cluster_secondary_range_name / services_secondary_range_name — use named subnet ranges.
    • release_channel { channel = "REGULAR" }; resource_labels for labels.
    • The page warns all arguments and attributes (including certificate outputs) are stored in state as plaintext — protect the state bucket.

    Glossary

    Project
    Container for resources, billing link, enabled APIs and IAM. Identified by immutable ID and numeric number.
    Billing account
    Pays for one or more projects; has its own IAM and budgets.
    Principal
    An identity IAM can grant roles to: user, group, service account, federated identity/principal set.
    Role
    Named set of permissions: basic, predefined or custom.
    Allow policy
    List of role bindings attached to a resource; inherited by descendants.
    Service account
    Identity for software (…@PROJECT.iam.gserviceaccount.com).
    Region / zone
    Geographic location / isolated failure domain within it.
    VPC-native
    Cluster networking mode using alias IP ranges; Pod IPs from a subnet secondary range.
    Node pool
    Group of nodes with identical configuration (Standard mode).
    Autopilot
    GKE mode where Google manages nodes; general-purpose Pods are billed by their requests.
    Release channel
    Rapid/Regular/Stable/Extended stream of GKE versions and auto-upgrades.
    Artifact Registry
    Google Cloud registry; Docker repos at LOCATION-docker.pkg.dev.
    Workload Identity Federation for GKE
    Lets a Kubernetes ServiceAccount act as an IAM principal via pool PROJECT_ID.svc.id.goog.
    Workload identity pool / provider
    Trust configuration for external identity tokens (e.g., GitHub OIDC), with attribute mapping and conditions.
    STS
    Security Token Service: exchanges external/federated tokens for Google access tokens.
    GatewayClass
    Type of load balancer a Gateway creates, e.g. gke-l7-regional-external-managed.
    PodMonitoring
    GMP custom resource declaring Prometheus scrape targets.
    Budget
    Spend-tracking object that sends alerts at thresholds; does not cap spending by itself.

    Self-check

    1. List the three things a project gives you that make it the natural unit for a lab.
    A billing link (who pays), an IAM boundary (who can act, inherited by resources), and a lifecycle boundary (deleting the project removes everything inside), plus per-project API enablement.
    2. Why can an alerts-only budget not protect you from a forgotten load balancer?
    It only notifies at thresholds of actual/forecast spend; it does not stop or delete resources. The LB keeps billing until someone deletes it. Only a cleanup procedure (and verification) removes the cost.
    3. You deploy reliability-api to Autopilot without resource requests. What happens and why does it matter?
    Autopilot applies default requests (general-purpose: 0.5 vCPU, 2 GiB, 1 GiB ephemeral). You are billed for those requests, so two Pods cost far more than with 100m/128Mi. Also the HPA's CPU utilisation percentage is calculated against the request, so scaling behaviour changes.
    4. What does a regional cluster protect against that a zonal one does not, and what does it cost in Standard mode?
    Control-plane and node availability during a single-zone failure and during control-plane upgrades. In Standard mode node counts are per zone (3 zones × N), and cross-zone traffic is billed. Autopilot is always regional and bills per Pod, so the node multiplication does not apply.
    5. Explain the difference between gcloud auth login and gcloud auth application-default login.
    The first stores credentials for the gcloud CLI (and tools that call it, like the kubectl auth plugin and Docker credential helper). The second creates Application Default Credentials used by client libraries and Terraform. Terraform failing with "could not find default credentials" while gcloud works means ADC is missing.
    6. Your Pod gets 403 calling Cloud Storage despite Workload Identity. Give three things to check.
    (1) The Pod's serviceAccountName matches the KSA in the principal string; (2) the principal uses the project number and the right namespace/KSA and has the role on that bucket; (3) no GOOGLE_APPLICATION_CREDENTIALS or key file overrides metadata credentials; also allow time for IAM propagation.
    7. Why does the GitHub provider need an attribute condition?
    Without it, any GitHub repository's OIDC token (same issuer) could be exchanged in your pool. The condition (e.g. assertion.repository_owner == 'you', better with numeric IDs and branch) restricts which workflows are trusted.
    8. What survives gcloud container clusters delete? Name at least four.
    Persistent disks from PVCs, possibly load balancer forwarding rules/IPs if Services/Gateways were not deleted first (cleanup can fail), reserved static IPs, Artifact Registry images, Cloud Storage buckets (incl. Terraform state), snapshots, retained logs, Cloud NAT/routers created separately, and the project itself.
    9. Why must you set deletion_protection = false and apply before terraform destroy works?
    Destroy succeeds only if the field is false in state. Changing the file alone is not enough: an apply records the new value in state; then destroy is allowed.
    10. When would you choose a Gateway over a LoadBalancer Service for reliability-api?
    When you need HTTP features: TLS termination, host/path routing to several Services, traffic splitting for canaries, or one shared LB for many apps. For a quick L4 demo a LoadBalancer Service is simpler; for a private lab, port-forward.
    11. Your M-series Mac pushes an image; Pods crash with exec format error. Fix?
    The image is arm64 and nodes are amd64. Rebuild with docker buildx build --platform linux/amd64 (or multi-arch) and push, or build in CI on amd64 runners.
