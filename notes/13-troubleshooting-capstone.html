    Module 13 · Troubleshooting Playbook & Capstone Project

    This module turns the previous twelve into one working habit. The first half is a systematic debugging method for reliability-api: a layered model, a decision tree, the exact commands to use, and practice scenarios where you break things on purpose. The second half is the capstone, the Kubernetes Reliability Lab. It lists every milestone, the evidence each one must produce, a production-readiness checklist, an experiment report template, and interview preparation.

    Prereq: Modules 01–12 (or at least 01–08)≈ 4 h study + capstone (multi-week)✓ Checked against official docs, Oct 2026

    Learning objectives

    • Apply a repeatable triage → isolate → hypothesise → test → fix → record loop instead of guessing.
    • Locate a failure in the right layer (app, container, Pod, scheduling, Service/network, cluster, pipeline, cloud).
    • Read Pod phases, container states and Events, and map each common status (Pending, ImagePullBackOff, CrashLoopBackOff, OOMKilled, unready) to its first diagnostic command.
    • Use kubectl debug ephemeral containers and Pod copies when kubectl exec is not enough.
    • Plan, execute and document the capstone so that every claim in the README is backed by evidence.

    Part A — A method, not a bag of commands

    Beginners debug by trying random commands until something changes. Experienced engineers follow a loop. The official Kubernetes guide starts the same way: "The first step in troubleshooting is triage. What is the problem? Is it your Pods, your Replication Controller or your Service?"

    Rules that prevent wasted hours

    1. Write down the symptom precisely. "API is broken" is not a symptom. "curl through the Service returns connection refused since 14:02; Pods show 0/1 READY" is.
    2. Ask "what changed?" Most incidents follow a change: a new image, a manifest edit, a config change, a dependency, or a traffic increase. kubectl rollout history, git log and CI runs are evidence.
    3. Work from the outside in, then the inside out. Confirm the symptom where the user sees it, then walk inward one layer at a time.
    4. Change one variable at a time. If you change the probe, the image and the resource limits together, you will not know which change fixed it.
    5. Distinguish facts from inferences. "The Pod restarted 4 times" is a fact (from kubectl get pods). "It ran out of memory" is an inference until lastState.terminated.reason says OOMKilled.
    6. Missing evidence is not success. If a dashboard is blank, the test is inconclusive, not passing.

    The layer model for reliability-api

    Each layer depends on the ones below it. When a symptom appears at the top, find the lowest layer that is broken. A broken layer makes every layer above it look broken too.

    Fast triage in three commands 
    kubectl -n reliability-lab get deploy,rs,pods,svc,endpointslices -o wide
kubectl -n reliability-lab get events --sort-by=.metadata.creationTimestamp | tail -20
kubectl -n reliability-lab describe pod -l app.kubernetes.io/name=reliability-api | sed -n '/Conditions/,$p'

    These three commands show desired vs actual state, the recent timeline, and the per-Pod conditions and Events. That is usually enough to know which layer to investigate.

    Reading Pod phases and container states

    A Pod has a single high-level phase. Each container inside it has its own state (Waiting, Running, Terminated) with a reason. The STATUS column in kubectl get pods is a summary that often shows the container reason (for example CrashLoopBackOff), not the phase.

    PhaseOfficial meaning (kubernetes.io, Pod Lifecycle)What it usually means for reliability-api
    PendingAccepted by the cluster, but one or more containers have not been set up and made ready to run. Includes time waiting to be scheduled and downloading images.Not scheduled yet (resources/taints) or the image is still pulling or failing to pull.
    RunningBound to a node and all containers created; at least one is running, starting or restarting."Running" does not mean ready or healthy. Check the READY column and restarts.
    SucceededAll containers terminated in success and will not be restarted.Normal for Jobs (e.g. a load-test Job), never expected for the API Deployment.
    FailedAll containers terminated, at least one in failure, and not set for automatic restart.Seen in Jobs with restartPolicy: Never.
    UnknownState could not be obtained, typically a communication problem with the node.Node trouble. Check kubectl get nodes.

    Restart back-off: why CrashLoopBackOff "waits"

    When a container keeps failing, the kubelet restarts it with an exponential back-off delay. The official Pod Lifecycle page gives the numbers: it starts at 10 seconds, doubles each time, is capped at 5 minutes, and resets after the container has run successfully for 10 minutes. CrashLoopBackOff means the kubelet is waiting out that delay; it is not an error type on its own. Image pulls back off in a similar way, also capped at 5 minutes (Images concept page).

    Back-off timeline explorer
    Model: 10 s initial delay, doubling, 300 s cap, as documented. Assume each crash happens a few seconds after start. Real timings vary slightly.

    The symptom playbook (expanded)

    This is the guide's troubleshooting table, expanded. Each row gives the first command, what to look for in its output, and the usual fixes for reliability-api.

    1. Pod stuck in Pending

    The official guide names two classic causes: you have run out of CPU or memory ("delete Pods, adjust resource requests, or add new nodes"), or the Pod uses a hostPort, which limits where it can be placed. Taints, node selectors, affinity and unbound PersistentVolumeClaims are the other usual suspects.

    kubectl -n reliability-lab describe pod <pod> | sed -n '/Events/,$p'
kubectl describe nodes | grep -A6 "Allocated resources"
    Events:
  Type     Reason            From               Message
  ----     ------            ----               -------
  Warning  FailedScheduling  default-scheduler  0/1 nodes are available: 1 Insufficient cpu. ...

    Fixes: lower an unrealistic requests.cpu (for example, someone typed 100 where they meant 100m), lower replicas/maxReplicas, add a kind worker node, or remove a selector or toleration mismatch.

    2. ErrImagePull / ImagePullBackOff

    The guide's three checks: the image name is correct, the image was pushed to the registry, and you can pull it manually. kind adds a fourth: a locally built image must be loaded into the cluster nodes with kind load docker-image. Also check the default pull policy. If the tag is :latest or omitted, imagePullPolicy defaults to Always, so the kubelet tries a remote registry even when you loaded the image locally.

    kubectl -n reliability-lab get pod <pod> -o jsonpath='{.spec.containers[*].image}{"\n"}{.spec.containers[*].imagePullPolicy}{"\n"}'
docker exec -it reliability-lab-control-plane crictl images | grep reliability-api
kind load docker-image reliability-api:0.1.0 --name reliability-lab

    3. CrashLoopBackOff

    The process keeps exiting. The logs of the current container may be empty because it has only just restarted, so read the previous one. Then read the exit code (see Module 01: 137 = 128 + 9 = SIGKILL, usually OOM; 1 = application error).

    kubectl -n reliability-lab logs <pod> --previous
kubectl -n reliability-lab get pod <pod> \
  -o jsonpath='{.status.containerStatuses[0].lastState.terminated}{"\n"}'
    {"exitCode":1,"reason":"Error","startedAt":"...","finishedAt":"..."}

    Common causes for this app: a typo in the command or module path (uvicorn app.mian:app), a missing Python dependency in the image, a bad LOG_LEVEL value that makes logging.basicConfig raise, or a liveness probe that kills a slow-starting container. Termination messages: set terminationMessagePolicy: FallbackToLogsOnError. If the termination-message file is empty and the container exited with an error, Kubernetes then uses the last chunk of log output, limited to 2048 bytes or 80 lines, whichever is smaller.

    4. OOMKilled

    kubectl -n reliability-lab describe pod <pod> | grep -A4 "Last State"
kubectl -n reliability-lab top pod

    Memory usage went above limits.memory (256Mi in our example). Measure real usage under load before you raise the limit, and look for unbounded caches or very large request payloads. A raised limit without measurement is only a guess.

    5. Running but READY 0/1

    The readiness probe is failing, so the Pod is removed from the Service endpoints. That is the probe working as designed. Find out why /ready fails: the warm-up from READY_DELAY_SECONDS is longer than expected, the probe uses the wrong port or path, or timeoutSeconds is too short while the CPU is saturated.

    kubectl -n reliability-lab describe pod <pod> | grep -i -A2 readiness
kubectl -n reliability-lab exec <pod> -- python -c "import urllib.request as u; print(u.urlopen('http://127.0.0.1:8000/ready').read())"

    6. Service has no endpoints / requests fail

    This follows the official "Debug Services" sequence. Does the Service exist? Does DNS resolve? Does it work by IP? Is it defined correctly? Does it have EndpointSlices? Are the Pods working? Is kube-proxy working?

    kubectl -n reliability-lab get svc reliability-api -o yaml | grep -A3 -E "selector|ports"
kubectl -n reliability-lab get pods --show-labels
kubectl -n reliability-lab get endpointslices -l kubernetes.io/service-name=reliability-api
kubectl -n reliability-lab run tmp --rm -it --image=busybox --restart=Never -- \
  sh -c 'nslookup reliability-api; wget -qO- reliability-api/ready'

    The classic bug is a selector/label mismatch. For example, the Service selects app: reliability-api but the Pods carry app.kubernetes.io/name: reliability-api. The second classic bug is a targetPort that does not match the container port (8000).

    7. HPA shows <unknown> or does not scale

    kubectl -n reliability-lab describe hpa reliability-api
kubectl get apiservices | grep metrics
kubectl -n kube-system get pods | grep metrics-server

    Usual causes: metrics-server is missing (on kind it often needs the --kubelet-insecure-tls flag; see Module 08), CPU requests are missing (CPU utilization is calculated relative to requests), the load is too low, maxReplicas has been reached, or the stabilization window is delaying scale-down.

    8. More replicas but latency does not improve

    Check the bottleneck hypotheses in order. The load generator is saturated (check its own CPU). The node is CPU-saturated, so new replicas share the same cores (kubectl top nodes). There is a CPU limit causing throttling. There is a downstream dependency. Errors are hiding as fast failures. Module 08 covers how to tell these apart.

    9. Grafana panel is blank

    Work backwards. Run the PromQL query in the Prometheus UI first. If it returns nothing, open Status → Targets: is reliability-api listed and UP? If it is not listed, the ServiceMonitor selector or labels do not match the Prometheus selector. If the target is DOWN, check the port name or path, or a NetworkPolicy.

    10. CI pipeline fails

    Read the first failing step, not the last. Reproduce it locally with the same command (pytest, docker build). For kind-in-CI failures, print kubectl get events and describe in an if: failure() step so the log contains the evidence.

    11. Cloud bill continues after the lab

    Deleting the cluster does not delete everything. Check load balancers and forwarding rules, reserved static IPs, persistent disks left by PVCs, Artifact Registry images, and log storage. Module 11 has a full cleanup checklist.

    Debugging inside Pods: exec vs debug

    The reliability-api image is built small (Module 02), so it may have no curl, ps or shell tools. Official docs: "Ephemeral containers are useful for interactive troubleshooting when kubectl exec is insufficient because a container has crashed or a container image doesn't include debugging utilities."

    # ephemeral container sharing the app container's process namespace
kubectl -n reliability-lab debug -it <pod> --image=busybox --target=reliability-api

# copy the Pod and override the crashing container's command with a shell
kubectl -n reliability-lab debug <pod> -it --copy-to=api-debug --container=reliability-api -- sh

# debug a node: runs in host namespaces, host filesystem mounted at /host
kubectl debug node/reliability-lab-control-plane -it --image=busybox

# clean up the copy afterwards
kubectl -n reliability-lab delete pod api-debug
    Know the limits

    The official docs say ephemeral containers "lack guarantees for resources or execution, and they will never be automatically restarted". They also say "you may not change or remove an ephemeral container after you have added it to a Pod." Ports, probes and resources are not allowed on them. Use them on a test cluster freely, and on a shared cluster only with permission.

    Practice: break-it scenarios

    Run each scenario on the kind cluster in a scratch namespace. Write down your hypothesis before you reveal the answer. These drills build troubleshooting skill fastest.

    Lab 13.1 — Set up a break-it namespace
    1. Create a scratch copy of your working manifests: 
      kubectl create namespace breakit
kubectl -n breakit apply -f deploy/kubernetes/   # Deployment + Service + ConfigMap from Module 03–05
kubectl -n breakit rollout status deploy/reliability-api
    2. For each scenario below, apply the break, observe it with the fast-triage commands, write your hypothesis, then reveal the answer.
    3. Restore after each one: kubectl -n breakit apply -f deploy/kubernetes/
    4. When finished: kubectl delete namespace breakit
    Scenario A — kubectl -n breakit set image deploy/reliability-api reliability-api=reliability-api:0.9.9

    Symptom: a new Pod shows ErrImagePull → ImagePullBackOff. The old Pods keep serving, because the rolling update does not remove old replicas until new ones are available. This is why rolling updates protect you.

    Evidence: describe pod Events show the failed pull. kubectl rollout status does not complete.

    Fix: kubectl -n breakit rollout undo deploy/reliability-api.

    Scenario B — patch the readiness probe path to /readyz
    kubectl -n breakit patch deploy reliability-api --type=json -p \
 '[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/readyz"}]'

    Symptom: new Pods are Running but 0/1 READY. The rollout stalls and old Pods stay. Events show Readiness probe failed: HTTP probe failed with statuscode: 404.

    Lesson: readiness failures never restart a container. They only remove it from endpoints.

    Scenario C — set the liveness probe initialDelaySeconds: 0, failureThreshold: 1, and READY_DELAY_SECONDS=30 with liveness pointing at /ready

    Symptom: restarts climb and the Pod ends in CrashLoopBackOff. The app is healthy but is killed while it is still warming up, because liveness checks a readiness-style endpoint.

    Lesson: liveness should check "is the process stuck?" (/health). Use a startupProbe for slow starts. A wrong liveness probe makes an incident worse.

    Scenario D — change the Service selector to app: reliability-api

    Symptom: Pods are 1/1 Ready, but requests through the Service fail and endpointslices lists no endpoints.

    Evidence: kubectl get pods --show-labels vs kubectl get svc -o yaml.

    Lesson: the Service ↔ Pod link is only a label query.

    Scenario E — set resources.requests.cpu: "8" and replicas 3 on a single-node kind cluster

    Symptom: new Pods stay Pending. Events show FailedScheduling … Insufficient cpu.

    Lesson: the scheduler uses requests, not actual usage. An idle Pod with a big request still blocks the node.

    Scenario F — set limits.memory: 20Mi

    Symptom: the container is killed at start or under load. lastState.terminated.reason: OOMKilled, exit code 137.

    Lesson: memory limits are enforced by killing the process. CPU limits are enforced by throttling it.

    Scenario G — change the container's command to uvicorn app.mian:app

    Symptom: CrashLoopBackOff. logs --previous shows a Python import error and the exit code is non-zero.

    Lesson: always read --previous. The current container may not have logged anything yet.

    Scenario H — apply a default-deny NetworkPolicy in the namespace

    Symptom: this depends on your network plugin. If it enforces NetworkPolicy, in-cluster wget calls to the Service time out. If it does not, you see no change at all. That is the lesson: kubernetes.io states that a NetworkPolicy has no effect unless the network plugin implements it. kind ships its own simple CNI (kindnetd). Whether yours enforces policies depends on the kind version, so check the kind release notes. You can also set disableDefaultCNI: true and install a CNI that enforces policies (kind Configuration docs).

    Diagnose: kubectl -n breakit get networkpolicy, then test from a busybox Pod. The policy's Pod selector and namespace decide which traffic is blocked.

    Makefile: one command per step

    A reviewer should be able to reproduce your lab without reading every doc. A thin Makefile gives each step one obvious entry point.

    CLUSTER ?= reliability-lab
IMAGE   ?= reliability-api:0.1.0
NS      ?= reliability-lab

cluster:      ## create local cluster
	kind create cluster --name $(CLUSTER)
image:        ## build and load image into kind
	docker build -t $(IMAGE) .
	kind load docker-image $(IMAGE) --name $(CLUSTER)
deploy:       ## install/upgrade the chart
	helm upgrade --install reliability-api charts/reliability-api -n $(NS) --create-namespace --wait
smoke:        ## verify through the Service
	kubectl -n $(NS) run smoke --rm -i --restart=Never --image=busybox -- wget -qO- reliability-api/ready
load:         ## baseline load test
	k6 run experiments/load/baseline.js --summary-export experiments/reports/$$(date +%F)-baseline.json
clean:        ## delete everything local
	kind delete cluster --name $(CLUSTER)

    Makefile recipes must be indented with a real tab character. Commands follow Modules 02, 06 and 08. Verify the flags against your installed tool versions.

    Interview preparation

    For each topic, practise a 30-second plain-language answer, then one deeper example from your lab. The study guide's note template ends with the same pattern.

    "A Pod is in CrashLoopBackOff. Walk me through it."

    "CrashLoopBackOff means the container keeps exiting and the kubelet is waiting before the next restart. The delay starts at 10 seconds, doubles, and is capped at 5 minutes. First I run kubectl logs --previous to see why the last instance died, and I read lastState.terminated for the exit code and reason. 137 with OOMKilled points to memory. Exit code 1 points to an application error. Then I check whether a liveness probe is killing a slow start. In my lab, a typo in the uvicorn module path produced an import error, which I found in the previous logs."

    "Readiness vs liveness vs startup probes?"

    "Readiness decides whether a Pod receives traffic. When it fails, the Pod is removed from the endpoints and is not restarted. Liveness decides whether to restart a stuck container. Startup protects slow starters by holding off the other probes until the app has started. In my lab I pointed liveness at the warm-up-dependent /ready endpoint and caused a restart loop, so liveness now checks /health and readiness checks /ready."

    "How does the HPA decide how many replicas to run?"

    "Roughly desired = ceil(current × currentMetric / targetMetric), with a tolerance so it does not react to small changes and a stabilization window for scale-down. For CPU, utilization is measured against the Pod's CPU request. That is why requests have to be set and realistic. I showed in my lab that scaling stopped improving latency once the single kind node was CPU-saturated, so HPA without node capacity has a ceiling."

    "How did you measure recovery?"

    "I defined the test SLO and the recovery criteria before the run. I kept the load at a constant arrival rate, recorded the fault timestamp, and measured the impact window as the time when the error ratio or p95 broke the target. Recovery time ran until the metrics returned within the SLO. I report the failed-request count, the sample size and the biases, such as a single run on a laptop."

    "What is the difference between Terraform and Helm?"

    "Terraform provisions infrastructure through provider APIs, such as the VPC, the GKE cluster and IAM, and it tracks that infrastructure in state. Helm packages and releases applications inside a cluster as versioned releases that you can upgrade and roll back. GitHub Actions automates running both. They are different layers."

    "Why not use :latest?"

    "It is mutable, so two deploys of the same tag can run different code, and rollbacks become ambiguous. In Kubernetes, :latest or an omitted tag also defaults imagePullPolicy to Always. I tag images with the git SHA in CI and can pin by digest."

    "Prometheus is installed, so why doesn't HPA use my custom metric?"

    "The standard HPA reads CPU and memory from the resource metrics API, which is usually served by metrics-server. Custom metrics need an adapter that implements the custom or external metrics API, such as prometheus-adapter, or a tool such as KEDA. Installing Prometheus alone does not connect it to the HPA."

    "Tell me about a time a test was misleading."

    Prepare a real story from your lab. Two good examples: a load generator that saturated its own CPU so latency looked flat, or a blank Grafana panel that had been read as "no errors". Explain how you detected it and what guardrail you added, such as recording load-generator CPU or marking runs with missing metrics as inconclusive.

    Self-check

    1. A Pod shows STATUS Running. Is it serving traffic?
    Not necessarily. Running means it is bound to a node and its containers were created. Check the READY column and the EndpointSlices; only ready Pods receive Service traffic.
    2. Why can kubectl logs POD be empty for a CrashLoopBackOff Pod?
    The current container may have just restarted, or may be waiting out its back-off. Use --previous to read the last terminated instance.
    3. Pending + "Insufficient cpu" on an idle cluster: how?
    Scheduling uses requests. The sum of requests on the node can be "full" while actual usage is low.
    4. You changed the image and a probe at the same time and the rollout fails. What's wrong with your process?
    Two variables changed at once. Roll back, then change one thing at a time so the cause is identifiable.
    5. When would you use --copy-to rather than an ephemeral container?
    When you need to change the Pod, for example to override the crashing container's command with sh or swap images, without touching the live Pod. Ephemeral containers also cannot be removed once added.
    6. Your Grafana error-rate panel is blank during a load test. Did the test pass?
    No. It is inconclusive. Check the query in Prometheus and the target health first.
    7. What resets the CrashLoopBackOff delay?
    The container running successfully for 10 minutes (Pod Lifecycle docs). Deleting or replacing the Pod also starts fresh.
    8. Name the official Debug Services checks in order.
    Service exists → network policy ingress rules → works by DNS name → works by IP → defined correctly → has EndpointSlices → Pods working → kube-proxy working.
    9. What makes an experiment result trustworthy in a portfolio?
    A plan with success criteria written beforehand, the recorded environment and exact commands, measured values with sample size, attached raw evidence, and an honest list of limitations.
    10. Image pulled fine yesterday on kind; today ImagePullBackOff with tag latest. Why?
    With :latest, imagePullPolicy defaults to Always, so the kubelet tries the remote registry even if the image was loaded locally. Use a specific tag, or set IfNotPresent for locally loaded images.
