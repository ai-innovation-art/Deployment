    Module 05 · Networking, Configuration, Storage & Access Control

    Module 04 made reliability-api Pods healthy, resourced and safely rolled out. But a Pod on its own is unreachable in any stable way, has its settings baked into the image, loses its files when it dies and runs with whatever identity it is given by default. This module covers the four things that turn running Pods into a usable service: networking (Pod IPs, Services, EndpointSlices, DNS, Ingress/Gateway, NetworkPolicy), configuration (ConfigMap, Secret), storage (volumes, PV/PVC/StorageClass) and access control (ServiceAccount, RBAC). Every idea is applied to reliability-api in the reliability-lab namespace.

    2. The Kubernetes network model

    Definition

    Kubernetes defines a small set of rules every cluster's network must satisfy, and leaves the implementation to a pluggable component. From the official Services & Networking overview:

    • Each Pod gets its own unique, cluster-wide IP address. All containers in a Pod share one network namespace, so they talk to each other over localhost.
    • All Pods can communicate with all other Pods, on the same node or different nodes, directly, without proxies or address translation (NAT) — "barring intentional network segmentation" (that is what NetworkPolicy adds later).
    • Agents on a node (system daemons, kubelet) can communicate with all Pods on that node — this is how the kubelet runs your HTTP probes against /ready and /health.

    The problem it solves

    In plain Docker (Module 02) containers sit behind NAT on a bridge network and you publish ports with -p 8000:8000. Port collisions and NAT make multi-host networking painful: two containers can't both publish 8000 on the same host, and the address a container sees for itself isn't the address others use. Kubernetes avoids this by treating each Pod like a small VM with a real, routable (inside the cluster) IP. Every replica of reliability-api can listen on port 8000 because each has its own IP.

    Who implements it: CRI + CNI

    Two pieces of node software cooperate:

    • The container runtime (via the Container Runtime Interface) creates the Pod's network namespace.
    • The pod network implementation wires that namespace into the cluster network and assigns the IP. On Linux most runtimes talk to it through the Container Network Interface (CNI), so these implementations are called CNI plugins (Calico, Cilium, kindnet, cloud-provider plugins…).

    On a kind cluster the default CNI is kindnetd, the default Pod subnet is 10.244.0.0/16 and the default Service subnet is 10.96.0.0/16 (kind configuration docs). So reliability-api Pods get 10.244.x.y addresses and the Service gets a 10.96.x.y ClusterIP.

    How it works, step by step (Pod creation)

    1. The scheduler binds a reliability-api Pod to reliability-lab-worker.
    2. The kubelet asks the container runtime (containerd) to create the Pod sandbox; the runtime creates a new network namespace.
    3. The runtime invokes the CNI plugin, which creates a virtual interface in that namespace, assigns an IP from the node's share of 10.244.0.0/16 and sets up routes.
    4. The app container starts inside that namespace and binds 0.0.0.0:8000. The IP is recorded in status.podIP.
    5. When the Pod is deleted the IP is released and may be reused by a different Pod later. Pod IPs are not stable — this is the reason Services exist.

    Self-check: two containers in the same Pod both try to bind port 8000. What happens?
    They share one network namespace, so the second bind fails with "address already in use". Containers in one Pod must use different ports; different Pods can reuse the same port freely because each has its own IP.
    Self-check: is NAT involved when Pod A on node 1 calls Pod B on node 2 by Pod IP?
    No — the network model requires Pod-to-Pod traffic without NAT, so Pod B sees Pod A's real Pod IP as the source address. (Traffic sent to a Service IP is a different story: the destination is translated to a Pod IP — see kube-proxy.)

    3. Services: a stable front door for changing Pods

    Definition

    A Service is an API object that gives a set of Pods a stable, long-lived IP address and DNS name, while the individual Pods behind it come and go. The set of Pods is chosen with a label selector. Clients talk to the Service; Kubernetes spreads connections across the Pods that are currently ready.

    The problem it solves

    reliability-api has two replicas today, six under HPA load tomorrow, and every rollout replaces all of them with new IPs. A load generator or another microservice cannot track that churn. The Service decouples "who serves the API" from "how you reach the API".

    The reliability-api Service

    apiVersion: v1
kind: Service
metadata:
  name: reliability-api
  namespace: reliability-lab
  labels:
    app.kubernetes.io/name: reliability-api
spec:
  type: ClusterIP                  # default; internal-only virtual IP
  selector:
    app.kubernetes.io/name: reliability-api   # must match the Pod template labels
  ports:
    - name: http                   # named ports enable SRV records + clearer config
      protocol: TCP
      port: 80                     # what clients connect to on the Service IP
      targetPort: 8000             # where the container listens (could also be the name "http")

    And the matching part of the Deployment from Module 04 (only the fields that matter here):

    spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: reliability-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: reliability-api   # ← the Service selector matches THIS
    spec:
      containers:
        - name: reliability-api
          image: reliability-api:0.1.0
          ports:
            - name: http
              containerPort: 8000
          readinessProbe:
            httpGet: { path: /ready, port: http }

    3.1 Selectors → EndpointSlices → Pod IPs

    The Service object itself contains no Pod IPs. The control plane computes them continuously. The official Service page puts it this way: the controller for the Service "continuously scans for Pods that match its selector, and then makes any necessary updates to the set of EndpointSlices for the Service."

    An EndpointSlice is a separate API object that lists backend addresses (IP + port + conditions) for a Service. It is labelled kubernetes.io/service-name: reliability-api so you can find it. By default the control plane keeps each slice to at most 100 endpoints (configurable up to 1000), so a Service with many Pods has several slices — this is what lets Services scale to large backends and lets the cluster update the list efficiently. The older Endpoints API still exists but was deprecated in Kubernetes v1.33 in favour of EndpointSlices.

    Each endpoint carries three conditions (EndpointSlices docs):

    • serving — for Pod-backed endpoints this maps to the Pod's Ready condition;
    • terminating — set when the Pod is first deleted;
    • ready — shortcut for "serving and not terminating". Proxies normally send new traffic only to ready endpoints.

    3.2 Readiness → endpoint membership (why Module 04's probe matters here)

    This is the link between Module 04 and this module. reliability-api's /ready returns 503 for READY_DELAY_SECONDS after start. During that window:

    1. The kubelet's readiness probe fails → the Pod's Ready condition is False.
    2. The EndpointSlice controller sees the Pod change and marks its endpoint serving=false, ready=false.
    3. kube-proxy on every node sees the slice change and removes that IP from the Service's forwarding rules.
    4. When /ready starts returning 200 the chain runs in reverse and the Pod starts receiving traffic.
    5. On deletion the endpoint becomes terminating and stops getting new connections, which is why graceful termination (Module 04) plus readiness gives zero-dropped-request rollouts.
    Each hop is asynchronous

    Probe period → API update → controller → kube-proxy on each node. These are separate watch loops, so there is always a short window where a just-unready or just-deleted Pod can still receive a connection. That is why Module 04 recommends a small preStop delay and a graceful shutdown in the app.

    3.5 kube-proxy: who makes the virtual IP work?

    A ClusterIP is not bound to any network interface. Nothing "listens" on 10.96.143.20:80. Instead, on every node, kube-proxy watches Service and EndpointSlice objects and programs the node's packet-processing rules so that a connection to ClusterIP:port is rewritten (DNAT) to one of the ready endpoints. From the virtual-IPs reference: "Each instance of kube-proxy watches the Kubernetes control plane for the addition and removal of Service and EndpointSlice objects. For each Service, kube-proxy calls appropriate APIs (depending on the kube-proxy mode) to configure the node to capture traffic to the Service's clusterIP and port, and redirect that traffic to one of the Service's endpoints."

    • Modes on Linux: iptables, ipvs, nftables. The docs state that in Kubernetes 1.37 the default is iptables and that a future version will switch the default to nftables, so you should set the mode explicitly.
    • kube-proxy is the programmer, not the data path in iptables/nftables mode: the kernel rewrites packets; in iptables mode a backend is chosen randomly (or by session affinity) and "packets are redirected to the backends without rewriting the client IP address".
    • Some CNIs (for example Cilium) can replace kube-proxy entirely; the concept — "Service VIP translated to a ready Pod IP on the client's node" — stays the same.
    • sessionAffinity: ClientIP makes connections from one client IP stick to one Pod. Leave it off for reliability-api; stickiness skews load tests.

    3.6 Traffic policies (brief)

    The Service page also documents traffic policies. Two you will meet: externalTrafficPolicy (for NodePort/LoadBalancer traffic arriving from outside: Cluster spreads to any node's Pods; Local only uses Pods on the receiving node and keeps the client source IP) and internalTrafficPolicy (the same idea for in-cluster traffic). Defaults are Cluster; leave them unless you have a specific reason such as needing real client IPs.

    3.9 Trade-offs

    • ClusterIP + Gateway/Ingress vs many LoadBalancers: one shared entry point is cheaper and centralises TLS/routing; per-Service LBs are simpler but cost money each.
    • Connection-level balancing is cheap and transparent, but HTTP/2 or keep-alive clients may not spread evenly. Request-level balancing needs an L7 proxy (Gateway implementation or service mesh).
    • Named targetPort (http) lets you change the container port without touching the Service; numeric is more obvious to readers. Use names in charts.
    Self-check: you omit targetPort in the reliability-api Service. What port does traffic go to on the Pod, and what happens?
    targetPort defaults to the value of port, so traffic is sent to Pod port 80. Uvicorn listens on 8000, so connections are refused. Set targetPort: 8000 (or the name http).
    Self-check: a Pod matches the selector but its readiness probe fails. Is it in the EndpointSlice?
    Yes, it is listed, but with serving=false/ready=false. Proxies don't send it new Service traffic. Membership comes from labels; usability comes from readiness.
    Self-check: why can't you ping a ClusterIP and expect a reply?
    The ClusterIP is virtual — no interface owns it. kube-proxy only programs rules for the Service's declared protocol/ports (e.g. TCP 80). ICMP to the VIP has no matching rule, so a lack of ping reply tells you nothing. Test with curl to the actual port.

    4. Cluster DNS: names instead of IPs

    Definition

    Every cluster runs a DNS service (CoreDNS on kind and most clusters) and the kubelet configures each Pod's /etc/resolv.conf to use it. Services get DNS records automatically, so code can call http://reliability-api instead of an IP.

    Record forms (from "DNS for Services and Pods")

    RecordFormreliability-api exampleResolves to
    Service A/AAAA (normal)my-svc.my-namespace.svc.cluster-domain.examplereliability-api.reliability-lab.svc.cluster.localThe ClusterIP
    Service A/AAAA (headless)same formreliability-api-headless.reliability-lab.svc.cluster.localIPs of all selected (ready) Pods
    SRV (named ports)_port-name._port-protocol.my-svc.my-namespace.svc.cluster-domain.example_http._tcp.reliability-api.reliability-lab.svc.cluster.localPort number + the Service's domain name
    Pod A/AAAA<pod-ip-with-dashes>.<namespace>.pod.<cluster-domain>10-244-1-5.reliability-lab.pod.cluster.localThat Pod IP

    Search domains: why the short name works

    The kubelet writes something like this into each Pod (example from the docs; your nameserver IP will differ):

    nameserver 10.96.0.10
search reliability-lab.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
    • A lookup for reliability-api is tried as reliability-api.reliability-lab.svc.cluster.local first → hit. That's why the short name works only from the same namespace.
    • From the monitoring namespace, reliability-api would be tried as reliability-api.monitoring.svc.cluster.local → miss. Use reliability-api.reliability-lab (the next search entry svc.cluster.local completes it) or the full name.
    • ndots:5 means a name with fewer than 5 dots is tried against the search list before being tried as-is. External names like api.github.com therefore cause a few extra failed lookups first; a trailing dot (api.github.com.) marks a name as fully qualified.
    Widget — DNS name builder
    Build the records for a Service and see which spellings resolve from a caller's namespace (search-list logic as configured by the kubelet).

    Failure cases

    • NXDOMAIN for the short name from another namespace → add .reliability-lab.
    • All lookups time out after you applied an egress NetworkPolicy → you forgot to allow DNS (UDP/TCP 53 to the DNS Pods). See §7.
    • CoreDNS Pods not running → kubectl -n kube-system get pods -l k8s-app=kube-dns (the conventional label; check yours with --show-labels).
    • Pod uses hostNetwork and gets the node's resolver → check dnsPolicy on the Pod.
    Self-check: Prometheus in namespace monitoring must scrape reliability-api. Which name should its config use and why?
    reliability-api.reliability-lab.svc (or the full ...svc.cluster.local). The bare reliability-api expands with the caller's namespace (monitoring) first and fails. In practice the Prometheus Operator discovers Pod endpoints via the API rather than DNS (Module 07), but the rule matters for every hand-written URL.

    5. kubectl port-forward: the developer's tunnel

    kubectl port-forward opens a tunnel from a port on your machine, through the API server and kubelet, to a port on one Pod. It is how you reach a ClusterIP-only service from a laptop during labs.

    kubectl -n reliability-lab port-forward svc/reliability-api 8080:80     # local:remote (remote = Service port)
kubectl -n reliability-lab port-forward deployment/reliability-api 8080:8000
kubectl -n reliability-lab port-forward pod/<pod-name> 8080:8000
kubectl -n reliability-lab port-forward svc/reliability-api :80         # let kubectl pick a free local port

    Example output (yours will differ): 

    Forwarding from 127.0.0.1:8080 -> 8000
Forwarding from [::1]:8080 -> 8000

    Note that the right-hand side shows the Pod port (8000) even when you forwarded to the Service port 80 — kubectl resolved the Service to a Pod and translated the port.

    port-forward is not a load test path

    The task docs are explicit: when you port-forward to a Service, kubectl selects a single Pod and does not load balance. It is TCP-only, blocks the terminal, and the tunnel dies if that Pod dies. Never measure scaling or failover through port-forward; run the load generator inside the cluster against the Service (Module 08).

    6. Getting traffic in from outside: Ingress vs Gateway API

    The problem

    A LoadBalancer Service per app gives you one external IP per Service, with no HTTP awareness (no host/path routing, no shared TLS). For HTTP services you want one entry point that routes api.example.test/ to reliability-api and grafana.example.test/ to Grafana. Kubernetes has two APIs for this.

    6.1 Ingress (stable, frozen)

    An Ingress "exposes HTTP and HTTPS routes from outside the cluster to services within the cluster". It can do host/path routing, TLS termination and name-based virtual hosting. Two facts from the official page that trip people up:

    • "You must have an Ingress controller to satisfy an Ingress. Only creating an Ingress resource has no effect." The controller (for example a proxy deployed in the cluster) watches Ingress objects and configures itself.
    • "The Kubernetes project recommends using Gateway instead of Ingress. The Ingress API has been frozen." It still works and is everywhere, but gets no new features.
    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: reliability-api
  namespace: reliability-lab
spec:
  ingressClassName: <your-ingress-class>   # kubectl get ingressclass
  rules:
    - host: api.reliability.test
      http:
        paths:
          - path: /
            pathType: Prefix                  # Exact | Prefix | ImplementationSpecific
            backend:
              service:
                name: reliability-api
                port:
                  number: 80

    6.2 Gateway API (the recommended successor)

    Gateway API is an add-on set of API kinds (installed as CRDs, implemented by many controllers) that splits the job by role:

          port: 80

    How it works

    1. An implementation (controller) is installed; it registers a GatewayClass with its controllerName.
    2. You create a Gateway referencing that class. The controller provisions the data plane (a cloud LB, or proxy Pods + a LoadBalancer Service) and reports an address in status.
    3. You create an HTTPRoute whose parentRefs names the Gateway. The Gateway's allowedRoutes decides whether the attachment is accepted; check kubectl describe httproute conditions.
    4. Requests to the Gateway address with Host: api.reliability.test are matched and proxied to the Service's ready endpoints.

    On kind, the kind docs state that cloud-provider-kind (v0.9.0+) natively supports Ingress and Gateway API; Module 06 covers that. For this project, port-forward is enough for v1; add Gateway API when you want a realistic entry point.

    IngressGateway API
    StatusStable but frozenRecommended; actively developed; installed as CRDs
    ProtocolsHTTP/HTTPSHTTP, gRPC (stable kinds) and more via other route types
    OwnershipOne object mixes infra and app concernsSplit across roles; cross-namespace attachment is explicit
    PortabilityMany features hidden in controller-specific annotationsMore expressive in the spec itself

    Failure cases

    • Ingress created, nothing happens → no controller / wrong ingressClassName. kubectl get ingressclass.
    • HTTPRoute exists but 404s → route not accepted by the Gateway (namespace not allowed, hostname mismatch). kubectl describe httproute reliability-api → Accepted/ResolvedRefs conditions.
    • no matches for kind "Gateway" → Gateway API CRDs not installed in the cluster.
    • 503 from the proxy → backend Service has no ready endpoints (back to §3).
    Self-check: you apply an Ingress to a fresh kind cluster and kubectl get ingress shows no ADDRESS. Is your YAML wrong?
    Not necessarily. An Ingress has no effect without an Ingress controller; on plain kind there isn't one serving it until you install one (or run cloud-provider-kind). Check kubectl get ingressclass and the controller's logs before editing YAML.

    7. NetworkPolicy: a firewall between Pods

    Definition

    A NetworkPolicy is a built-in API object that controls which traffic may reach (ingress) or leave (egress) selected Pods, at the IP/port level (L3/L4). It selects Pods by label and describes allowed peers by Pod labels, namespace labels or IP blocks.

    The problem it solves

    The network model says every Pod can reach every Pod. That's convenient and dangerous: a compromised Pod in any namespace could call reliability-api, or the API could call anything. NetworkPolicy lets you move to "deny by default, allow what's needed".

    Enforcement depends on the network plugin

    From the official page: "Network policies are implemented by the network plugin. To use network policies, you must be using a networking solution which supports NetworkPolicy. Creating a NetworkPolicy resource without a controller that implements it will have no effect." The API server will happily accept your policy either way — so always test that a policy actually blocks something. kind's default CNI (kindnetd) has had out-of-the-box NetworkPolicy support since kind v0.24.0 (via sigs.k8s.io/kube-network-policies, per the kind release notes); older kind versions silently ignore policies.

    The rules, precisely

    • Default: a Pod is non-isolated; all inbound and outbound connections are allowed.
    • Isolation: a Pod becomes isolated for ingress as soon as any NetworkPolicy selects it and lists Ingress in policyTypes (same for egress).
    • Additive: policies never conflict. The allowed set is the union of all policies that select the Pod. There are no "deny" rules — deny is what's left over.
    • Both ends: a connection needs the source's egress and the destination's ingress to allow it.
    • AND vs OR: a single from element containing both namespaceSelector and podSelector means "Pods with these labels in namespaces with these labels" (AND). Two separate list elements mean either one (OR). One misplaced - changes the meaning.
    • Node traffic: traffic to and from the node where a Pod is running is always allowed — so kubelet probes keep working under default-deny.
    • Existing connections: changes affect new connections; reply traffic for allowed connections is implicitly allowed.
    • Namespace by name: every namespace carries the label kubernetes.io/metadata.name: <name>, which you can select on.
    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: reliability-lab
spec:
  podSelector: {}          # selects every Pod in the namespace
  policyTypes:
    - Ingress              # no ingress rules listed => nothing allowed in
    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-reliability-api
  namespace: reliability-lab
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: reliability-api
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector: {}                      # OR: any Pod in reliability-lab
        - namespaceSelector:                   # OR: any Pod in namespace "monitoring"
            matchLabels:
              kubernetes.io/metadata.name: monitoring
      ports:
        - protocol: TCP
          port: 8000                           # Pod port, not the Service port 80!
    Policies see Pod ports, not Service ports

    Service translation happens before the policy is evaluated at the destination Pod, so rules name the container port 8000. Writing port: 80 here is a classic bug that blocks everything.

    If you also restrict egress, allow DNS

    An egress default-deny blocks DNS too, and then every name lookup fails. If you add egress policies, allow UDP and TCP port 53 to the cluster DNS Pods (in kube-system) explicitly. For v1 of this project, start with ingress policies only.

    Widget — Will this connection be allowed?
    Toggle the two policies above and pick a source and port. The logic follows the documented rules: isolation if any policy selects the Pod for Ingress; allowed set is the union of rules.

    Failure cases & trade-offs

    • Policy applied, nothing changes → CNI doesn't enforce. Test from a Pod in default; it should time out.
    • Everything broke after default-deny → you forgot an allow rule (Prometheus, ingress controller/gateway proxy namespace, load generator).
    • Allow rule "doesn't work" → AND/OR indentation, wrong namespace label, or Service port instead of Pod port.
    • Trade-off: tight policies reduce blast radius but add an inventory burden — every new caller needs a rule. Keep policies in the same chart/kustomization as the app so they evolve together.
    Self-check: you have only allow-reliability-api (no default-deny). Can a Pod in default reach a different app in reliability-lab?
    Yes. allow-reliability-api only selects reliability-api Pods, so only they become isolated. Other Pods in the namespace stay non-isolated until some policy selects them — that's what podSelector: {} in default-deny does.

    8. ConfigMap: configuration outside the image

    Definition

    A ConfigMap is an API object that stores non-confidential data as key–value pairs (data for UTF-8 strings, binaryData for base64 binary). Pods consume it as environment variables, command-line arguments, or files in a read-only volume — or code can read it through the API. A ConfigMap cannot exceed 1 MiB and must be in the same namespace as the Pod that uses it. It provides no secrecy or encryption.

    The problem it solves

    The twelve-factor rule from Module 02: build one image (reliability-api:0.1.0) and run it in many environments with different settings. LOG_LEVEL=debug in the lab, info in production, READY_DELAY_SECONDS=10 for a failure experiment — without rebuilding.

    apiVersion: v1
kind: ConfigMap
metadata:
  name: reliability-api-config
  namespace: reliability-lab
data:
  APP_MODE: "normal"
  LOG_LEVEL: "info"
  READY_DELAY_SECONDS: "5"       # values are strings; the app parses float()
  # file-like key, for the volume example below
  experiment.yaml: |
    name: baseline
    work_ms: 50

    Two ways in: env vs volume

          containers:
        - name: reliability-api
          image: reliability-api:0.1.0
          envFrom:                              # every key becomes an env var (valid names only)
            - configMapRef:
                name: reliability-api-config
          env:
            - name: LOG_LEVEL                   # or pick single keys explicitly
              valueFrom:
                configMapKeyRef:
                  name: reliability-api-config
                  key: LOG_LEVEL
          volumeMounts:
            - name: config
              mountPath: /etc/reliability-api
              readOnly: true
      volumes:
        - name: config
          configMap:
            name: reliability-api-config
            items:
              - key: experiment.yaml
                path: experiment.yaml          # → /etc/reliability-api/experiment.yaml

    Update behaviour (the part people get wrong)

    • Env vars do not update when the ConfigMap changes. The container keeps the values it started with.
    • Mounted ConfigMap volumes are updated eventually by the kubelet (not instantly). Your app must notice and reload the file.
    • Mounts using subPath never receive updates.
    • immutable: true (stable since v1.19) forbids changes after creation; it protects against accidental edits and reduces watch load on the API server. To change config you create a new ConfigMap (e.g. reliability-api-config-v2) and point the Deployment at it — which itself triggers a rollout.

    For reliability-api, the standard way to apply a changed ConfigMap is a rolling restart:

    kubectl -n reliability-lab apply -f deploy/kubernetes/configmap.yaml
kubectl -n reliability-lab rollout restart deployment/reliability-api
kubectl -n reliability-lab rollout status deployment/reliability-api

    Module 06 shows how Helm automates this with a checksum/config annotation, so a values change produces a new Pod template hash and a normal rolling update.

    SymptomCauseCheck

    "I changed LOG_LEVEL but logs are still info"Env vars don't updatekubectl exec … -- env | grep LOG_LEVEL; then rollout restart

    Self-check: you mount the ConfigMap as a volume with subPath: experiment.yaml, then edit the ConfigMap. What does the Pod see?
    Nothing changes — subPath mounts never receive ConfigMap updates. Without subPath the file would update eventually, and the app would still need to re-read it.

    9. Secret: sensitive values, and what actually protects them

    Definition

    A Secret is like a ConfigMap but intended for confidential data: passwords, tokens, keys. It separates sensitive values from Pod specs and images, and Kubernetes handles it somewhat differently (it is a separate resource type you can restrict with RBAC independently of ConfigMaps, and Secret volumes are backed by tmpfs, so they are not written to the node's disk). Same 1 MiB limit; can be immutable.

    base64 is encoding, not encryption

    In YAML, data: values must be base64-encoded; stringData: accepts plain text and the API server encodes it for you. Anyone who can read the object can decode it instantly. Try it:

    Widget — "Encrypt" a secret with base64 (spoiler: you can't)
    Type a value as it would appear under stringData, see what data stores, and decode it back with no key at all.

    The official Secret page opens with a caution worth memorising: by default Secrets are stored unencrypted in the API server's datastore (etcd); anyone with API access can retrieve or modify them, and anyone authorised to create a Pod in a namespace can read any Secret in that namespace (by mounting it). The docs then list the controls that actually protect them:

    1. Enable encryption at rest for Secrets — the API server's --encryption-provider-config with an EncryptionConfiguration. The first provider in the list encrypts new writes; identity means plain text. Providers include aescbc, aesgcm, secretbox and kms. (On kind you don't configure this; on GKE etcd/application-layer encryption is a platform setting — Module 11.)
    2. RBAC with least privilege on Secrets: few subjects get get/list/watch on secrets; consider resourceNames to restrict to specific Secrets. Note that list and watch return Secret contents too.
    3. Restrict Secret access to specific containers — only mount it where needed.
    4. Consider external secret stores (e.g. via the Secrets Store CSI Driver) so the source of truth isn't etcd.

    And outside Kubernetes: never commit Secret manifests with real values to Git (study guide §24: "secrets are not committed"). Create them from the CLI or a secret manager.

    reliability-api example

    The app in this course has no real secret. To practise, give it a fake token for a future upstream dependency:

    # imperative creation — nothing sensitive lands in a file in your repo
kubectl -n reliability-lab create secret generic reliability-api-secrets \
  --from-literal=UPSTREAM_TOKEN='change-me-lab-only'

kubectl -n reliability-lab get secret reliability-api-secrets -o yaml   # note: data is base64
kubectl -n reliability-lab get secret reliability-api-secrets \
  -o jsonpath='{.data.UPSTREAM_TOKEN}' | base64 --decode; echo            # proves it isn't encrypted
              env:
            - name: UPSTREAM_TOKEN
              valueFrom:
                secretKeyRef:
                  name: reliability-api-secrets
                  key: UPSTREAM_TOKEN

    Secret types you'll see: Opaque (default, arbitrary data), kubernetes.io/dockerconfigjson (registry credentials for imagePullSecrets — used for private GHCR images in Module 09), kubernetes.io/tls (cert + key for Ingress/Gateway TLS), kubernetes.io/service-account-token (legacy long-lived SA tokens), plus basic-auth, ssh-auth and bootstrap tokens.

    Env var or file?

    • Env vars: simplest, but leak easily (crash dumps, /proc/<pid>/environ, debug endpoints that print config, child processes inherit them), and don't update.
    • Files: can be updated (eventually), harder to leak by accident, permission bits can be set. Preferred for anything long-lived and sensitive.

    Failure cases

    • CreateContainerConfigError — missing Secret/key, same as ConfigMap.
    • Value has a trailing newline — you base64-encoded echo value instead of echo -n value; use --from-literal or stringData.
    • Secret printed in CI logs or kubectl describe pasted into a ticket — describe shows only byte counts, but get -o yaml shows the (decodable) data.
    Self-check: a teammate says "our Secrets are safe, they're base64". Give two concrete counter-arguments.
    (1) base64 is reversible without any key — base64 --decode recovers the value. (2) By default Secrets sit unencrypted in etcd, and anyone who can create a Pod in the namespace can mount and read them. Real protection is encryption at rest, least-privilege RBAC on secrets and Pod creation, limited mounting, and optionally an external secret store.

    10. Storage: volumes, PV, PVC and StorageClass

    Definition

    A container's filesystem is ephemeral: when the container is replaced, files written to it are gone. A volume is a directory, declared in the Pod spec (spec.volumes) and mounted into containers (volumeMounts), whose lifetime is not tied to the container. The official volumes page distinguishes:

    • Ephemeral volumes — live as long as the Pod (e.g. emptyDir, configMap, secret, projected, downwardAPI). An emptyDir is created when the Pod is assigned to a node and deleted permanently when the Pod is removed; a container crash does not remove it. medium: Memory puts it in RAM; sizeLimit caps it.
    • Persistent volumes — exist beyond any individual Pod. Kubernetes doesn't destroy them when a Pod ends.

    In both cases data survives container restarts.

    The persistent storage API: three objects

    ObjectScopeWho creates itMeaning
    PersistentVolume (PV)ClusterAdmin (static) or a provisioner (dynamic)A piece of real storage (cloud disk, NFS share, local path) represented in the API, with a lifecycle independent of Pods
    PersistentVolumeClaim (PVC)NamespaceApp developerA request: "I need 1Gi, ReadWriteOnce, of class X". Pods mount claims, not PVs.
    StorageClassClusterAdmin / platformA "type" of storage: which provisioner creates volumes, with what parameters, reclaimPolicy (default Delete), volumeBindingMode and allowVolumeExpansion

    How it works, step by step

    1. Static provisioning: an admin pre-creates PVs; a control loop binds a new PVC to a matching PV. Dynamic provisioning: if no static PV matches and the PVC names a StorageClass (or omits it and a default class exists), the class's provisioner creates a volume on demand.
    2. Binding is exclusive and one-to-one: a PV is bound to exactly one PVC. You get at least what you asked for.
    3. With volumeBindingMode: Immediate (the default) provisioning happens when the PVC is created. With WaitForFirstConsumer it is delayed until a Pod using the claim is scheduled — so a local or zonal volume ends up where the Pod runs. Until then the PVC is Pending, which is normal.
    4. "Storage object in use protection" prevents deleting a PVC that a Pod is using, or a PV bound to a claim, from destroying data underneath a running Pod.
    5. When the PVC is deleted, the PV's reclaim policy applies: Delete (default for dynamic PVs) removes the PV and the backing storage; Retain keeps it for manual cleanup; Recycle is deprecated.

    Access modes

    ModeShortMeaning (from the docs)
    ReadWriteOnceRWORead-write by a single node. Multiple Pods on that same node can still use it.
    ReadOnlyManyROXRead-only by many nodes
    ReadWriteManyRWXRead-write by many nodes (needs a storage system that supports it, e.g. a network filesystem)
    ReadWriteOncePodRWOPRead-write by a single Pod — stricter than RWO

    Access modes describe what the volume supports and is mounted as; they are not a lock you can rely on for application-level consistency.

    On kind

    kind installs a default StorageClass during cluster creation. Observed on a kind v0.33.0 cluster (age will differ):

    kubectl get storageclass
NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  22d

    That provisioner creates directories on the node's (container's) filesystem: fine for labs, gone when you delete the cluster, and tied to one node.

    Applied to reliability-api

    reliability-api is stateless — every replica is interchangeable, which is exactly what lets the HPA add and remove Pods freely. It should not get a PVC. Where storage does appear in this project:

    • emptyDir for scratch space (e.g. if you run with readOnlyRootFilesystem: true and Python needs a writable /tmp).
    • A PVC for Prometheus' TSDB in the monitoring stack (Module 07) so metrics survive Prometheus Pod restarts.
    • A PVC for an experiment Job that writes result files you want to collect afterwards (the lab below).
    apiVersion: v1

  name: results
  namespace: reliability-lab
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
  # storageClassName omitted => the default class ("standard" on kind)
---
apiVersion: v1
kind: Pod
metadata:
  name: results-writer
  namespace: reliability-lab
spec:
  restartPolicy: Never
  containers:
    - name: writer
      image: busybox:1.36
      command: ["sh", "-c", "date >> /results/runs.log && cat /results/runs.log"]

    Self-check: why is "add a PVC to reliability-api so it can cache results" a bad idea for this project?
    It makes replicas non-interchangeable.     11. Identity & access: ServiceAccounts and RBAC

    Definitions

    • ServiceAccount (SA): a namespaced, non-human identity used by Pods (and automation such as CI) to authenticate to the API server. Every namespace gets a default SA automatically; a Pod with no serviceAccountName uses it.
    • RBAC (Role-Based Access Control): authorisation via four objects in rbac.authorization.k8s.io:
      • Role — permissions within one namespace;
      • ClusterRole — cluster-wide or cluster-scoped resources, or a reusable set of namespaced permissions;
      • RoleBinding — grants a Role or a ClusterRole to subjects, within one namespace;
      • ClusterRoleBinding — grants a ClusterRole across the whole cluster.

    Key properties: rules are purely additive (no deny rules); a binding's roleRef is immutable (delete and recreate to change it); you can't grant permissions you don't hold yourself (escalation prevention).

    The problem it solves

    Two different questions for this project:

    1. reliability-api itself never calls the Kubernetes API. It needs no permissions and ideally no token mounted at all.
    2. An experiment runner (a Job that kills a Pod and watches recovery, Module 08) does need to list, watch and delete Pods — but only in reliability-lab, and never read Secrets or touch other namespaces.

    Tokens

    Since Kubernetes v1.22, Pods get a short-lived, automatically rotating token obtained via the TokenRequest API and mounted as a projected volume at /var/run/secrets/kubernetes.io/serviceaccount. The default SA has no permissions beyond the API discovery permissions granted to all authenticated principals — but the token is still a credential. Set automountServiceAccountToken: false on workloads that don't need it. The docs also recommend a separate SA per workload rather than sharing default.

    Least-privilege manifests

    apiVersion: v1
kind: ServiceAccount
metadata:
  name: reliability-api
  namespace: reliability-lab
automountServiceAccountToken: false     # the app never calls the API
# Deployment: spec.template.spec.serviceAccountName: reliability-api
    apiVersion: v1
kind: ServiceAccount
metadata:
  name: experiment-runner
  namespace: reliability-lab
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-chaos
  namespace: reliability-lab
rules:
  - apiGroups: [""]                       # "" = core API group (pods, services, secrets…)
    resources: ["pods"]
    verbs: ["get", "list", "watch", "delete"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: experiment-runner
  namespace: reliability-lab
subjects:
  - kind: ServiceAccount
    name: experiment-runner
    namespace: reliability-lab
roleRef:
  kind: Role
  name: pod-chaos
  apiGroup: rbac.authorization.k8s.io

    Verify with kubectl auth can-i

    A ServiceAccount's username is system:serviceaccount:<namespace>:<name>. Impersonate it with --as:

    SA=system:serviceaccount:reliability-lab:experiment-runner
kubectl auth can-i delete pods          --as=$SA -n reliability-lab    # yes
kubectl auth can-i list deployments.apps --as=$SA -n reliability-lab   # yes
kubectl auth can-i delete deployments.apps --as=$SA -n reliability-lab # no
kubectl auth can-i get secrets          --as=$SA -n reliability-lab    # no
kubectl auth can-i delete pods          --as=$SA -n default            # no (binding is namespaced)
kubectl auth can-i --list               --as=$SA -n reliability-lab    # everything it can do
    Widget — kubectl auth can-i simulator for experiment-runner
    Evaluates the Role and RoleBinding above (additive rules, namespaced binding). Real clusters also grant some discovery permissions to all authenticated users; those aren't modelled.

    Failure cases

    • Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:reliability-lab:experiment-runner" cannot delete resource "pods" ... — the message names the exact user, verb, resource and namespace: add precisely that rule, nothing more.
    • Rule for deployments with apiGroups: [""] does nothing — Deployments are in the apps group.
    • Want kubectl exec or logs? Those are subresources: pods/exec, pods/log.
    • Changing roleRef fails — it's immutable; delete and recreate the binding.
    • Granting edit "to make it work": the default ClusterRoles cluster-admin, admin, edit, view are handy for humans but far broader than an automation needs (for example edit can read Secrets in the namespace).

    Trade-offs

    • Fine-grained Roles are safer but need maintenance as tools evolve; start minimal and add rules driven by Forbidden errors.
    • Reusing a ClusterRole via a namespaced RoleBinding gives you one definition with per-namespace grants.
    • Remember RBAC protects the API. It does nothing for network traffic between Pods — that's NetworkPolicy's job.
    Self-check: a RoleBinding in reliability-lab references the ClusterRole view. Can the subject list Pods in monitoring?
    No. A RoleBinding grants the referenced role's permissions only within the binding's own namespace, even when the role is a ClusterRole. A ClusterRoleBinding would be needed for cluster-wide access.

    Glossary

    CNI plugin
    Pod network implementation that assigns Pod IPs and routes between nodes; may also enforce NetworkPolicy. kindnetd on kind.
    ClusterIP
    Virtual, in-cluster IP of a Service; not bound to any interface.
    EndpointSlice
    API object listing a Service's backend IPs/ports with ready/serving/terminating conditions; ≤100 endpoints per slice by default.
    kube-proxy
    Per-node agent that watches Services/EndpointSlices and programs iptables/nftables/ipvs rules to translate VIP traffic to Pod IPs.
    targetPort
    Pod port (number or name) a Service forwards to; defaults to port.
    NodePort
    Port (30000–32767 by default) opened on every node for a Service.
    Headless Service
    clusterIP: None; DNS returns Pod IPs, no proxying.
    ExternalName
    Service that is just a DNS CNAME to an external name.
    CoreDNS
    The usual cluster DNS server; answers *.svc.cluster.local.
    ndots
    resolv.conf option: names with fewer dots are tried with search domains first (5 in Pods).
    Ingress
    Frozen HTTP routing API; needs an Ingress controller.
    Gateway API
    Role-oriented successor: GatewayClass, Gateway, HTTPRoute, GRPCRoute; installed as CRDs.
    NetworkPolicy
    L3/L4 allow-list for Pod ingress/egress; additive; enforced only by supporting CNIs.
    ConfigMap
    Non-confidential key–value config (≤1 MiB) consumed as env, args or files.
    Secret
    Confidential key–value data; base64-encoded, unencrypted in etcd unless encryption at rest is configured.
    PV / PVC
    Real storage in the API / a namespaced request for storage; bound one-to-one.
    StorageClass
    Describes a provisioner and parameters for dynamic provisioning.
    Access modes
    RWO (one node), ROX, RWX, RWOP (one Pod).
    ServiceAccount
    Namespaced workload identity; short-lived projected token.
    Role / ClusterRole
    Sets of allowed verbs on resources; namespaced / cluster-wide.
    RoleBinding
    Grants a Role or ClusterRole to subjects within a namespace.

    Self-check

    1. Walk a request from the load-generator Pod to a reliability-api container, naming every component involved.
    Client resolver → CoreDNS returns the ClusterIP for reliability-api.reliability-lab.svc.cluster.local → client connects to VIP:80 → kernel rules programmed by kube-proxy DNAT to a ready endpoint from the EndpointSlice (Pod IP:8000) → CNI Pod network delivers it → NetworkPolicy (if enforced) checks ingress → Uvicorn handles it → reply is reverse-translated.
    2. Your Service has endpoints, but all are ready=false. Name two likely causes and the command to tell them apart.
    Readiness probe failing because the app is still warming up (READY_DELAY_SECONDS) or because the probe path/port is wrong. kubectl describe pod shows "Readiness probe failed" with the HTTP status (503 = app says not ready; connection refused = wrong port).
    3. Map these four numbers for reliability-api exposed as NodePort 30080: 8000, 80, 8000, 30080.
    containerPort: 8000 (app listens), port: 80 (Service VIP port), targetPort: 8000 (Pod port the Service forwards to), nodePort: 30080 (port on every node). Path: nodeIP:30080 → ClusterIP rules → PodIP:8000.
    4. Why does a LoadBalancer Service stay <pending> on a bare local cluster?
    The external IP is provisioned by a cloud controller. Without one (plain kind) nothing fulfils the request. Use port-forward, NodePort + kind port mappings, or cloud-provider-kind.
    5. You applied default-deny-ingress and the Pods stayed Ready. Why weren't probes blocked?
    Traffic to and from the node where a Pod runs is always allowed by NetworkPolicy, and kubelet probes come from the node.
    6. In a NetworkPolicy, what's the difference between one from item with both namespaceSelector and podSelector, and two items each with one?
    One item = AND (Pods with those labels in namespaces with those labels). Two items = OR (any Pod from those namespaces, or Pods with those labels in the policy's own namespace).
    7. You edit LOG_LEVEL in the ConfigMap. When does reliability-api pick it up?
    Only when containers restart, because it's consumed as an env var. Do kubectl rollout restart deployment/reliability-api (or have Helm change a checksum annotation).
    8. List four controls that actually protect Kubernetes Secrets.
    Encryption at rest in etcd; least-privilege RBAC on secrets (and on Pod creation, since Pod creators can mount Secrets); mounting Secrets only into containers that need them; an external secret store. Plus: never commit them to Git.
    9. A PVC is Pending on kind before any Pod uses it. Bug?
    No — kind's default class uses WaitForFirstConsumer, so provisioning waits until a Pod using the claim is scheduled.
    10. What's the difference between RWO and RWOP?
    RWO restricts read-write mounting to a single node (several Pods on that node may share it). RWOP restricts it to a single Pod.
    11. Write the auth can-i command that checks whether experiment-runner can read Secrets, and predict the answer.
    kubectl auth can-i get secrets --as=system:serviceaccount:reliability-lab:experiment-runner -n reliability-lab → no; the Role only covers pods and apps/deployments, and RBAC is additive with nothing granting secrets.
    12. Ingress or Gateway API for a new project, and why?
    Gateway API: the Kubernetes project recommends it and has frozen Ingress. It is role-oriented and more expressive. Ingress is still fine to understand and maintain where it already exists.
