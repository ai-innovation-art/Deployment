    Module 02 · Docker & Containers

    In Module 01 you ran reliability-api as a plain Linux process. Here you package it as a versioned, immutable image, reliability-api:0.1.0, that runs the same way on your laptop, in CI, and in Kubernetes.     Why containers? VMs vs containers

    Problem. "It works on my machine" happens because the app depends on many things outside its own code: the Python version, installed packages, OS libraries, environment variables, and file paths. Each machine differs slightly. A container image packages the app together with its userland dependencies into one versioned artifact. A container runs that artifact as an isolated process.

    Key point from Module 01: a container is not a small VM. It is a normal Linux process placed in namespaces (its own view of PIDs, network, mounts, hostname) and cgroups (CPU and memory limits), with the image's files as its root filesystem. All containers on a host share one kernel.

    Virtual machineContainer
    Isolation boundaryHardware virtualisation, separate kernelKernel namespaces + cgroups, shared kernel
    StartupBoots an OSStarts a process
    SizeGBs (full OS)MBs to hundreds of MBs (userland only)
    SecurityStronger. A kernel bug in a guest rarely affects the hostA kernel bug can affect all containers. Hence non-root and minimal images
    Used for reliability-apiKubernetes nodes are often VMs (GKE, Module 11)The app itself, in every environment

    Images, containers, registries, and the OCI standard

    Image
    A read-only, layered filesystem plus metadata (default command, env, user, exposed ports). From the Docker docs: "Images are immutable. Once an image is created, it can't be modified. You can only make a new image or add changes on top of it."
    Container
    A running (or stopped) instance of an image: the image layers plus a thin writable layer, a process, namespaces, cgroups, and config (ports, env, mounts).
    Registry
    A server that stores and serves images: Docker Hub, GitHub Container Registry (ghcr.io, Module 09), Google Artifact Registry (Module 11). Inside a registry, a repository holds the versions of one image.
    Tag
    A human-friendly, mutable pointer to an image version, e.g. 0.1.0, 3.12-slim, latest.
    Digest
    The content hash (sha256:…) of an image manifest. It is immutable: same digest ⇒ same bytes.

    What an image actually is

    OCI: why your Docker image runs on Kubernetes

    The Open Container Initiative (OCI) is "a lightweight, open governance structure (project), formed under the auspices of the Linux Foundation, for the express purpose of creating open industry standards around container formats and runtimes". It was launched in 2015 by Docker, CoreOS, and others. It maintains three specifications:

    • Image Specification: the manifest/config/layers format above.
    • Runtime Specification: how to run an unpacked "filesystem bundle". runc is the reference implementation that Docker and containerd use.
    • Distribution Specification: the HTTP API for pushing to and pulling from registries.

    Because of these standards, an image you build with Docker can be pushed to GHCR and pulled and run by containerd on a kind node or a GKE node. Kubernetes does not need Docker itself (Module 03).

    Layers, the union filesystem, and copy-on-write

    From the Docker docs: "Each layer in an image contains a set of filesystem changes - additions, deletions, or modifications." When a container starts, "a union filesystem is created where layers are stacked on top of each other, creating a new and unified view", and "a directory is created specifically for the running container". This directory is the writable layer.

    • Copy-on-write (Docker storage docs): "If a file or directory exists in a lower layer within the image, and another layer (including the writable layer) needs read access to it, it just uses the existing file. The first time another layer needs to modify the file … the file is copied into that layer and modified."
    • Deleting a file in a later layer does not shrink the image. The bytes remain in the earlier layer, and the later layer only records "deleted". That is why cleanup must happen in the same RUN that created the files, or why you use multi-stage builds.
    • Ephemeral by design: anything the app writes to its writable layer disappears when the container is removed or replaced (every Kubernetes rollout replaces containers). Persistent data belongs in volumes.

# ---- Base image: pinned tag. For fully reproducible builds also pin the digest:
#      ARG PYTHON_IMAGE=python:3.12-slim@sha256:<digest-you-resolved>
ARG PYTHON_IMAGE=python:3.12-slim

# ================= Stage 1: builder — create a virtualenv with dependencies =================
FROM ${PYTHON_IMAGE} AS builder
ENV PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
# Copy ONLY the dependency list first, so code edits don't invalidate the slow pip layer
COPY requirements.txt /tmp/requirements.txt
RUN pip install -r /tmp/requirements.txt

# ================= Stage 2: runtime — only what is needed to run =================
FROM ${PYTHON_IMAGE} AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH" \
    APP_MODE=normal \
    LOG_LEVEL=info \
    READY_DELAY_SECONDS=0
# Dedicated unprivileged user with a fixed numeric UID/GID (Kubernetes runAsNonRoot can verify it)
RUN groupadd --system --gid 10001 app \
 && useradd --system --uid 10001 --gid app --no-create-home --shell /usr/sbin/nologin app
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
# Code is owned by root (default) and only readable by the app user: the app can't modify itself
COPY app/ ./app/
USER 10001:10001
EXPOSE 8000
# Docker-only health status (Kubernetes ignores this; it uses probes — see below)
HEALTHCHECK --interval=10s --timeout=3s --start-period=10s --retries=3 \
  CMD ["python", "-c", "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2).status == 200 else 1)"]
# Exec form: uvicorn becomes PID 1 and receives SIGTERM directly. Bind 0.0.0.0 (Module 01).
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

    Build context and .dockerignore

    Definition. The build context is "the set of files that your build can access". When you run docker build ., the . is the context. Only files inside it can be COPY'd. A .dockerignore file, placed "in the root directory of the context", excludes files from it using glob patterns similar to shell globs.

    Problems it solves. (1) Secrets: without it, a broad COPY . . can bake .env, cloud keys, or .git history into an image layer, where anyone who pulls the image can extract them. (2) Speed: sending a 2 GB .venv or dataset to the builder on every build. (3) Cache stability: irrelevant files changing (e.g. .git) would invalidate a COPY . . layer.

    Defence in depth

    This Dockerfile copies only requirements.txt and app/, an allow-list, so it is safe even without .dockerignore. The ignore file protects against a future COPY . . and keeps the context small. Use both.

    Deleting a secret later does not remove it

    COPY .env . followed by RUN rm .env leaves the file inside the earlier layer, recoverable with docker save and a tar viewer. Keep secrets out of the context. Inject them at run time (-e, --env-file, Kubernetes Secrets) or use BuildKit build secrets (RUN --mount=type=secret) when a build step itself needs a credential.

    The build cache: why instruction order matters

    How it works (Docker "Build cache invalidation"): "The builder begins by checking if the base image is already cached. Each subsequent instruction is compared against the cached layers." For COPY/ADD, "the builder calculates a cache checksum from file metadata", and "The modification time of a file (mtime) is not taken into account". For RUN, only the command string is compared, not what it would download. The critical rule: "Once a layer changes, then all downstream layers need to be rebuilt as well. Even if they wouldn't build anything differently, they still need to re-run."

    Layer-cache simulator
    Pick a Dockerfile and a change, then build. Steps turn ✔ CACHED or ⟳ REBUILT following Docker's rule: the first invalidated step and everything after it re-run. Timings are illustrative.

    Cache gotchas

    • RUN apt-get update alone in a layer gets cached forever. A later apt-get install newpkg then uses a stale package index. Docker's best-practices guide: always combine apt-get update and apt-get install in one RUN, and clean /var/lib/apt/lists/* in the same step.
    • Unpinned dependencies plus cache = "works on my machine" for builds. pip install fastapi is cached on your laptop with last month's version, while CI (no cache) gets today's. Pin versions in requirements.txt.
    • Fresh build on purpose: docker build --pull --no-cache … re-checks the base image and ignores the cache. The best-practices guide recommends this combination for periodic rebuilds that pick up security fixes.

    Multi-stage builds

    Definition (Docker docs): "Each FROM instruction can use a different base, and each of them begins a new stage of the build. You can selectively copy artifacts from one stage to another, leaving behind everything you don't want in the final image." Stages are named with AS name, files move with COPY --from=name, and docker build --target name stops at a chosen stage. With BuildKit, "only … stages your target depends on" are built.

    Honest trade-off for this app

    reliability-api's dependencies are pure-Python or ship prebuilt wheels, so the size win over a careful single-stage build is modest (mostly pip's own leftovers). The pattern pays off as soon as a dependency needs a compiler (build-essential can add hundreds of MB), and it is the standard shape you will reuse for Go, Node, or model-serving images. Measure it in Lab 2 rather than assuming.

    $ docker build --target builder -t reliability-api:builder .   # stop at the builder stage (debugging)
$ docker run --rm -it reliability-api:builder bash              # poke around inside it
$ docker build -t reliability-api:0.1.0 .                       # full build → runtime stage

    Running as non-root

    Problem. By default a container's process runs as root (UID 0) unless the image sets USER. Namespaces limit what that root can see, but it is still UID 0 to the shared kernel. If the app is compromised, root inside the container can install tools, rewrite the app, and make any kernel or runtime escape bug much more dangerous. Docker's best-practices guide: create a dedicated user and switch with USER.

    How the reliability-api image does it

    1. groupadd --system --gid 10001 app && useradd --system --uid 10001 …: a fixed, high, numeric ID that cannot collide with host system users.
    2. Code is copied before USER and without --chown. Docker's reference: "Without this flag, files are created with UID and GID of 0." The code is therefore root-owned and world-readable, and the app user can read and execute it but not modify it.
    3. USER 10001:10001 uses numeric IDs. Kubernetes' runAsNonRoot: true check can verify a numeric UID without reading /etc/passwd (Module 05).
    4. The port is 8000, so no CAP_NET_BIND_SERVICE is needed (Module 01, privileged ports).
    $ docker run --rm reliability-api:0.1.0 id
uid=10001(app) gid=10001(app) groups=10001(app)
$ docker run --rm reliability-api:0.1.0 sh -c 'touch /app/app/x'
touch: cannot touch '/app/app/x': Permission denied       # good: code is immutable to the app

    Failure case: the app needs to write somewhere

    If you later add a feature that writes a file (a cache, an upload), it fails with PermissionError. Do not "fix" it with USER root or chmod 777. Write to /tmp, or mount a volume (or a Kubernetes emptyDir) at a dedicated path and give the app user ownership of that path only.

    Image vs container lifecycle

    An image has a simple life: it is built or pulled, tagged, pushed, and eventually removed. A container is a state machine. docker ps filters recognise these states: "created, restarting, running, removing, paused, exited, or dead".

    $ docker create --name ra reliability-api:0.1.0     # created (not running)
$ docker start ra                                   # running
$ docker pause ra; docker unpause ra                # frozen / resumed
$ docker stop ra                                    # SIGTERM → (10 s) → SIGKILL → exited
$ docker ps -a --filter name=ra --format '{{.Names}}  {{.Status}}'
ra  Exited (0) 4 seconds ago
$ docker inspect -f '{{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' ra
exited exit=0 oom=false
$ docker logs ra                                    # logs survive until rm
$ docker rm ra                                      # removed: writable layer + logs gone
# Example output (yours will differ). Exit may be 0 or 143 depending on Uvicorn version (Module 01).

    Tags, digests, and registries

    A full image reference is [registry/][namespace/]repository[:tag][@digest]. reliability-api:0.1.0 is local (Docker Hub is the default registry when none is given). In CI you will push ghcr.io/<you>/reliability-api:<git-sha> (Module 09).

    Tag (:0.1.0, :latest)Digest (@sha256:…)
    MutabilityMutable: anyone with push rights can point it at a new imageImmutable: a hash of the content
    Good forHumans, release names, "which version is this?"Reproducible builds, deploys, rollbacks, supply-chain security
    RiskTwo nodes pulling :0.1.0 at different times can run different bytesHard to read. You will not get security fixes until you update it deliberately

    Docker's best-practices guide: "By pinning your images to a digest, you're guaranteed to always use the same image version, even if a publisher replaces the tag with a new image." The pull docs describe the digest as an "immutable identifier". Digests work in pull, run, create, rmi, and in a Dockerfile's FROM.

    Why latest is not a version

    latest is just the default tag name used when you omit one. It does not mean "newest", and it says nothing about what is inside. Deploying :latest makes rollbacks ambiguous ("which latest?"). Kubernetes also defaults imagePullPolicy to Always for :latest (Module 03). Use explicit versions, and in CI an immutable tag such as the git SHA.

    PID 1, exec form, and signal handling

    This is where Module 01 pays off. docker stop sends SIGTERM (or the image's STOPSIGNAL; "The default is SIGTERM if not defined") to the container's PID 1. It waits "10 seconds for Linux containers" by default (-t/--stop-timeout changes it), then sends SIGKILL. Whether shutdown is graceful depends entirely on which process is PID 1 and whether it handles SIGTERM. A PID 1 with no handler silently ignores SIGTERM (pid_namespaces(7)).

    Exec form vs shell form

    Exec form (✔ use this)Shell form (✘ avoid for the main process)
    SyntaxCMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]CMD uvicorn app.main:app --host 0.0.0.0 --port 8000
    What runsThe executable directly, as PID 1/bin/sh -c "uvicorn …": the shell is PID 1 and Uvicorn is its child
    SignalsUvicorn receives SIGTERM and drains gracefullyDocker: "/bin/sh -c … does not pass signals". SIGTERM goes to the shell, which (as PID 1 without a handler) ignores it. Result: 10 s wait, SIGKILL, exit 137
    Env var expansionNo shell, so $VAR is not expandedShell expands $PORT etc.

    FastAPI's Docker guide makes the same point: "Make sure to always use the exec form to ensure that FastAPI can shutdown gracefully and lifespan events are triggered." Some /bin/sh implementations replace themselves with the command when given a single simple command, so shell form sometimes appears to work. Do not rely on that behaviour. Use exec form.

    Need a shell for variable expansion?

    Use a tiny entrypoint script that ends with exec: exec uvicorn app.main:app --host 0.0.0.0 --port "${PORT:-8000}". exec replaces the shell with Uvicorn (same PID), so Uvicorn becomes PID 1 again.

    docker stop simulator
    Choose how the image starts and run docker stop (default 10 s timeout). The outcome follows the PID 1 rules above.
    Kubernetes uses the same rule

    At Pod termination the kubelet "triggers the container runtime to send a TERM signal to process 1 inside each container", waits terminationGracePeriodSeconds ("The default … is 30 seconds"), then kills. A shell-form image that takes 10 s to stop in Docker takes 30 s per Pod in Kubernetes, and drops in-flight requests at the end. Rolling updates get slow and lossy (Module 04).

    Port mapping: two hops, two bindings

    Docker's port-publishing docs: "when a container's ports are mapped without any specific host address, the Docker daemon publishes ports to all host addresses (0.0.0.0 and [::])", and "publishing container ports is insecure by default". To restrict to the local machine: -p 127.0.0.1:8080:80. -P publishes all EXPOSEd ports to random host ports.

    Port-mapping explorer
    Build a docker run and a curl. See whether it works, what docker ps shows, and why.

    Resource limits: --memory, --cpus, and exit 137

    These flags write cgroup settings (Module 01): "Docker modifies the settings for the container's cgroup on the host machine." They behave differently:

    Storage: writable layer, volumes, bind mounts, tmpfs

    The writable layer is ephemeral: "When a container is destroyed, the writable layer is destroyed with it. Using a volume ensures that the data is persisted even if the container using it is removed." Docker offers three mount types:

    $ docker volume create ra-data
$ docker run --rm --mount type=volume,src=ra-data,dst=/data alpine sh -c 'date >> /data/log; cat /data/log'
$ docker run --rm -v ra-data:/data alpine cat /data/log        # -v short form; data still there
$ docker run --rm --mount type=bind,src="$PWD/app",dst=/app/app,readonly reliability-api:0.1.0   # live code, read-only
$ docker run --rm --mount type=tmpfs,dst=/tmp/scratch reliability-api:0.1.0
    • Mounting over a non-empty directory hides it: "the pre-existing files are obscured by the mount". Bind-mounting an empty host folder over /app/app makes the app's code "disappear", and Uvicorn fails with ModuleNotFoundError.
    • Permissions with bind mounts: files keep their host UID/GID. The container's UID 10001 may not be able to read them. Check with ls -ln.
    • reliability-api is stateless: it needs no volume. That is deliberate. Stateless replicas are what make Kubernetes scaling and self-healing easy.

    Networks: user-defined bridges and container DNS

    Containers "have networking enabled by default, and they can make outgoing connections." Every container without --network joins the default bridge. On it, containers reach each other only by IP. User-defined bridge networks add two things: "automatic DNS resolution between containers" by name or alias, and isolation, because only containers attached to the network can talk to each other.

    $ docker network create reliability-net
$ docker run -d --rm --name reliability-api --network reliability-net reliability-api:0.1.0
$ docker run --rm --network reliability-net curlimages/curl -s http://reliability-api:8000/health

    HEALTHCHECK vs Kubernetes probes

    Docker's HEALTHCHECK "tells Docker how to test a container to check that it's still working. This can detect cases such as a web server stuck in an infinite loop and unable to handle new connections, even though the server process is still running." Status starts as starting, becomes healthy after a passing check, and becomes unhealthy after --retries consecutive failures.

    OptionDefaultreliability-api value
    --interval30s10s
    --timeout30s (a check that runs longer fails and is SIGKILLed)3s
    --start-period0s (failures here do not count)10s
    --start-interval5s (Docker Engine 25.0+)default
    --retries33

    Exit status of the check command: 0 = healthy, 1 = unhealthy, 2 = reserved ("don't use this exit code"). Only one HEALTHCHECK counts, the last one in the Dockerfile. Check output (first 4096 bytes) is stored and visible with docker inspect.

    $ docker inspect --format '{{.State.Health.Status}}' reliability-api
healthy
$ docker inspect --format '{{json .State.Health}}' reliability-api | python3 -m json.tool | head -20
    Docker HEALTHCHECKKubernetes probes (Module 04)
    Defined inThe image (Dockerfile)The Pod spec. Kubernetes does not use the image's HEALTHCHECK
    Who runs itDocker daemon, inside the container (needs Python/curl in the image)The kubelet: httpGet from outside the container, or exec/tcp/gRPC
    KindsOneThree: startup, liveness (restart if failing), readiness (remove from Service endpoints if failing)
    Action on failureOnly marks unhealthy. Plain docker run does not restart the container. Compose can wait on itLiveness: restart the container. Readiness: stop sending traffic. Startup: hold off the other probes
    reliability-api/healthliveness → /health, readiness → /ready (503 during READY_DELAY_SECONDS)

    Kubernetes probe docs: "Based on the probe results, Kubernetes can restart unhealthy containers or stop sending traffic to containers that are not ready." An HTTP probe succeeds if "the response has a status code greater than or equal to 200 and less than 400". Keep the Docker HEALTHCHECK for local and Compose use, and define real probes in Kubernetes.

    Docker Compose (brief)

    What it is. A YAML file (compose.yaml, following the Compose Specification) that declares several services (containers), their networks, and volumes. docker compose up creates them together. Compose automatically creates a network for the project, so services resolve each other by service name. It is a stepping stone toward Kubernetes' declarative model, not a replacement for it.

    services:
  reliability-api:
    build: .
    image: reliability-api:0.1.0
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      LOG_LEVEL: info
      READY_DELAY_SECONDS: "5"
    mem_limit: 256m
    cpus: 1.0

  loadgen:
    image: curlimages/curl
    depends_on:
      reliability-api:
        condition: service_healthy    # waits for the image's HEALTHCHECK to pass
    entrypoint: ["sh", "-c", "while true; do curl -s 'http://reliability-api:8000/work?ms=50'; echo; sleep 1; done"]
    $ docker compose up -d --build
$ docker compose ps
$ docker compose logs -f loadgen
$ docker compose down               # stops and removes containers and the default network

    Docker docs on depends_on: "Compose waits for healthchecks to pass on dependencies marked with service_healthy." Compose has no rolling updates, no multi-node scheduling, and no Service load balancing across replicas the way Kubernetes has them. That gap is why Module 03 exists.

    Restart policies, run-time hardening, and pushing to a registry

    Restart policies: Docker's tiny "self-healing"

    A restart policy "controls whether the Docker daemon restarts a container after exit".

    --restartBehaviour (docs)When for reliability-api
    no (default)Don't automatically restartLabs. You want to see the crash
    on-failure[:max-retries]Restart if it exits with a non-zero codeA single host running the API without an orchestrator
    alwaysAlways restart if it stops (a manual stop sticks until the daemon or container restarts)Long-running services on one host
    unless-stoppedLike always, but a stopped container is not restarted even after a daemon restartSame, when you want manual stops to persist

    The docs also note "An increasing delay (double the previous delay, starting at 100 milliseconds) is added before each restart". That is the same idea as Kubernetes' CrashLoopBackOff, which you will meet in Module 04. Docker restarts on exit only. It does not restart a container that is unhealthy but still running. Kubernetes liveness probes add exactly that.

    Run-time hardening flags (defence in depth)

    $ docker run --rm -d --name reliability-api -p 127.0.0.1:8000:8000 \
    --read-only --tmpfs /tmp \
    --cap-drop ALL \
    --security-opt no-new-privileges=true \
    --pids-limit 100 \
    --memory 256m --cpus 1 \
    reliability-api:0.1.0
    FlagDocsWhy it is safe for reliability-api
    --read-only"Mount the container's root filesystem as read only"The app writes nothing to disk. A --tmpfs /tmp gives libraries that expect a writable temp dir somewhere to write
    --cap-drop ALL"Drop Linux capabilities"Port 8000 needs no CAP_NET_BIND_SERVICE, and a non-root user rarely needs any capability
    --security-opt no-new-privileges=true"Disable container processes from gaining new privileges"Blocks setuid-binary privilege escalation inside the container
    --pids-limit"Tune container pids limit"Caps fork bombs. Uvicorn with one worker uses only a few PIDs

    These map almost one-to-one to Kubernetes securityContext fields (readOnlyRootFilesystem, capabilities.drop, allowPrivilegeEscalation: false), which you will set in Module 05. Verify each flag in Lab 1 by running the app with it and calling every endpoint. A hardening flag that breaks the app gets removed in a hurry, so test first.

    Glossary

    Image
    Immutable, layered filesystem + config. Identified by digest, named by tags.
    Container
    Process(es) started from an image, with namespaces, cgroups, and a writable layer.
    Layer
    A set of filesystem changes produced by one build step. Shared between images and containers.
    Writable layer
    Per-container copy-on-write layer. Deleted with the container.
    Build context
    The set of files the builder can access (the . in docker build .).
    .dockerignore
    Patterns excluding files from the build context.
    Build cache
    Reuse of previous step results. Invalidated from the first changed step downward.
    Multi-stage build
    Several FROM stages in one Dockerfile. Copy only artifacts into the final stage.
    Exec form / shell form
    CMD ["a","b"] runs directly as PID 1. CMD a b runs under /bin/sh -c.
    PID 1
    First process in the container's PID namespace. It receives docker stop's signal and ignores signals it has no handler for.
    docker-init / tini
    Minimal init (--init) that forwards signals and reaps zombies.
    Registry / repository
    Image server / a named collection of versions of one image within it.
    Tag / digest
    Mutable human label / immutable sha256 content address.
    OCI
    Open Container Initiative. Image, Runtime, and Distribution specifications that make images portable across Docker, containerd, and Kubernetes.
    Port publishing
    -p hostIP:hostPort:containerPort: forward host traffic into a container.
    Volume / bind mount / tmpfs
    Docker-managed persistent storage / a host path mounted in / memory-backed temporary storage.
    User-defined bridge
    Docker network with embedded DNS (127.0.0.11) and isolation from other networks.
    HEALTHCHECK
    Image-defined check that sets a Docker health status. Not used by Kubernetes.
    OOMKilled
    Container's main process was SIGKILLed for exceeding its memory limit (exit 137).
    Throttling
    CPU over the --cpus quota is delayed to the next period. Slower, not killed.

    Self-check

    1. What is the difference between an image and a container, in one sentence each?
    An image is an immutable, layered package of a filesystem plus run configuration, identified by a digest. A container is a running (or stopped) instance of it: a process with namespaces, cgroups, and its own thin writable layer on top of the shared image layers.
    2. You edit app/main.py. Which steps of the reliability-api Dockerfile re-run, and why does the pip install not re-run?
    Only the runtime stage's COPY app/ ./app/ and the metadata steps after it (USER, EXPOSE, HEALTHCHECK, CMD). The builder stage copies only requirements.txt, whose checksum did not change, so pip install and COPY --from=builder stay cached.
    3. Why is CMD uvicorn app.main:app … (shell form) a reliability bug?
    It runs under /bin/sh -c, so the shell is PID 1. docker stop or the kubelet sends SIGTERM to the shell, which typically neither handles nor forwards it, and PID 1 ignores signals without handlers. Uvicorn never drains. After the grace period (10 s Docker / 30 s Kubernetes) everything is SIGKILLed: exit 137, slow rollouts, dropped requests.
    4. docker run -p 8000:8000 reliability-api:0.1.0 works from your laptop. Who else can reach it, and how do you restrict it?
    Without a host IP, Docker publishes on all host addresses (0.0.0.0 and ::), so anyone who can reach your machine's network interfaces can, subject to host firewalls. Use -p 127.0.0.1:8000:8000 to restrict it to the local machine.
    5. Why pin the base image by digest if you already pin the tag 3.12-slim?
    Tags are mutable. 3.12-slim is re-pointed whenever upstream publishes patch releases or OS updates. A digest guarantees the exact same bytes, so builds are reproducible and changes are deliberate. Combine it with a scheduled rebuild (or a dependency bot) so you still pick up security fixes.
    6. A container exits with 137. List the checks that tell you whether it was an OOM kill.
    docker inspect -f '{{.State.OOMKilled}}' (true = OOM). docker stats history or metrics near the limit. Kernel log (journalctl -k on Linux hosts). If OOMKilled is false and the stop took exactly the stop timeout, it was SIGKILL after an ignored SIGTERM.
    7. Two containers on the default bridge cannot reach each other by name. Why, and what is the fix?
    Only user-defined networks get Docker's embedded DNS (127.0.0.11) with name resolution. On the default bridge, containers can reach each other only by IP. Create a network (docker network create reliability-net) and attach both with --network.
    8. Docker reports healthy. Will Kubernetes consider the Pod ready?
    Not because of that. Kubernetes ignores the image's HEALTHCHECK. Readiness comes only from a readiness probe in the Pod spec (for reliability-api, /ready). Without a readiness probe, a container counts as ready as soon as it is running, which may be before the app can serve traffic.
    9. Why does the runtime stage use USER 10001:10001 instead of USER app?
    Numeric IDs are unambiguous and let Kubernetes' runAsNonRoot check verify the user without resolving names inside the image. A fixed high UID also avoids colliding with system users.
    10. You COPY .env . and then RUN rm .env. Is the secret gone from the image?
    No. The file still exists in the layer created by the COPY step. Later layers only mark it deleted. Anyone with the image can extract it. Keep it out of the context (.dockerignore) and inject secrets at run time.
    11. What do the three OCI specifications standardise, and why does that matter for this course?
    Image format (manifest/config/layers), runtime (how to run a filesystem bundle; runc), and distribution (registry push/pull API). Because of them, the image you build with Docker and push to GHCR runs unchanged on containerd in kind or GKE.
