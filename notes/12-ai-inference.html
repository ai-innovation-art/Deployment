    Model server vs application; online vs batch

    Definition. A model server is a long-running process that loads model weights into (GPU or CPU) memory once and answers inference requests over a network API — vLLM, Triton, TGI, or KServe's runtimes. The application is your business logic: auth, prompt templates, validation, retries, logging, rate limits. In this course, reliability-api is the application and the model server is a separate Deployment behind its own Service.

    Problem it solves. Model servers have a completely different resource profile: gigabytes of weights, minutes to start, accelerator-bound, and throughput that depends on batching. Keeping them separate lets you scale, upgrade and place them independently (cheap CPU nodes for the app, expensive GPU nodes for the model), and swap the model server without rewriting the app.

    The LLM request lifecycle: prefill vs decode

    Definition. Autoregressive generation has two phases. Prefill processes all prompt tokens in one forward pass (highly parallel, compute-bound), writing each layer's attention keys/values into the KV cache, and produces the first output token. Decode then produces one token per step per sequence, each step reading the whole KV cache (memory-bandwidth-bound) and appending one more entry.

    Why an operator must care. The two phases map to different user-visible metrics (prefill + queueing → TTFT; decode → inter-token latency) and different bottlenecks. Long prompts hurt TTFT; long outputs and many concurrent sequences hurt ITL and fill the KV cache; a full KV cache forces the server to queue or preempt requests — which shows up as queue depth, not CPU.

    The KV cache as the real capacity limit

    Each running sequence holds KV entries for prompt + generated tokens. Memory per token depends on layers × heads × head size × dtype, so a server has a fixed budget of tokens it can hold at once. vLLM manages this budget in fixed-size blocks (PagedAttention) and reports vllm:kv_cache_usage_perc (fraction of used blocks, 0–1). When it approaches 1, new requests wait (queue grows) or running ones are preempted (vllm:num_preemptions). This is why "how many concurrent requests can one replica take?" depends on prompt and output lengths, not just on request count.

    Self-check: users complain that the first word appears slowly, but once text starts it streams quickly. Which phase/metric do you investigate first?
    TTFT = queueing + prefill. Check queue depth (vllm:num_requests_waiting, vllm:request_queue_time_seconds) and prompt lengths (vllm:request_prompt_tokens, prefill time). Fast streaming means decode/ITL is fine. Fixes: more replicas (queue), shorter prompts / prefix caching (prefill), or limiting concurrency per replica.

    Why averages lie (again)

    Module 08's lesson applies doubly: report p50/p90/p99 of TTFT and ITL, not means. A server can have a fine mean TTFT while 5% of requests wait seconds in the queue. And never average percentiles across replicas — aggregate histogram buckets, then compute quantiles:

    histogram_quantile(0.95,
  sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))

    Self-check: run A shows 900 output tokens/s; run B shows 1,400 tokens/s. B is "better", right?
    Not necessarily. B may achieve higher system throughput by running more concurrent sequences, which raises ITL and TTFT per user. Compare at a fixed latency SLO (goodput), and check per-user tokens/s, p95 TTFT/ITL, error rate and that both runs used the same prompts, lengths and concurrency.

    Batching: static, dynamic, continuous

    Definition. Batching runs several requests through the model in the same forward pass. Accelerators are far more efficient on a batch than on a single sequence, because weight reads from memory are amortised across sequences.

    Problem it solves. Serving one request at a time leaves most of a GPU idle and makes tokens/s (and cost per token) terrible. The question is how to form batches without making individual users wait too long.

    StrategyHow it worksStrengthWeakness
    Staticfixed batch formed by the caller/client; runs to completionsimple; fine for offline jobs with equal-length itemsoutput lengths vary wildly for LLMs → idle slots; head-of-line blocking
    Dynamicserver collects requests for up to T ms or B items, then runs themgreat for fixed-shape models (classifiers, embeddings)adds up to T ms latency; still static once started
    Continuousscheduler re-forms the batch every decode step; new requests prefill and joinhighest utilisation for generationmore sequences per step → each step slower (ITL ↑); KV cache becomes the limit

    Server knobs (vLLM examples): --max-num-seqs (max sequences per step), --max-num-batched-tokens (token budget per step), --enable-chunked-prefill (split long prefills so they do not stall decodes; the vLLM Kubernetes GPU example uses it). Defaults and availability vary by version — check vllm serve --help.

    Concurrency vs latency: the core trade-off

    More concurrent requests per replica means bigger batches: throughput goes up, then flattens (the batch or KV cache is full), while per-request latency goes up — slowly at first (each step a little slower), then sharply (requests start queueing). The knee of that curve is the replica's useful capacity, and it is what your autoscaler target should be based on.

    Concurrency ↔ latency visualiser — a TOY model
    Illustrative only. A deliberately simple closed-loop model: each decode step costs d₀·(1 + k·(active−1)) ms; at most B sequences run; extra clients queue. Real servers differ (chunked prefill, preemption, memory limits). Use it to build intuition, never to predict capacity — measure that with AIPerf.

    What to notice: below B, throughput rises almost linearly while latency rises gently — free capacity. Above B, throughput is flat and every extra client only adds queueing delay (TTFT explodes first). Production lesson for reliability-api: cap concurrency per model-server replica near the knee and add replicas rather than letting one replica queue endlessly.

    CPU vs GPU on Kubernetes

    Definition. Kubernetes natively understands CPU and memory. GPUs are extended resources advertised by a vendor device plugin. Per the Kubernetes "Schedule GPUs" task page: the administrator installs vendor drivers on nodes and runs the vendor's device plugin; Pods then request e.g. nvidia.com/gpu or amd.com/gpu.

    Rules for GPU resources (from kubernetes.io)

    • GPUs "are only supposed to be specified in the limits section": you may set only a limit (the request defaults to it); if you set both they must be equal; you cannot set a request without a limit.
    • GPUs are whole integers per container in this model — no 0.5 GPU. Sharing is done by other mechanisms (below).
    • Label GPU nodes (e.g. kubectl label nodes node1 accelerator=example-gpu-x100) and use nodeSelector/affinity to target a GPU type; the page recommends Node Feature Discovery to label automatically.
    spec:
  nodeSelector:
    accelerator: example-gpu-x100        # your label (or cloud provider label)
  tolerations:
  - key: nvidia.com/gpu                  # match the taint your platform applies
    operator: Exists
    effect: NoSchedule
  containers:
  - name: model-server
    image: vllm/vllm-openai:<pinned-version>
    resources:
      limits:
        nvidia.com/gpu: 1                # request defaults to the limit
        memory: 20Gi
      requests:
        cpu: "2"
        memory: 6Gi

    Why taints? GPU nodes are expensive. Tainting them (commonly with a key like nvidia.com/gpu, effect NoSchedule) keeps reliability-api and other CPU Pods off them; only Pods with a matching toleration land there. Check the actual taint with kubectl describe node.

    On GKE Autopilot (Module 11), you instead set nodeSelector: cloud.google.com/gke-accelerator: "nvidia-tesla-t4" (for example) plus limits: nvidia.com/gpu: 1; Autopilot installs default NVIDIA drivers, and GPU Pods use the node-based billing model. Both type and quantity are required. GPU availability and quotas vary by region — and GPUs are the fastest way to an unpleasant bill.

    CPU inference

    Small models (sub-1B parameters) run on CPU, slowly — perfectly adequate for learning the operational workflow. vLLM's own Kubernetes guide notes its CPU deployment is "for demonstration and testing purposes only". Treat CPU results as functional tests, not performance claims.

    Failure cases

    • Pod Pending: Insufficient nvidia.com/gpu — no free GPU, device plugin not running, or node not ready. kubectl describe node | grep -A5 Allocatable.
    • Pending: untolerated taint — add the toleration. Pending: node affinity mismatch — label typo.
    • CUDA errors at start — driver/CUDA version mismatch between node driver and image.
    • OOMKilled — host memory limit too small for weight loading (weights often pass through host RAM). GPU OOM appears in logs, not as OOMKilled.

    Model weights, startup and probes

    Problem. reliability-api starts in under a second. A model server may need minutes: pull a multi-GB image, download several GB of weights, load them into memory, allocate the KV cache, compile/warm kernels. Module 04 probe defaults would kill it long before it is ready, and a rolling update could route traffic to Pods that cannot answer.

    Techniques

    • startupProbe with a generous budget: failureThreshold × periodSeconds ≥ worst-case load time (e.g. 60 × 10 s = 10 min for big models). Once it succeeds, liveness can be strict.
    • Readiness that means "can generate": vLLM exposes /health (the vLLM Kubernetes example uses it for both probes). Our mock returns 503 until "weights are loaded", like reliability-api's READY_DELAY_SECONDS.
    • Model cache on a PVC: mount a PersistentVolumeClaim at the Hugging Face cache path (/root/.cache/huggingface in the vLLM examples) so restarts skip the download. With ReadWriteOnce volumes only one node can mount it; for many replicas use read-only-many storage, pre-baked node images, or per-replica caches (KServe offers LocalModelCache resources for this).
    • Do not bake weights into the image unless they are small: a 15 GB image slows every pull, every node, every rollout. Keep images lean and load weights from a cache.
    • Rollouts: with slow startup, use maxUnavailable: 0, maxSurge: 1 (Module 04) — and remember the surge Pod needs a whole extra GPU.
    • Shared memory: tensor-parallel inference needs /dev/shm; the vLLM GPU example mounts an emptyDir with medium: Memory.
    startupProbe:
  httpGet: { path: /health, port: 8000 }
  periodSeconds: 10
  failureThreshold: 60          # up to 10 minutes to load
readinessProbe:
  httpGet: { path: /health, port: 8000 }
  periodSeconds: 5
  failureThreshold: 3
livenessProbe:
  httpGet: { path: /health, port: 8000 }
  periodSeconds: 10
  failureThreshold: 6           # tolerate short stalls under heavy batches

    Failure cases

    • Restart loop during load: liveness (or a too-short startupProbe) kills the container mid-load. Symptom: RESTARTS climbs, logs end mid-download. vLLM's k8s troubleshooting section describes probe failures with "KeyboardInterrupt: terminated" in logs — that is the kubelet's SIGTERM.
    • Liveness failing under load: a saturated server responds slowly to /health; kubelet restarts it, dropping every in-flight generation and making overload worse. Give liveness a generous timeout/threshold.
    • Disk pressure / evictions: weights downloaded to the container filesystem fill node ephemeral storage. Use a PVC or set ephemeral-storage requests.

    vLLM: an OpenAI-compatible model server

    vLLM implements OpenAI-style HTTP APIs (/v1/completions, /v1/chat/completions, /v1/models, embeddings and more) and exposes Prometheus metrics at /metrics on the same port (8000 by default). Start it with vllm serve <model>:

    vllm serve NousResearch/Meta-Llama-3-8B-Instruct --dtype auto --api-key token-abc123
curl http://localhost:8000/metrics       # Prometheus text format, vllm:* series
    Security note from the vLLM docs

    --api-key only protects endpoints under /v1, /v2 and /inference; other endpoints on the same server (e.g. /invocations) are not authenticated. Do not expose vLLM directly — keep it a ClusterIP Service behind reliability-api or a gateway, and add NetworkPolicy (Module 05) so only reliability-api can reach it.

    The mock model server (default for labs)

    To learn the operational workflow without GPUs or multi-GB downloads, we use mock-llm: a ~90-line FastAPI app that speaks the OpenAI chat API (including SSE streaming), simulates weight loading, prefill and decode with a bounded batch, and exports Prometheus metrics with names modelled on (but deliberately not identical to) vLLM's, so nobody mistakes mock numbers for vLLM numbers.

    import asyncio, json, os, time, uuid
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse, Response, StreamingResponse
from prometheus_client import Counter, Gauge, Histogram, generate_latest, CONTENT_TYPE_LATEST

MAX_BATCH = int(os.getenv("MAX_BATCH", "8"))                      # sequences decoded together
PREFILL_MS_PER_TOKEN = float(os.getenv("PREFILL_MS_PER_TOKEN", "0.5"))
DECODE_STEP_MS = float(os.getenv("DECODE_STEP_MS", "25"))         # step time with 1 running sequence
STEP_COST_PER_SEQ = float(os.getenv("STEP_COST_PER_SEQ", "0.06")) # slowdown per extra running sequence
LOAD_SECONDS = float(os.getenv("LOAD_SECONDS", "20"))             # simulated weight loading

RUNNING = Gauge("mockllm_num_requests_running", "Sequences in prefill/decode")
WAITING = Gauge("mockllm_num_requests_waiting", "Requests waiting for a batch slot")
TTFT = Histogram("mockllm_time_to_first_token_seconds", "Server-side TTFT",
                 buckets=(0.05, 0.1, 0.25, 0.5, 1, 2, 5, 10, 30))
E2E = Histogram("mockllm_e2e_request_latency_seconds", "Server-side E2E latency",
                buckets=(0.5, 1, 2, 5, 10, 20, 40, 80))
GEN_TOKENS = Counter("mockllm_generation_tokens", "Generated tokens")
PROMPT_TOKENS = Counter("mockllm_prompt_tokens", "Prompt tokens")

app = FastAPI()
STARTED = time.monotonic()
slots = asyncio.Semaphore(MAX_BATCH)
running = 0


def loaded() -> bool:
    return time.monotonic() - STARTED >= LOAD_SECONDS


async def generate(prompt_tokens: int, max_tokens: int):
    """Yield tokens with LLM-like timing: queue, prefill, then decode steps."""
    global running
    t0 = time.perf_counter()
    PROMPT_TOKENS.inc(prompt_tokens)
    WAITING.inc()
    await slots.acquire()                       # queue until a batch slot is free
    WAITING.dec()
    RUNNING.inc()
    running += 1
    try:
        await asyncio.sleep(prompt_tokens * PREFILL_MS_PER_TOKEN / 1000)   # prefill
        TTFT.observe(time.perf_counter() - t0)
        GEN_TOKENS.inc()
        yield "tok0 "                           # first token comes out of prefill
        for i in range(1, max_tokens):
            step_ms = DECODE_STEP_MS * (1 + STEP_COST_PER_SEQ * (running - 1))
            await asyncio.sleep(step_ms / 1000)  # one decode step
            GEN_TOKENS.inc()
            yield f"tok{i} "
    finally:
        running -= 1
        RUNNING.dec()
        slots.release()
        E2E.observe(time.perf_counter() - t0)


@app.get("/health")
def health():
    if not loaded():
        return JSONResponse({"status": "loading"}, status_code=503)
    return {"status": "ok"}


@app.get("/v1/models")
def models():
    return {"object": "list", "data": [{"id": "mock-llm", "object": "model"}]}


@app.post("/v1/chat/completions")
async def chat(req: Request):
    if not loaded():
        return JSONResponse({"error": {"message": "model loading"}}, status_code=503)
    body = await req.json()
    text = " ".join(str(m.get("content", "")) for m in body.get("messages", []))
    prompt_tokens = max(1, len(text.split()))   # crude: 1 word = 1 token
    max_tokens = int(body.get("max_tokens") or body.get("max_completion_tokens") or 64)
    model = body.get("model", "mock-llm")
    rid = "chatcmpl-" + uuid.uuid4().hex[:12]

    if body.get("stream"):
        async def sse():
            async for tok in generate(prompt_tokens, max_tokens):
                chunk = {"id": rid, "object": "chat.completion.chunk", "created": int(time.time()),
                         "model": model,
                         "choices": [{"index": 0, "delta": {"content": tok}, "finish_reason": None}]}
                yield f"data: {json.dumps(chunk)}\n\n"
            done = {"id": rid, "object": "chat.completion.chunk", "created": int(time.time()),
                    "model": model, "choices": [{"index": 0, "delta": {}, "finish_reason": "length"}]}
            yield f"data: {json.dumps(done)}\n\n"
            yield "data: [DONE]\n\n"
        return StreamingResponse(sse(), media_type="text/event-stream")

    out = [tok async for tok in generate(prompt_tokens, max_tokens)]
    return {"id": rid, "object": "chat.completion", "created": int(time.time()), "model": model,
            "choices": [{"index": 0, "finish_reason": "length",
                         "message": {"role": "assistant", "content": "".join(out)}}],
            "usage": {"prompt_tokens": prompt_tokens, "completion_tokens": len(out),
                      "total_tokens": prompt_tokens + len(out)}}

def metrics():
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

    Integrating with reliability-api: the inference adapter

    Definition. An adapter is a thin route in your application that translates your API into the model server's API (here: OpenAI chat completions), applies timeouts and error mapping, and emits its own metrics. The study guide's rule: "The inference backend should be an adapter, not a reason to rewrite the entire platform."

    Why it matters. Clients keep a stable contract (POST /generate), the model server can be swapped (mock → vLLM → KServe → hosted API) by changing MODEL_BASE_URL, and your existing Helm chart, CI, dashboards, HPA and failure experiments keep working.

    import httpx

MODEL_BASE_URL = os.getenv("MODEL_BASE_URL", "http://mock-llm.reliability-lab.svc.cluster.local:8000")
MODEL_NAME = os.getenv("MODEL_NAME", "mock-llm")
MODEL_TIMEOUT_SECONDS = float(os.getenv("MODEL_TIMEOUT_SECONDS", "60"))

UPSTREAM = Histogram("model_upstream_duration_seconds", "Model server call latency", ["outcome"])
client = httpx.AsyncClient(base_url=MODEL_BASE_URL,
                           timeout=httpx.Timeout(MODEL_TIMEOUT_SECONDS, connect=2.0))


@app.post("/generate")
async def generate(payload: dict, response: Response):
    start = time.perf_counter()
    try:
        r = await client.post("/v1/chat/completions", json={
            "model": MODEL_NAME,
            "messages": [{"role": "user", "content": str(payload.get("prompt", ""))}],
            "max_tokens": int(payload.get("max_tokens", 64)),
        })
        r.raise_for_status()
    except httpx.HTTPError as exc:                    # timeout, connect error, 4xx/5xx
        UPSTREAM.labels("error").observe(time.perf_counter() - start)
        REQUESTS.labels("/generate", "502").inc()
        log.warning("model upstream error: %r", exc)
        response.status_code = 502
        return {"error": "model upstream unavailable"}
    UPSTREAM.labels("ok").observe(time.perf_counter() - start)
    LATENCY.labels("/generate").observe(time.perf_counter() - start)
    REQUESTS.labels("/generate", "200").inc()
    data = r.json()
    return {"text": data["choices"][0]["message"]["content"], "usage": data.get("usage", {})}

    Add httpx to the app's dependencies, add MODEL_BASE_URL/MODEL_NAME to ConfigMap/reliability-api-config, and bump the image tag. Nothing else in the chart changes.

    Design decisions (and their trade-offs)

    DecisionChoice hereWhy / trade-off
    Should /ready check the model server?NoIf the model is down, making every reliability-api Pod unready removes /health, /work and turns a partial outage into a total one (cascading failure). Return 502 from /generate and alert on it instead.
    Timeoutsconnect 2 s, total 60 sGeneration is long; a short total timeout cancels valid requests. But unbounded waits pile up connections. Match to max_tokens × expected ITL plus margin.
    Retriesnone in the adapterRetrying a generation doubles GPU work under overload. If you add retries, only for connect errors, with a budget.

    KServe: model serving as a Kubernetes API

    Definition. KServe is "a cloud-native, Kubernetes-based model serving platform". It adds CRDs so you declare what to serve and it creates the Deployments/Services/autoscalers for you:

    • InferenceService (serving.kserve.io/v1beta1) — the main object. Its predictor names a modelFormat and a storageUri (e.g. hf://…, gs://…); optional transformer/explainer components exist for pre/post-processing.
    • ServingRuntime / ClusterServingRuntime (namespace- vs cluster-scoped) — a template for Pods that can serve particular model formats: container image, args, supported formats. Built-ins include kserve-huggingfaceserver (Hugging Face models; uses a vLLM backend for generative models) and kserve-tritonserver.
    • Storage initializer — an init container that downloads the model from storageUri before the server starts (configurable via ClusterStorageContainer).
    • Deployment modes — Standard (plain Deployments + Services; recommended in the docs for generative inference; autoscale with HPA or KEDA; no HTTP scale-from-zero) and Knative (Knative Services; request-driven autoscaling with scale-to-zero; the default mode at install unless changed).
    apiVersion: "serving.kserve.io/v1beta1"
kind: "InferenceService"
metadata:
  name: "huggingface-llm"
spec:
  predictor:
    model:
      modelFormat:
        name: huggingface
      storageUri: "hf://meta-llama/llama-3-8b-instruct"
      resources:
        requests:
          cpu: "1"
          memory: "2Gi"
          nvidia.com/gpu: 1
        limits:
          cpu: "1"
          memory: "2Gi"
          nvidia.com/gpu: 1

    KServe prefixes its OpenAI-compatible endpoints with openai (per the generative-inference docs), so the adapter's base path changes when you switch backends — another reason to keep that knowledge in one adapter.

    Autoscaling inference

    Why CPU-based HPA is a poor signal

    • GPU-bound servers keep host CPU low even when saturated; CPU-HPA never scales. (Our mock shows the extreme: zero CPU at full saturation.)
    • CPU servers look 100% busy whether serving 4 or 40 requests — utilisation saturates, it does not tell you how far over capacity you are.
    • GPU utilisation is also misleading: "utilisation" means a kernel ran during the sample window, not that the GPU is full; it fluctuates with batch composition (the KServe autoscaling docs make the same point).
    • What users feel is queueing. The signal closest to user pain and to capacity is queue depth (num_requests_waiting) and in-flight concurrency per replica (num_requests_running), with KV-cache usage as a secondary pressure signal.

    KEDA ScaledObject for the mock (or vLLM)

    KEDA is a Kubernetes event-driven autoscaler; its Prometheus scaler runs a query and scales a target so that metric / replicas ≈ threshold. The KServe docs use exactly this approach for LLMs (scaling on vllm:num_requests_running with a target of 2 per Pod, in Standard mode).

    apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: mock-llm
  namespace: reliability-lab
spec:
  scaleTargetRef:
    name: mock-llm                 # the Deployment
  minReplicaCount: 1               # keep one warm replica: cold start is slow
  maxReplicaCount: 4
  cooldownPeriod: 300
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://monitoring-kube-prometheus-prometheus.monitoring.svc:9090
      query: sum(mockllm_num_requests_waiting) + sum(mockllm_num_requests_running)
      threshold: "6"               # target in-flight per replica (below MAX_BATCH=8)

    The Prometheus Service name depends on your kube-prometheus-stack release (kubectl -n monitoring get svc). For vLLM, use sum(vllm:num_requests_running) + sum(vllm:num_requests_waiting) or scale on waiting alone with a small threshold.

    How to pick the target

    1. Benchmark one replica with an AIPerf concurrency sweep (next section).
    2. Find the highest concurrency that still meets your SLO (e.g. p95 TTFT ≤ 500 ms, p95 ITL ≤ 50 ms) — the knee.
    3. Set the per-replica target a bit below that (headroom for the slow scale-up loop).
    4. Load-test the autoscaler itself: step load from 4 → 24 users and measure time-to-scale and SLO violations during the ramp (Module 08 method).
    OptionSignalNotes
    HPA on CPU (Module 08)CPU utilisation vs requestfine for reliability-api itself; wrong for the model server
    HPA + prometheus-adaptercustom/external metrics API from PromQLno extra controller semantics; more config
    KEDAPromQL (and many other scalers)manages the HPA for you; supports activation thresholds; scale-to-zero for non-HTTP sources
    Knative KPA (KServe Knative mode)in-flight requests per Pod (concurrency) or RPSrequest-driven, scale-to-zero, panic window for bursts; cold starts include model load

    Failure cases

    • Flapping: queue empties as soon as a replica becomes ready, then fills again. Use stabilisation/cooldown and a combined running+waiting signal.
    • Scaling too late: model load takes minutes; by the time the replica is ready the burst is over. Keep minReplicaCount warm capacity, scale earlier, and pre-pull images.
    • Scale to zero surprise: the first request after idle waits for a full cold start (possibly including a GPU node). Fine for batch, painful for chat.
    • Metric missing (Prometheus down, query typo): KEDA cannot compute; check kubectl get scaledobject READY/ACTIVE columns and KEDA operator logs. Consider KEDA's fallback settings.

    Benchmarking with AIPerf

    Definition. AIPerf (ai-dynamo/aiperf) is a benchmarking tool for generative-AI serving. It sends requests to OpenAI-compatible (and other) endpoints in concurrency or request-rate modes, measures client-side TTFT, ITL, request latency and throughput, and exports CSV/JSON artifacts.

    Problem it solves. A naive loop of curl calls measures the wrong thing: it ignores streaming (no TTFT), uses one prompt (unrealistic cache hits), has no warm-up (cold-start pollution), and runs one concurrency level (no curve). AIPerf encodes the methodology.

    python3 -m venv venv && source venv/bin/activate
pip install aiperf
aiperf profile \
  --model "granite4:350m" \
  --streaming \
  --endpoint-type chat \
  --tokenizer ibm-granite/granite-4.0-micro \
  --url http://localhost:11434 \
  --concurrency 5 \
  --request-count 10

    Useful options (names from the AIPerf CLI reference, 29 Oct 2026; run aiperf profile --help for your version):

    OptionMeaning
    --model, --url, --endpoint-type chattarget; the path (e.g. /v1/chat/completions) is appended from the endpoint type
    --streamingenables TTFT and ITL measurement
    --concurrency N / --request-rate Rclosed-loop (N in flight) vs open-loop (R req/s) load (Module 08 terms)
    --request-count, --benchmark-durationhow long to measure
    --warmup-request-countrequests sent first and discarded
    --synthetic-input-tokens-mean / --isl, --output-tokens-mean / --osl (+ -stddev)synthetic prompt and output lengths
    --input-file + --custom-dataset-type single_turnyour fixed prompt set (JSONL, e.g. {"text": "…"} per line)
    --random-seedreproducible synthetic data and sampling
    --extra-inputsextra request fields (e.g. max_tokens:128, ignore_eos:true where supported)
    --tokenizertokenizer used to count tokens client-side
    --artifact-dir, --ui-type simple|none|dashboardwhere results go; UI mode (use none in CI)
    Output length is not guaranteed

    The README notes that --output-tokens-mean "cannot be guaranteed unless you pass ignore_eos and/or min_tokens via --extra-inputs to an inference server that supports them". If baseline and candidate stop at different lengths, their latencies are not comparable — record the measured output sequence length too.

    Methodology checklist

    1. Freeze the workload: a fixed prompt file (committed to experiments/load/prompts.jsonl), fixed max_tokens, fixed seed. Never compare runs with different prompts.
    2. Warm up: discard the first requests (JIT, cache allocation, connection setup, lazy loading).
    3. Sweep concurrency (e.g. 1, 2, 4, 8, 16, 32) to draw the latency/throughput curve — one point is an anecdote.
    4. Repeat each point ≥ 3 times; report median and spread. Restart the server between candidates.
    5. Check the load generator is not the bottleneck (its CPU, network; Module 08). Run it in-cluster or on a separate machine for serious runs.
    6. Correlate client metrics (AIPerf) with server metrics (Prometheus: queue, running, KV cache) and Kubernetes metrics (restarts, throttling, OOM).
    7. Record the environment: model + revision, server + version + flags, image digest, node type, GPU/CPU, replicas, Kubernetes version, AIPerf version and full command.

    Glossary

    Model server
    Process that holds model weights in memory and serves inference over an API.
    Prefill
    Forward pass over the whole prompt; fills the KV cache; yields the first token.
    Decode
    Iterative generation, one token per step per sequence.
    KV cache
    Stored attention keys/values for every token of every running sequence; main memory limit for concurrency.
    TTFT
    Time to first token: send → first streamed token.
    ITL / TPOT
    Inter-token latency / time per output token: average gap between generated tokens.
    E2E latency
    Send → last token.
    Goodput
    Throughput counting only requests that met the SLO.
    Continuous batching
    Re-forming the batch at each decode step so finished sequences are replaced immediately.
    Device plugin
    Node agent that advertises extended resources (e.g. nvidia.com/gpu) to the kubelet.
    MIG
    Multi-Instance GPU: hardware partitioning of one GPU into isolated slices.
    InferenceService
    KServe CRD declaring a model to serve (predictor, format, storage URI).
    ServingRuntime
    KServe template describing which container serves which model formats.
    KEDA
    Event-driven autoscaler that feeds external metrics (e.g. PromQL) into an HPA.
    AIPerf
    Client-side benchmarking tool for generative-AI endpoints.
    Inference adapter
    App route that translates its API to the model server's, with timeouts and metrics.

    Self-check

    1. Why should reliability-api and the model server be separate Deployments?
    Different resource profiles (CPU vs GPU, MB vs GB memory), startup times (seconds vs minutes), scaling signals (CPU vs queue depth) and release cadences. Separating them allows independent placement, scaling and upgrades, and swapping the backend via the adapter.
    2. A request has TTFT 400 ms, E2E 3,580 ms and 128 output tokens. What is the ITL and per-user tokens/s?
    ITL = (3580 − 400)/(128 − 1) ≈ 25.0 ms; per-user ≈ 1000/25 = 40 tokens/s.
    3. With 12 requests in flight on average and an average E2E of 4 s, what is the request rate?
    Little's law: λ = L / W = 12 / 4 = 3 requests/s.
    4. Why does continuous batching increase throughput but also ITL?
    It keeps every batch slot busy (no waiting for the longest sequence), so more tokens are produced per step and per second overall. But each step processes more sequences and reads more KV cache, so the time per step — the gap between a single user's tokens — grows.
    5. What are the three rules for specifying GPUs in a container spec?
    Specify GPUs in limits; a limit alone is enough (request defaults to it); if both are set they must be equal; you cannot set a GPU request without a limit. Values are whole numbers.
    6. A model server restarts every 3 minutes during startup with "Startup probe failed". What do you change and why not just remove probes?
    Increase the startupProbe budget (failureThreshold × periodSeconds) beyond worst-case load time, and/or speed loading (PVC cache). Removing probes would let traffic hit an unready server (no readiness) and leave hung servers running (no liveness).
    7. Why is num_requests_waiting a better autoscaling signal than CPU for vLLM on GPUs?
    Host CPU barely changes with GPU load, and utilisation metrics saturate. Waiting requests directly measure demand exceeding the replica's capacity and correlate with TTFT — what users feel.
    8. Why should /ready of reliability-api not depend on the model server?
    A model outage would mark all reliability-api Pods unready, removing them from the Service and breaking unrelated endpoints — a cascading failure. Return 502 on /generate, alert on its error rate, and keep readiness about the Pod's own ability to serve.
    9. Name four things that make two AIPerf runs incomparable.
    Different prompt sets or lengths, different output lengths (EOS vs max_tokens), no/different warm-up, different concurrency or request-rate mode, different server flags/versions/image digests, load-generator bottleneck in one run, different hardware.
    10. What does KServe Standard mode give up compared to Knative mode, and why might LLM serving still prefer it?
    Standard mode lacks request-driven scale-to-zero for HTTP. LLM servers have long cold starts and expensive accelerators, so scale-to-zero is rarely acceptable for interactive traffic; Standard mode is simpler (no Knative dependency) and integrates with HPA/KEDA on LLM metrics.
    11. Your candidate is 25% faster on AIPerf. What else must be true before you ship it?
    Quality evaluation on the fixed eval set shows no unacceptable regression; error rates are equal or lower; results repeat across runs; the environment and workload were identical; and the decision rule written in advance is satisfied.
