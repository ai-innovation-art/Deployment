    Module 10 · Terraform & Infrastructure as Code

    Kubernetes manifests and Helm describe what runs inside a cluster. Something still has to create the cluster, its network, its identities, the registry and the bucket that stores state — and do it repeatably, reviewably and reversibly. Terraform is that tool. This module teaches the model behind it (desired configuration vs recorded state vs real world), the HCL language, providers, the dependency graph, state and locking, how to read a plan before you let it touch anything, and safe refactoring. You practise entirely for free against your kind cluster first, then see the skeleton of the Google Cloud setup that Module 11 builds on — with the cost traps called out.

    Infrastructure as Code: declarative, idempotent, drift

    Definition. Infrastructure as Code (IaC) means describing infrastructure — clusters, networks, buckets, IAM bindings, namespaces — in version-controlled text files, and letting a tool make reality match the files. HashiCorp's definition of Terraform: "an infrastructure as code tool that lets you build, change, and version cloud and on-prem resources safely and efficiently."

    Problem it solves. Infrastructure created by clicking in a console is undocumented, unreviewable and unreproducible: nobody knows exactly which settings the staging cluster has, re-creating it after a mistake takes days, and two environments that "should be identical" quietly aren't. With IaC, a change is a pull request — diffable, reviewable, revertible — and a new environment is a command.

    Declarative
    You describe the end state ("a namespace named reliability-tf with these labels exists"), not the steps. Terraform computes the steps. Same idea as a Kubernetes Deployment (Module 03).
    Idempotent
    Applying the same configuration twice produces the same result; the second apply changes nothing ("No changes. Your infrastructure matches the configuration."). A shell script that runs kubectl create namespace is not idempotent — the second run fails.
    Drift
    Real infrastructure diverges from what the configuration/state says, usually because someone changed it by hand (kubectl edit, console click). Terraform detects drift when it refreshes during plan.

    Imperative vs declarative, concretely

    kubectl create namespace reliability-tf            # fails if it exists
kubectl -n reliability-tf create configmap reliability-api-config \
  --from-literal=LOG_LEVEL=info                    # fails if it exists; changes need a different command
    resource "kubernetes_namespace_v1" "lab" {
  metadata { name = "reliability-tf" }
}
resource "kubernetes_config_map_v1" "app" {
  metadata {
    name      = "reliability-api-config"
    namespace = kubernetes_namespace_v1.lab.metadata[0].name   # reference = dependency
  }
  data = { LOG_LEVEL = "info" }
}

    Trade-offs

    • Pro: reviewable diffs, reproducibility, self-documentation, safe teardown, drift detection.
    • Con: a new layer to learn; state to protect; provider bugs/version churn; a powerful tool can delete powerful things — plan review is mandatory.
    • Rule of ownership: each real object must have exactly one owner (Terraform, Helm, or a human). Two tools managing the same object fight forever (each apply "fixes" the other's changes).
    Self-check: you apply, then immediately apply again with no edits. What should the second plan say, and what does it mean if it proposes changes?
    "No changes. Your infrastructure matches the configuration." If it proposes changes, something is non-idempotent: drift (someone/something changes the object between runs — e.g. a controller mutating a field), a provider normalising values differently from your config, or a value that changes every run (e.g. timestamp()). Use lifecycle.ignore_changes only for fields legitimately owned by something else.

    The core workflow: write → init → plan → apply → destroy

    CommandWhat it doesSafe to run anytime?

    HCL syntax: blocks, arguments, expressions

    Terraform configuration is written in HCL (HashiCorp Configuration Language). Everything is built from three things:

    • Blocks — a type, zero or more labels, and a body in braces: resource "kubernetes_config_map_v1" "app" { … }. Blocks can nest (metadata { … }).
    • Arguments — name = expression inside a block body.
    • Expressions — literals ("info", 2, true), references (var.log_level, kubernetes_namespace_v1.lab.metadata[0].name), string templates ("${var.project_id}-tfstate"), function calls (toset(…), merge(…)), conditionals (a ? b : c), and for expressions.

    The top-level block types you will meet

    BlockPurposeAddress / reference
    terraform { }settings: required_version, required_providers, backend—
    provider "x" { }configure a provider (endpoint, credentials, project)—
    resource "T" "n" { }an object Terraform creates/managesT.n
    data "T" "n" { }read an existing object (no management)data.T.n
    variable "n" { }input parametervar.n
    output "n" { }exported valuemodule.m.n from a parent
    locals { }named intermediate valueslocal.n
    module "n" { }call a child modulemodule.n
    moved, importrefactor addresses / adopt existing objects—

    All .tf files in a directory form one module; file names are only for humans. Convention: versions.tf, providers.tf, variables.tf, main.tf, outputs.tf.

    locals {
  envs        = ["dev", "staging"]
  ns_names    = [for e in local.envs : "reliability-${e}"]           # list comprehension
  ns_by_env   = { for e in local.envs : e => "reliability-${e}" }    # map comprehension
  replicas    = var.environment == "prod" ? 3 : 2                     # conditional
  all_labels  = merge(local.common_labels, { tier = "api" })          # function call
}

    Providers, version constraints and the lock file

    Definition. A provider is a plugin that teaches Terraform one API: hashicorp/kubernetes talks to a Kubernetes API server, hashicorp/google to Google Cloud, hashicorp/random generates values locally. Terraform core knows nothing about ConfigMaps or buckets; it builds graphs, diffs and state, and delegates every CRUD call to providers.

    terraform {
  required_version = ">= 1.7, < 2.0"          # Terraform CLI itself (latest release at writing: v1.17.1)

  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"          # = registry.terraform.io/hashicorp/kubernetes
      version = "~> 3.4"                        # >= 3.4, < 4.0
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.9"
    }
  }
}
    • Source address = [HOSTNAME/]NAMESPACE/TYPE; hostname defaults to registry.terraform.io.
    • Constraint operators: =, !=, >, >=, <, <=, and ~> ("pessimistic": allow only the rightmost component to increase — ~> 3.4 allows 3.5, 3.99 but not 4.0; ~> 3.4.0 allows only 3.4.x).
    • Guidance: root modules (where you run apply) set both lower and upper bounds to avoid accidental major upgrades; reusable child modules set only minimums (>=) so they don't block their callers.
    • Latest registry versions when this was written: kubernetes 3.4.0, google 8.9.0, random 3.9.1. Check the registry when you start.

    The dependency lock file .terraform.lock.hcl

    init records the exact provider versions it selected plus checksums (h1: and zh: hashes). Later inits reuse those exact versions even if newer ones match the constraint — like package-lock.json or a pip lock. Commit it. Upgrading is explicit: terraform init -upgrade, review the lock-file diff in a PR. It tracks providers only — not modules (remote modules are re-selected as the newest matching version, so pin module versions exactly). If teammates or CI use another OS/CPU, pre-populate hashes: terraform providers lock -platform=linux_amd64 -platform=darwin_arm64.

    Provider configuration for kind

    provider "kubernetes" {
  config_path    = "~/.kube/config"
  config_context = "kind-reliability-lab"     # kind names contexts kind-<cluster>
}
    Gotchas from the provider docs
    • The Kubernetes provider does not read the KUBECONFIG environment variable by default; set config_path (or KUBE_CONFIG_PATH). Always pin config_context so a plan can never run against the wrong cluster because your current kubectl context changed.
    • Don't create a cluster and use the Kubernetes provider against it in the same configuration/apply — the provider docs warn this causes intermittent, hard-to-debug errors. Create the cluster in one root module (Module 11), configure in-cluster resources in a separate apply.

    Resources, data sources and the dependency graph

    A resource block declares an object Terraform owns: it creates it, updates it, and destroys it when the block is removed. A data source (data block) only reads an object that something else owns — for example the reliability-api Service that your Helm release (Module 06) created. Data sources let Terraform consume facts without taking ownership.

    Resource behaviour on apply

    • In config, not in state → create.
    • In state, not in config → destroy.
    • Argument changed that the API can update → update in place.
    • Argument changed that the API can't update (e.g. a ConfigMap's metadata.name, "Cannot be updated") → destroy and re-create (replace).

    Dependencies: implicit vs explicit

    When one block references another (namespace = kubernetes_namespace_v1.lab.metadata[0].name), Terraform adds a graph edge: the namespace is created first and destroyed last. That is an implicit dependency and covers almost everything. depends_on = [ … ] adds an explicit edge for hidden dependencies that no attribute expresses; HashiCorp calls it a last resort, because it makes plans more conservative (more values become "known after apply").

    Failure cases

    • Missing edge: you hard-code namespace = "reliability-tf" instead of referencing the resource. On the first apply, Terraform may create the ConfigMap in parallel with the namespace → "namespaces "reliability-tf" not found". Fix: reference, don't repeat.
    • Data source target missing: data.kubernetes_service_v1.api fails the plan if the Helm release isn't installed. That's a feature: the dependency on "something outside Terraform" is explicit.
    • Cycles: A references B and B references A → "Cycle:" error. Break it with a local value or by splitting a resource.

    Variables, outputs and locals

    Input variables

    variable "namespace" {
  description = "Namespace Terraform creates and owns for this lab"
  type        = string
  default     = "reliability-tf"
}

variable "log_level" {
  description = "LOG_LEVEL for reliability-api"
  type        = string
  default     = "info"
  validation {
    condition     = contains(["debug", "info", "warning", "error"], var.log_level)
    error_message = "log_level must be one of debug, info, warning, error."
  }
}

variable "ready_delay_seconds" {
  type    = number
  default = 5
  validation {
    condition     = var.ready_delay_seconds >= 0 && var.ready_delay_seconds <= 120
    error_message = "ready_delay_seconds must be between 0 and 120."
  }
}

variable "environments" {
  description = "Extra per-environment namespaces (for_each demo)"
  type        = set(string)
  default     = []
}

variable "api_token" {
  description = "Example secret input — never give it a default"
  type        = string
  sensitive   = true
  default     = null
  nullable    = true
}
    • Types: string, number, bool, list(T), set(T), map(T), object({…}), tuple([…]), any. Types convert and validate input early.
    • Validation blocks reject bad input at plan time with your message — far better than a cryptic API error halfway through apply.
    • sensitive = true redacts the value in CLI output, but Terraform still stores it in state. ephemeral = true keeps a variable out of state and plan files (with restrictions on where it can be used).

    Where variable values come from (precedence)

    Later sources override earlier ones (lowest → highest): variable default → environment variables TF_VAR_name → terraform.tfvars → terraform.tfvars.json → *.auto.tfvars / *.auto.tfvars.json (lexical order) → -var and -var-file on the command line (in the order given).

    Outputs

    output "namespace" {
  description = "Namespace managed by Terraform"
  value       = kubernetes_namespace_v1.lab.metadata[0].name
}

output "lab_id" {
  value = random_pet.lab.id
}

output "api_cluster_ip" {
  description = "ClusterIP of the Helm-managed Service (read via data source)"
  value       = data.kubernetes_service_v1.api.spec[0].cluster_ip
}

    Outputs print after apply, can be read with terraform output (-raw for scripts, -json for tools), expose values from child modules to parents (module.NAME.OUTPUT), and can be read from another configuration's state. sensitive = true on an output shows <sensitive> in the CLI, but the value is in state and -raw/-json print it.

    Locals

    locals {
  common_labels = {
    "app.kubernetes.io/name"       = "reliability-api"
    "app.kubernetes.io/managed-by" = "terraform"
  }
}

    Locals are named expressions inside a module — use them to avoid repetition (labels, name prefixes). Unlike variables, callers can't override them. Don't over-abstract: a local used once is noise.

    State

    What it is. State (terraform.tfstate, JSON) stores the binding between each resource address in your configuration and the real object it manages (kubernetes_config_map_v1.app ↔ ConfigMap reliability-tf/reliability-api-config), plus the last-known attributes and dependency metadata. Why it exists: many APIs can't answer "which of these objects did Terraform create for which block?"; state remembers, enables diffs, records deletion order even after a block is removed, and avoids scanning everything on each run.

    Why it's sensitive. State contains every attribute the provider returns — including secrets: database passwords, private keys, sensitive variables, kubeconfig credentials if you model them. Anyone who can read state can read those. HashiCorp warns against storing state in version control or any storage without locking and access control.

    The GCS backend

    terraform {
  backend "gcs" {
    bucket = "<your-project-id>-tfstate-<suffix>"   # created by the bootstrap config below
    prefix = "reliability-lab/gke"
  }
}
    • Locking: the GCS backend supports state locking. Locking happens automatically on all operations that could write state. -lock=false exists but HashiCorp doesn't recommend it; -lock-timeout=60s waits for a lock instead of failing immediately.
    • Versioning: HashiCorp "highly recommends" enabling Object Versioning on the bucket so state can be recovered after accidental deletion or human error.
    • Auth: Application Default Credentials (gcloud auth application-default login), GOOGLE_APPLICATION_CREDENTIALS, or impersonate_service_account. Supply credentials via environment, not -backend-config or hard-coding — those values end up in .terraform/ and plan files.
    • Encryption: Google encrypts at rest by default; the backend also supports customer-supplied (encryption_key) or Cloud KMS (kms_encryption_key) keys.
    • Backend blocks can't use variables, locals or data sources. Use partial configuration (terraform init -backend-config="bucket=…" or a -backend-config=gcs.hcl file) to keep environment-specific values out of the code.
    • Changing backends = re-run terraform init; Terraform offers to migrate existing state. Back up terraform.tfstate first.
    Stale lockIf a run is killed (laptop sleeps, CI cancelled) the lock can stay. terraform force-unlock LOCK_ID removes it — the lock ID acts as a nonce so you unlock the right lock. "Be very careful with this command": unlocking while someone else is actually applying lets two writers corrupt state. Confirm nobody is running first.

    State commands

    CommandUse
    terraform state list [addr…]List managed addresses; filter by address or module; -id=… finds which address manages a given real ID.
    terraform state show ADDRShow all recorded attributes of one instance.
    terraform state mv SRC DSTRe-bind an existing object to a new address (rename/move into module) without re-creating it; -dry-run first. Prefer moved blocks — declarative, reviewable, applies for everyone.
    terraform plan -refresh-only / apply -refresh-onlyShow/accept drift into state without changing infrastructure.

    Never edit the state JSON by hand; the terraform state commands insulate you from format changes.

    Refactoring with moved

    resource "kubernetes_config_map_v1" "api_config" {   # was "app"
  # … unchanged …
}

moved {
  from = kubernetes_config_map_v1.app
  to   = kubernetes_config_map_v1.api_config
}
      # kubernetes_config_map_v1.app has moved to kubernetes_config_map_v1.api_config
    resource "kubernetes_config_map_v1" "api_config" {
        id   = "reliability-tf/reliability-api-config"
        # (2 unchanged attributes hidden)
        # (1 unchanged block hidden)
    }

Plan: 0 to add, 0 to change, 0 to destroy.

    Without the moved block the plan would be "1 to add, 1 to destroy" — Terraform sees an unknown new address and an orphaned old one. In shared modules, keep historical moved blocks: removing them is a breaking change for callers still on old versions.

    Adopting existing objects with import blocks

    import {
  to = kubernetes_namespace_v1.legacy
  id = "legacy-tools"                # namespaces import by name (provider docs)
}

resource "kubernetes_namespace_v1" "legacy" {
  metadata { name = "legacy-tools" }
}

    Plan shows # kubernetes_namespace_v1.legacy will be imported; apply records it in state; afterwards you may delete the import block. Don't want to write the resource body yourself? Write only the import block and run terraform plan -generate-config-out=generated.tf, then review and clean the generated code. The ID format differs per resource type (a ConfigMap imports as namespace/name) — always check the provider docs.

    Reading plans: symbols and danger signs

    "Terraform used the selected providers to generate the following execution plan. Resource actions are indicated with the following symbols:" — then a legend containing only the symbols that occur in this plan, the per-resource diff, and a summary Plan: X to add, Y to change, Z to destroy.

    SymbolLegend textHeader lineRisk
    +create# ADDR will be createdlow (cost?)
    -destroy# ADDR will be destroyed (+ reason, e.g. "because … is not in configuration", "because key ["dev"] is not in for_each map")high — data loss
    ~update in-place# ADDR will be updated in-placeusually low; read which fields
    -/+destroy and then create replacement# ADDR must be replaced; offending field marked # forces replacementhigh — downtime, new IDs, data loss
    +/-create replacement and then destroysame, with create_before_destroymedium — brief overlap; name conflicts
    <=read (data resources)# data.ADDR will be read during apply (+ why: config refers to values not yet known, or depends on pending changes)low

    Other lines you'll see: (known after apply) — the value is computed by the API; # (3 unchanged attributes hidden); Note: Objects have changed outside of Terraform — drift detected during refresh, shown before the proposed changes.

    Plan-review checklist
    1. Read the summary line first. Any destroy count you didn't expect → stop.
    2. Search the plan for must be replaced and # forces replacement. Is a stateful object (bucket, database, cluster, PVC) being replaced?
    3. Check drift notes: is your apply about to revert someone's emergency fix?
    4. Check the context/project: is this plan against kind-reliability-lab / the intended GCP project?
    5. For important changes save the plan: terraform plan -out=tfplan, review, then terraform apply tfplan — what you approved is exactly what runs.

    Read the (example) plan excerpt and pick the action symbol Terraform would show. All excerpts use the reliability-api lab resources.

  }

    count vs for_each

    Both create several instances from one block. count = N gives instances addressed by integer index (x[0], x[1], count.index). for_each takes a map or set of strings and addresses instances by key (x["dev"], each.key, each.value). HashiCorp's guidance: use count for nearly identical instances; use for_each when instances need distinct values that can't be derived from an integer. The keys must be known at plan time and can't be sensitive values. A block can't have both.

    resource "kubernetes_namespace_v1" "env" {
  for_each = var.environments                       # set(string), e.g. ["dev", "staging"]
  metadata {
    name   = "reliability-${each.key}"
    labels = merge(local.common_labels, { environment = each.key })
  }
}

# count is right for "0 or 1" toggles:
resource "kubernetes_config_map_v1" "debug" {
  count = var.log_level == "debug" ? 1 : 0
  metadata {
    name      = "reliability-api-debug"
    namespace = kubernetes_namespace_v1.lab.metadata[0].name
  }
  data = { NOTE = "debug mode enabled by terraform" }
}
    count vs for_each simulator
    Currently applied: ["dev", "staging", "prod"]. Change the desired list and compare the plans.
    count = length(var.envs)
    for_each = toset(var.envs)

    Modules

    Definition. A module is a set of .tf files in one directory managed as a unit. The directory where you run terraform is the root module; it can call child modules with module blocks. Published modules come from the public Terraform Registry, a private registry, Git, or buckets. terraform init downloads them into .terraform/modules.

    variable "name"      { type = string }
variable "log_level" { type = string }
variable "labels" {
  type    = map(string)
  default = {}
}

resource "kubernetes_namespace_v1" "this" {
  metadata {
    name   = var.name
    labels = var.labels
  }
}

resource "kubernetes_config_map_v1" "app" {
  metadata {
    name      = "reliability-api-config"
    namespace = kubernetes_namespace_v1.this.metadata[0].name
  }
  data = { LOG_LEVEL = var.log_level, APP_MODE = "normal" }
}

output "name" { value = kubernetes_namespace_v1.this.metadata[0].name }
    module "app_namespace" {
  source    = "../../modules/app-ns"
  name      = "reliability-dev"
  log_level = "debug"
  labels    = local.common_labels
}

output "dev_namespace" { value = module.app_namespace.name }
    • When to write a module: when you instantiate the same group of resources more than once (per environment, per service) or want a stable interface. Not for a single resource ("wrapper modules" add indirection without value).
    • Registry modules save time for complex infra (VPCs, GKE), but you inherit their design and upgrade cadence. Pin exact versions and read the changelog before bumping.
    • Moving existing resources into a module changes their addresses (kubernetes_namespace_v1.lab → module.app_namespace.kubernetes_namespace_v1.this) — add moved blocks or Terraform will plan destroy + create.

    Environments: workspaces vs separate directories

    CLI workspaces let one configuration have several named states in the same backend (terraform workspace new staging; the built-in default can't be deleted; terraform.workspace is usable in expressions). HashiCorp states workspaces are not appropriate for system decomposition or for deployments that require separate credentials and access controls.

    CLI workspacesSeparate root directories (envs/dev, envs/prod)
    Codeidentical for all envseach env calls shared modules with its own values
    Statesame backend, <prefix>/<workspace>.tfstateseparate backend config / prefix (or bucket)
    Credentialssame — you need prod access to touch devcan differ per env (dev project vs prod project)
    Riskwrong selected workspace = apply to wrong env; it's invisible in the codeenv is visible in the path and PR diff
    Good forshort-lived copies (feature test stacks)long-lived environments, different blast radius

    For reliability-api: use separate directories once you have both a throw-away lab and anything you care about. For the kind lab, one directory is enough.

    fmt, validate and Terraform in CI

    Run cheap checks on every PR (Module 09 pattern): fmt -check catches style drift, validate catches type errors and bad references without credentials. A plan in CI needs credentials to reach the backend and APIs — use OIDC (Module 11) and post the plan for review; keep apply behind an environment with a required reviewer.

    name: terraform
on:
  pull_request:
    branches: [main]
permissions:
  contents: read
jobs:
  checks:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: infra/terraform/local-kind
    steps:
      - uses: actions/checkout@v7                 # pin to SHA
        with: { persist-credentials: false }
      - uses: hashicorp/setup-terraform@v4        # pin to SHA
      - run: terraform fmt -check -recursive
      - run: terraform init -backend=false
      - run: terraform validate

    Secrets handling

    • Never put secret values in .tf or committed .tfvars. Pass them at runtime: TF_VAR_api_token from a secret manager / CI secret, or better, have Terraform not handle the secret at all (create the Secret Manager entry, let the workload read it).
    • sensitive ≠ secret-safe: sensitive = true hides values from CLI output only; they are stored in state in plain text. Treat state as a secret: restricted bucket IAM, versioning, encryption.
    • ephemeral variables/outputs keep values out of state and plan files where supported.
    • Saved plan files contain values too (including backend config passed with -backend-config). Don't upload tfplan as a public CI artifact.
    • Provider credentials come from the environment (ADC/OIDC for Google, kubeconfig for Kubernetes) — never as provider arguments in code.

    Where Terraform stops: Terraform vs Helm vs kubectl vs GitHub Actions

    • Why not deploy the app with Terraform too? You can (kubernetes/helm providers), but the app changes on every commit while infrastructure changes rarely; mixing them couples slow, high-risk infra plans with fast app releases, and the Kubernetes provider docs warn against creating a cluster and its in-cluster resources in the same apply.
    • Our local lab breaks that rule on purpose in a separate namespace (reliability-tf) so you can learn Terraform with zero cost. The Helm release in reliability-lab stays Helm-owned; Terraform only reads its Service via a data source.

    Worked example 1 (free): Terraform against your kind cluster

    Directory: kubernetes-reliability-lab/infra/terraform/local-kind/. Uses the versions.tf, providers.tf, variables.tf, outputs.tf shown above plus this main.tf:

    locals {
  common_labels = {
    "app.kubernetes.io/name"       = "reliability-api"
    "app.kubernetes.io/managed-by" = "terraform"
  }
}

resource "random_pet" "lab" {
  length = 2
}

resource "kubernetes_namespace_v1" "lab" {
  metadata {
    name   = var.namespace
    labels = local.common_labels
  }
}

# Read-only: the Service created by the Helm release in Module 06.
data "kubernetes_service_v1" "api" {
  metadata {
    name      = "reliability-api"
    namespace = "reliability-lab"
  }
}

resource "kubernetes_config_map_v1" "app" {
  metadata {
    name      = "reliability-api-config"
    namespace = kubernetes_namespace_v1.lab.metadata[0].name
    labels    = local.common_labels
  }
  data = {
    APP_MODE            = "normal"
    LOG_LEVEL           = var.log_level
    READY_DELAY_SECONDS = tostring(var.ready_delay_seconds)
    LAB_ID              = random_pet.lab.id
    API_CLUSTER_IP      = data.kubernetes_service_v1.api.spec[0].cluster_ip

  for_each = var.environments
  metadata {
    name   = "reliability-${each.key}"
    labels = merge(local.common_labels, { environment = each.key })
  }
}

    Lab 2 — Drift detection exercise

    Goal: see drift, then practise both ways to resolve it. Start from an applied Lab 1 (terraform apply again if you destroyed).

    1. Simulate an "emergency hotfix" outside Terraform: 
      kubectl -n reliability-tf patch configmap reliability-api-config \
  --type merge -p '{"data":{"LOG_LEVEL":"debug"}}'
kubectl -n reliability-tf label namespace reliability-tf owner=oncall
    2. Detect drift without proposing changes: 
      terraform plan -refresh-only
      Note: Objects have changed outside of Terraform

Terraform detected the following changes made outside of Terraform since the
last "terraform apply" which may have affected this plan:

  # kubernetes_config_map_v1.app has changed
  ~ resource "kubernetes_config_map_v1" "app" {
      ~ data = {
          ~ "LOG_LEVEL" = "info" -> "debug"
            # (4 unchanged elements hidden)
        }
    ...
  # kubernetes_namespace_v1.lab has changed
  ...
          + "owner" = "oncall"
    3. Now run a normal terraform plan: it shows the drift note and proposes ~ updates that revert LOG_LEVEL to info and remove the owner label.
    4. Decision A — the code is right: terraform apply reverts the manual change. (In real life: confirm the hotfix is no longer needed first!)
    5. Decision B — the manual change is right: repeat step 1, then update the code (log_level default to "debug", add owner = "oncall" to the namespace labels) until terraform plan shows no changes. Optionally terraform apply -refresh-only first to record the observed values in state without touching infrastructure.
    6. Bonus — legitimately shared fields: if an on-call tool really owns the namespace labels, lifecycle { ignore_changes = [metadata[0].labels] } stops Terraform fighting it. Discuss why that is acceptable for labels written by another system, and why ignoring data would hide real drift.
    7. Automate detection: in CI, a scheduled job can run terraform plan -detailed-exitcode; exit code 2 means changes/drift exist → alert.
    Lab 3 — import and refactor without re-creating
    1. Create a namespace by hand: kubectl create namespace legacy-tools.
    2. Add the import + resource "kubernetes_namespace_v1" "legacy" blocks shown above. terraform plan → # kubernetes_namespace_v1.legacy will be imported, "Plan: 1 to import, 0 to add, 0 to change, 0 to destroy." (an in-place update may also appear if your config differs from the live object, e.g. labels). Apply. Remove the import block; plan → no changes.
    3. Rename kubernetes_config_map_v1.app to api_config without a moved block and plan: observe "1 to add, 1 to destroy". Add the moved block: plan shows "has moved to", 0 to add/destroy. Apply.
    4. Compare with the imperative alternative: terraform state mv -dry-run kubernetes_config_map_v1.app kubernetes_config_map_v1.api_config — works, but only on your copy of state and leaves no record in code review.
    Lab 4 — for_each environments and the count trap
    1. terraform apply -var 'environments=["dev","staging","prod"]' → three namespaces reliability-dev/staging/prod. terraform state list | grep env shows kubernetes_namespace_v1.env["dev"] etc.
    2. terraform plan -var 'environments=["staging","prod"]' → only env["dev"] destroyed "(because key ["dev"] is not in for_each map)".
    3. Rewrite the block with count = length(var.envs) over a list(string) in a scratch copy and repeat: observe the -/+ cascade on [0] and [1] and "(because index [2] is out of range for count)". Use the simulator above to predict first.
    4. Clean up: terraform destroy.

    Worked example 2 (costs money): GCP skeleton for remote state

    Cost warning — read before running anything here
    • Creating Google Cloud resources requires a billing-enabled project. A small GCS bucket costs very little, but not zero: storage, operations, retained object versions (versioning keeps old state copies) and possibly soft-deleted objects (see the bucket's soft_delete_policy) are billed. Check current pricing on cloud.google.com.
    • The expensive resources (GKE cluster, nodes, load balancers, NAT, logging volume) come in Module 11. Set a billing budget with alerts before creating anything, and keep a written list of what you created.
    • Free-tier/credit programs don't guarantee every associated resource is free. Destroy experiments when done and verify deletion in the console.

    Chicken-and-egg: the state bucket must exist before any configuration can store its state in it. Standard answer: a tiny bootstrap root module with local state creates the bucket; everything else uses the gcs backend. (You can later migrate the bootstrap's own state into the bucket.)

    terraform {
  required_version = ">= 1.7, < 2.0"
  required_providers {
    google = { source = "hashicorp/google", version = "~> 8.9" }
    random = { source = "hashicorp/random", version = "~> 3.9" }
  }
}

variable "project_id" { type = string }                 # e.g. passed with -var or TF_VAR_project_id
variable "region" {
  type    = string
  default = "us-central1"
}

provider "google" {
  project = var.project_id                              # credentials come from ADC, not from code
  region  = var.region
}

resource "random_id" "suffix" {
  byte_length = 4                                       # .hex = 8 hex characters
}

resource "google_storage_bucket" "tf_state" {
  name                        = "${var.project_id}-tfstate-${random_id.suffix.hex}"   # globally unique, lowercase, ≤ 63 chars
  location                    = var.region
  force_destroy               = false                   # default: refuse to delete a non-empty bucket
  uniform_bucket_level_access = true                    # IAM only, no per-object ACLs
  public_access_prevention    = "enforced"              # state must never be public

  versioning {
    enabled = true                                      # recover earlier state versions
  }

  labels = {
    app        = "reliability-api"
    managed-by = "terraform"
  }

  lifecycle {
    prevent_destroy = true
  }
}

output "state_bucket" {
  value = google_storage_bucket.tf_state.name
}

    1. Authenticate for Terraform with ADC and select your project (Module 11 covers projects/IAM): 
      gcloud auth application-default login
export TF_VAR_project_id="<your-project-id>"
    2. Bootstrap: 
      cd infra/terraform/gcp-bootstrap

terraform apply tfplan
terraform output -raw state_bucket
    3. Point a configuration at it with partial backend configuration so the bucket name isn't hard-coded: 
      terraform {
  backend "gcs" {
    prefix = "reliability-lab/dev"
  }
}
      terraform init -backend-config="bucket=$(terraform -chdir=../../gcp-bootstrap output -raw state_bucket)"
      If that directory already had local state, init offers to copy it to the new backend — back up terraform.tfstate first and answer yes.
    4. Verify locking: in two terminals run terraform apply in the same directory at the same time; the second reports Error acquiring the state lock with the holder's details.
    5. Inspect the stored state object: gcloud storage ls gs://<bucket>/reliability-lab/dev/ → default.tfstate.
    6. Cleanup (when you're done with the cloud modules): destroy the configurations that use the bucket first. Then for the bucket itself: remove prevent_destroy, set force_destroy = true only if you're sure the state is no longer needed, terraform apply, then terraform destroy. Verify in the console that the bucket is gone.

    Glossary

    IaC
    Infrastructure described in version-controlled code and applied by tools.
    Declarative
    Describe the end state; the tool computes the steps.
    Idempotent
    Re-applying the same input causes no further change.
    Drift
    Real infrastructure differs from configuration/state due to out-of-band changes.
    HCL
    HashiCorp Configuration Language: blocks, arguments, expressions.
    Provider
    Plugin implementing CRUD against one API.
    Resource / data source
    Object Terraform manages / object Terraform only reads.
    Address
    Terraform's identity for an instance, e.g. kubernetes_namespace_v1.env["dev"].
    State
    Record binding addresses to real objects plus their attributes; sensitive.
    Backend
    Where state is stored (local, gcs, …) and whether it's locked.
    Lock file
    .terraform.lock.hcl: exact provider versions + checksums.
    Plan
    Proposed actions computed from config vs refreshed state.
    Replace
    Destroy + create because an argument can't be updated in place.
    Module (root/child)
    Directory of .tf files; the one you run in / ones it calls.
    Workspace
    Named extra state for the same configuration and backend.
    moved / import
    Declarative address refactoring / adopting existing objects into state.

    Self-check

    1. What three things does terraform plan compare or consult, and which one does it update first?
    Configuration, state, and the real objects via provider APIs. It first refreshes its view of state from the real objects, then diffs against configuration to propose actions.
    2. Why commit .terraform.lock.hcl but never terraform.tfstate?
    The lock file pins exact provider versions/checksums so everyone and CI use the same plugins — it's reviewable and contains no secrets. State contains real attribute values including secrets and must be shared via a locked, access-controlled backend, not git.
    3. A plan shows -/+ on google_storage_bucket.tf_state with # forces replacement next to location. What would happen if you applied, and what protects you?
    Terraform would try to destroy the bucket (with all state versions) and create a new one — data loss. prevent_destroy = true makes the plan error instead; force_destroy = false makes deletion of a non-empty bucket fail. The right fix is to revert the location change.
    4. Difference between sensitive = true and ephemeral = true on a variable?
    sensitive only redacts the value in CLI output; it's still stored in state. ephemeral omits the value from state and plan files (with restrictions on where it can be referenced).
    5. You renamed a resource and the plan says "1 to add, 1 to destroy". What do you do?
    Add a moved block (from = old address, to = new address); re-plan should show "has moved to" with nothing to add or destroy. (Alternative: terraform state mv, but it's imperative and invisible in review.)
    6. Why can removing the first item from a list used with count recreate everything?
    count instances are identified by index. Removing item 0 shifts every later item down one index, so each index's arguments change (often forcing replacement) and the last index is destroyed. for_each identifies instances by key, so only the removed key is destroyed.
    7. Two engineers apply against the GCS backend at once. What happens?
    The first acquires the state lock; the second gets "Error acquiring the state lock" (or waits up to -lock-timeout). Without locking, both would write state and could corrupt it or create duplicates.
    8. Why might you use separate directories instead of workspaces for dev and prod?
    Workspaces share configuration, backend and credentials; HashiCorp says they're not appropriate when deployments need separate credentials and access controls. Separate directories make the environment explicit in paths and reviews and let prod use different projects/credentials.
    9. Where is the line between Terraform and Helm for reliability-api on GKE?
    Terraform: project services, network, GKE cluster/node pools, Artifact Registry, IAM, Workload Identity, state bucket. Helm: the reliability-api Deployment/Service/ConfigMap/HPA and the monitoring stack. One owner per object; Terraform may read in-cluster facts via data sources.
    10. Someone ran kubectl edit on a Terraform-managed ConfigMap during an incident. List the steps to resolve the drift safely.
    Run terraform plan -refresh-only to see exactly what changed. Decide with the incident owner whether the change should stay. If yes, update the configuration (PR) until plan is clean (optionally apply -refresh-only to record state). If no, apply the normal plan to revert it. Never blindly apply and silently undo an emergency fix.
    11. What does terraform apply tfplan do differently from terraform apply?
    It executes the previously saved plan without re-planning and without prompting. Plain apply computes a fresh plan and asks for approval. Saved plans guarantee you apply exactly what was reviewed.
