    Module 01 · Linux & Networking Foundations

    Docker and Kubernetes do not replace Linux. They sit on top of it. When reliability-api fails in a container or a Pod, the cause usually comes down to a few things: a process that exited, a signal that was ignored, a file the app could not read, an environment variable that was missing, a socket bound to the wrong address, a DNS name that did not resolve, or an HTTP status that meant something other than you thought. This module covers each of those ideas in depth, using the same running app throughout. It ends with namespaces and cgroups, the two kernel features that make containers possible.

    Prereq: none (comfortable in a terminal)≈ 5 h study + 3 h lab✓ Checked against official docs, Oct 2026
    You are on macOS?

    Several commands here (ss, free, journalctl, /proc) exist only on Linux. You have three options: (1) use a Linux VM (UTM, Multipass, a cloud VM); (2) once Docker is installed (Module 02), open a throwaway Linux shell with docker run --rm -it python:3.12-slim bash and install tools with apt-get update && apt-get install -y iproute2 procps curl dnsutils lsof; (3) use the macOS equivalents shown in the notes (lsof -nP -iTCP -sTCP:LISTEN instead of ss -ltnp, vm_stat instead of free). Containers and Kubernetes nodes run Linux, so learn the Linux versions.

    Learning objectives

    • Explain what a process is, how it gets a PID, who its parent is, and why PID 1 is special (this is the key to understanding container shutdown).
    • Tell SIGTERM apart from SIGKILL, predict what each does to reliability-api, and explain why graceful shutdown matters during rolling updates.
    • Decode any exit code, including 137 = 128 + 9 (killed by SIGKILL, often an out-of-memory kill) and 143 = 128 + 15.
    • Read and set file permissions, and explain why the app should run as a non-root user.
    • Use environment variables for configuration, and send logs to stdout and stderr where platforms can collect them.
    • Describe the TCP/IP layers, ports, and sockets well enough to explain connection refused versus timeout.
    • Predict who can reach a server bound to 127.0.0.1 versus 0.0.0.0. This is the most common reason a container "works inside but not outside".
    • Trace a DNS lookup and an HTTP request/response, and read status codes the way probes and load balancers do.
    • Use ps, top, ss, lsof, curl -v, dig, df/du/free, and journalctl to collect evidence.
    • Explain how namespaces (what a process can see) and cgroups (what it can use) combine into a container.

    The big picture: what sits under reliability-api

    The app is a few dozen lines of Python. Running it pulls in a whole stack: an interpreter process, a user it runs as, an environment it reads, file descriptors it writes logs to, a listening socket on a port, and the kernel's TCP/IP stack, which turns network packets into the HTTP requests FastAPI sees. Every later module adds layers on top (container, Pod, Service, Ingress), but the stack in this picture stays underneath all of them.

    The canonical app you will run

    This is the exact app/main.py used in every module. Save it now. You will run it natively in this module's labs and in a container in Module 02.

    import os, time, logging
from fastapi import FastAPI, Response
from prometheus_client import Counter, Histogram, generate_latest, CONTENT_TYPE_LATEST

LOG_LEVEL = os.getenv("LOG_LEVEL", "info").upper()
READY_DELAY = float(os.getenv("READY_DELAY_SECONDS", "0"))
logging.basicConfig(level=LOG_LEVEL, format="%(asctime)s %(levelname)s %(message)s")
log = logging.getLogger("reliability-api")

REQUESTS = Counter("http_requests_total", "Total HTTP requests", ["path", "status"])
LATENCY = Histogram("http_request_duration_seconds", "Request latency", ["path"])

app = FastAPI()
STARTED = time.monotonic()

@app.get("/health")
def health():
    return {"status": "ok"}

@app.get("/ready")
def ready(response: Response):
    if time.monotonic() - STARTED < READY_DELAY:
        response.status_code = 503
        return {"ready": False}
    return {"ready": True}

@app.get("/work")
def work(ms: int = 50):
    start = time.perf_counter()
    while (time.perf_counter() - start) * 1000 < ms:
        pass                                   # burn CPU deliberately
    elapsed = time.perf_counter() - start
    LATENCY.labels("/work").observe(elapsed)
    REQUESTS.labels("/work", "200").inc()
    return {"worked_ms": round(elapsed * 1000, 1)}

@app.get("/metrics")
def metrics():
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

prometheus-client==0.20.0

    Each line of the app maps to a topic in this module. os.getenv reads environment variables. logging.basicConfig writes to stderr by default. /ready returns HTTP 503 during warm-up. /work burns CPU, which you will watch in top. Uvicorn is the process that owns the listening socket.

    Processes and PIDs

    Definition. A process is a running instance of a program. The kernel keeps a record for each one, identified by a numeric PID (process ID). The record holds the program's memory, its open files (as numbered file descriptors), its current working directory, its user and group IDs, its environment variables, and its parent's PID (PPID).

    Problem it solves. Many programs need to share one CPU and one kernel. Processes give each program its own memory and identity. The kernel can schedule them, account for their resources, deliver signals to them, and report how each one ended.

    How a process is born: fork + exec

    On Linux a new process is created in two steps:

    1. fork: an existing process (for example your shell, zsh or bash) makes a copy of itself. The copy is the child and gets a new PID. Its PPID is the shell's PID. As environ(7) says, the child "inherits a copy of its parent's environment".
    2. exec: the child replaces its program image with a new program (here the Python interpreter running Uvicorn). The PID stays the same. The code is now different.

    The result is a process tree. Every process has a parent, up to PID 1 (on most Linux hosts, systemd), which the kernel starts at boot.

    Self-check: you start Uvicorn from bash, then close the terminal. What happens to the Uvicorn process, and why?
    Closing the terminal sends SIGHUP (hang-up) to the session. Its default action is to terminate, so Uvicorn usually dies. That is why services run under a supervisor (systemd, Docker, Kubernetes) and not from an interactive shell. The supervisor becomes the parent, restarts the process, and collects its exit code.

    Signals: SIGTERM vs SIGKILL

    Definition. A signal is a small asynchronous notification the kernel delivers to a process. It carries no data beyond its number. Each signal has a default action (terminate, core dump, ignore, stop, continue). A process can install a handler to run its own code instead, except for two signals that can never be caught.

    Problem it solves. The OS, a supervisor, or a human needs a standard way to say "please shut down", "reload config", or "stop right now". Every orchestrator you will use stops your app with signals: systemd, docker stop, and the Kubernetes kubelet during a rolling update or scale-down.

    SignalNo. (x86/ARM)Default actionCan be caught?Who sends it to reliability-api
    SIGHUP1TermYesTerminal closed; some daemons treat it as "reload config"
    SIGINT2TermYesYou press Ctrl+C
    SIGQUIT3CoreYesCtrl+\
    SIGKILL9TermNoKernel OOM killer; docker stop / kubelet after the grace period; kill -9
    SIGTERM15TermYeskill PID (default), docker stop, kubelet at Pod termination, systemd stop
    SIGCHLD17IgnYesKernel, when a child process exits (parent should reap it)
    SIGSTOP19StopNokill -STOP, debuggers (note: Ctrl+Z sends the catchable SIGTSTP)

    From signal(7): "The signals SIGKILL and SIGSTOP cannot be caught, blocked, or ignored." Signal numbers vary by CPU architecture. The ones above are for x86 and ARM, which covers almost every laptop and cloud node. Use names (kill -TERM) instead of numbers in scripts.

    Graceful vs forced shutdown, step by step

    1. The supervisor sends SIGTERM to the process. In a container this is PID 1. Kubernetes' kubelet "triggers the container runtime to send a TERM signal to process 1 inside each container".
    2. If the process has a handler, the handler runs. Uvicorn's handler (it registers SIGINT and SIGTERM) stops accepting new connections, waits for in-flight requests (bounded by --timeout-graceful-shutdown if set), runs FastAPI shutdown events, and exits. You see log lines such as Shutting down, Waiting for application shutdown., Application shutdown complete., Finished server process [4321].
    3. If the process is still alive when the grace period ends, the supervisor sends SIGKILL. The kernel destroys the process immediately. No handler runs, buffers are not flushed, and open connections are reset.

    Why this matters so much for containers

    On a normal host, a process with no SIGTERM handler takes the default action, which is terminate. That makes SIGTERM look harmless. Inside a container, the main process is PID 1 of its PID namespace, and the kernel gives PID 1 a special rule. From pid_namespaces(7):

    "Only signals for which the "init" process has established a signal handler can be sent to the "init" process by other members of the PID namespace. … a process in an ancestor namespace can … send signals to the "init" process of a child PID namespace only if the "init" process has established a handler for that signal. … SIGKILL or SIGSTOP are treated exceptionally: these signals are forcibly delivered when sent from an ancestor PID namespace."

    Consequence: if the PID 1 process has no SIGTERM handler, SIGTERM is simply not delivered. Nothing happens. The process does not get the default "terminate". It keeps running until SIGKILL arrives at the deadline. You see a 10-second docker stop (or a 30-second Pod termination) and exit code 137. Two common ways to end up there:

    • The container's PID 1 is a shell (/bin/sh -c "uvicorn …", from a shell-form CMD). The shell may not forward the signal to Uvicorn.
    • PID 1 is a plain Python script that never registered a SIGTERM handler. Python installs a handler for SIGINT (raising KeyboardInterrupt) but not for SIGTERM.

    Uvicorn does register SIGTERM and SIGINT handlers, so if Uvicorn itself is PID 1 (exec-form CMD, Module 02) you get graceful shutdown.

    Failure case: requests dropped on every deploy

    During a Kubernetes rolling update, old Pods are terminated. If reliability-api ignores SIGTERM, every old Pod is SIGKILLed after 30 s, and any requests in flight at that moment fail. If it exits instantly on SIGTERM without finishing in-flight work, those requests fail too. The fix is a SIGTERM handler that drains and then exits, plus readiness going false so new traffic stops arriving (Module 04).

    $ kill -l                       # list signal names and numbers
$ kill 4321                     # same as kill -TERM 4321 (SIGTERM is kill's default)
$ kill -INT 4321                # like Ctrl+C
$ kill -KILL 4321               # last resort: no cleanup possible
$ grep -E 'SigCgt|SigIgn' /proc/4321/status   # bitmasks of caught / ignored signals

    SigCgt is a hexadecimal bitmask of the signals the process has handlers for. Bit n−1 stands for signal n. For SIGTERM (15), check bit 14, which is value 0x4000. It is a quick way to check, without reading code, whether a PID 1 will react to SIGTERM.

    Trade-offs

    • Longer grace period: more time to drain slow requests, but slower deploys and slower node drains. Shorter: faster rollouts, but more risk of cut requests.
    • SIGKILL as routine (kill -9 in scripts) skips cleanup: buffered logs and metrics are lost and temp files are left behind. Use it only when SIGTERM failed.
    Self-check: docker stop on your container always takes exactly ~10 seconds and the exit code is 137. What is the most likely cause?
    SIGTERM is not reaching a process that handles it. Usually PID 1 is a shell from a shell-form CMD, or a program with no SIGTERM handler. Because PID 1 ignores signals it has no handler for, nothing happens until Docker's 10 s timeout, then SIGKILL gives 128+9 = 137. The fix is an exec-form CMD so Uvicorn is PID 1, or --init / a tiny init that forwards signals.

    Exit codes

    Definition. When a process ends, the kernel keeps a small status for its parent to collect with wait(). Either the process exited with a number from 0 to 255 (its own exit(n), where only the low 8 bits are kept), or it was terminated by a signal. Shells merge the two into one number. From bash(1): "When a command terminates on a fatal signal N, bash uses the value of 128+N as the exit status." Docker and Kubernetes report container exit codes the same way.

    Problem it solves. The exit code is the cheapest diagnostic you will ever get. Before reading a single log line, it tells you whether the app chose to quit (an error path), could not start at all, or was killed from outside.

    CodeMeaningTypical reliability-api cause
    0SuccessClean shutdown after SIGTERM / Ctrl+C (Uvicorn finished draining)
    1Generic failure chosen by the programUnhandled Python exception at import (e.g. float("abc") from a bad READY_DELAY_SECONDS), port already in use
    2Misuse / bad CLI arguments (convention; bash builtins use it)Typo in a Uvicorn flag (Click-based CLIs exit 2 on usage errors)
    126Command found but not executableScript missing the +x bit, or wrong interpreter. Docker uses 126 for "contained command can't be invoked"
    127Command not founduvicorn not on PATH (venv not activated / not copied into the image)
    125(Docker only) error in the Docker daemon itselfBad docker run flag, port already allocated on host
    130128 + 2: killed by SIGINTYou pressed Ctrl+C on a program without a handler
    137128 + 9: killed by SIGKILLOut-of-memory kill (memory limit hit), or SIGTERM ignored until the grace period ended, or kill -9
    143128 + 15: killed by SIGTERM (no handler)A process without a SIGTERM handler, not PID 1, got kill or docker stop. Newer Uvicorn versions also re-raise SIGTERM after graceful cleanup, so a clean drain can show 143 instead of 0
    137 does not automatically mean "out of memory"

    137 only says "SIGKILL". To tell an OOM kill from a grace-period kill, look for extra evidence. Docker sets State.OOMKilled in docker inspect. Kubernetes shows Reason: OOMKilled in kubectl describe pod (Module 04). On a host, the kernel log has Out of memory: Killed process … (journalctl -k or dmesg). If none of those appear and the shutdown took exactly the grace period, the app ignored SIGTERM.

    Exit-code decoder
    Type the code you saw (from echo $?, docker ps -a, or Kubernetes Last State: Terminated, Exit Code). Pick the context.
    $ python3 -c 'import sys; sys.exit(3)'; echo "exit=$?"

$ sleep 100 & kill -TERM $!; wait $!; echo "exit=$?"

$ sleep 100 & kill -KILL $!; wait $!; echo "exit=$?"

# Example output from bash; job-control messages such as "Terminated" may also print
    Self-check: a Python program calls sys.exit(256). What exit code does the shell show, and why?
    0. Only the low 8 bits of the status survive (256 mod 256 = 0). Exit codes are 0–255, so never use values outside that range to mean anything.

    Users, groups, and file permissions

    Definition. Every process runs with a set of credentials: a user ID (UID), a primary group ID (GID), and supplementary groups (see credentials(7)). Every file has an owner UID, an owner GID, and a 9-bit mode: read/write/execute for user (owner), group, and others. UID 0 is root, which bypasses most permission checks.

    Problem it solves. Least privilege. If an attacker gets code execution inside reliability-api, the damage is limited to what the process's UID can touch. Running as root means the attacker can modify system files. In a container it also makes kernel-escape bugs more dangerous.

    How a permission check works

    1. The process (e.g. Uvicorn running as UID 10001) asks to open /app/app/main.py for reading.
    2. The kernel walks the path. Every directory along it needs x for the matching class.
    3. On the final file it picks one class: owner if UIDs match, otherwise group if one of the process's groups matches, otherwise others. It then checks the requested bit. Classes are not combined.
    4. If the bit is missing, the call fails with EACCES, which Python raises as PermissionError: [Errno 13] Permission denied.

    Applied to reliability-api

    • The app only needs to read its code and execute Python. It never needs to write to /app. So in Module 02 the image creates a dedicated non-root user (UID 10001), and code is owned by root and readable by everyone (mode 644 for files, 755 for directories). The app cannot modify its own code even if compromised.
    • Port 8000 is above 1024. From ip(7): "port numbers below 1024 are called privileged ports … Only a privileged process (on Linux: a process that has the CAP_NET_BIND_SERVICE capability …) may bind(2) to these sockets." Choosing 8000 means no extra privilege is needed. The Kubernetes Service maps port 80 to it later.
    $ id                                   # who am I?
uid=1000(dev) gid=1000(dev) groups=1000(dev),27(sudo)
$ ls -l app/
-rw-r--r-- 1 dev dev 1342 Oct 29 10:02 main.py
$ chmod 640 app/main.py                # owner rw, group r, others nothing
$ sudo chown root:root app/main.py     # change owner (needs privilege)
$ ps -o user,uid,pid,args -p 4321      # which user is the app running as?
# Example output (yours will differ in names/IDs/timings)
    Failure cases
    • PermissionError at startup: files were copied as root with mode 600, and the app runs as UID 10001. Diagnose with ls -ln (numeric IDs) and id inside the container.
    • Cannot write a log/temp file: the app tries to write into a root-owned directory. Fix: write logs to stdout instead; use /tmp or a mounted volume for scratch files.
    • "Fixing" it with chmod 777: this makes the error go away and silently gives write access to everyone. Fix ownership instead.
    Self-check: directory /data is drw-r--r-- owned by your user. Can you cat /data/file.txt?
    No. Reading a file inside a directory requires x (traverse) on the directory. Without x you may be able to list the names (with r), but you cannot access entries. You get "Permission denied".

    Environment variables

    Definition. A list of NAME=value strings handed to a program when it starts (execve). Child processes "inherit a copy of [their] parent's environment" (environ(7)). Changes made in a child never flow back to the parent.

    Problem it solves. The same build of a program can behave differently per environment (laptop, CI, production) without code changes. This is the basis of "build once, configure at deploy time". The same image runs everywhere; only -e flags (Docker) or a ConfigMap/Secret (Kubernetes) differ.

    reliability-api's configuration contract

    VariableDefaultRead byEffect

    Env vars are not secret storage

    Anyone who can read /proc/PID/environ (same user or root), run docker inspect, or read the Pod spec can see them. They also leak into crash dumps and debug pages. Never bake secrets into an image with ENV. Inject them at runtime from a secret store (Kubernetes Secret, Module 05; CI secrets, Module 09) and keep their scope small.

    Failure cases

    • "I exported it but the app does not see it": you exported it in a different shell, or after the process started. Check /proc/PID/environ, not your shell.
    • Typo in the name (LOGLEVEL): os.getenv silently falls back to the default. Log the effective config at startup so this is visible.
    • Bad value (READY_DELAY_SECONDS=ten): float() raises ValueError at import and the app exits with 1. In Kubernetes this becomes CrashLoopBackOff.

    stdout, stderr, and logs

    Definition. Every process starts with three open file descriptors: 0 = stdin, 1 = stdout (normal output), and 2 = stderr (diagnostics). They are just numbers pointing at whatever the parent connected: a terminal, a file, a pipe, or (in Docker) a log driver.

    Problem it solves. The program does not need to know where its output goes. The platform decides. That is why the modern rule for services is to log to stdout/stderr and let the platform collect it. docker logs, kubectl logs, and journalctl all read exactly these streams.

    • Buffering: when stdout is a pipe or file rather than a terminal, Python buffers output in blocks. Logs can then appear late, or be lost if the process is SIGKILLed. Containers set PYTHONUNBUFFERED=1 to avoid this (Module 02).
    • Order matters in redirection: cmd > f 2>&1 sends both to f. cmd 2>&1 > f sends stderr to the old stdout (the terminal) and only stdout to f.
    • Do not log to files inside a container: they fill the writable layer, disappear when the container is replaced, and are invisible to kubectl logs.
    Self-check: you run uvicorn app.main:app > app.log. Startup messages still print to the terminal, while app.log only collects request lines. Why?
    > redirects only fd 1 (stdout). With Uvicorn's default logging config, the access log goes to stdout, while server messages and Python logging output go to stderr (fd 2), which still points at the terminal. Use > app.log 2>&1 to capture both.

    Ports and sockets

    A port is a 16-bit number (0–65535) that lets one IP address host many services. A socket is the kernel object a program uses to talk over the network. It is a file descriptor, so lsof lists it next to files. Two kinds of TCP socket matter:

    • Listening socket: created by socket() → bind(addr, port) → listen(). Uvicorn has one, bound to (0.0.0.0, 8000). It accepts nothing on its own. It is a queue of incoming connections (the backlog).
    • Connected socket: created by accept() for each client. It is identified by the 4-tuple (src IP, src port, dst IP, dst port). That is how 1,000 clients can all talk to port 8000 at once: each connection differs by client IP or client (ephemeral) port.

    The TCP handshake and the two errors you will see most

    Binding: 127.0.0.1 vs 0.0.0.0

    Definition. When a server calls bind(), it chooses which local IP address (and port) the listening socket accepts connections on.

    • 127.0.0.1 (localhost, the loopback interface lo): only connections that originate on the same network stack can reach it. Same machine, or (inside a container) the same container.
    • 0.0.0.0 (INADDR_ANY): from ip(7), "When INADDR_ANY is specified in the bind call, the socket will be bound to all local interfaces." That covers loopback and every real or virtual interface (eth0, the container's veth, Wi-Fi). :: is the IPv6 equivalent.
    • A specific address such as 192.168.1.20: only connections arriving at that one interface.

    Problem it solves. Binding is a security and exposure control. A dev database bound to 127.0.0.1 is invisible to the coffee-shop Wi-Fi. It is also the single most common reason a containerized app "works inside but not from outside".

    The trap that bites everyone

    Uvicorn's default --host is 127.0.0.1 (Uvicorn settings docs: "Default: '127.0.0.1'", default --port 8000). That is a safe default on a laptop, but inside a container "localhost" means the container's own loopback. Docker's port forwarding and Kubernetes Services deliver traffic to the container's eth0 address, not its loopback. With the default, every request from outside the container is refused. That is why reliability-api always runs with --host 0.0.0.0.

    Trade-offs

    • 0.0.0.0 on a laptop exposes the app to your whole network. That is fine inside a container (the container's network is isolated and only published ports are forwarded), but think twice on a bare host.
    • Docker's -p 8000:8000 itself publishes on all host addresses by default. To keep a container reachable only from your laptop, use -p 127.0.0.1:8000:8000 (Module 02). There are two separate binding decisions: the app's inside the container, and Docker's on the host.
    Self-check: inside the container curl localhost:8000/health works, but from your laptop curl localhost:8000/health gives "connection reset" or "empty reply". The container was run with -p 8000:8000. Most likely cause?
    Uvicorn is bound to 127.0.0.1 inside the container (the default). Docker forwards host:8000 to the container's eth0 address, where nothing listens. Restart with --host 0.0.0.0. The exact client error varies by Docker setup ("connection reset", "empty reply from server", or "refused"). The diagnosis is the same: run ss -ltn inside the container.

    DNS resolution

    Definition. DNS (Domain Name System, RFC 1034/1035) is a distributed, cached database that maps names to records: A (IPv4), AAAA (IPv6), CNAME (alias), and others. Each answer has a TTL, the number of seconds it may be cached.

    Problem it solves. IPs change: containers are replaced, Pods get new IPs, cloud load balancers move. Names stay stable. In Kubernetes your load generator will call http://reliability-api.reliability-lab.svc.cluster.local and never an IP (Module 05). On a Docker user-defined network it calls http://reliability-api:8000 (Module 02).

    How a lookup flows (click through)

    DNS lookup walk-through
    $ cat /etc/resolv.conf
nameserver 10.0.0.2
search lan
$ dig +noall +answer example.com A          # just the answer section
example.com.        287   IN   A   203.0.113.10
#                    ^^^ remaining TTL in seconds (counts down in caches)
$ dig @1.1.1.1 example.com A +short        # ask a specific resolver, bypassing resolv.conf
$ nslookup example.com                     # older, simpler tool; also available on macOS
$ getent hosts example.com                 # uses the same path as apps: /etc/hosts AND DNS
# Example output: real IPs for example.com differ; 203.0.113.0/24 is a documentation range
    dig vs getent

    dig and nslookup talk to DNS directly and skip /etc/hosts. getent hosts goes through nsswitch like your app does. If dig works and the app fails (or the reverse), compare them. The difference is usually /etc/hosts or the search domains.

    Failure cases

    • NXDOMAIN ("Name or service not known" in Python): the name does not exist. Check for typos, the wrong namespace in Kubernetes, or a missing search domain.
    • SERVFAIL / timeout: the resolver is unreachable or broken. In Kubernetes, check CoreDNS Pods (Module 05).
    • Stale answer: the IP changed but a cache still holds the old record until its TTL expires. Clients that cache forever (some JVMs, long-lived connection pools) keep using dead IPs.
    • Containers on Docker's default bridge cannot resolve each other by name. Only user-defined networks get embedded DNS (Module 02).

    HTTP request and response anatomy

    Definition. HTTP is a request/response protocol over a TCP connection (HTTP/1.1, HTTP/2; HTTP/3 uses QUIC over UDP). A client sends a method + target + headers + optional body. The server returns a status code + headers + optional body. Semantics are defined in RFC 9110.

    Status code classes (RFC 9110 §15)

    ClassRFC meaningCodes you will meetreliability-api example
    1xxInformational: request received, continuing101 Switching Protocols(not used)
    2xxSuccessful200 OK, 201 Created, 204 No Content/health, /work → 200
    3xxRedirection: further action needed301, 302, 307, 308FastAPI may 307-redirect a trailing-slash mismatch
    4xxClient error400, 401, 403, 404, 405, 422, 429/work?ms=abc → 422 (validation), /nope → 404
    5xxServer error500, 502, 503, 504/ready → 503 during warm-up; 502/504 come from proxies in front of the app
    Why the class matters for reliability

    SLOs usually count 5xx as server failures and treat 4xx as the client's fault. A metric that lumps them together (or a /ready that returns 500 instead of 503) misleads dashboards and alerts (Module 07). 502 Bad Gateway and 504 Gateway Timeout mean a proxy could not get a good answer from the app. The app itself may never have seen the request.

    Namespaces and cgroups: the bridge to containers

    Here is the key insight for Module 02. A container is an ordinary Linux process started with two extra kernel features applied:

    • Namespaces change what the process can see. From namespaces(7): "A namespace wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance of the global resource."
    • cgroups (control groups) change what the process can use. From cgroups(7): "A cgroup is a collection of processes that are bound to a set of limits or parameters". The kernel's subsystems make it possible to limit CPU time and memory, among other resources.

    Self-check: a container has a 256 MiB memory limit and the app slowly leaks memory. What do you observe, in Linux terms?
    When the cgroup's memory usage reaches its limit and the kernel cannot reclaim enough, the kernel OOM killer kills a process in that cgroup with SIGKILL. If that is the main process, the container exits with 137 (128 + 9). Docker reports OOMKilled: true, Kubernetes reports Reason: OOMKilled, and the restart policy decides what happens next. No SIGTERM is sent and no handler runs.

    Lab 3 — Signals, exit codes, and the PID 1 rule

    Goal: see graceful shutdown, 143 and 137, and prove that PID 1 ignores signals it has no handler for.

    1. Graceful SIGTERM with an in-flight request. Start the app (terminal A). In B, start a slow request: curl 'localhost:8000/work?ms=5000'. Within 5 s, in C: kill -TERM $(pgrep -f 'uvicorn app.main:app'). Observe in A: 
      INFO:     Shutting down
INFO:     Waiting for application shutdown.
INFO:     Application shutdown complete.
INFO:     Finished server process [4321]
      Does the curl in B still get {"worked_ms":5000.0}? Then run echo $? in A. Depending on your Uvicorn version you will see 0 or 143, because newer versions re-raise the signal after cleanup. Either way the shutdown was graceful. Record which you got.
    2. A process without a handler. 
      $ python3 -c 'import time; time.sleep(600)' &
$ kill -TERM $!; wait $!; echo "exit=$?"
exit=143
$ python3 -c 'import time; time.sleep(600)' &
$ kill -KILL $!; wait $!; echo "exit=$?"
exit=137
    3. The PID 1 rule (the container problem, without a container). Terminal A: 
      $ sudo unshare --pid --fork --mount-proc python3 -c 'import time; print("I am PID 1"); time.sleep(600)'
      Terminal B: 
      $ P=$(pgrep -f '^python3 -c import time'); echo $P   # host PID of that python
$ sudo kill -TERM $P            # nothing happens: PID 1 of its namespace has no SIGTERM handler
$ sleep 3; ps -p $P -o pid,stat,args   # still alive
$ sudo kill -KILL $P            # SIGKILL is always delivered from an ancestor namespace
      Terminal A returns. Check echo $? there (expect a 128+9 style status). This is exactly why docker stop on a badly written image takes 10 s and ends in 137.

    Glossary

    Process / PID
    A running program instance; the numeric ID the kernel assigns it.
    PPID
    Parent's PID. The parent collects the child's exit status.
    PID 1 / init
    First process of a PID namespace. It adopts orphans and only receives signals it has handlers for (except SIGKILL/SIGSTOP from an ancestor namespace).
    Zombie
    A process that exited but whose status was not yet collected by its parent.
    Signal
    Asynchronous notification to a process (SIGTERM = please stop, SIGKILL = stop now, uncatchable).
    Grace period
    Time between SIGTERM and SIGKILL (docker stop 10 s, Kubernetes default 30 s).
    Exit code
    0–255 status of a finished process; 128+N means terminated by signal N.
    UID / GID
    Numeric user / group identity of a process or file owner. UID 0 = root.
    Mode bits
    rwx for user, group, and others; written in octal (e.g. 755, 644).
    Environment variable
    NAME=value pair passed at exec time and inherited by children.
    File descriptor
    Integer handle to an open file or socket. 0/1/2 = stdin/stdout/stderr.
    Port
    16-bit number selecting a service on an IP address. Below 1024 is privileged.
    Socket
    Kernel endpoint for network I/O. Listening sockets accept, connected sockets carry data.
    Bind address
    Local IP a listening socket accepts on. 127.0.0.1 = loopback only, 0.0.0.0 = all interfaces.
    Loopback (lo)
    Virtual interface for traffic that never leaves the network stack (127.0.0.0/8).
    DNS / TTL
    Name → record lookup system; TTL is how long an answer may be cached.
    Resolver
    Stub resolver (in libc, reads resolv.conf) vs recursive resolver (does the lookup and caches).
    HTTP status class
    1xx info, 2xx success, 3xx redirect, 4xx client error, 5xx server error.
    Namespace
    Kernel feature giving a process its own view of a global resource (PIDs, network, mounts, …).
    cgroup
    Kernel feature grouping processes to limit and account for CPU, memory, and more.
    OOM killer
    Kernel mechanism that SIGKILLs a process when memory (global or a cgroup's limit) runs out.

    Self-check

    1. What is the difference between SIGTERM and SIGKILL, and which one does a well-behaved orchestrator send first?
    SIGTERM (15) can be caught. The app can finish in-flight work and clean up. SIGKILL (9) cannot be caught, blocked, or ignored, and the kernel ends the process immediately. Orchestrators send SIGTERM first, wait a grace period, then SIGKILL.
    2. A container shows exit code 143. What happened?
    143 = 128 + 15: the main process was terminated by SIGTERM (it had a handler that re-raised the signal after cleanup, or it was not PID 1 and took the default action). Usually this is a normal stop (docker stop, rolling update), not a crash.
    3. Why does Uvicorn's default --host 127.0.0.1 break the app in a container even though it works on your laptop?
    In a container, 127.0.0.1 is the container's own loopback. Traffic forwarded by Docker (-p) or Kubernetes arrives on the container's eth0 IP, where nothing is listening, so the connection is refused or reset. Bind to 0.0.0.0.
    4. "Connection refused" vs "Connection timed out": which layer does each point to?
    Refused: the host was reached and replied with a TCP RST because nothing listens on that address:port (app down, wrong port, wrong bind). Timeout: no reply at all. Packets were dropped (firewall, wrong IP, no route) or the server is too overloaded to complete the handshake.
    5. dig api.internal returns an IP but the app gets "Name or service not known". Name two reasons.
    (a) The app resolves through nsswitch and /etc/resolv.conf with different nameservers or search domains than the server you queried with dig. (b) The app runs in a different network namespace (a container) with its own resolv.conf. Compare with getent hosts run in the same environment as the app.
    6. Your app is OOM-killed. Does its SIGTERM handler run? Does it log anything?
    No. The OOM killer sends SIGKILL, so no handler runs and buffered logs may be lost. Evidence comes from outside: exit code 137, OOMKilled status, kernel log.
    7. Why is it better to log to stdout/stderr than to /var/log/app.log in a container?
    The runtime captures stdout and stderr (docker logs, kubectl logs, log shippers). Files inside the container are invisible to those tools, fill the writable layer, and vanish when the container is replaced.
    8. What permission does a directory need for a process to open a file inside it?
    Execute (x, "search/traverse") on that directory and every parent directory, for the class (user/group/other) that applies to the process.
    9. Why does /ready return 503 and not 500 during warm-up?
    503 Service Unavailable means a temporary condition: try later or elsewhere. Probes and load balancers treat any status outside 200–399 as failure, so both would remove the Pod from rotation, but 503 keeps dashboards and SLOs honest: it is "not ready", not "broken".
    10. In one sentence each: what do namespaces and cgroups contribute to a container?
    Namespaces control what the process can see (its own PIDs, network stack, hostname, mounts). Cgroups control what it can use (CPU time, memory), and exceeding the memory limit leads to an OOM kill.
    11. You set export LOG_LEVEL=debug in terminal B, but the app started in terminal A still logs at INFO. Why?
    Environment variables are copied into a process at exec time from its parent. Terminal B's shell is not the app's parent, and even a parent's later changes do not reach an already-running child. Restart the app with the variable set.
