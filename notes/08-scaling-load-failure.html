    1. Three autoscalers, three different knobs

    “Autoscaling” means three different mechanisms acting at three different levels. Confusing them is the most common beginner error in interviews and in incident calls.

Only a node autoscaler fixes that — and only in clouds. In a kind cluster, HPA’s ceiling is whatever your laptop’s Docker VM can schedule.

    2. metrics-server and the resource metrics API

    The HPA does not read Prometheus. For CPU and memory it reads the Metrics API (metrics.k8s.io), an aggregated API that is usually served by the metrics-server add-on. The pipeline:

    What the Metrics API reports

    • CPU: average core usage in CPU units over a short window, derived from the rate of a cumulative CPU counter. 1 CPU = 1 vCPU/core (cloud) or 1 hyper-thread (bare-metal Intel).
    • Memory: the working set in bytes at collection time — memory in use that cannot be freed under pressure.
    • metrics-server keeps only the latest values, no history. Its README states it is meant only for autoscaling purposes, not as a monitoring solution — that is Prometheus’s job. It scrapes on a 15-second cycle by default.
    • The Metrics API has a v1 version in current Kubernetes docs, but the HPA page notes that the HPA currently supports metrics.k8s.io/v1beta1 for resource metrics, not v1 yet. Use whichever version kubectl api-versions | grep metrics shows in your cluster when you query it by hand.

    3. The HPA algorithm

    The HorizontalPodAutoscaler is a control loop in kube-controller-manager. It is intermittent, not continuous: by default it runs every 15 seconds (--horizontal-pod-autoscaler-sync-period). On each pass it finds the target’s Pods via the target’s .spec.selector, fetches their metrics, and computes:

    desiredReplicas = ceil( currentReplicas × currentMetricValue / desiredMetricValue )

    For a CPU Utilization target, each Pod’s value is usage ÷ request (summed over its containers), and currentMetricValue is the mean across Pods. If any container in the Pod lacks a CPU request, utilization is undefined and the HPA takes no action for that metric.

    Step by step, with the details that matter

    1. Tolerance. If the ratio current/desired is within the tolerance of 1.0 (default 0.1, i.e. 54 %–66 % for a 60 % target), nothing happens. The cluster-wide default is set by --horizontal-pod-autoscaler-tolerance; newer clusters with the HPAConfigurableTolerance feature can also set a per-HPA, per-direction tolerance under behavior.scaleUp/scaleDown.
    2. Ignored and set-aside Pods. Pods being deleted are ignored and failed Pods discarded. Pods with missing metrics are set aside. For CPU, Pods that are not yet ready (or whose latest metric predates readiness) are set aside too.
    3. Conservative recomputation. If metrics were missing, the average is recomputed assuming those Pods use 100 % of the target on scale-down and 0 % on scale-up. If not-yet-ready Pods exist and the result would be a scale-up, they are assumed to use 0 %. If the recomputed ratio reverses direction or falls inside the tolerance, the HPA does nothing. (The status still reports the original average.)
    4. Start-up noise. Two cluster-wide flags limit the effect of start-up CPU spikes: --horizontal-pod-autoscaler-initial-readiness-delay (default 30 s) and --horizontal-pod-autoscaler-cpu-initialization-period (default 5 min). The docs recommend a startupProbe or readinessProbe that reports Ready only after the warm-up spike — relevant because reliability-api has READY_DELAY_SECONDS.
    5. Multiple metrics. Each metric proposes a count; the HPA takes the largest. If some metrics cannot be fetched and the others suggest scaling down, scaling is skipped — it can still scale up.
    6. Behavior (stabilization window, policies — section 4), then clamp to minReplicas/maxReplicas, then write the scale subresource. The Deployment controller does the rest.

    Why requests decide everything: the reliability-api numbers

    reliability-api requests 100m CPU and the HPA targets 60 %. So the HPA considers a Pod “at target” when it uses 60 millicores. One /work?ms=50 request burns ≈ 50 ms of CPU, so at target each Pod handles only about 0.06 / 0.05 = 1.2 requests/s. Work it through:

    Load (req/s of /work?ms=50)CPU needed (cores)Per Pod with 2 PodsUtilization vs 100mFormulaAfter clamp (max 6)
    10.0525m25 %ceil(2 × 25/60) = 12 (min)
    2.40.1260m60 %within tolerance2
    100.5250m250 %ceil(2 × 250/60) = 96 (ScalingLimited)
    201.0500m500 %ceil(2 × 500/60) = 176 (ScalingLimited)

    Two lessons. First, with a tiny request the HPA saturates at maxReplicas under modest load — the 100m request was chosen for scheduling density, not for autoscaling accuracy. Second, a Pod can use far more CPU than it requests (there is no CPU limit), so utilization above 100 % is normal; a single Uvicorn worker running a pure-Python busy loop is effectively limited to about one core. If you set the request to 500m, the same 20 req/s gives 100 % per Pod with 2 Pods → ceil(2 × 100/60) = 4 replicas. Choose requests from measured usage first; then choose the HPA target.

    Self-check: 3 Pods, average utilization 70 %, target 60 %. Scale? To what?
    Ratio = 70/60 ≈ 1.167, outside the 0.1 tolerance. desired = ceil(3 × 1.167) = ceil(3.5) = 4. If one of the 3 Pods were not yet ready, the controller would set it aside and, because this is a scale-up, recompute assuming it uses 0 % — possibly cancelling or shrinking the scale-up.

    4. HPA behavior: stabilization windows and scaling policies

    The raw formula reacts to every wobble in the metric. Left alone, replicas would flap (also called thrashing): add Pods, load per Pod drops, remove Pods, load per Pod rises, add Pods… The autoscaling/v2 behavior field controls this separately for scaleUp and scaleDown. If you omit it, these defaults apply:

    behavior:
  scaleDown:
    stabilizationWindowSeconds: 300      # or --horizontal-pod-autoscaler-downscale-stabilization
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
    - type: Pods
      value: 4
      periodSeconds: 15
    selectPolicy: Max
    • Stabilization window. When metrics suggest scaling down, the controller looks at all recommendations within the window and uses the highest. With the default 300 s, the HPA scales down only after five minutes of consistently lower recommendations — approximating a rolling maximum. Scale-up has no window by default: it reacts at the next sync.
    • Policies cap the change per periodSeconds (max 1800). Default scale-up: at most +100 % or +4 Pods per 15 s, whichever allows more (selectPolicy: Max). So 2 replicas can become 6 in one step (2 + 4), and 6 can become 12. Default scale-down: up to 100 % per 15 s, i.e. straight down to minReplicas once the window allows it.
    • selectPolicy: Min picks the most restrictive policy; Disabled turns off scaling in that direction entirely.

    Tuning for a load-test lab

    GoalSettingTrade-off
    See scale-down within a short experimentscaleDown.stabilizationWindowSeconds: 60More flapping risk with bursty load
    Avoid over-reacting to a spikescaleUp.stabilizationWindowSeconds: 30Slower response; more requests during under-provisioning
    Remove Pods gentlyscaleDown.policies: [{type: Pods, value: 1, periodSeconds: 60}]Pays for extra Pods longer
    Freeze replica count during a failure experimentscaleDown.selectPolicy: Disabled (or delete the HPA and set replicas)Remember to restore it

    Change one setting at a time and record it in the experiment report; otherwise you cannot attribute a different result to the change.

    5. HPA simulator

    The simulator below runs a simplified HPA controller every 15 s against a step load on /work. It models: CPU demand = requests/s × CPU cost per request; each Pod can use at most the “per-Pod CPU ceiling” (≈ 1 core for one Uvicorn worker); utilization = usage ÷ request; metrics lag one sync; new Pods count as not-ready for the readiness delay (set aside, and assumed 0 % on scale-up); tolerance; default scale-up policies (+100 % or +4 per 15 s); scale-down stabilization; min/max.     Self-check (use the simulator): with request 100m and spike 20 req/s, the HPA hits max 6 and stays there. Is the service overloaded?
    Not necessarily. 20 req/s × 50 ms = 1 core of demand; 6 ready Pods with a ~1-core ceiling each can supply up to 6 cores, so there is no CPU overload — yet utilization stays at ~167 % of the 100m request, far above 60 %, so the HPA reports ScalingLimited. The HPA is “unhappy” because the request is unrealistically small, not because users suffer. Latency and error SLIs, not HPA utilization, tell you whether users suffer.

    6. The HPA manifest for reliability-api

    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: reliability-api
  namespace: reliability-lab
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: reliability-api
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
  behavior:                         # optional; shown with a shorter scale-down window for labs
    scaleDown:
      stabilizationWindowSeconds: 120

    The imperative equivalent (current kubectl syntax from the docs walkthrough) is kubectl -n reliability-lab autoscale deployment reliability-api --cpu=60% --min=2 --max=6. Prefer the YAML: it is reviewable and lives in Git or the Helm chart.

In the Helm chart, render replicas only when autoscaling is disabled.

{{- if not .Values.autoscaling.enabled }}

    7. Custom and external metrics: prometheus-adapter and KEDA

    CPU is a proxy. For /work it is a good one (the endpoint is CPU-bound). For an I/O-bound API or a queue worker, CPU stays low while users wait — you want to scale on requests per second, in-flight requests or queue depth. autoscaling/v2 supports four metric source types:

    TypeMeaningTarget typesAPI
    ResourceCPU/memory of the PodsUtilization, AverageValuemetrics.k8s.io
    ContainerResourceCPU/memory of one named container (ignore sidecars)Utilization, AverageValuemetrics.k8s.io
    PodsA custom metric describing each Pod, averagedAverageValue onlycustom.metrics.k8s.io
    ObjectA metric describing another object (e.g. an Ingress)Value, AverageValuecustom.metrics.k8s.io
    ExternalA metric not tied to any Kubernetes object (e.g. a hosted queue)Value, AverageValueexternal.metrics.k8s.io

    Kubernetes does not ship anything that serves the custom/external APIs. You install an adapter:

    • prometheus-adapter implements the custom, resource and external metrics APIs on top of Prometheus. Rules map PromQL to API metrics: seriesQuery (which series to discover), resources (map labels like namespace/pod to Kubernetes objects), name (matches/as to rename, e.g. http_requests_total → http_requests_per_second) and metricsQuery (the PromQL template with <<.LabelMatchers>> and <<.GroupBy>>).
    • KEDA (“scale applications based on real-world events”) works with the HPA rather than replacing it: its operator creates and manages an HPA for each ScaledObject, its metrics API server serves external metrics, and it handles scaling between zero and one replica itself. It has a Prometheus scaler:
    apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: reliability-api
  namespace: reliability-lab
spec:
  scaleTargetRef:
    name: reliability-api                 # the Deployment
  minReplicaCount: 2
  maxReplicaCount: 6
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://monitoring-kube-prometheus-prometheus.monitoring.svc:9090
        query: sum(rate(http_requests_total{namespace="reliability-lab", path="/work"}[1m]))
        threshold: "10"                   # scaling threshold; see the KEDA Prometheus scaler docs

    Do not run this and the CPU HPA on the same Deployment — KEDA creates its own HPA, and two HPAs fighting over one Deployment produce undefined behaviour. The study guide’s advice stands: start with CPU HPA, then add custom metrics only when you can test them.

    Scale to zeroThe HPA can scale to minReplicas: 0 only for object/external metrics (resource metrics need running Pods to measure) and only when the HPAScaleToZero feature gate is enabled on both API server and controller manager. KEDA implements 0↔1 itself. A load-tested API usually should not scale to zero: the first request pays the full start-up and READY_DELAY_SECONDS.

    8. Vertical Pod Autoscaler

    The VPA adjusts requests (and, proportionally, limits) to match observed usage — “rightsizing”. It is a CRD (autoscaling.k8s.io/v1) installed separately, with three components: the recommender (analyses current and historical CPU/memory and OOM events, writes target, lower-bound and upper-bound recommendations to .status.recommendation), the updater (evicts Pods or resizes them in place when they drift from the recommendation, respecting PodDisruptionBudgets) and the admission controller (a mutating webhook that sets requests on new Pods). It needs a metrics source such as metrics-server.

    updateModeBehaviourUse in this course
    OffRecommendations only, written to status; nothing changesYes — measure what requests should be
    InitialApplies recommendations only when Pods are createdMaybe
    RecreateEvicts Pods whose requests differ significantly; replacements get new requestsNo (disrupts experiments)
    InPlaceOrRecreateResize in place when possible, else evictNo
    InPlaceAlpha (VPA 1.7.0+, Kubernetes 1.33+ with feature gates); never evicts, retries laterNo
    AutoDeprecated since VPA 1.4.0; alias for RecreateNo
    apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler

  name: reliability-api
  namespace: reliability-lab
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: reliability-api
  updatePolicy:
    updateMode: "Off"                 # recommend only — safe alongside the CPU HPA

    containerPolicies:

    HPA + VPA conflictThe VPA project’s known-limitations page: the VPA should not be used with the HPA on the same resource metric (CPU or memory). Both would react to the same signal in opposite ways — VPA raises the request, which lowers HPA utilization, which removes Pods, which raises per-Pod usage… Combine them only on different signals (e.g. VPA for memory, HPA on CPU or on a custom metric), or use VPA in Off mode as a sizing advisor.

    9. Node autoscaling and how the layers interact

    Node autoscalers provision nodes when Pods cannot be scheduled, and consolidate (remove) under-utilised nodes. Both decisions use Pod resource requests, not real usage. Kubernetes SIG Autoscaling sponsors two: Cluster Autoscaler (resizes pre-configured node groups) and Karpenter (auto-provisions individual nodes from NodePool constraints and manages node lifecycle). Cloud platforms such as GKE integrate their own (Module 11).

    Consequences for design: keep headroom (target below 100 %), keep images small and start-up fast, set requests from measurements (VPA Off mode helps), and do not expect autoscaling to absorb a spike faster than the sum of the delays in Figure 5. In kind, the “add node” stage does not exist; new Pods either fit on the existing nodes or stay Pending.

    Self-check: the Cluster Autoscaler never adds a node although your Pods are at 300 % CPU utilization. Why?
    Node provisioning is triggered by unschedulable Pods, based on requests — not by high usage of running Pods. If all Pods fit, there is nothing to provision. High usage must first be turned into more Pods (HPA); only if those cannot be scheduled does the node autoscaler act.

    10. Load-testing theory

    A load test answers: does the service behave acceptably under a defined traffic pattern? The important word is defined. “I hit it with 100 users and the average was 80 ms” is not a result; it is an anecdote. A useful test states the workload model, the rate or concurrency, the duration and warm-up, the request mix, the success criteria (written before the run), the environment, and the measured percentiles with sample counts.

    Test type (k6 terminology)Purposereliability-api example
    SmokeValidate the script works and the system performs adequately under minimal load1 VU, 30 s, all checks pass
    Average-loadPerformance under expected normal conditionsBaseline 2 replicas, 5 req/s for 5 min
    StressPerformance at its limits when load exceeds the averageRamp to 20+ req/s; observe HPA and latency
    SoakReliability over extended periods2 h at baseline: memory growth? restarts?
    SpikeBehaviour and survival under sudden, short, massive increases2 → 30 req/s in 10 s: how many errors before HPA catches up?
    BreakpointGradually increase load to find capacity limitsRamp until p95 > 250 ms or errors > 1 %

    Closed vs open workload models

    In a closed model, the iteration duration dictates how many iterations run: each VU waits for its response before sending again. Real public traffic is closer to an open model: new users arrive whether or not the service is slow. The k6 docs put the consequence plainly: when the target slows down, a closed-model test waits, iteration durations grow, and the arrival rate tapers off. The test “goes easy” on the system exactly when it is struggling.

    Coordinated omission

    With 20 intended requests in Figure 7, the closed generator records 10 samples of which 1 is slow (10 % → p95 is slow but p90 looks fine), while the open generator records 20 samples of which 10 are slow — the honest picture of what users arriving during the stall experienced. Use arrival-rate executors when your question is “what latency do users see at X requests/s”, and watch k6’s dropped_iterations metric: it counts iterations that could not start because no VU was free — evidence that the generator could not keep the promised rate.

    Little’s Law

    For any stable system, the average number of requests in the system L equals the arrival rate λ times the average time each spends in it W: L = λ × W. It needs no assumptions about distributions, and it is your sanity check for every test:

    • 20 closed-loop VUs with no think time against reliability-api with 2 Pods (≈ 2 cores → ≈ 40 req/s of 50 ms work): L = 20, λ ≈ 40/s, so W ≈ 20 / 40 = 0.5 s average latency — mostly queueing, although each request only needs 50 ms of CPU.
    • Scale to 6 Pods (≈ 120 req/s capacity): the same 20 VUs push λ up toward 20 / (0.05 s + overhead) ≈ 400/s → now limited by Pods again… or by the load generator, or by the node’s total CPU. Little’s Law tells you which number must have changed.

    Service: /work?ms=S, each ready Pod serves about 1 request at a time (one CPU-bound worker). Capacity μ ≈ replicas × 1000 / S req/s.

    Warm-up, steady state and duration

    The first seconds of a test are not representative: connections are being established, the HPA has not reacted, Python code paths are cold, and Pods with READY_DELAY_SECONDS are not yet serving. Define a warm-up stage, exclude it from the SLO evaluation (tag it, or evaluate only the steady-state window in PromQL), and make the steady-state stage long enough to include several HPA syncs and scrape intervals (minutes, not seconds).

    Percentiles and sample size

    A percentile is only as trustworthy as the number of samples behind it. With N requests, only N × (1 − p) samples lie beyond the p-th percentile:

    Requests in windowSamples above p95Samples above p99Verdict
    10051p99 is literally one request — do not report it
    1,0005010p95 usable; p99 noisy
    10,000500100p99 reasonable
    100,0005,0001,000p99.9 starts to mean something

    Rules: report the sample count next to every percentile; never average percentiles across runs or Pods (aggregate raw data or histogram buckets); repeat each configuration at least three times and report the spread; and remember that Prometheus percentiles are bucket-interpolated estimates (Module 07), while k6 computes percentiles from its own raw samples — they measure different things (server handler time vs client-observed time) and will differ.

    The load generator is part of the experiment

    If the generator runs out of CPU, memory or network, it sends less than you asked and its own timing measurements inflate. The k6 docs on large tests advise keeping load-generator CPU utilisation within 80 % and memory under 90 %, monitoring network throughput, and using discardResponseBodies: true to save memory. In a kind cluster the generator Pod shares the same machine as reliability-api: every CPU cycle k6 uses is unavailable to the Pods under test. Record where the generator ran, give it its own resource requests, and check its CPU on the dashboard. Also avoid kubectl port-forward as a load path: it is a debugging tunnel through the API server and kubelet, forwards to a single Pod chosen at start, and becomes the bottleneck itself.

    Self-check: your closed-model test reports p95 = 120 ms at 50 VUs and also at 100 VUs, but throughput did not change. What happened?
    The system (or the generator) is saturated: throughput is capped, so doubling VUs only doubles the number of requests waiting (Little’s Law: W = L/λ should have doubled). If reported latency did not double, the latency is probably being measured somewhere that excludes the queueing — or the generator itself is saturated and its VUs are not actually sending. Check generator CPU, http_reqs rate, and server-side request rate.

    11. k6: a load test for /work

    k6 runs JavaScript test scripts. Init code runs once per VU; the default function runs repeatedly for the configured duration. Checks validate responses but do not fail the test by themselves; thresholds are pass/fail criteria — when any threshold fails, k6 exits with a non-zero code (99, ThresholdsHaveFailed), which is what makes it CI-friendly.

    12. Locust as an alternative

    Locust describes user behaviour in Python, which may feel more natural to you. Each simulated user runs tasks; wait_time controls pacing: between(min, max), constant(t), constant_throughput(rate) (task runs at most X times per second per user), constant_pacing(interval), and poisson(rate). constant_throughput approximates a fixed arrival rate per user, but it is still a user-based model: if responses are slower than the pacing interval, the user cannot catch up.

    from locust import HttpUser, task, constant_throughput

class WorkUser(HttpUser):
    wait_time = constant_throughput(1)       # ≤ 1 request/s per user

    @task
    def work(self):
        with self.client.get("/work?ms=50", catch_response=True) as r:
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")
    locust -f experiments/load/locustfile.py --headless \
  -u 20 -r 2 -t 10m -H http://reliability-api.reliability-lab.svc.cluster.local \
  --csv experiments/reports/locust-run1 --html experiments/reports/locust-run1.html

    -u = users, -r = spawn rate (users/s), -t = run time, -H = host; --csv writes request statistics and failures, --html a report. Without --headless, the web UI listens on port 8089.     14. Failure testing

    Failure testing asks whether the system behaves as expected when a defined fault occurs. It borrows the method of chaos engineering: define a measurable steady state; hypothesise that it continues during the fault; introduce a realistic variable (a crashed server, a bad release); try to disprove the hypothesis by looking for a difference. And always minimise the blast radius.

    Safety rules (non-negotiable)
    1. Only in your own lab cluster/namespace (reliability-lab), never a shared or production cluster without explicit written authorisation and isolation.
    2. Write the hypothesis, success thresholds and abort criteria before injecting.
    3. Smallest blast radius first: one Pod, one fault, short duration.
    4. Know the rollback command and test it before the experiment.
    5. Silence expected alerts (Module 07) and tell anyone who shares the environment.
    6. Freeze other variables: no HPA changes, no deploys during the experiment.

    Experiment B — ship a broken image

    With the default RollingUpdate strategy (maxUnavailable 25 % rounded down, maxSurge 25 % rounded up), a 2-replica Deployment may create 1 extra Pod and may not remove any old Pod until a new one is available. A new Pod that can never pull its image therefore never replaces anything: users should see no extra errors, and the rollout should report failure.

    Experiment C — break readiness

    Set READY_DELAY_SECONDS=600 on a rollout. New Pods start and pass liveness (/health) but return 503 on /ready for 10 minutes, so they never join the Service endpoints within the test. The rollout stalls; old Pods keep serving. This proves your readiness probe protects users — and shows what would happen if it pointed at /health instead (traffic would reach Pods that are not ready).

    Glossary

    HPA
    Controller that sets a workload’s replica count from metrics.
    VPA
    Add-on that recommends or applies container resource requests.
    Node autoscaler
    Provisions/consolidates nodes based on Pod requests (Cluster Autoscaler, Karpenter).
    Metrics API
    metrics.k8s.io, usually served by metrics-server; latest CPU/memory only.
    Utilization
    Usage as a percentage of the resource request.
    Tolerance
    Band around 1.0 (default 0.1) inside which the HPA does not scale.
    Stabilization window
    Period whose highest (down) recommendation is used, to prevent flapping.
    Scaling policy
    Limit on replicas added/removed per period.
    Closed model
    Fixed number of users who wait for responses before sending again.
    Open model
    Requests arrive at a set rate independent of responses.
    Coordinated omission
    Measurement bias where a slowed client fails to send — and record — the requests that would have been slow.
    Little’s Law
    L = λW for a stable system.
    Steady state
    Measurable normal behaviour used as the experiment baseline.
    Blast radius
    The scope of what an experiment can affect.
    Impact window
    Time during which requests fail or violate latency targets.
    Recovery time
    Time from fault until all agreed SLIs are back within target.

    Self-check

    1. 4 Pods, average CPU 45 % of request, target 60 %, min 2. What does the HPA do?
    Ratio = 0.75, outside tolerance. Raw desired = ceil(4 × 0.75) = 3. Because this is a scale-down, the stabilization window applies: the HPA uses the highest recommendation of the last 300 s (default). If load was higher recently, it stays at 4 until those recommendations age out.
    2. Why can the same load produce 6 replicas with a 100m request and 4 replicas with 500m?
    Utilization is usage ÷ request. At 1 core of total demand over 2 Pods: 500m ÷ 100m = 500 % → ceil(2 × 500/60) = 17 → clamped to 6; 500m ÷ 500m = 100 % → ceil(2 × 100/60) = 4.
    3. Prometheus is installed and scraping http_requests_total. Can the HPA scale on it now?
    No. The HPA reads metrics only through the metrics APIs. Request-rate scaling needs prometheus-adapter (custom/external metrics API) or KEDA (which creates the HPA and serves external metrics).
    4. Why must you not run VPA in Recreate mode and a CPU HPA on the same Deployment?
    Both react to CPU: VPA raises requests, which lowers HPA utilization, which removes Pods, which raises per-Pod usage, which VPA then raises again… The VPA project lists this as a known limitation. Use VPA in Off mode, or let them act on different signals.
    5. Explain coordinated omission in one sentence and name the k6 feature that avoids it.
    A closed-loop client waits on a slow server and therefore never sends (or measures) the requests that would have experienced the slowness, making tail latency look better than users saw; arrival-rate executors (constant-arrival-rate, ramping-arrival-rate) keep sending on schedule.
    6. An open-model test at 40 req/s shows mean latency 250 ms. How many requests are in the system on average?
    Little’s Law: L = 40 × 0.25 = 10. With 2 single-worker Pods, about 8 of those are queued — latency is mostly waiting, not work.
    7. A test ran 200 requests and reports p99 = 900 ms. What do you write in the report?
    That p99 is determined by about 2 samples (200 × 0.01) and is not statistically meaningful; report p50/p90 with n = 200, or run longer to collect enough samples.
    8. In Lab 3 you saw 3 FAIL lines, all within 1 s after the fault. What is the most likely mechanism and a mitigation?
    The race between Pod A receiving SIGTERM and every node’s kube-proxy removing A from the Service rules: some connections still went to a Pod that had stopped accepting them. Mitigate with a short preStop sleep so the endpoint is removed before shutdown begins, plus graceful shutdown in the app, and client retries for idempotent requests.
    9. Why did the broken-image rollout cause zero user-visible errors, and which setting would have made it harmful?
    With 2 replicas, maxUnavailable 25 % rounds down to 0, so no old Pod is removed until a new Pod is available; the new Pod never becomes available, so old Pods keep serving. A large maxUnavailable (e.g. 100 %) would allow old Pods to be removed first, leaving no ready endpoints.
    10. You run HPA Lab 2 on kind and Pods stay Pending at 5 replicas. Will a node autoscaler help?
    kind has no node autoscaler — nodes are Docker containers on your machine. Reduce requests (if measurements justify it), add kind worker nodes in the cluster config, or accept the ceiling and document it. On GKE (Module 11), node autoscaling would provision capacity for the Pending Pods.
    11. Why freeze the HPA during a Pod-deletion experiment?
    To keep one independent variable. If the HPA scales up during the fault, recovery depends on HPA timing as well as on the ReplicaSet replacement, and you cannot attribute the result. Test HPA-assisted recovery as a separate experiment.
