    1. Health probes: liveness, readiness, startup

    Definition. A probe is a diagnostic the kubelet performs periodically on a container. Each probe returns Success, Failure or Unknown. There are three kinds, and the difference between them is not the check — it is what Kubernetes does with the result.

    ProbeQuestion it answersOn failure (after failureThreshold)reliability-api endpoint
    startupHas the app finished starting?Kill the container; restart per restartPolicy. While it has not succeeded, liveness and readiness are not run./health
    livenessIs the process stuck in a way only a restart fixes?Kill and restart the container (same Pod, restart count +1)./health
    readinessShould this Pod receive traffic right now?Mark container not ready → Pod Ready=False → EndpointSlice controller removes the Pod IP from all matching Services. No restart. Probing continues for the Pod's whole life./ready

    Problem they solve. "The process exists" is not the same as "the service works". Without probes Kubernetes only knows whether PID 1 is running: a deadlocked app would stay in rotation forever, and a warming-up app would receive traffic before it can answer. Probes let the platform react to application-level health.

    If a container does not define a probe, the kubelet treats that probe's result as Success. One subtlety from the docs: for readiness, the result is considered Failure before the initial delay — a new Pod is not Ready until a readiness probe has actually passed.

    Check mechanisms

    Each probe must define exactly one mechanism:

    MechanismSuccess whenNotes
    httpGetHTTP status ≥ 200 and < 400Sent by the kubelet to the Pod IP on port (number or named port) and path. Optional httpHeaders and scheme: HTTPS. The kubelet follows redirects only to the same host; a redirect to another host is treated as success with a ProbeWarning event. The natural choice for reliability-api.
    tcpSocketTCP connection opensOnly proves something is listening. Good for non-HTTP servers; weak for HTTP apps.
    execCommand exits with 0Runs inside the container (the binary must exist in the image). The docs warn exec forks processes on every run, adding node CPU overhead at high Pod density.
    grpcHealth service returns SERVINGFor gRPC apps implementing the standard gRPC health-checking protocol. Generally available.

    Timing fields and their defaults

    FieldDefaultMinMeaning
    initialDelaySeconds00Seconds after the container starts before the probe begins. With a startup probe, liveness/readiness delays start counting only after startup succeeds.
    periodSeconds101How often to probe. (While a container is not Ready, readiness may be run more often than this to make the Pod ready faster.)
    timeoutSeconds11How long to wait for a response; a timeout is a failure.
    successThreshold11Consecutive successes needed to count as passing after a failure. Must be 1 for liveness and startup.
    failureThreshold31Consecutive failures before acting (restart for liveness/startup; not-ready for readiness).
    terminationGracePeriodSeconds (probe-level)inherits Pod's (30)1Liveness/startup only: grace period used when the probe triggers a kill, if you want it shorter than the Pod-level value.

    The arithmetic you should do for every probe

    • Time to detect a failure ≈ failureThreshold × periodSeconds (plus up to timeoutSeconds for the last attempt). Defaults: 3 × 10 s ≈ 30 s.
    • Maximum start-up allowance with a startup probe = failureThreshold × periodSeconds. The docs' example uses 30 × 10 s = up to 300 s to start, without making liveness slow afterwards.
    • Time to become Ready ≥ app warm-up, rounded up to the next readiness probe tick (+ successThreshold − 1 extra periods).
    • Time to return to Ready after a blip = successThreshold × periodSeconds.

    Correct probe configuration for reliability-api

    Our app has exactly the endpoints we need: /health returns 200 as long as the event loop answers; /ready returns 503 until READY_DELAY_SECONDS have passed since start. In a real service, readiness would also reflect "my model is loaded / my cache is warm / I am not shedding load".

              env:
            - name: READY_DELAY_SECONDS
              value: "20"              # simulate a 20 s warm-up for this module
          startupProbe:                # protects slow starts; disables the others until it passes
            httpGet: { path: /health, port: http }
            periodSeconds: 5
            failureThreshold: 12       # up to 60 s to bind the port before we give up
          readinessProbe:              # traffic gate: only route to Pods that are warmed up
            httpGet: { path: /ready, port: http }
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3        # ~15 s of failures before removal from endpoints
            successThreshold: 1
          livenessProbe:               # deadlock detector: restart only if truly stuck
            httpGet: { path: /health, port: http }
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3        # ~30 s of consecutive failures before a restart

    Why these choices:

    • Liveness uses /health, not /ready. A Pod that is warming up or temporarily overloaded is not ready, but killing it makes things worse: it restarts, warms up again, and the remaining replicas take even more load. Readiness handles "not now"; liveness handles "never again without a restart".
    • Startup probe instead of a big initialDelaySeconds. A fixed delay is paid on every start even when the app is fast, and is still wrong when the app is slower than expected. The startup probe ends as soon as the app answers and allows up to 60 s if it is slow.
    • timeoutSeconds: 2. The default 1 s is tight. /work is a CPU-bound busy loop; when a Pod is saturated by load, /health responses can queue behind it. A too-short timeout turns load into liveness failures and restarts — a cascading failure. Tune it with data from load tests (Module 08).
    • Liveness never checks dependencies. If a database were down and liveness checked it, every replica would restart simultaneously — and the database would still be down.

    Failure cases & how to diagnose

    SymptomTypical causeEvidence
    READY 0/1 forever, no restartsReadiness path/port wrong, or app never becomes readykubectl describe pod → Events: Readiness probe failed: HTTP probe failed with statuscode: 503 (or 404, or connection refused)
    RESTARTS climbing every ~30 s, then CrashLoopBackOffLiveness failing (wrong path, too-short timeout, slow start without startup probe)Events: Liveness probe failed: … followed by Container reliability-api failed liveness probe, will be restarted; Last State: Terminated with Exit Code: 137 or 143

    Event message wording varies slightly between Kubernetes versions; the reason fields (Unhealthy, Killing, BackOff) are the stable things to grep for: kubectl get events --field-selector reason=Unhealthy.

    Self-check: Readiness fails on one of two replicas for 2 minutes. What do clients see, and what does Kubernetes do to the container?
    Clients going through the Service are routed only to the other replica (more load on it, but no errors from the unready one). Kubernetes does nothing to the container — no restart — and keeps probing; when readiness passes again it is added back to the endpoints.
    Self-check: With periodSeconds: 10 and failureThreshold: 3, how long can a deadlocked container keep running before restart? How would you halve it, and what is the risk?
    About 30 s (three failed probes 10 s apart, plus up to the timeout). Halve with periodSeconds: 5 (or failureThreshold lower). Risk: more false positives — a brief GC pause or load spike could trigger an unnecessary restart. Faster detection always trades against false restarts.

    2. Resource requests and limits

    Definitions. For each container you can set, per resource (CPU, memory, and others like ephemeral-storage):

    • request — the amount the scheduler reserves for the container when choosing a node, and (for CPU) its relative weight under contention. A container may use more than its request if the node has spare capacity.
    • limit — a ceiling enforced by the kernel through cgroups. For CPU it is a hard cap enforced by throttling; for memory it is enforced reactively by the OOM killer.

    Problem it solves. Without requests the scheduler cannot know whether a node has room, so it overpacks nodes and Pods starve each other. Without limits a single leaking Pod can consume a node's memory and trigger evictions of innocent neighbours. Requests make placement predictable; limits contain the blast radius.

    Units

    ResourceUnitExamplesGotchas
    CPUcpu units: 1 = one physical core or one virtual core (vCPU)100m = 0.1 = one hundred millicpu; 1500m = 1.5Precision finer than 1m is not allowed. CPU is absolute: 500m is about the same compute on a 2-core or a 48-core node.
    Memorybytes, with suffixes128Mi = 128 × 220 = 134,217,728 bytes; 128M = 128,000,000 bytesCase matters: 400m of memory means 0.4 bytes (m = milli). You meant 400Mi. Prefer binary suffixes Ki, Mi, Gi.

    If you set a limit but no request for a resource (and no admission policy sets a default), Kubernetes copies the limit into the request.

    What the scheduler sees: requests, not usage

    Each node publishes status.allocatable (capacity minus what is reserved for the OS and Kubernetes daemons). The scheduler's resource filter checks that the sum of requests of Pods on the node plus the new Pod's requests fits in allocatable. See it with kubectl describe node reliability-lab-control-plane → Allocatable and Allocated resources.

    CPU limits: CFS throttling

    On Linux the container runtime configures cgroups from your values. A CPU limit becomes a CFS bandwidth quota: in each scheduling period (the kernel default period is 100 ms) the container's cgroup may consume at most quota of CPU time; once it is used up, its threads are throttled — not allowed to run — until the next period. On cgroup v2 this is the cpu.max file ("$MAX $PERIOD"), and the throttling counters nr_periods, nr_throttled, throttled_usec are in cpu.stat. A CPU request becomes a relative weight: under contention, containers with larger requests get proportionally more CPU time.

    CFS throttling calculator
    Idealised single-threaded model: how long does a CPU-bound request take under a CPU limit? (Multi-threaded processes share the same quota and can exhaust it faster.)

    Memory limits: the OOM killer

    A memory limit becomes the cgroup's memory limit. If the container tries to allocate beyond it, the kernel's out-of-memory handling typically kills a process in the container. If that process is PID 1, the container terminates with reason OOMKilled and exit code 137 (128 + 9, SIGKILL), and Kubernetes restarts it per restartPolicy. The docs stress that enforcement is reactive: a container can briefly exceed its limit and is killed only when the kernel detects memory pressure. Memory, unlike CPU, is not compressible: there is no way to "slow down" memory use, so the only remedy is to kill.

    Exceeding the requestAllowed if the node has idle CPUAllowed, but makes the Pod an eviction candidate under node memory pressure

    Applied to reliability-api: our choices and why

              resources:
            requests:
              cpu: 100m        # scheduler reserves 0.1 core; also the base for HPA "CPU 60%" in Module 08
              memory: 128Mi    # measured baseline of a FastAPI + Uvicorn worker, with headroom
            limits:
              memory: 256Mi    # contain leaks; 2× request leaves room for bursts
              # no cpu limit: see trade-off below
    • Memory limit, yes. A leak in one Pod should OOM-kill that Pod, not push the node into memory pressure and evict other workloads.
    • CPU limit — a real trade-off. Without a CPU limit, /work can use idle CPU on the node: lower latency, better use of hardware. The cost: one busy Pod can take spare CPU from neighbours (they still get at least their requested share through weighting), and behaviour depends on how busy the node is, making load tests less reproducible. With a CPU limit you get predictable, isolated performance but pay throttling latency even when the node is idle. For this lab we leave it off and measure; Lab 2 shows what a 200m limit does.
    • Requests drive HPA. CPU utilisation for the HPA is computed relative to the CPU request. Change the request and you change what "60%" means.
    • Measure, then set. These numbers are starting points. Use kubectl top pod (needs metrics-server, Module 08) and Prometheus under load to adjust.
    Failure cases & diagnosis
    • Pending with Insufficient cpu/memory — requests too large for any node. kubectl describe pod Events; kubectl describe node → Allocated resources.
    • RESTARTS rising, OOMKilled — memory limit too low or a leak. kubectl describe pod → Last State; check memory metrics before the kill.
    • p99 latency high, CPU usage looks "low" — throttling. Averages hide it: a container can be throttled every period while average CPU is under the limit. Check cpu.stat (nr_throttled) or the cAdvisor metric for throttled periods in Prometheus (Module 07).
    • Typo units — memory: 256m (millibytes) is accepted by the API but makes the container unstartable; always Mi/Gi.

    3. QoS classes and eviction

    Definition. Kubernetes assigns every Pod a Quality of Service class from its containers' requests and limits. The class is stored in status.qosClass and decides the order in which Pods are evicted when a node runs out of resources.

    ClassRule (all containers in the Pod)Under node pressure
    GuaranteedEvery container has CPU and memory requests and limits, and request = limit for each.Evicted last. Kubelet sets oom_score_adj = -997.
    BurstableNot Guaranteed, but at least one container has a CPU or memory request or limit.Evicted after BestEffort. oom_score_adj between 2 and 999, lower for larger memory requests (formula below).
    BestEffortNo container has any CPU or memory request or limit.Evicted first. oom_score_adj = 1000.

    For Burstable Pods the kubelet sets oom_score_adj = min(max(2, 1000 − (1000 × memoryRequestBytes) / machineMemoryCapacityBytes), 999). The kernel adds this to its own badness score when choosing what to kill under node-wide memory exhaustion. The intuition: the more memory you request (relative to the machine), the less likely the kernel OOM killer is to pick you. (A container exceeding its own limit is killed regardless of class.) Memorise the ordering, not the constants.

    Node-pressure eviction (the kubelet's last line of defence)

    Separately from the kernel OOM killer, the kubelet watches eviction signals such as memory.available, nodefs.available, imagefs.available and pid.available. Default hard thresholds on Linux include memory.available < 100Mi, nodefs.available < 10%, imagefs.available < 15%, nodefs.inodesFree < 5% and imagefs.inodesFree < 5% (these defaults apply only if you change none of them). When a threshold is crossed the kubelet sets a node condition (e.g. MemoryPressure=True), the node gets a matching taint so new Pods avoid it, it tries to reclaim node-level resources (unused images, dead containers), and then evicts Pods ranked by:

    1. whether the Pod's usage exceeds its requests,
    2. Pod priority,
    3. usage relative to requests.

    Consequences you must know: node-pressure eviction does not respect PodDisruptionBudgets, and for hard thresholds it does not honour terminationGracePeriodSeconds (0 s grace). Evicted Pods show Status: Failed, Reason: Evicted; their controller creates replacements elsewhere.

    Applied to reliability-api

    Our Pods are Burstable (requests set; memory limit ≠ request; no CPU limit). To make them Guaranteed we would need CPU request = CPU limit and memory request = memory limit — i.e. adopt a CPU limit and its throttling. For a stateless API with 2+ replicas, Burstable is a reasonable trade: if one Pod is evicted, the other serves while the controller replaces it. The bigger protection is keeping usage near requests so we are not first in line.

    4. Scheduling basics

    Definition. kube-scheduler watches for Pods with no node assigned and, for each, picks the best node in two steps: filtering (which nodes are feasible?) and scoring (which feasible node is best?). It then binds the Pod by telling the API server. If no node is feasible the Pod stays Pending (unschedulable) until something changes, and a FailedScheduling Event explains why.

    Placement tools, from simplest to most expressive

    ToolLives onHard / softUse it for
    nodeSelectorPodHard"Only nodes with all these labels" (e.g. disktype: ssd).
    Node affinityPodrequired… hard, preferred… soft (weight 1–100)Expressive node label rules with operators In, NotIn, Exists, DoesNotExist, Gt, Lt.
    Inter-pod affinity / anti-affinityPodHard or soft"Near / away from Pods with these labels" within a topologyKey domain (node, zone).
    Taints & tolerationsTaint on Node, toleration on PodNoSchedule, PreferNoSchedule, NoExecuteNodes repel Pods unless they tolerate (dedicated/GPU nodes, control plane, unhealthy nodes).
    topologySpreadConstraintsPodDoNotSchedule hard / ScheduleAnyway softEven spread of replicas across zones/nodes with a maximum skew.
    nodeNamePodBypasses the schedulerAlmost never; debugging only.

    The suffix IgnoredDuringExecution in affinity rules means: if node labels change after the Pod is running, the Pod is not evicted. Only NoExecute taints affect already-running Pods.

    Spreading reliability-api replicas

    Two replicas on the same node die together with that node. A soft anti-affinity asks the scheduler to put them on different nodes when possible but still schedule them on a single-node kind cluster:

          affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                topologyKey: kubernetes.io/hostname       # domain = individual node
                labelSelector:
                  matchLabels:
                    app.kubernetes.io/name: reliability-api

    On a multi-zone cloud cluster (Module 11) you would rather express "even across zones" with topology spread:

          topologySpreadConstraints:
        - maxSkew: 1                                   # zone counts may differ by at most 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway            # soft; DoNotSchedule would make it hard
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: reliability-api
    Trade-off: hard anti-affinity

    requiredDuringScheduling… anti-affinity on kubernetes.io/hostname guarantees one replica per node — and makes replica N+1 Pending when you have N nodes. It also blocks rolling updates with maxSurge on small clusters, because the surge Pod has nowhere legal to go. Prefer soft rules unless co-location is truly unacceptable.

    Taints and tolerations

    A taint on a node (key=value:Effect) repels Pods; a toleration on a Pod lets it ignore a matching taint. A toleration matches when key and effect match and either operator: Exists or operator: Equal with the same value. A toleration permits scheduling on the node; it does not attract the Pod there — combine with node affinity for dedicated nodes.

    EffectNew Pods without tolerationRunning Pods without toleration
    NoScheduleNot scheduledKeep running
    PreferNoScheduleScheduler tries to avoid the nodeKeep running
    NoExecuteNot scheduledEvicted (immediately, or after tolerationSeconds if the toleration sets it)

kubectl taint nodes reliability-lab-control-plane dedicated=lab:NoSchedule-    # remove (trailing -)

    Kubernetes uses taints itself: control-plane nodes typically carry node-role.kubernetes.io/control-plane:NoSchedule, and the node lifecycle controller adds taints such as node.kubernetes.io/not-ready and node.kubernetes.io/unreachable (effect NoExecute) to failing nodes — that is how Pods are eventually evicted from a dead node. Node-pressure conditions also add taints (e.g. node.kubernetes.io/memory-pressure).

    Diagnosing Pending

    kubectl describe pod <p> → Events → FailedScheduling. The message summarises, per reason, how many nodes were rejected — e.g. "0/3 nodes are available: 1 Insufficient memory, 2 node(s) didn't match Pod's node affinity/selector" (wording varies by version). Then: kubectl get nodes --show-labels, kubectl describe node (Taints, Allocatable, Allocated resources). Remember a Pod can be Pending for non-scheduling reasons too (e.g. waiting for a PersistentVolumeClaim).

    5. Rolling updates, rollout and rollback

    Definition. When a Deployment's Pod template changes, the Deployment controller creates a new ReplicaSet and gradually scales it up while scaling the old one down. Two knobs bound how aggressive this is:

    • maxSurge — how many Pods may exist above replicas during the update. Number or percentage; percentages round up. Default 25%.
    • maxUnavailable — how many Pods may be unavailable below replicas. Number or percentage; percentages round down. Default 25%.
    • They cannot both be 0 (nothing could ever change).

    So with the defaults and 10 replicas: maxSurge = ceil(2.5) = 3, maxUnavailable = floor(2.5) = 2 → at most 13 Pods total, at least 8 available. With reliability-api's 2 replicas: ceil(0.5) = 1 and floor(0.5) = 0 → at most 3 Pods, at least 2 available. That is exactly what we wrote explicitly in the manifest.

    Problem it solves. Zero-downtime deploys. Because "available" is defined by readiness (plus minReadySeconds), the rollout naturally waits for new Pods to warm up before removing old ones — if your readiness probe is honest.

    Rollback is not "git revert"

    kubectl rollout undo changes the live Deployment's template back to an older ReplicaSet's template; that restored revision reappears in the history under a new, higher revision number. Your manifest in Git still says 0.2.0, so the next kubectl apply (or CI run) re-deploys the bad version. Use undo to stop the bleeding, then fix Git.

    Failure cases

    • Bad image tag → new Pod ImagePullBackOff; with maxUnavailable: 0 old Pods are untouched, so users see no impact, but the rollout is stuck until ProgressDeadlineExceeded. (Lab 3.)
    • New version fails readiness → same: stuck, safe. This is why honest readiness matters.
    • New version passes readiness but is broken → rollout completes and you are fully on a broken version. Readiness is not a test suite; add smoke tests in CI and metrics/alerts (Modules 07, 09).
    • Mixed versions → during any rolling update, v0.1.0 and v0.2.0 serve traffic at the same time. API and schema changes must be backward compatible.

    6. Pod lifecycle: phases, container states, conditions

    A Pod's status.phase is a deliberately coarse, high-level summary. Each container additionally has a detailed state, and the Pod has a list of conditions. When you debug, read all three.

    Container states

    Waiting — not running yet; reason says why: ContainerCreating, ErrImagePull, ImagePullBackOff, CrashLoopBackOff, CreateContainerConfigError.

    Running — executing (postStart hook, if any, has run).

    Terminated — finished; has exitCode, reason (Completed, Error, OOMKilled), signal, startedAt, finishedAt.

    Pod conditions

    PodScheduled → PodReadyToStartContainers (sandbox + network ready) → Initialized (init containers done) → ContainersReady → Ready (can serve; this is what Services use).

    Each has status, reason, message, lastTransitionTime.

    restartPolicy

    Always (default; required for Deployments), OnFailure, Never (Jobs use the latter two).

    Restarts use exponential back-off: 10 s, 20 s, 40 s, … capped at 300 s; reset after a container has run 10 minutes without problems.

    kubectl get pod <p> -o jsonpath='{.status.phase}{"\n"}'
kubectl get pod <p> -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'
kubectl get pod <p> -o jsonpath='{.status.containerStatuses[0].lastState}{"\n"}'

    7. Graceful termination

    Definition. When a Pod is deleted (scale-down, rolling update, drain, kubectl delete), Kubernetes gives its processes a chance to finish work before forcibly killing them. The time budget is terminationGracePeriodSeconds, default 30.

    Problem it solves. Every rolling update deletes Pods. If deleting a Pod dropped its in-flight requests, every deploy would cause errors. Graceful termination plus readiness-driven endpoint removal is what makes rollouts zero-downtime — but only if the app and the Pod spec cooperate.

    The sequence (two things happen in parallel)

    1. You (or a controller) delete the Pod. The API server records a deletion timestamp and grace period; kubectl get pods shows Terminating.
    2. On the node: the kubelet runs each container's preStop hook (if defined and the grace period is not 0). The hook must finish before TERM is sent. If it is still running when the grace period expires, the kubelet grants a one-off 2-second extension.
    3. The kubelet has the runtime send TERM to process 1 in each container (or the image's STOPSIGNAL, if set). Without sidecars, containers receive TERM in arbitrary order.
    4. In parallel in the control plane: the Pod is no longer a valid replica for its ReplicaSet (the replacement is created immediately), and its endpoints in EndpointSlices are marked terminating with ready: false, so load balancers and kube-proxy stop sending it new traffic — after the change propagates to every node.
    5. When the grace period expires, the runtime sends SIGKILL to anything still running; the kubelet sets the terminal phase and the Pod object is removed from the API.

    Why the preStop sleep?

    Step 2–3 (kubelet) and step 4 (endpoints) race. If the app exits immediately on SIGTERM while some node's kube-proxy still routes to this Pod's IP, clients get connection refused/reset. A short preStop sleep keeps the app serving normally for a few seconds while the endpoint removal propagates; only then does SIGTERM start the drain. The app itself must also handle SIGTERM properly — as Module 02 covered, that requires the server to be PID 1 (exec-form CMD) or a proper init. Uvicorn performs a graceful shutdown: it stops accepting new connections and waits for in-flight responses, bounded by --timeout-graceful-shutdown if you set it.

        spec:
      terminationGracePeriodSeconds: 30     # budget for preStop + app shutdown
      containers:
        - name: reliability-api
          lifecycle:
            preStop:
              sleep:
                seconds: 5                  # built-in sleep action, executed by the kubelet
          # Alternative on clusters/images where needed:
          #   preStop: { exec: { command: ["sleep", "5"] } }   # requires a sleep binary in the image
    • Budget check: 5 s preStop + Uvicorn drain (our longest request is a few hundred ms of /work) ≪ 30 s. If you had 60-second requests (e.g. LLM streaming, Module 12), you would raise terminationGracePeriodSeconds.
    • Hook failures kill the container and are reported as a FailedPreStopHook Event. Hook logs are not shown in Pod events.
    • kubectl delete pod --grace-period=0 --force removes the API object immediately without waiting for confirmation from the kubelet. Use only for stuck Pods you understand; it is not a "faster delete".
    Failure cases & diagnosis
    • 5xx/connection resets during every deploy → missing preStop delay or app exits instantly on SIGTERM. Reproduce under load during kubectl rollout restart (Module 08).
    • Pods take exactly 30 s to terminate → app ignores SIGTERM (shell-form CMD, PID 1 is sh), so it waits for SIGKILL. Exit code 137 in lastState confirms.
    • Pod stuck in Terminating for minutes → node unreachable, or finalizers on the object. kubectl get pod -o yaml → metadata.finalizers; kubectl describe node.

    8. PodDisruptionBudget

    Definition. A PodDisruptionBudget (PDB, policy/v1) limits how many Pods of a replicated application can be down at the same time due to voluntary disruptions.

    Voluntary (PDB can limit)Involuntary (PDB cannot prevent)
    Draining a node for upgrade/repair (kubectl drain); cluster autoscaler removing a node; an admin evicting Pods via the Eviction APIHardware/VM failure, kernel panic, node network partition, node-pressure eviction (out of resources)

    How it works. Tools that respect PDBs use the Eviction API instead of plain delete. The API server checks the budget: if allowed it returns 200 and the Pod is gracefully terminated (honouring terminationGracePeriodSeconds); if not, it returns 429 Too Many Requests and the caller (e.g. kubectl drain) retries later. Important limits:

    • Deleting Pods or Deployments directly, and Deployment rolling updates, are not governed by PDBs (rollouts use maxUnavailable).
    • Involuntary disruptions still count against the budget.
    • Set either minAvailable or maxUnavailable, not both. Percentages round up (e.g. minAvailable: "50%" of 7 → 4).
    apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: reliability-api
  namespace: reliability-lab
spec:
  minAvailable: 1                       # of 2 replicas → at most 1 voluntary disruption at a time
  selector:
    matchLabels:
      app.kubernetes.io/name: reliability-api
  unhealthyPodEvictionPolicy: AlwaysAllow   # do not let crash-looping Pods block a drain
    NAME              MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
reliability-api   1               N/A               1                     20s
    Trade-offs & traps
    • minAvailable = replicas (e.g. 2 of 2) means ALLOWED DISRUPTIONS = 0: node drains block forever. A common way to accidentally freeze cluster upgrades.
    • unhealthyPodEvictionPolicy: the default IfHealthyBudget lets running-but-not-ready Pods be evicted only if the budget is not already violated; AlwaysAllow lets them be evicted regardless — usually what you want so a broken Pod cannot block maintenance.
    • A PDB with 1 replica and minAvailable: 1 is a contradiction: the only way to move it is downtime. Run ≥ 2 replicas for anything with a PDB.

    Glossary

    Probe
    Periodic diagnostic run by the kubelet: exec, httpGet, tcpSocket or grpc.
    Liveness / readiness / startup
    Restart-if-stuck / route-traffic-if-ready / protect-slow-start checks.
    Request
    Resource amount reserved for scheduling (and CPU weight).
    Limit
    Kernel-enforced ceiling: CPU throttled, memory OOM-killed.
    Allocatable
    Node capacity minus system reservations; what the scheduler can hand out.
    CFS quota / period
    Linux CPU bandwidth control: max CPU time per period for a cgroup (cpu.max on cgroup v2).
    Throttling
    Runnable threads prevented from running because the quota is used up.
    OOMKilled
    Container terminated by the kernel out-of-memory killer; exit code 137.
    QoS class
    Guaranteed, Burstable, BestEffort — derived from requests/limits; drives eviction order and oom_score_adj.
    Node-pressure eviction
    Kubelet terminating Pods to reclaim memory/disk/PIDs; ignores PDBs.
    Filtering / scoring
    Scheduler steps: remove infeasible nodes, then rank feasible ones.
    Affinity / anti-affinity
    Rules attracting or repelling Pods relative to node labels or other Pods within a topology domain.
    Taint / toleration
    Node-side repulsion / Pod-side permission to ignore it.
    Topology spread
    Constraint limiting the skew of Pod counts across domains (zones, nodes).
    maxSurge / maxUnavailable
    Rolling update bounds above / below the desired replica count.
    minReadySeconds
    How long a new Pod must be Ready before it counts as available.
    Revision
    A Deployment Pod-template version, backed by a ReplicaSet.
    CrashLoopBackOff
    Waiting reason while the kubelet delays restarting a repeatedly failing container.
    Grace period
    terminationGracePeriodSeconds: time from start of termination to SIGKILL.
    preStop hook
    Action (exec, httpGet, sleep) run before TERM is sent.
    PodDisruptionBudget
    Limit on concurrent voluntary disruptions, enforced via the Eviction API.
    Eviction API
    Policy-aware Pod removal used by kubectl drain; returns 429 when a PDB would be violated.
    Job / CronJob / DaemonSet / StatefulSet
    Run-to-completion / scheduled Jobs / one per node / stable identity and storage.

    Self-check

    1. Why should liveness not check /ready for reliability-api?
    /ready is 503 during warm-up and could be 503 under overload. Liveness failure restarts the container, which repeats warm-up (making the outage longer) and moves load to other replicas (possibly making them fail too). Readiness is for "not now", liveness for "stuck forever".
    2. App takes up to 90 s to start, then must be restarted within ~30 s of hanging. Give probe settings.
    startupProbe on /health with periodSeconds: 10, failureThreshold: 9 (or 5 s × 18) → up to 90 s to start. livenessProbe periodSeconds: 10, failureThreshold: 3 → ~30 s detection once started. Readiness separately on /ready.
    3. A container has requests cpu 100m and no CPU limit. The node is idle. How much CPU can it use? What if the node is busy?
    On an idle node it can use as much CPU as is free (requests are a floor/weight, not a cap). On a busy node, CPU is shared in proportion to requests (weights), so it is guaranteed roughly its 100m share but not more.
    4. Memory request 128Mi, limit 256Mi; the process grows to 300Mi. What happens? What if the limit were absent?
    With the limit: the kernel OOM-kills it (OOMKilled, exit 137) and it restarts with back-off. Without a limit: it can keep growing until the node runs low; then the kubelet's node-pressure eviction (and/or kernel OOM at node level) acts, and because it exceeds its request it is a prime eviction candidate — possibly after other Pods have suffered.
    5. Classify: container A requests cpu 200m / mem 256Mi with equal limits; container B (sidecar) has no resources.
    Burstable. Guaranteed requires every container to have equal CPU and memory requests and limits; B has none, so the Pod is not Guaranteed, but A has some, so it is not BestEffort.
    6. replicas 10, maxSurge 30%, maxUnavailable 30%. Bounds during a rollout?
    maxSurge = ceil(3.0) = 3 → at most 13 Pods. maxUnavailable = floor(3.0) = 3 → at least 7 available. (With 25%: ceil(2.5) = 3 and floor(2.5) = 2.)
    7. Why can replicas 1 with default strategy cause downtime during a rollout, and how do you fix it?
    Defaults with 1 replica: maxSurge = ceil(0.25) = 1, maxUnavailable = floor(0.25) = 0, so a rollout itself keeps 1 available. But a single replica still means downtime on node failure, eviction or drain, and no capacity spare during restarts. Fix: run ≥ 2 replicas, plus a PDB.
    8. During a rollout clients see a few connection errors each time an old Pod goes away. Diagnose.
    Endpoint removal and SIGTERM happen in parallel; the app likely exits (or stops accepting) before all nodes stop routing to it. Add a preStop delay (e.g. sleep 5), make sure the app handles SIGTERM gracefully (PID 1, Uvicorn graceful shutdown), and ensure grace period covers both.
    9. Your PDB has minAvailable: 2 and the Deployment has 2 replicas. What happens on a node upgrade?
    ALLOWED DISRUPTIONS = 0, so every eviction returns 429 and kubectl drain blocks until timeout. Use minAvailable: 1 (or maxUnavailable: 1), or more replicas.
    10. Pod is in phase Running but kubectl shows CrashLoopBackOff. Contradiction?
    No. Phase is the Pod-level summary; with restartPolicy: Always the Pod stays Running while its container cycles. CrashLoopBackOff is the container's Waiting state reason during the restart back-off.
    11. A toleration for gpu=true:NoSchedule is added to reliability-api. Will it run on GPU nodes?
    It may, but nothing makes it prefer them; a toleration only removes the repulsion. To steer it there you would add node affinity; to keep it off, simply don't add the toleration.
    12. kubectl rollout undo fixed production. What must you do next, and why?
    Update Git (and/or the Helm values) to the good version. The undo changed only the live object; the next declarative apply from Git or a CI pipeline would re-deploy the bad version.
    13. When would a Job be better than a Deployment for the smoke test?
    When the work should run to completion and report success/failure (exit code), not run forever. A Deployment would restart the finished container endlessly (restartPolicy Always).
